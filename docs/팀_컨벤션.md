# 팀 컨벤션

> 커밋·브랜치·PR·이슈를 어떻게 다룰지 정한 문서다. 작업을 시작하기 전에 [이슈](#4-이슈-규칙) → [브랜치](#2-브랜치-전략) → [커밋](#1-커밋-메시지) → [PR](#3-pr-규칙) 순서로 읽으면 실제 작업 순서와 같다.
>
> 개발 환경 세팅은 [개발 환경 가이드](./개발_환경_가이드.md)에 있다.

---

## 1. 커밋 메시지

[AngularJS Git Commit Message Conventions](https://gggimmin-development-technology.tistory.com/18)를 참고한다.

### 형식

```
<유형>: <제목>

<본문>
```

- 유형과 제목은 한 줄로 쓰고, **본문은 빈 줄로 분리**한다.
- 제목 끝에 마침표(`.`)를 찍지 않는다.
- 제목은 한국어로 쓴다.

### 커밋 유형

유형은 **영어 소문자**로 쓴다.

| 유형 | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 formatting, 세미콜론 누락 등 코드 자체의 변경이 없는 경우 |
| `refactor` | 코드 리팩토링 |
| `test` | 테스트 코드, 리팩토링 테스트 코드 추가 |
| `chore` | 패키지 매니저 수정, 그 외 기타 수정 (예: `.gitignore`) |

### 본문

- **어떻게가 아니라 무엇을·왜**를 적는다. 어떻게는 코드를 보면 알 수 있지만, 왜는 작성자만 안다.
- 항목이 여럿이면 글머리 기호로 나눈다.
- **"이 정도는 코드만 봐도 알겠지"라고 넘기지 않는다.** 3개월 뒤의 나와 오늘 처음 이 코드를 보는 팀원은 그 맥락을 모른다.

### 예시

```
feat: 구글 OAuth 로그인 추가

- 사용자 인증을 위해 Google OAuth를 추가함
- 기존 로컬 로그인 방식과 함께 사용 가능하도록 병행 지원
- Google OAuth를 선택한 사용자의 프로필 정보(이름, 이메일)를 DB에 저장
- 보안을 강화하기 위해 OAuth 로그인 시 자동으로 HTTPS로 리다이렉트되도록 설정함
```

## 2. 브랜치 전략

참고: https://da-nyee.github.io/posts/git-git-branch-strategy/

### 브랜치 종류

| 브랜치 | 용도 |
|---|---|
| `main` | 배포용 |
| `develop` | 개발용 |
| `feature` | 새로운 기능 |
| `hotfix` | 급하게 고칠 일이 생겼을 때 |

### 규칙

- `main`을 기준으로 `develop`을 최초 생성한다.
- 각 기능은 `develop`을 기준으로 `feature`를 생성해 진행한다. 개발 중 `develop`에 새 커밋이 추가되면 **최신 커밋으로 rebase**한다.
- **작업 시작 전 이슈를 생성**하고, 브랜치 이름에 이슈 번호를 명시한다.
- 개발이 끝나면 `feature → develop` PR을 생성한다.
- 배포할 때는 `develop → main` PR을 생성한다. **팀원 전원 Approve 시 squash-merge**하고, `develop`에도 pull(fetch + merge)로 반영한다.
- `main`에 버그가 있으면 `hotfix`로 해결하고 **`main`과 `develop` 양쪽에 반영**한다.
- 배포 버전 관리를 위해 `main`에 tag를 붙인다.

### 브랜치 이름

```
<브랜치 타입>/<이슈번호>-<브랜치 내용>
```

예시
- `feature/44-user-login`
- `hotfix/43-fix-cors-error`

## 3. PR 규칙

### 올리기 전에

- SonarQube 플러그인 검증과 AI 검증을 완료한다.
- PR 생성 후 CodeRabbit으로 가볍게 추가 검증한다.

### 작성

- **코드 설계 방향, 고민했던 지점, 선택한 이유**를 팀원이 이해할 수 있게 쓴다.
- 템플릿은 가능한 한 채우되, 모든 항목을 반드시 채울 필요는 없다.

### 리뷰와 병합

- **최소 두 명**에게 코드 리뷰를 받은 뒤 병합한다.
- 팀원이 내용을 이해하고 모두 동의하면 병합한다.
- `develop`에 병합하면 팀원에게 공유한다. 각 팀원은 진행 중인 브랜치에 변경 사항을 리베이스한다.

### PR 템플릿

PR을 열면 [`.github/pull_request_template.md`](../.github/pull_request_template.md)의 내용이 자동으로 채워진다. 항목을 바꾸려면 그 파일을 고친다.

## 4. 이슈 규칙

- **작업 시작 전** 하려는 작업의 이슈를 생성하고 본문을 작성한다.
- 브랜치 생성 시 해결하려는 이슈 번호를 명시한다.
- PR 생성 시 관련된 이슈 번호를 명시한다.
- **커밋 메시지에 이슈 번호를 넣을지는 아직 정하지 않았다.** 일단 진행해보고 불편함을 느끼면 그때 도입한다.

### 이슈 템플릿

이슈를 생성하면 GitHub이 아래 두 템플릿 중 하나를 고르게 한다. 항목을 바꾸려면 해당 파일을 고친다.

| 템플릿 | 파일 |
|---|---|
| ✨ 기능 추가 (`[FEAT]`) | `.github/ISSUE_TEMPLATE/feature.md` |
| 🐞 버그 리포트 (`[BUG]`) | `.github/ISSUE_TEMPLATE/bug.md` |

---

## 부록. 이 문서의 유지

1. **규칙을 바꾸면 이 문서를 같은 PR에서 고친다.** 합의만 하고 문서를 안 고치면 다음 사람은 옛 규칙을 따른다.
2. **규칙이 불편하면 지키지 않는 대신 바꾼다.** 아무도 안 지키는 규칙이 문서에 남아 있는 상태가 가장 나쁘다.

## 0. 이 문서에 대하여

### 목적

새로 합류한 팀원이 이 문서만 보고 **혼자서** 프론트엔드 개발 환경을 재현하고, 개발 서버를 띄우고, 커밋·push 때 걸리는 검사를 통과할 수 있게 하는 것이다.

막히는 부분이 생기면 해결한 사람이 이 문서를 직접 고치도록 하자.

### 이 문서가 다루는 범위

- 프론트엔드 로컬 개발 환경의 구성과 실행
- 커밋·push 때 동작하는 린트·리뷰 검사
- 저장소에 커밋된 프론트엔드 설정 파일이 그렇게 구성된 이유

### 이 문서가 다루지 않는 범위

| 항목 | 어디서 다루나 |

| 백엔드 환경 (JDK, DB, Spring) | [백엔드 개발 환경 가이드](백엔드_개발_환경_가이드.md) |
| 기술 선택의 근거와 트레이드오프 | [`docs/adr`](adr/README.md)에 결정별로 정리 |
| 배포 환경 (Vercel, API 연결) | [프론트엔드 배포 가이드](프론트엔드_배포_가이드.md) |

### 로컬 실행 구조

```
┌───────────────────────────────────────┐
│  내 노트북                            │
│                                       │
│  브라우저 ──► Vite 개발 서버 :5173    │
│                 │  /api, /actuator    │
│                 ▼  (프록시)           │
│              Spring Boot :8080        │  ← IDE에서 실행
│                 │                     │
│                 ▼                     │
│              MySQL :3306 (Docker)     │
└───────────────────────────────────────┘
```

**코드는 API를 상대 경로(`/api/...`)로 호출한다.** 로컬에서는 Vite 개발 서버가, 배포 환경에서는 Vercel이 그 요청을 백엔드로 넘긴다. 백엔드가 떠 있지 않아도 화면은 뜨지만, 데이터 요청은 실패한다.

## 2. 사전 준비물

### 2-1. Node.js 22 이상

```bash
node --version
# v22 이상이어야 함
```

### 2-2. 에디터의 Biome 플러그인

VS Code와 IntelliJ 모두 Biome 플러그인이 있다. 설치하면 저장할 때 커밋 훅과 같은 규칙으로 포맷된다. 설치하지 않아도 커밋할 때 훅이 포맷하므로 개발은 된다.

### 2-3. 코딩 에이전트 (Claude Code 또는 Codex)

push 전에 에이전트로 리뷰를 돌려야 한다([5장](#push가-막혔을-때)). 에이전트는 **저장소 루트에서** 실행한다. 루트의 `AGENTS.md`와 리뷰 Skill을 거기서 읽는다.

### 2-4. 백엔드 환경 (데이터가 필요할 때)

화면에서 실제 데이터를 보려면 백엔드가 떠 있어야 한다. [백엔드 개발 환경 가이드](백엔드_개발_환경_가이드.md)의 사전 준비물과 최초 세팅을 마친다. 레이아웃이나 스타일만 고칠 때는 없어도 된다.

## 3. 최초 세팅

### Step 1. 의존성 설치

```bash
cd frontend
npm install
```

**`npm install`은 Git 훅도 함께 설치한다**(`prepare` 스크립트가 husky를 실행한다). 훅이 없으면 커밋할 때 린트·포맷이 적용되지 않고, 리뷰 기록 검사도 push가 아니라 PR의 CI 단계에서야 걸린다.

### Step 2. 백엔드 실행 (선택)

데이터가 필요하면 DB 컨테이너와 Spring Boot를 띄운다([백엔드 개발 환경 가이드 3장](백엔드_개발_환경_가이드.md#3-최초-세팅)의 Step 4·5). 건너뛰면 API 요청이 `502`로 실패한다.

### Step 3. 개발 서버 실행

```bash
npm run dev
```

http://localhost:5173 에서 첫 화면이 뜨면 개발 서버는 준비된 것이다.

백엔드도 띄웠다면 첫 화면에 **"지금은 사양 정보를 불러오지 못했습니다"** 안내가 없어야 한다. 이 안내가 보이면 백엔드가 떠 있는지(`:8080`) 확인한다.

## 4. 설정 파일

### 4-1. `vite.config.ts`

| 설정 | 이유 |
|---|---|
| `/api`, `/actuator` 프록시 | 배포 환경과 같은 동일 오리진을 개발 서버에서도 만든다. 코드가 상대 경로로 호출하므로 환경마다 API 주소를 바꿀 필요가 없다([ADR 0027](adr/0027-API-요청-연결-방식.md)) |
| `css.transformer: 'lightningcss'` | 변환과 압축이 서로 다른 엔진으로 갈리면 `@keyframes`에서 빌드가 깨진다. 하나로 맞춘다 |

### 4-2. `tsconfig.json`

| 설정 | 이유 |
|---|---|
| `strict` | 타입 검사를 가장 엄격하게 둔다 |
| `noUnusedLocals`, `noUnusedParameters` | 사용하지 않는 변수·인자는 타입 검사가 잡는다. 그래서 린터에는 같은 규칙을 두지 않았다 |
| `noEmit` | 타입 검사만 하고, 빌드 결과물은 Vite가 만든다 |

### 4-3. `biome.json`

| 설정 | 이유 |
|---|---|
| JS·TS 2칸, CSS 4칸 들여쓰기, 작은따옴표, 한 줄 120자 | 기존 코드의 형식에 맞춰, 도입할 때 바뀌는 줄을 최소로 했다 |
| 권장 규칙에 더해 hook 규칙·effect 의존성·`key`·`any`·`!`·`==`·`console` 등을 error로 | LLM 리뷰어가 매번 보지 않아도 되는 기계적 판정을 린터로 옮겼다 |
| import 정렬(assist) | 기본값대로 켜져 있다. CSS import(`import './x.css'`)는 정렬 경계로 취급돼 순서가 바뀌지 않는다 |

**자동 수정은 안전한 것만 적용된다.** Biome은 동작을 바꿀 수 있는 수정(effect 의존성 추가, `==` → `===` 등)을 `unsafe`로 분류해 `--write`에서 적용하지 않는다. 이런 에러는 직접 고치고, `--unsafe`로 한꺼번에 고치지 않는다.

### 4-4. Git 훅 (`.husky/`, `package.json`의 `lint-staged`)

| 설정 | 이유 |
|---|---|
| `.husky/`를 저장소 루트에 둠 | Git 훅은 저장소 단위라 루트에 둔다. `package.json`은 `frontend/`에 있어서 `prepare`가 `cd .. && husky`로 루트에서 설치한다 |
| pre-commit은 `frontend/` 변경이 있을 때만 실행 | 백엔드만 고친 커밋에는 영향이 없게 한다 |
| 타입 검사는 스테이징된 파일이 아니라 프로젝트 전체 | `tsc`는 파일 일부만 골라 프로젝트 설정대로 검사할 수 없다 |

## 5. 일상 개발 흐름

### 자주 쓰는 명령어

`frontend/`에서 실행한다.

| 하려는 일 | 명령어 |
|---|---|
| 개발 서버 | `npm run dev` |
| 타입 검사 + 빌드 | `npm run build` |
| 린트·포맷 검사 (수정 없음) | `npm run lint` |

> `npm run lint`는 지금 기존 에러 때문에 실패한다. [6장](#6-알려진-한계)을 본다.

### 커밋과 push에서 일어나는 일

| 시점 | 하는 일 | 막히면 |
|---|---|---|
| 커밋 (pre-commit) | 스테이징된 `frontend/` 파일에 Biome 자동 수정(안전한 것만)과 타입 검사 | 남은 에러를 고치고 다시 커밋한다 |
| push (pre-push) | 리뷰 기록(`.review/`)이 push하는 코드와 맞는지 검사 | 아래를 따른다 |
| PR (CI) | push와 같은 검사 | push와 같다 |

### push가 막혔을 때

1. 저장소 루트에서 연 에이전트 대화창에서 `review` Skill을 실행해 달라고 요청한다.
2. 에이전트가 규칙별로 리뷰하고, 지적을 반영하고, `.review/`에 기록을 남긴다.
3. 바뀐 코드와 기록 파일을 함께 커밋하고 다시 push한다.

작업 흐름 전체는 [`AGENTS.md`](../AGENTS.md)에 있다.

## 6. 알려진 한계

**기존 파일 일부에 린트 에러가 남아 있다.** 대부분 effect 의존성이고, 접근성과 import 정렬도 있다. 고치면 동작이 바뀔 수 있어 Biome을 도입할 때 고치지 않았다. 어느 파일에 무엇이 남았는지는 `npm run lint`로 본다.

- `npm run lint`는 이 에러 때문에 실패한다. 내가 고친 파일에 에러가 없다면 무시해도 된다.
- 이 파일을 고쳐 커밋하면 pre-commit이 이 에러로 막는다. 그 화면을 작업하는 김에 함께 고친다.

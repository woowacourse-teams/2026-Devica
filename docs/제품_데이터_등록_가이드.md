# 제품 데이터 등록 가이드

prototype 제품 20개를 개발 환경에 등록하고 검증할 때 사용한다. 이미지 저장·제공 방식의 결정은 [ADR 0030](adr/0030-제품-이미지-저장과-제공.md)에, 일반 배포 절차는 [백엔드 배포 가이드](백엔드_배포_가이드.md)에 있다. 아래 명령은 저장소 루트에서 실행한다.

## 1. 데이터와 이미지의 위치

| 파일 | 역할 |
|---|---|
| [`source-products.json`](../data/product-catalog/source-products.json) | prototype의 제품 ID·가격·구매 링크·가격 확인일 원본. 보완한 사양으로 덮어쓰지 않는다. |
| [`cpus.json`](../data/product-catalog/cpus.json) | CPU 모델·코어 수·PassMark 점수·출처. 제품은 `cpuKey`로 참조한다. |
| [`products.json`](../data/product-catalog/products.json) | DB에 등록할 제품 20개, 사양·판매처·`imageKey`·검수 근거. `metadata.verificationStatus`가 `READY`인 것만 생성한다. |
| [`images/`](../data/product-catalog/images/) | WebP 20개. SQL 생성기가 파일 SHA-256과 `imageKey`를 비교한다. |
| [`generate_product_seed.py`](../scripts/generate_product_seed.py) | 위 JSON과 이미지를 검사하고 Flyway SQL을 생성한다. DB나 AWS에는 접속하지 않는다. |
| [`V1.6__seed_prototype_products.sql`](../src/main/resources/db/migration/V1.6__seed_prototype_products.sql) | 실제 배포 시 Flyway가 실행하는 CPU 10개·제품/노트북/판매처 각 20개 INSERT. |

이미지는 현재 `techcourse-project-2026` 버킷의 `devica/dev/product-images/{prototypeId}/{sha256}.webp` 키에 있다. `imageKey`는 **버킷 이름을 제외한 전체 객체 키**다. 별도 제품 전용 버킷을 사용하지 않는다. 앱은 `PRODUCT_IMAGE_BASE_URL`(기본값 `https://techcourse-project-2026.s3.ap-northeast-2.amazonaws.com`) 뒤에 `/`와 `imageKey`를 붙여 API의 `imageUrl`을 만든다. 따라서 환경 변수에는 **버킷 루트 주소만** 넣는다. `devica/dev`를 함께 넣으면 경로가 중복된다.

새 이미지를 올릴 때는 WebP 파일의 SHA-256을 계산해 위 형식의 키를 만들고, 해당 키에 `Content-Type: image/webp`로 업로드한다. 로컬 파일 경로와 만든 키를 각각 `IMAGE_FILE`, `IMAGE_KEY`로 지정한 뒤 `aws s3 cp "$IMAGE_FILE" "s3://techcourse-project-2026/$IMAGE_KEY" --content-type image/webp`처럼 실행한다. 업로드 뒤 `products.json`의 `metadata.imageFile`, `metadata.imageSha256`, `metadata.imageKey`를 같은 파일·키로 맞춘다. 기존 20개 객체를 다시 업로드할 필요는 없다.

S3 콘솔에서 이 버킷의 퍼블릭 액세스 차단 설정과 버킷 정책을 별도로 확인한다. 브라우저가 S3 URL로 직접 이미지를 받는 현재 구성은 해당 객체에 `s3:GetObject`가 허용되어야 한다. 공개 범위는 가능한 한 `arn:aws:s3:::techcourse-project-2026/devica/dev/product-images/*`로 한정한다. **객체에 HTTP 200이 반환되는 것만으로 정책의 공개 범위가 적절하다고 판단할 수는 없다.**

## 2. SQL 생성과 배포 전 검증

`V1.6`을 공유 DB에 최초 적용하기 전에는 다음 명령으로 SQL을 다시 생성할 수 있다. 이미 공유 DB에 `V1.6`이 적용되었다면 이 파일을 변경하지 않고 새 버전의 마이그레이션을 추가한다.

```bash
python3 scripts/generate_product_seed.py \
  --data-dir data/product-catalog \
  --output src/main/resources/db/migration/V1.6__seed_prototype_products.sql
./gradlew build
```

생성기는 원본의 가격·구매 링크·가격 확인일, CPU 참조, 필수 사양, WebP 해시와 키를 검사한다. `V1.6`은 `V1.4`의 `checked_at`과 `V1.5`의 `image_key`를 전제로 한다. `./gradlew build`는 전용 MySQL 테스트 DB에서 전체 Flyway 마이그레이션과 시드 데이터를 적용하고, API 응답 및 실패 시 롤백을 확인한다. 테스트 DB는 `src/test/resources/application-flyway-test.yml`의 `devica_flyway_test`와 롤백 전용 `devica_seed_rollback_test`다. 로컬 MySQL 연결은 기본적으로 `localhost:3307`과 테스트용 `root/root`를 사용하며 포트는 `TEST_DB_PORT`로 바꿀 수 있다. **테스트의 Flyway `clean`은 이 두 전용 DB에서만 실행한다.**

배포 전에는 생성된 SQL diff와 JSON을 함께 검토하고, 같은 버전의 SQL이 이미 다른 공유 DB에 적용됐는지 확인한다. [ADR 0028](adr/0028-DB-스키마-마이그레이션-관리.md)에 따라 적용된 마이그레이션은 수정하지 않는다.

## 3. 배포 후 확인

`develop`에 병합되면 개발 서버의 CodePipeline이 애플리케이션을 배포한다. 앱 시작 시 Flyway가 `V1.6`을 적용하므로 공유 DB에서 SQL을 수동으로 실행하지 않는다. 배포 로그에서 Flyway 성공과 앱 기동 성공을 먼저 확인한다. 그 다음 개발 DB에서 아래 읽기 전용 쿼리를 실행한다. 기존 제품이 이미 있다면 전체 건수 대신 `products.json`의 20개 `code`를 기준으로 비교한다.

```sql
SELECT version, description, success
FROM flyway_schema_history
WHERE version IN ('1.4', '1.5', '1.6')
ORDER BY installed_rank;

SELECT COUNT(*) FROM cpu;
SELECT COUNT(*) FROM product;
SELECT COUNT(*) FROM laptop;
SELECT COUNT(*) FROM product_offer;
SELECT COUNT(*) FROM product WHERE image_key IS NOT NULL;
SELECT COUNT(*) FROM product_offer WHERE checked_at IS NOT NULL;
```

새 빈 제품 DB 기준 기대값은 CPU 10개, 제품·노트북·판매처 각 20개, 이미지 키·가격 확인일 각 20개다. API에서 `GET /api/product-categories/LAPTOP/products?size=100`의 `content` 20개를 확인하고, 반환된 ID로 `GET /api/products/{id}`를 호출해 `imageUrl`, 가격, 구매 링크, `offers[].checkedAt`을 JSON과 대조한다. 브랜드 필터, 키워드 검색, 가격순 정렬도 함께 확인한다. 자동화된 같은 검증은 `ProductCatalogSeedTest`에 있다.

S3 객체는 `products.json`의 **각 `metadata.imageKey`**로 `HeadObject`를 호출해 20개 모두 존재하고 `ContentType`이 `image/webp`인지 확인한다. AWS CLI 자격 증명이 있다면 아래 명령으로 반복 검증할 수 있다. 이 검사는 객체 메타데이터와 JSON 키의 일치를 확인하며, 공개 URL과 버킷 정책은 별도로 점검한다.

```bash
python3 - <<'PY'
import json
import subprocess
from pathlib import Path

products = json.loads(Path("data/product-catalog/products.json").read_text(encoding="utf-8"))["products"]
keys = [item["metadata"]["imageKey"] for item in products]
assert len(keys) == len(set(keys)) == 20
for key in keys:
    result = subprocess.run(
        ["aws", "s3api", "head-object", "--bucket", "techcourse-project-2026",
         "--key", key, "--query", "ContentType", "--output", "text"],
        check=True, capture_output=True, text=True,
    )
    assert result.stdout.strip() == "image/webp", key
print("S3 imageKey 20개 확인 완료")
PY
```

## 4. 실패·수정 시 처리

`V1.6` 실패가 나면 배포 로그의 **실패한 SQL과 원인**을 확인하고 `flyway_schema_history`, CPU·제품·노트북·판매처 건수를 읽어 실제 DB 상태를 기록한다. 마지막 제품의 중복 코드를 주입한 MySQL 통합 테스트에서는 `V1.6`의 여러 INSERT가 진행된 뒤 오류가 발생해도 새 행이 모두 롤백되었다. 이는 현재 `V1.6`의 DML과 테스트 DB에서 확인한 결과이며, 모든 환경·모든 마이그레이션의 자동 롤백을 보장하지는 않는다. 개발·운영 DB에서 `flyway clean`이나 볼륨 삭제로 복구하지 않는다.

`V1.6`이 **아직 어느 공유 DB에도 성공 적용되지 않았다면** 원인과 DB 상태를 확인한 뒤 SQL을 수정해 재배포한다. 실패 이력 때문에 Flyway가 재실행을 막는 경우에는 남은 행·이력을 먼저 확인하고 Flyway `repair` 필요 여부를 판단한다. **이미 성공 적용됐다면** `V1.6`이나 원본 JSON만 고쳐 재배포해도 DB 값은 바뀌지 않는다. 정정용 다음 버전의 마이그레이션을 만들고, 같은 검증을 다시 수행한다. 애플리케이션 버전 롤백도 이미 커밋된 DB 변경을 취소하지 않는다.

## 5. CloudFront를 도입할 때

현재의 S3 버킷을 일반 S3 원본으로 지정하고 **Origin Path는 비워 둔다.** `imageKey`에 이미 `devica/dev/product-images/...`가 있으므로 Origin Path를 같은 접두사로 설정하면 요청 경로가 두 번 붙는다. [AWS의 Origin Path 설명](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html)을 참고한다.

CloudFront 도메인에서 20개 키가 모두 이미지로 반환되는 것을 확인한 뒤 서버의 `/opt/app/.env`에 `PRODUCT_IMAGE_BASE_URL`을 CloudFront 도메인의 루트 주소로 지정하고 앱을 재배포한다. 목록·상세 API 및 브라우저 표시를 재검증한다. S3 직접 공개를 닫고 CloudFront만 사용하려면 일반 S3 원본에 [Origin Access Control(OAC)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html)을 연결하고 배포 전용 버킷 정책을 적용한 뒤, CloudFront 경유 접근을 확인하고 기존 공개 읽기 권한을 제거한다. 이 전환은 별도 배포 작업이다.

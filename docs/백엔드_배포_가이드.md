# 백엔드 배포 가이드

**서버를 다룰 때 보는 문서다.** 파이프라인이 어떻게 구성됐고 왜 그렇게 정했는지는 [ADR 0014](adr/0014-CD-파이프라인.md)에, 기술 선택의 근거는 [`docs/adr`](adr/README.md)에 있다. 프론트엔드 배포는 [프론트엔드 배포 가이드](프론트엔드_배포_가이드.md)에서, 로컬 개발 환경은 [백엔드 개발 환경 가이드](백엔드_개발_환경_가이드.md)에서 다룬다.

제품 시드와 S3 이미지 등록·확인 절차는 [제품 데이터 등록 가이드](제품_데이터_등록_가이드.md)에 있다.

## 1. 배포는 어떻게 이뤄지나

**일반적인 애플리케이션 배포에는 수동 작업이 없다.** 브랜치에 push하면 해당 환경의 CodePipeline이 실행되어 배포까지 완료한다. 다만 서버를 처음 구성하거나 DB 관리 방식을 전환하는 경우에는 환경
설정과 DB 상태를 사전에 확인해야 한다.

| push한 브랜치   | 배포되는 곳                  |
|-------------|-------------------------|
| `develop`   | 개발 서버 `ec2-devica-dev`  |
| `main`      | 운영 서버 `ec2-devica-prod` |

운영에는 `develop`을 `main`에 병합해 배포한다.

파이프라인은 소스를 받아 테스트하고, 이미지를 만들어 배포 번들에 실어 보내고, 서버의 CodeDeploy 에이전트가 컨테이너를 교체한 뒤 헬스체크로 확인한다. 실패하면 이전 리비전으로 자동 롤백된다. 배포 그룹
설정과 훅 구성은 [ADR 0014](adr/0014-CD-파이프라인.md)에 있다.

### Flyway 최초 전환

Flyway 최초 전환은 일반적인 애플리케이션 배포와 달리 DB 상태를 미리 준비해야 하는 일회성 작업이다.

개발 서버 DB에는 Hibernate의 `ddl-auto: update`로 생성된 테이블이 있었지만 `flyway_schema_history`는 없었다. 기존 데이터는 보존할 필요가 없는 V0 테스트 데이터였으므로,
최초 Flyway 배포 전에 기존 `app_mysql-data` 볼륨을 삭제해 빈 DB로 전환했다. 이후 애플리케이션을 배포하면 Flyway가 `V1.1`부터 최신 마이그레이션까지 적용한다.

개발 서버의 볼륨 초기화는 이번 최초 전환에만 수행한다. Flyway가 최초 적용된 이후에는 볼륨을 삭제하지 않고 DB 데이터를 유지하면서 새로운 마이그레이션을 누적 적용한다.

운영 서버는 운영 소스 브랜치를 `prototype`에서 `main`으로 바꾸면서 새 빈 DB에 연결해 `V1.1`의 초기 스키마와 `V1.2`의 기준 데이터부터 적용했다. V0 데이터는 이관하지 않았고 기존 V0 DB도 삭제하지 않았다.

이번 Flyway 도입에서는 `baseline-on-migrate`를 사용하지 않는다. 데이터를 보존해야 하는 기존 DB에 Flyway를 도입해야 한다면 해당 환경의 전환 및 baseline 정책을 별도로 결정한다.
결정 배경은 [ADR 0028](adr/0028-DB-스키마-마이그레이션-관리.md)에 있다.

## 2. 서버 구성

|       | 개발 (dev)                                                           | 운영 (prod)                                                           |
|-------|--------------------------------------------------------------------|---------------------------------------------------------------------|
| 인스턴스  | `ec2-devica-dev` (public subnet)                                   | `ec2-devica-prod` (private subnet)                                  |
| 접속    | SSH                                                                | **AWS 콘솔의 SSM 세션 매니저만** — EC2 > 인스턴스 선택 > Connect > Session Manager |
| 접근 경로 | `http://<EC2 주소>` (HTTPS 없음)                                       | `https://api.devica.co.kr` → ALB → EC2                              |
| 아키텍처  | 둘 다 ARM64 (Graviton). 서버에서 `uname -m`이 `aarch64`                   | 〃                                                                   |
| 실행    | `docker compose -f docker-compose.server.yml` — 호스트 80 → 컨테이너 8080 | 〃                                                                   |
| DB    | RDS for MySQL 8.4 (`db-devica-dev`). 접속 주소는 `.env`의 `DB_HOST` | RDS for MySQL 8.4 (`db-devica-prod`) | 〃                                                                   |
| 헬스체크  | 메인 포트의 `/readyz` (DB 연결까지 검사). 배포 검증(`validate.sh`)이 쓴다             | 〃. ALB 대상 그룹 헬스체크도 이 경로를 쓴다                                         |
| Actuator | 관리 포트 8081. 호스트에 열지 않아 같은 도커 네트워크에서만 접근한다                         | 〃                                                                   |

**두 서버가 같은 compose 파일을 쓴다.** 구성이 같고 값만 다르기 때문이다. 환경 차이는 각 서버의 `.env`가 흡수한다 — `SPRING_PROFILES_ACTIVE`가 `dev`냐 `prod`냐에
따라 쿼리 로그 등의 설정이 갈린다. 스키마 변경은 두 환경 모두 Flyway가 적용하고 Hibernate는 `validate`만 수행한다.

**compose에는 `app`, `alloy` 두 컨테이너가 있다.** `alloy`는 앱 메트릭(`app:8081`)과 호스트 지표를 60초마다 Grafana Cloud로 보낸다. 설정은
`monitoring/config.alloy`에 있다. 접속 정보가 `.env`에 없으면 `alloy`만 실패하고 앱은 뜬다.

### RDS 설정

RDS를 다시 만들거나 백업으로 복원할 때도 같은 값으로 맞춘다. 결정 배경은 [ADR 0038](adr/0038-DB-RDS-이전.md)에 있다.

| 항목 | 값 |
|---|---|
| 엔진 | MySQL 8.4 (로컬·테스트 컨테이너와 같은 버전) |
| 인스턴스 | `db.t4g.micro`, 단일 AZ |
| 퍼블릭 액세스 | 아니오 |
| 서브넷 그룹 | `project-rds-subnet-group` (공용 계정 지정) |
| 보안 그룹 | `project-db` (공용 계정 지정. 팀 공용이라 같은 환경 EC2만 허용하지는 못한다. 환경 구분은 계정·비밀번호가 맡는다) |
| 파라미터 그룹 | `time_zone=Asia/Seoul`, `character_set_server=utf8mb4`, `collation_server=utf8mb4_0900_ai_ci` |
| 자동 백업 | 켬, 보존 7일 |
| 유지 관리 기간 | 트래픽이 적은 새벽 |
| 앱 계정 | 마스터 계정과 별도. `devica` DB 권한만 가진다. 이름·비밀번호는 `.env`의 `MYSQL_USER`·`MYSQL_PASSWORD` |
| 태그 | `Service=techcourse`, `Role=techcourse-etc`, `ProjectTeam=devica`. 공용 계정 규칙이라 없으면 삭제된다. 파라미터 그룹과 백업에도 붙인다 |

시간대는 반드시 맞춘다. 마이그레이션의 `NOW()`·`CURRENT_TIMESTAMP`가 DB 시간대를 따르는데, RDS 기본값은 UTC다.

RDS는 퍼블릭 접근이 막혀 있어 서버에서만 접속할 수 있다. 서버에 `mysql` 클라이언트가 없으므로 MySQL 이미지를 잠깐 띄워 쓴다.

```bash
sudo docker run --rm -it mysql:8.4 mysql -h <RDS 엔드포인트> -u admin -p
```

dev는 SSH 터널로 노트북에서 접속할 수도 있다. 로컬 3306·3307은 개발·테스트 DB가 쓰므로 다른 포트를 연다. prod는 SSM 세션 매니저로만 접근할 수 있어 SSH 터널을 쓸 수 없다.

```bash
ssh -L 3310:<dev RDS 엔드포인트>:3306 ubuntu@<dev EC2 주소>   # 이후 localhost:3310 으로 접속
```

## 3. 설정과 비밀값

**비밀값은 각 서버의 `/opt/app/.env`에만 있다.** 규격은 저장소의 `.env.server.example`에 있고, 실제 값이 담긴 `.env`는 커밋하지 않는다.

로그 전송에는 `GRAFANA_CLOUD_LOKI_URL`(끝에 `/loki/api/v1/push` 포함)과 `GRAFANA_CLOUD_LOKI_USER`(Loki 사용자 ID)를 추가한다. 값은 Grafana Cloud 포털의 기존 스택에서 Loki 접속 정보를 확인해 넣는다. dev·prod가 같은 스택을 사용하므로 두 서버에 같은 접속 정보를 넣는다. 토큰은 `metrics:write`와 `logs:write` 권한을 확인한 기존 `GRAFANA_CLOUD_TOKEN`을 사용한다.

로그 전용 경로는 `/opt/app/logs/app/app.log`다. 배포 스크립트가 디렉터리 소유자를 앱 이미지의 실행 사용자로, 그룹을 Alloy의 GID `473`으로 설정한다. 하위 디렉터리는 `2750`으로 설정해 새 파일도 그룹 `473`을 상속하게 하고, 기존 파일에는 그룹 읽기 권한을 부여한다. Alloy는 일반 계정 `473:473`으로 실행하며, Alloy에는 `/opt/app/logs`만 읽기 전용으로 연결한다. Docker 내부 디렉터리는 연결하지 않는다. Alloy의 파일 읽기 위치는 `alloy-data` 볼륨에 보존하므로 이 볼륨을 삭제하지 않는다.

- 앱 로그: Spring Boot가 파일 크기가 10MB에 도달하면 새 파일에 기록하고, 최근 7일의 보관 파일을 총 100MB 이내로 유지한다. 현재 파일은 이 보관 용량과 별도다.
- Docker 표준 출력 로그: 컨테이너마다 최대 10MB 파일 3개로 제한한다. Alloy는 이 사본을 수집하지 않는다.

Alloy는 현재 `app.log`만 수집한다. RDS의 로그는 서버에 없어 수집하지 않는다. 중단 중 로그가 보관 파일로 넘어가면 그 파일의 미전송 로그는 자동으로 재수집하지 않는다. 읽기 위치 볼륨은 보관 파일 수집이나 전송 완료를 보장하지 않는다. 이 누락을 허용할지, 보관 파일도 수집할지는 추가 결정이 필요하다. 보관 기간 안에는 서버의 원본 파일에서 로그를 확인할 수 있다.

`application-prod.yml`은 `${MYSQL_USER}`처럼 참조만 하므로 커밋한다. 운영 설정이 서버에만 존재하면 **인스턴스를 다시 만들 때 무엇이 적용돼 있었는지 알 방법이 없기** 때문이다.

`.env`의 `IMAGE_TAG`는 배포 스크립트가 갱신한다. 값은 커밋 SHA 앞 7자리이므로, **지금 서버에 떠 있는 코드가 어느 커밋인지 이 파일로 확인한다.**

```bash
grep IMAGE_TAG /opt/app/.env
```

### 설정파일의 구성

새 설정을 추가할 때 어디에 적을지의 기준이다. **기준이 없으면 사람마다 다른 곳에 넣는다.**

| 위치                           | 담는 것                                      | 환경별로 다른가 | 저장소에 커밋                |
|------------------------------|-------------------------------------------|----------|------------------------|
| `application.yml`            | 환경과 무관한 공통 설정                             | 아니오      | 예                      |
| `application-{dev,prod}.yml` | 환경별로 값이 갈리는 설정 (쿼리 로그, API 문서 노출 등)       | 예        | 예                      |
| 각 서버의 `/opt/app/.env`        | 비밀값과 환경 식별자 (DB 호스트·계정·비밀번호, Grafana Cloud 접속 정보, 활성 프로파일, 이미지 태그) | 예        | **아니오** — 규격 예시 파일만 커밋 |

비밀값은 `.env`에 둔다. 공개 가능한 값이라도 환경별로 반드시 지정해야 하면 `.env`에 둔다. `PRODUCT_IMAGE_BASE_URL`은 공개 주소지만 서버별로 명시해 설정 누락을 즉시 발견한다.

`.env`의 `SPRING_PROFILES_ACTIVE`가 그 서버가 어느 환경인지를 정한다. `SPRING_PROFILES_ACTIVE`, `PRODUCT_IMAGE_BASE_URL`, `DB_HOST` 중 하나라도 비어 있으면 컨테이너를 만들기 전에 배포가 멈춘다. 프로파일을 지정하지 않으면 기본 프로파일(`local`)로 떠서 엉뚱한 DB를 찾다 실패하는데, 그때는 원인이 한참 뒤에 드러나기 때문이다.

로컬·개발·운영은 Flyway로 변경을 적용한 뒤 Hibernate의 `validate`로 엔티티 매핑을 검증한다. 공유 환경에 적용된 마이그레이션은 수정·삭제하지 않고 새 버전으로 보완한다.

CI의 `./gradlew build`는 전용 테스트 DB에서 전체 마이그레이션과 기준 데이터를 검증한다. 테스트의 `clean`은 검증용 DB를 초기화하는 용도이며, 개발·운영 앱 시작 시에는 실행하지 않는다.
테스트 구성은 [백엔드 개발 환경 가이드](백엔드_개발_환경_가이드.md#4-6-srctestresourcesapplicationyml)를 참고한다.

배포 환경에서는 첫 기동 시 V1.1·V1.2 적용과 앱 기동 성공을, 재기동 시 기존 마이그레이션이 다시 실행되지 않는지 확인한다. 앱을 이전 리비전으로 롤백해도 DB 변경은 자동 취소되지 않으므로 이전 앱과의
스키마 호환성도 확인한다.

## 4. 주의사항

**사고로 이어지는 것들이다. 서버에서 명령을 실행하기 전에 확인한다.**

- **compose 프로젝트 이름을 바꾸지 않는다.** Alloy 읽기 위치 볼륨 이름에 접두사로 붙어 있어(`app_alloy-data`), 이름이 어긋나면 Alloy가 로그를 처음부터 다시 읽는다.
  `scripts/deploy.sh`가 `COMPOSE_PROJECT_NAME=app`을 명시하는 이유다.
- **배포 전에 각 서버의 `.env`에 `SPRING_PROFILES_ACTIVE`, `PRODUCT_IMAGE_BASE_URL`, `DB_HOST`를 넣는다.** 하나라도 비어 있으면 배포가 컨테이너를 만들기 전에 멈춘다. 배포 스크립트는 `IMAGE_TAG` 줄만 갱신하므로 나머지 필수값은 사람이 넣어야 한다.
- **RDS 전환(#184) 이전 리비전으로 롤백하지 않는다.** 그 리비전은 DB 주소가 컨테이너(`db`)로 고정되어 있어, 앱이 전환 전의 옛 DB나(볼륨을 지운 뒤라면) 빈 DB에 붙는다. 앱은 정상처럼 보이지만 RDS의 데이터와 갈라진다.
- **로컬에서 만든 이미지를 서버에 올리지 않는다.** 서버가 ARM64라 x86에서 빌드한 이미지는 `exec format error`로 실행되지 않는다. 이미지는 CodeBuild의 ARM 환경에서만 만든다.

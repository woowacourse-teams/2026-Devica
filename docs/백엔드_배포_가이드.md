# 백엔드 배포 가이드

**서버를 다룰 때 보는 문서다.** 파이프라인이 어떻게 구성됐고 왜 그렇게 정했는지는 [ADR 0014](adr/0014-CD-파이프라인.md)에, 기술 선택의 근거는 [
`docs/adr`](adr/README.md)에 있다. 프론트엔드 배포는 [프론트엔드 배포 가이드](프론트엔드_배포_가이드.md)에서, 로컬 개발 환경은 [개발 환경 가이드](개발_환경_가이드.md)에서 다룬다.

---

## 1. 배포는 어떻게 이뤄지나

**일반적인 애플리케이션 배포에는 수동 작업이 없다.** 브랜치에 push하면 해당 환경의 CodePipeline이 실행되어 배포까지 완료한다. 다만 서버를 처음 구성하거나 DB 관리 방식을 전환하는 경우에는 환경
설정과 DB 상태를 사전에 확인해야 한다.

| push한 브랜치   | 배포되는 곳                  |
|-------------|-------------------------|
| `develop`   | 개발 서버 `ec2-devica-dev`  |
| `prototype` | 운영 서버 `ec2-devica-prod` |

현재 운영 서버는 `prototype`의 V0를 테스트용으로 배포하고 있다. 정식 버전 개발 완료 후에는 운영 파이프라인의 소스 브랜치를 `main`으로 전환하고, 이후 `develop`을 `main`에 병합해
배포한다.

파이프라인은 소스를 받아 테스트하고, 이미지를 만들어 배포 번들에 실어 보내고, 서버의 CodeDeploy 에이전트가 컨테이너를 교체한 뒤 헬스체크로 확인한다. 실패하면 이전 리비전으로 자동 롤백된다. 배포 그룹
설정과 훅 구성은 [ADR 0014](adr/0014-CD-파이프라인.md)에 있다.

### Flyway 최초 전환

Flyway 최초 전환은 일반적인 애플리케이션 배포와 달리 DB 상태를 미리 준비해야 하는 일회성 작업이다.

개발 서버 DB에는 Hibernate의 `ddl-auto: update`로 생성된 테이블이 있었지만 `flyway_schema_history`는 없었다. 기존 데이터는 보존할 필요가 없는 V0 테스트 데이터였으므로,
최초 Flyway 배포 전에 기존 `app_mysql-data` 볼륨을 삭제해 빈 DB로 전환했다. 이후 애플리케이션을 배포하면 Flyway가 `V1.1`부터 최신 마이그레이션까지 적용한다.

개발 서버의 볼륨 초기화는 이번 최초 전환에만 수행한다. Flyway가 최초 적용된 이후에는 볼륨을 삭제하지 않고 DB 데이터를 유지하면서 새로운 마이그레이션을 누적 적용한다.

정식 운영의 첫 배포는 새 빈 DB에 연결해 `V1.1`의 초기 스키마와 `V1.2`의 기준 데이터부터 적용한다. V0 데이터는 이관하지 않으며 기존 V0 DB도 삭제하지 않는다. 운영 소스 브랜치를
`prototype`에서 `main`으로 변경해도 DB 연결 대상은 자동으로 변경되지 않으므로 배포 전에 연결 설정을 함께 확인한다.

이번 Flyway 도입에서는 `baseline-on-migrate`를 사용하지 않는다. 데이터를 보존해야 하는 기존 DB에 Flyway를 도입해야 한다면 해당 환경의 전환 및 baseline 정책을 별도로 결정한다.
결정 배경은 [ADR 0028](adr/0028-DB-스키마-마이그레이션-관리.md)에 있다.

## 2. 서버 구성

|       | 개발 (dev)                                                           | 운영 (prod)                                                           |
|-------|--------------------------------------------------------------------|---------------------------------------------------------------------|
| 인스턴스  | `ec2-devica-dev` (public subnet)                                   | `ec2-devica-prod` (private subnet)                                  |
| 접속    | SSH                                                                | **AWS 콘솔의 SSM 세션 매니저만** — EC2 > 인스턴스 선택 > Connect > Session Manager |
| 접근 경로 | `http://<EC2 주소>` (HTTPS 없음)                                       | `https://` → ALB → EC2                                              |
| 아키텍처  | 둘 다 ARM64 (Graviton). 서버에서 `uname -m`이 `aarch64`                   | 〃                                                                   |
| 실행    | `docker compose -f docker-compose.server.yml` — 호스트 80 → 컨테이너 8080 | 〃                                                                   |
| DB    | EC2 안의 MySQL 컨테이너. 볼륨 `mysql-data`로 데이터를 유지                        | 〃                                                                   |

**두 서버가 같은 compose 파일을 쓴다.** 구성이 같고 값만 다르기 때문이다. 환경 차이는 각 서버의 `.env`가 흡수한다 — `SPRING_PROFILES_ACTIVE`가 `dev`냐 `prod`냐에
따라 쿼리 로그 등의 설정이 갈린다. 스키마 변경은 두 환경 모두 Flyway가 적용하고 Hibernate는 `validate`만 수행한다.

## 3. 설정과 비밀값

**비밀값은 각 서버의 `/opt/app/.env`에만 있다.** 규격은 저장소의 `.env.server.example`에 있고, 실제 값이 담긴 `.env`는 커밋하지 않는다.

`application-prod.yml`은 `${MYSQL_USER}`처럼 참조만 하므로 커밋한다. 운영 설정이 서버에만 존재하면 **인스턴스를 다시 만들 때 무엇이 적용돼 있었는지 알 방법이 없기** 때문이다.

`.env`의 `IMAGE_TAG`는 배포 스크립트가 갱신한다. 값은 커밋 SHA 앞 7자리이므로, **지금 서버에 떠 있는 코드가 어느 커밋인지 이 파일로 확인한다.**

```bash
grep IMAGE_TAG /opt/app/.env
```

### 설정파일의 구성

새 설정을 추가할 때 어디에 적을지의 기준이다. **기준이 없으면 사람마다 다른 곳에 넣는다.**

| 위치                           | 담는 것                                      | 환경별로 다른가 | 저장소에 커밋                |
|------------------------------|-------------------------------------------|----------|------------------------|
| `application.yml`            | 환경과 무관한 공통 설정                             | 아니오      | 예                      |
| `application-{dev,prod}.yml` | 환경별로 값이 갈리는 설정 (쿼리 로그, API 문서 노출 등)       | 예        | 예                      |
| 각 서버의 `/opt/app/.env`        | 비밀값과 환경 식별자 (DB 계정·비밀번호, 활성 프로파일, 이미지 태그) | 예        | **아니오** — 규격 예시 파일만 커밋 |

기준은 하나다. **값이 드러나도 되면 yml에, 드러나면 안 되면 `.env`에 둔다.**

`.env`의 `SPRING_PROFILES_ACTIVE`가 그 서버가 어느 환경인지를 정한다. **값이 없으면 컨테이너를 만들기 전에 배포가 멈춘다.** 지정하지 않으면 기본 프로파일(`local`)로 떠서 엉뚱한
DB를 찾다 실패하는데, 그때는 원인이 한참 뒤에 드러나기 때문이다.

로컬·개발·운영은 Flyway로 변경을 적용한 뒤 Hibernate의 `validate`로 엔티티 매핑을 검증한다. 공유 환경에 적용된 마이그레이션은 수정·삭제하지 않고 새 버전으로 보완한다.

CI의 `./gradlew build`는 전용 테스트 DB에서 전체 마이그레이션과 기준 데이터를 검증한다. 테스트의 `clean`은 검증용 DB를 초기화하는 용도이며, 개발·운영 앱 시작 시에는 실행하지 않는다.
테스트 구성은 [개발 환경 가이드](개발_환경_가이드.md#4-6-srctestresourcesapplicationyml)를 참고한다.

배포 환경에서는 첫 기동 시 V1.1·V1.2 적용과 앱 기동 성공을, 재기동 시 기존 마이그레이션이 다시 실행되지 않는지 확인한다. 앱을 이전 리비전으로 롤백해도 DB 변경은 자동 취소되지 않으므로 이전 앱과의
스키마 호환성도 확인한다.

## 4. 주의사항

**사고로 이어지는 것들이다. 서버에서 명령을 실행하기 전에 확인한다.**

- **운영에서 `docker compose down -v`를 실행하지 않는다.** `-v`는 볼륨을 지워 DB 데이터를 삭제한다. 앱만 교체할 때는
  `docker compose -f docker-compose.server.yml up -d app`을 쓴다.
- **compose 프로젝트 이름을 바꾸지 않는다.** 볼륨 이름에 접두사로 붙어 있어(`app_mysql-data`), 이름이 어긋나면 빈 볼륨이 새로 생겨 **DB가 통째로 사라진 것처럼 보인다.**
  `scripts/deploy.sh`가 `COMPOSE_PROJECT_NAME=app`을 명시하는 이유다.
- **서버를 새로 만들면 `.env`에 `SPRING_PROFILES_ACTIVE`를 먼저 넣는다.** 없으면 배포가 컨테이너를 만들기 전에 멈춘다. 배포 스크립트는 `IMAGE_TAG` 줄만 갱신하므로 이 값은
  사람이 한 번 넣어야 한다.
- **로컬에서 만든 이미지를 서버에 올리지 않는다.** 서버가 ARM64라 x86에서 빌드한 이미지는 `exec format error`로 실행되지 않는다. 이미지는 CodeBuild의 ARM 환경에서만 만든다.
- **인스턴스를 재생성하면 데이터가 사라진다.** DB가 EC2 안의 컨테이너이고 백업 방안이 없다.

## 5. 알려진 한계

서버 운영에 관한 것만 적는다. 파이프라인 쪽 한계는 [ADR 0014의 감수하는 것](adr/0014-CD-파이프라인.md#감수하는-것)에 있다.

| # | 한계                                  | 언제 다룰 것인가                                                                                 |
|---|-------------------------------------|-------------------------------------------------------------------------------------------|
| 1 | DB에 백업이 없다                          | 인스턴스 장애 시 데이터가 사라진다. `mysqldump` 주기 실행이나 RDS 이전을 별도 이슈로                                   |
| 2 | 앱 롤백이 DB 변경까지 되돌리지 않는다              | 스키마 이력은 Flyway로 관리한다. 배포 시 이전 앱 버전과의 호환성을 확인하고, 이미 성공한 migration의 변경은 후속 migration으로 보완한다 |
| 3 | 개발 서버에 HTTPS가 없다                    | TLS가 필요한 동작은 개발 서버에서 검증할 수 없다 ([ADR 0017](adr/0017-서버-환경-분리.md))                          |
| 4 | 로컬(IDE 실행)과 서버(컨테이너 실행)의 실행 방식이 다르다 | 컨테이너 환경에서만 드러나는 문제는 배포 단계에서 처음 확인된다 ([ADR 0007](adr/0007-컨테이너-적용-범위.md))                  |

## 0. 이 문서에 대하여

### 목적
새로 합류한 팀원이 이 문서만 보고 **혼자서** 개발 환경을 재현하고, 서버를 띄우고, 테스트를 돌릴 수 있게 하는 것이다.

막히는 부분이 생기면 해결한 사람이 이 문서를 직접 고치도록 하자.

### 이 문서가 다루는 범위
- 로컬 개발 환경 구성 및 실행
- 테스트 실행 환경
- AI 에이전트 규칙 파일 연결 ([Step 7](#step-7-ai-에이전트-설정-선택))
- 위 결정들의 근거와 트레이드오프

### 이 문서가 다루지 않는 범위
| 항목 | 언제 다루나 |
|---|---|
| AWS 배포 | 지정 요구사항 2 수행 시 별도 문서 |
| CI/CD 자동화 | 자율 요구사항으로 별도 진행 |
| 운영 환경 DB 운영·백업 | 배포 문서에서 |

### 로컬 실행 구조

```
┌─────────────────────────────┐
│  내 노트북                    │
│                             │
│  IntelliJ ──► Spring Boot   │   ← 앱은 IDE에서 직접 실행
│                 │            │      (디버깅·핫리로드 목적)
│                 ▼            │
│  ┌──────────────────────┐   │
│  │ Docker               │   │
│  │  mysql      :3306    │◄──┘   ← 개발용 DB
│  │  mysql-test :3307    │◄──────← 테스트용 DB
│  └──────────────────────┘   │
└─────────────────────────────┘
```

**앱은 컨테이너에 넣지 않는다.** 로컬에서는 브레이크포인트를 걸고 코드를 고쳐가며 개발하는 것이 우선이라, IDE에서 직접 띄우는 편이 훨씬 빠르다. DB만 컨테이너로 두면 "MySQL 설치했는데 버전이 다름", "포트가 이미 쓰이고 있음" 같은 팀원 간 환경 차이가 사라진다.

### 실행 구성 한눈에 보기

같은 코드가 상황에 따라 **어떤 설정 파일을 읽고 어느 DB에 붙는지** 정리한 표다. 문제가 생겼을 때 "지금 내가 어느 구성으로 돌리고 있지"를 먼저 확인하면 원인이 빨리 좁혀진다.

| | **로컬 실행** | **로컬 테스트** | **배포** (아직 미구성) |
|---|---|---|---|
| 앱 실행 주체 | IntelliJ ▶ (JVM 직접) | `./gradlew test` (JVM 직접) | Docker 컨테이너 (`Dockerfile`) |
| 붙는 DB | `devica-mysql` **:3306** | `devica-mysql-test` **:3307** | EC2 내 MySQL 컨테이너 |
| Compose 파일 | `docker-compose.yml` | `docker-compose.yml` (같은 파일이 두 DB를 함께 띄움) | `docker-compose.prod.yml` |
| 읽는 설정 파일 | `application.yml` + `application-local.yml` | `src/test/resources/application.yml` **만** | `application-prod.yml` |
| 활성 프로파일 | `local` (`profiles.default`) | 없음 (`default`) | `prod` |
| `ddl-auto` | `update` | `create-drop` | `validate` 또는 `none` ([6-6](#6-6-스키마-관리-ddl-auto)) |
| 데이터 보존 | 볼륨 `mysql-data`, 재시작해도 유지 | 볼륨 없음, 컨테이너 삭제 시 소멸 | 볼륨 필요, 백업 방안 미정 ([7](#7-알려진-한계와-다음-액션)) |
| 실행 명령 | `docker compose up -d` → IDE ▶ | `docker compose up -d` → `./gradlew test` | `docker compose -f docker-compose.prod.yml up -d` |

**로컬 실행과 로컬 테스트는 DB만 다르다.** 앱을 켜둔 채로 테스트를 돌려도 서로의 데이터를 건드리지 않는다. `docker compose up -d` 한 번이면 두 DB가 같이 뜨므로 상황에 따라 명령을 바꿀 필요는 없다.

> **테스트는 `local` 프로파일이 아니다.** `src/test/resources/application.yml`이 main의 `application.yml`을 **대체**하기 때문에(이름이 같으면 하나만 로드된다), `profiles.default: local`도 `application-local.yml`도 테스트에서는 읽히지 않는다. main의 설정 중 테스트에도 필요한 값은 테스트 설정 파일에 **다시 적어야 한다.** → [4-6](#4-6-srctestresourcesapplicationyml)

## 2. 사전 준비물

설치 순서대로 적었다. 위에서부터 하나씩 확인하면 된다.

### 2-1. JDK 21

배포판은 **Eclipse Temurin 21**로 통일한다.

- 다운로드: https://adoptium.net/temurin/releases/?version=21
- IntelliJ 안에서 설치해도 된다. `File > Project Structure > SDKs > + > Download JDK > Version 21, Vendor: Eclipse Temurin`

> **"`build.gradle`의 toolchain이 알아서 받아준다면서 왜 직접 설치하지?"** — toolchain은 *Gradle이 컴파일에 쓸* JDK를 자동으로 확보해준다. 하지만 [Step 3 (1)](#1-gradle-jvm을-21로-맞춘다)에서 지정할 **Gradle JVM(= Gradle 자신이 돌아갈 JDK)** 은 이미 설치되어 있어야 한다. 그래서 한 번은 직접 설치한다.

확인:

```bash
java -version
# openjdk version "21.0.x" 이어야 함
```

> 배포판을 통일하는 이유는 특별한 기술적 필요보다 **"내 JDK는 왜 다르지"를 논의하는 시간을 없애기 위해서**다. Temurin은 무료이고 상용 라이선스 이슈가 없다.

### 2-2. Docker Desktop

- 다운로드: https://www.docker.com/products/docker-desktop/
- **Windows**: 설치 시 WSL 2 백엔드를 선택한다. WSL이 없으면 설치 과정에서 자동으로 안내된다.
- **Mac**: 칩에 맞는 버전을 받는다. (Apple Silicon / Intel)

확인:

```bash
docker --version
docker compose version
```

> `docker-compose`(하이픈)가 아니라 `docker compose`(공백)다. 하이픈 버전은 구버전 명령어이며, 검색으로 나오는 자료가 대부분 하이픈이라 혼동하기 쉽다.

## 3. 최초 세팅

**소요 시간 약 20분.** 한 번만 하면 된다.

### Step 1. 저장소 클론

```bash
git clone <저장소 URL>
cd devica
```

### Step 2. IntelliJ로 열기

`File > Open` → 클론한 폴더 선택 → **Gradle 프로젝트로 인식되면 "Load Gradle Project" 클릭.**

첫 임포트는 의존성을 내려받느라 2~5분 걸린다.

### Step 3. IntelliJ 설정 4가지

**(1)과 (2)는 필수다.** 안 하면 빌드가 실패하거나 한글이 깨진다.
(3)과 (4)는 코드 스타일을 맞추기 위한 것으로, 지금 안 해도 개발은 되지만 리뷰에서 지적을 반복해서 받게 된다.

#### (1) Gradle JVM을 21로 맞춘다

`Settings > Build, Execution, Deployment > Build Tools > Gradle`

| 항목 | 값 |
|---|---|
| Gradle JVM | **21 (Temurin)** |
| Build and run using | IntelliJ IDEA |
| Run tests using | IntelliJ IDEA |

> `Build and run using`을 IntelliJ로 두면 실행이 빠르다. 단 빌드 결과가 Gradle과 미세하게 다를 수 있으므로, **PR 올리기 전에는 반드시 `./gradlew build`로 한 번 확인한다.**

#### (2) 파일 인코딩을 UTF-8로 맞춘다

`Settings > Editor > File Encodings`

| 항목 | 값 |
|---|---|
| Global Encoding | UTF-8 |
| Project Encoding | UTF-8 |
| Default encoding for properties files | UTF-8 |

> **Windows 사용자는 이걸 꼭 확인한다.** 기본값이 MS949로 잡혀 있으면 한글 주석과 한글 문자열이 컴파일 시점에 깨진다. Mac 팀원과 같은 파일을 열었을 때 한쪽만 글자가 깨지는 현상의 원인이 대부분 이것이다.

#### (3) 우테코 코드 스타일 적용

1. https://github.com/woowacourse/woowacourse-docs/tree/main/styleguide/java 에서 `intellij-java-wooteco-style.xml` 다운로드
2. `Settings > Editor > Code Style > Java`
3. 우측 톱니바퀴(⚙) → `Import Scheme > IntelliJ IDEA code style XML`
4. 다운로드한 파일 선택 → Scheme을 방금 임포트한 것으로 지정

#### (4) 저장할 때 자동 정리

`Settings > Tools > Actions on Save` 에서 아래 두 개를 켠다.

- ☑ Reformat code
- ☑ Optimize imports

> 이걸 켜두면 스타일을 신경 쓰지 않아도 저장할 때마다 자동으로 맞춰진다. **(3)번 스타일 적용의 효과가 실제로 나타나려면 이 설정이 필요하다.**

### Step 4. DB 컨테이너 실행

Docker Desktop이 실행 중인지 먼저 확인한다.

```bash
docker compose up -d
```

정상적으로 떴는지 확인:

```bash
docker compose ps
```

```
NAME                IMAGE       STATUS         PORTS
devica-mysql        mysql:8.4   Up (healthy)   0.0.0.0:3306->3306/tcp
devica-mysql-test   mysql:8.4   Up (healthy)   0.0.0.0:3307->3306/tcp
```

두 컨테이너 모두 **`(healthy)`** 가 될 때까지 기다린다. 최초 실행 시 MySQL 초기화에 20~40초 걸린다. `Up (health: starting)` 상태에서 앱을 실행하면 연결 실패가 난다.

### Step 5. 애플리케이션 실행

IntelliJ에서 `DevicaApplication` 클래스를 열고 좌측 ▶ 버튼을 누른다.

로그에 아래가 보이면 성공이다.

```
No active profile set, falling back to 1 default profile: "local"
Tomcat started on port 8080 (http)
Started DevicaApplication in x.xxx seconds
```

브라우저에서 http://localhost:8080 접속 확인. **컨트롤러를 아직 만들지 않았다면 404가 정상이다.** 위 로그 세 줄이 떴다면 성공한 것이다.

### Step 6. 테스트 실행

```bash
# Mac / Linux
./gradlew test

# Windows (PowerShell)
.\gradlew.bat test
```

```
BUILD SUCCESSFUL
```

여기까지 나오면 세팅 완료다.

> **아직 테이블은 하나도 생기지 않는다.** 엔티티(`@Entity`) 클래스가 없기 때문이다. DB에 접속해 `SHOW TABLES;`가 비어 있어도 정상이니, 세팅이 잘못된 것으로 오해하지 않아도 된다. 첫 엔티티를 만들고 앱을 다시 실행하면 그때 테이블이 생긴다.

### Step 7. AI 에이전트 설정 (선택)

AI 에이전트 설정은 필수가 아니다. AI 에이전트를 쓰는 경우에만 수행하도록 한다.
팀은 Claude Code와 Codex를 함께 쓴다. **규칙은 두 도구에 동일하게 적용하되, 어떤 에이전트를 어떻게 쓸지는 각자 선택한다.** 그래서 저장소에는 도구 중립 파일인 [`AGENTS.md`](../AGENTS.md)와 [`harness/`](../harness/README.md)만 커밋하고, 도구별 설정은 각자 로컬에 둔다.

| 파일 | 저장소 | 읽는 도구 |
|---|---|---|
| `AGENTS.md` | 커밋됨 | Codex가 그대로 읽는다 |
| `harness/` | 커밋됨 | `AGENTS.md`가 필요할 때 열도록 안내한다 |
| `CLAUDE.md` | **커밋 안 함** (`.gitignore`) | Claude Code |

#### Claude Code를 쓴다면

Claude Code는 `AGENTS.md`를 읽지 않는다. 프로젝트 루트에 **한 줄짜리 `CLAUDE.md`** 를 만들어 `AGENTS.md`를 불러오게 한다.

`CLAUDE.md`의 전체 내용은 이 한 줄이다.

```
@AGENTS.md
```

```bash
# Mac / Linux
echo "@AGENTS.md" > CLAUDE.md
```

```powershell
# Windows (PowerShell)
"@AGENTS.md" | Out-File -Encoding utf8 CLAUDE.md
```

에디터로 새 파일을 만들어 저 한 줄을 쓰고 저장해도 똑같다. **그 편이 OS를 안 타서 확실하다.**

> **심볼릭 링크(`ln -s`) 대신 이 방식을 쓰는 이유** — `ln -s`는 Windows에서 그대로 동작하지 않는다. PowerShell로 만들려면 개발자 모드나 관리자 권한이 필요하고, Git Bash의 `ln -s`는 기본 설정에서 링크가 아니라 **복사본**을 만든다. 복사본이 만들어지면 `AGENTS.md`를 고쳐도 따라오지 않는데, `CLAUDE.md`는 `.gitignore` 대상이라 **아무도 어긋난 걸 알아채지 못한다.** `@AGENTS.md` 한 줄이면 OS 분기도 권한도 필요 없고 항상 최신을 읽는다.

#### Codex를 쓴다면

추가 설정이 없다. `AGENTS.md`를 그대로 읽는다.

#### 확인

에이전트를 띄우고 물어본다.

> AGENTS.md의 금지 패턴 5개를 말해봐

**파일을 열어보지 않고 바로 답하면** 규칙이 주입된 것이다. 파일을 찾아 읽으려 하면 안 먹은 것이니, 그때는 심볼릭 링크(`ln -s AGENTS.md CLAUDE.md`)로 대체한다.

> `.claude/`, `.codex/`, `CLAUDE.md`는 모두 `.gitignore`에 있다. **커밋되지 않는 게 정상이다.**

## 4. 설정 파일

아래 파일들은 모두 **저장소에 커밋되어 있다.** 새로 만들 필요 없이 내용을 이해하는 용도로 읽으면 된다.

### 4-1. `docker-compose.yml`

```yaml
services:
  mysql:
    image: mysql:8.4
    container_name: devica-mysql
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: devica
      TZ: Asia/Seoul
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot"]
      interval: 5s
      timeout: 5s
      retries: 10

  mysql-test:
    image: mysql:8.4
    container_name: devica-mysql-test
    ports:
      - "3307:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: devica_test
      TZ: Asia/Seoul
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
    # 테스트 DB는 볼륨을 두지 않는다. 컨테이너를 지우면 데이터도 사라지는 게 맞다.
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  mysql-data:
```

**읽을 때 짚어둘 점**

| 설정 | 이유 |
|---|---|
| 테스트 DB를 별도 컨테이너(`3307`)로 | 왜 H2나 Testcontainers가 아닌지는 [6-5](#6-5-테스트-db-전략)에 있다. |
| 개발 DB에만 `volumes` | 개발 중 넣은 데이터는 컨테이너를 껐다 켜도 남아야 한다. 테스트 DB는 반대로 매번 깨끗한 게 낫다. |
| `healthcheck` | MySQL은 컨테이너가 뜬 뒤에도 초기화에 수십 초가 걸린다. 이게 없으면 "컨테이너는 켰는데 연결이 안 됨"을 계속 겪는다. |
| `utf8mb4` 명시 | MySQL 8.4 기본값이긴 하지만, 이모지 저장 실패는 원인을 찾기 어려운 버그라 명시해둔다. |
| `TZ: Asia/Seoul` | 앱과 DB의 시간대를 맞춘다. 안 맞으면 저장한 시각이 9시간 어긋난다. |

**로컬 DB 비밀번호를 `root`로 두고 그대로 커밋한 이유**

로컬 컨테이너는 외부에서 접근할 수 없고, 여기 담기는 건 개발용 더미 데이터뿐이다. 비밀번호를 숨기려고 `.env` 파일을 도입하면 "클론했는데 `.env`가 없어서 안 뜬다"는 문제가 새로 생긴다. **얻는 것보다 잃는 게 크다.**

> **운영 환경 자격증명은 절대 커밋하지 않는다.** 배포 문서에서 별도 방식(환경변수 주입)을 정한다.

**읽을 때 짚어둘 점**

| 설정 | 이유 |
|---|---|
| `toolchain` 사용 | 팀원의 `JAVA_HOME`이 무엇이든 Gradle이 JDK 21을 찾아 쓴다. 없으면 자동으로 받는다. `sourceCompatibility`만 쓰는 것보다 환경 차이에 강하다. |
| `starter-web`이 아니라 **`starter-webmvc`** | Spring Boot 4에서 웹 스타터가 세분화되었다. **검색으로 나오는 `spring-boot-starter-web`은 3.x 표기다.** |
| `starter-test`가 아니라 **모듈별 test starter** | 마찬가지로 Boot 4에서 쪼개졌다. `data-jpa-test` / `webmvc-test` / `thymeleaf-test` 조합으로 JUnit 5·AssertJ·Mockito가 모두 들어온다. 따로 추가할 필요 없다. |
| 의존성에 버전이 없음 | Spring Boot BOM이 검증된 조합으로 관리한다. **임의로 버전을 명시하면 호환성이 깨질 수 있으므로 하지 않는다.** |
| `com.mysql:mysql-connector-j` | 예전 좌표인 `mysql:mysql-connector-java`는 폐기되었다. 검색으로 나오는 옛날 자료를 그대로 쓰지 않는다. |
| Lombok이 `compileOnly` + `annotationProcessor` 두 줄 | 컴파일 시점에만 필요하고 결과물에는 포함되지 않는다. 두 줄 중 하나라도 빠지면 `@Getter` 같은 애너테이션이 동작하지 않는다. |

### 4-3. Gradle Wrapper 버전 고정

Spring Boot 4.1은 **Gradle 8.14 이상**을 요구한다. 저장소에 포함된 `gradle/wrapper/gradle-wrapper.properties`가 버전을 고정하므로, 팀원이 Gradle을 따로 설치할 필요는 없다. 현재 고정된 버전은 **9.5.1**이다.

```properties
distributionUrl=https\://services.gradle.org/distributions/gradle-9.5.1-bin.zip
```

> 그래서 명령어는 항상 `gradle`이 아니라 **`./gradlew`(Windows는 `.\gradlew.bat`)** 를 쓴다. 로컬에 설치된 Gradle을 쓰면 버전이 달라 빌드 결과가 달라질 수 있다.

### 4-4. `src/main/resources/application.yml`

```yaml
spring:
  application:
    name: devica

  profiles:
    default: local

  jpa:
    open-in-view: false
    properties:
      hibernate:
        format_sql: true
```

`profiles.default: local`을 두면 **아무 설정을 하지 않아도 로컬 프로파일로 실행된다.** 팀원마다 Run Configuration을 손볼 필요가 없다.

> `open-in-view: false`로 두는 이유: 기본값(`true`)은 컨트롤러가 응답을 다 만들 때까지 DB 커넥션을 붙잡고 있어서, 나중에 트래픽이 늘면 커넥션이 고갈된다. 끄면 지연 로딩 오류가 **개발 단계에서** 드러나므로 문제를 일찍 발견할 수 있다.

### 4-5. `src/main/resources/application-local.yml`

```yaml
spring:
  datasource:
    # 3306 이 이미 쓰이고 있으면 DB_PORT 환경변수로 바꾼다 (이 파일은 고치지 않는다)
    url: jdbc:mysql://localhost:${DB_PORT:3306}/devica?characterEncoding=UTF-8&serverTimezone=Asia/Seoul
    username: root
    password: root
    driver-class-name: com.mysql.cj.jdbc.Driver

  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true

logging:
  level:
    org.hibernate.orm.jdbc.bind: trace
```

> **포트만 환경변수로 열어둔 이유** — 로컬에 MySQL이 이미 설치된 팀원은 3306을 쓸 수 없다. 그때 이 파일을 고치면 **그 수정이 PR에 섞여 다른 팀원의 환경을 깨뜨린다.** `${DB_PORT:3306}` 이면 환경변수만 주고 파일은 그대로 둘 수 있다. 사용법은 [9장 포트 충돌](#포트-충돌--address-already-in-use--port-is-already-allocated)에 있다.
>
> 나머지 값(호스트·DB명·계정)은 로컬에서 달라질 일이 없어 그대로 적었다. 바뀌지 않는 값을 변수로 빼면 읽는 사람만 피곤해진다.

> `logging.level.org.hibernate.orm.jdbc.bind: trace`는 쿼리의 `?` 자리에 실제로 어떤 값이 들어갔는지 로그로 보여준다. Hibernate 6부터 패키지 경로가 바뀌어서, 검색으로 나오는 `org.hibernate.type.descriptor.sql`은 더 이상 동작하지 않는다.

### 4-6. `src/test/resources/application.yml`

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:${TEST_DB_PORT:3307}/devica_test?characterEncoding=UTF-8&serverTimezone=Asia/Seoul
    username: root
    password: root
    driver-class-name: com.mysql.cj.jdbc.Driver

  jpa:
    # main 의 application.yml 은 테스트에서 아예 로드되지 않으므로 여기 다시 적는다
    open-in-view: false
    hibernate:
      ddl-auto: create-drop
    show-sql: true
```

포트를 `${TEST_DB_PORT:3307}` 로 둔 이유는 [4-5](#4-5-srcmainresourcesapplication-localyml)와 같다. 개발 DB와 따로 바꿀 수 있어야 해서 변수 이름만 다르다.

테스트 소스의 설정 파일이 우선 적용되므로, 테스트는 **자동으로 3307 포트의 테스트 DB**를 바라본다. 테스트 코드에 `@ActiveProfiles`를 붙일 필요가 없다.

**주의 — 이 파일은 main의 `application.yml`을 "덮어쓰는" 게 아니라 "대체"한다.**

이름이 같은 설정 파일이 클래스패스에 둘 있으면 Spring은 **앞에 오는 하나만 읽는다.** 테스트 실행 시에는 `src/test/resources`가 앞이므로, main의 `application.yml`은 **아예 로드되지 않는다.** 두 파일이 병합될 거라고 생각하기 쉬운데 그렇지 않다.

실제로 테스트 로그를 보면 이렇게 나온다.

```
No active profile set, falling back to 1 default profile: "default"
```

`local`이 아니라 `default`다. 즉 `profiles.default: local`도, `application-local.yml`도 테스트에서는 적용되지 않는다.

그래서 **main에 적어둔 값 중 테스트에도 필요한 것은 여기에 다시 적어야 한다.** 위의 `open-in-view: false`가 그 예다. 빠뜨리면 테스트에서만 기본값(`true`)으로 돌아가, [6-4](#6-4-로컬에서-앱은-ide-db는-컨테이너)에서 의도한 "지연 로딩 문제를 개발 단계에 드러낸다"가 정작 테스트에서 무력화된다.

`ddl-auto: create-drop`이라 테스트를 실행할 때마다 스키마를 새로 만들고 끝나면 지운다. 엔티티를 바꿔도 테스트 DB 스키마가 어긋나지 않는다.

## 6. 기술 선택 근거와 트레이드오프

각 결정에 대해 **왜 골랐는지 / 무엇을 검토했는지 / 무엇을 포기했는지**를 남긴다.

### 6-1. Spring Boot 4.1.0

**결정 근거**

버전을 고를 때 기능보다 **지원 기간**을 먼저 봤다. 프로젝트 기간 동안 보안 패치를 받을 수 있는지가 기준이다.

| 버전 | OSS 지원 종료 | 판단 |
|---|---|---|
| 3.5.x (마지막 3.x) | **2026-06-30 — 이미 종료** | 보안 패치를 받을 수 없음 |
| 4.0.x | 2026-12-31 | 프로젝트 기간 중 만료 |
| **4.1.x** | **2027-07-31** | 채택 |

모든 3.x 브랜치는 이미 오픈소스 지원이 끝났다. 익숙하다는 이유로 3.5를 골랐다면 **보안 패치를 못 받는 상태로 사용자에게 서비스를 여는 셈**이 된다. 4.0은 지원 기간이 5개월뿐이라 프로젝트 도중 버전을 다시 올려야 한다. 실질적으로 4.1이 유일한 선택지였다.

**검토한 대안**

- *Spring Boot 3.5* — 국내 자료가 압도적으로 많고 팀이 미션에서 써 본 버전이다. 지원 종료로 탈락.
- *Spring Boot 4.0* — 4.1보다 자료가 조금 더 쌓여 있으나, 지원 기간이 5개월뿐이라 프로젝트 중 다시 올려야 한다.

**트레이드오프 — 감수하기로 한 것**

레퍼런스가 부족하다. 국내 블로그와 강의 자료 대부분이 3.x 기준이라, 막혔을 때 검색으로 답이 안 나오는 상황을 자주 만날 것이다.

**대응 방침**

1. **공식 레퍼런스를 1차 출처로 삼는다.** https://docs.spring.io/spring-boot/
2. 검색 결과를 적용하기 전 **버전을 먼저 확인한다.** 3.x 기준 코드가 4.x에서 그대로 동작하지 않는 경우가 있다.
3. 해결한 문제는 아래 [트러블슈팅](#9-트러블슈팅)에 기록해 같은 문제를 두 번 겪지 않는다.

**알아둘 변경점**

- Spring Framework 7 기반이다. (3.x는 Framework 6)
- Spring Boot 4.0에서 deprecated였던 것들이 4.1에서 제거되었다.
- Gradle 8.14 이상이 필수다.

### 6-2. JDK 21

**결정 근거**

Spring Boot 4.1은 Java 17~26을 지원한다. 그중 공급자로부터 보안 패치와 기술 지원을 장기간 받을 수 있는 **LTS**만 후보로 뒀다. 17보다 현대적인 기능을 지원하고 Virtual Threads를 활용할 수 있는 21과 25를 비교한 끝에, 호환성과 운영 사례가 충분히 축적되어 실무 기본값으로 자주 쓰이는 **21**을 골랐다.

**트레이드오프**

25의 최신 기능을 쓰지 못한다. 다만 이번 프로젝트에서 21에 없는 언어 기능이 필요한 상황은 예상되지 않는다.

### 6-3. MySQL 8.4

**결정 근거**

**DBMS 종류** — 리뷰 공유 서비스는 사용자·전자기기·카테고리·리뷰·태그처럼 관계가 명확한 정형 데이터를 주로 다룬다. 무결성을 관리할 스키마와 제약조건이 필요하고, 리뷰 조회·필터링·정렬·페이지네이션에는 MySQL의 관계형 모델·트랜잭션·인덱스로 충분하다. 팀원들이 MySQL 사용 경험이 있어 스키마 설계, SQL 작성, Spring Boot 연동, 성능·오류 대응을 빠르게 진행할 수 있고 레퍼런스와 지원 도구도 풍부하다.

**버전** — LTS 중에서 고르되, MySQL 9.7의 JSON Duality Views·최신 옵티마이저·고급 복제 및 관측 기능은 이번 프로젝트에서 활용할 가능성이 낮다고 봤다. 더 먼저 안정화된 8.4 LTS를 쓴다.

**검토한 대안**

- *PostgreSQL* — JSONB, 고급 SQL, 확장 기능을 활용한 복잡한 데이터 처리에 강점이 있다. 다만 현재 서비스에서는 그 기능의 필요성이 명확하지 않아, 팀이 익숙하고 핵심 리뷰 탐색 기능을 안정적으로 구현할 수 있는 MySQL을 골랐다.
- *NoSQL* — 다루는 데이터가 관계 중심의 정형 데이터라 맞지 않는다.
- *H2 (인메모리)* — 설치가 필요 없어 편하지만 운영과 DBMS가 달라진다. [6-5](#6-5-테스트-db-전략)에서 다룬다.

**주의점**

MySQL 8.4는 `mysql_native_password` 인증 플러그인이 기본 비활성화되었다. 오래된 클라이언트로 접속하면 인증 오류가 날 수 있다. `mysql-connector-j` 최신 버전(Boot가 관리)을 쓰면 문제없다.

### 6-4. 로컬에서 앱은 IDE, DB는 컨테이너

**결정 근거**

두 가지를 동시에 얻기 위한 조합이다.

| 목표 | 이 방식이 해결하는 것 |
|---|---|
| 빠른 개발 반복 | 앱이 IDE에 있으니 브레이크포인트, 즉시 재실행이 가능하다 |
| 환경 통일 | DB가 컨테이너라 팀원 전원이 동일한 MySQL 8.4를 쓴다 |

**검토한 대안**

- *앱까지 컨테이너로 실행* — 운영과 환경이 완전히 같아지지만, 코드 한 줄 고칠 때마다 이미지를 다시 빌드해야 해서 개발 속도가 크게 떨어진다. 디버거 연결도 번거롭다. **운영 환경 재현은 배포 단계에서 하고, 로컬은 개발 속도를 우선한다.**
- *MySQL을 로컬에 직접 설치* — 컨테이너 기동 시간이 없어 빠르지만, 팀원마다 버전·설정·포트가 달라지는 문제가 그대로 남는다. 이건 이 프로젝트가 피하려는 것 그 자체다.

**트레이드오프**

로컬 실행 방식과 운영 실행 방식이 다르다. "로컬은 되는데 배포하면 안 되는" 문제가 생길 여지가 있다. 배포 단계에서 이 간극을 어떻게 좁힐지 별도로 다룬다.

### 6-5. 테스트 DB 전략

**결정: 운영과 동일한 MySQL 8.4 컨테이너를 별도 포트(3307)로 띄운다.**

**결정 근거**

테스트는 **운영에서 실제로 동작할지**를 검증하는 것이 목적이다. DBMS가 다르면 그 검증이 성립하지 않는다.

**검토한 대안 1 — H2 인메모리 DB**

| 장점 | 단점 |
|---|---|
| 컨테이너가 필요 없어 세팅이 간단 | **MySQL과 SQL 문법·타입·제약 동작이 다르다** |
| 테스트가 매우 빠르다 | H2에서 통과한 쿼리가 운영에서 깨질 수 있다 |

MySQL 전용 함수, `ON DUPLICATE KEY UPDATE`, 인덱스 힌트 등을 쓰는 순간 H2에서는 검증이 불가능하다. **통과하는데 못 믿는 테스트**는 없는 것보다 위험하다는 판단으로 탈락.

**검토한 대안 2 — Testcontainers**

테스트 코드가 실행 시점에 직접 컨테이너를 띄우는 방식이다.

| 장점 | 단점 |
|---|---|
| 운영과 동일한 이미지 사용 | 컨테이너 기동에 회당 8~15초 |
| 테스트 간 격리가 확실하다 | 개념을 새로 익혀야 한다 |
| CI에서 추가 설정이 거의 없다 | Docker가 반드시 켜져 있어야 한다 |

기술적으로는 현재 선택보다 낫다. 다만 **지금 시점에 팀이 겪지 않은 문제를 미리 해결하는 도구**라고 판단해 보류했다. 아래 조건 중 하나라도 발생하면 도입한다.

- 테스트 순서에 따라 결과가 달라지는 일이 반복될 때
- CI 구축 시 테스트 DB 설정을 이중으로 관리하는 부담이 실제로 느껴질 때

> 이건 "안 쓴다"가 아니라 **"문제를 먼저 겪고 나서 도입한다"** 는 뜻이다. 전환하게 되면 그 과정(어떤 문제를 겪었고 → 무엇을 근거로 → 무엇을 바꿨고 → 결과가 어땠는지)을 남긴다.

**현재 방식이 안고 있는 한계 (알고 쓴다)**

1. **테스트 간 데이터 격리** — `@Transactional`로 롤백되지 않는 통합 테스트(`webEnvironment = RANDOM_PORT`)에서는 데이터가 남는다. 문제가 생기면 테이블 초기화 유틸을 만든다.
2. **CI 설정 이중화** — CI를 붙일 때 `docker-compose.yml`과 별개로 CI용 서비스 컨테이너를 정의해야 한다. 그 결과 **테스트 DB 포트가 세 곳에 존재한다.**

   | 파일 | 무엇 |
   |---|---|
   | `src/test/resources/application.yml` | `TEST_DB_PORT` 기본값 |
   | `docker-compose.yml` | `mysql-test` 포트 매핑 |
   | `.github/workflows/ci.yml` | service container 포트 매핑 |

   **포트를 바꾸려면 세 곳을 함께 고친다.** 하나만 고치면 CI에서만 실패하는데, 메시지가 아래 3번과 같은 `Communications link failure`라 컨테이너 기동 실패와 구분되지 않는다.
3. **컨테이너를 안 켜면 테스트가 실패한다** — 실패 메시지가 `Communications link failure`라 처음 보면 원인을 짐작하기 어렵다. [트러블슈팅](#9-트러블슈팅)에 적어두었다.

### 6-6. 스키마 관리: `ddl-auto`

**결정: 지금은 `ddl-auto`에 맡기고, 필요해지면 Flyway를 도입한다.**

| 환경 | 설정 | 이유 |
|---|---|---|
| local | `update` | 엔티티를 고치면 테이블이 따라온다. 초기 개발 속도가 가장 빠르다 |
| test | `create-drop` | 매번 새 스키마. 이전 테스트의 흔적이 남지 않는다 |

**검토한 대안 — Flyway**

`V1__create_member.sql` 같은 SQL 파일로 스키마 변경 이력을 관리하는 도구다. 누가 언제 무엇을 바꿨는지 추적되고 운영에서 안전하다. 다만 **테이블을 바꿀 때마다 SQL을 손으로 써야 해서**, 도메인이 하루에도 몇 번씩 바뀌는 초기 단계에는 속도를 크게 떨어뜨린다.

**도입 시점**

**실제 사용자 데이터가 쌓이기 시작하면 도입한다.** 그때부터는 스키마를 마음대로 갈아엎을 수 없기 때문이다.

**지금 방식의 위험 (반드시 알고 쓴다)**

`update`는 **컬럼 추가만 반영하고, 삭제와 타입 변경은 반영하지 않는다.**

- 필드 이름을 바꾸면 → 새 컬럼이 생기고 **옛 컬럼이 그대로 남는다**
- 필드를 지우면 → **컬럼이 남는다**

로컬 DB가 이상하다 싶으면 미련 없이 초기화한다.

```bash
docker compose down -v && docker compose up -d
```

> **운영 환경에서는 `update`를 절대 쓰지 않는다.** 배포 시에는 `validate` 또는 `none`으로 두고 스키마를 명시적으로 관리한다. 이 원칙을 배포 문서에 다시 적는다.

### 6-7. 코드 스타일

**결정: 우테코 IntelliJ 스타일 XML + `.editorconfig`**

두 도구의 역할이 다르다.

| 도구 | 역할 | 적용 방식 |
|---|---|---|
| 우테코 스타일 XML | 상세한 포맷 규칙 (줄바꿈, 중괄호 위치 등) | 각자 IntelliJ에 임포트 |
| `.editorconfig` | 기본 규칙 (들여쓰기, 줄바꿈 문자, 인코딩) | **클론하면 자동 적용** |

XML만 쓰면 임포트를 깜빡한 팀원의 코드가 전혀 다른 모양이 된다. `.editorconfig`를 함께 두면 최소한의 일관성은 자동으로 확보된다. 추가 비용은 파일 하나 커밋뿐이다.

**검토한 대안 — 커스텀 스타일 / 다른 공개 스타일**

Google Java Style, 네이버 스타일, Palantir Java Format도 후보였다. 팀 규모가 작고 빠른 검증이 목표라 컨벤션을 자체 설계할 여력이 없고, 검증된 공개 표준 중에서는 **팀 전원이 이미 써본 wooteco 스타일의 도입 비용이 사실상 없어** 가장 빠르게 적용된다.

**검토한 대안 — Checkstyle**

규칙 위반 시 **빌드를 실패시켜 강제할 수 있는** 도구다. CI에서 검사하면 스타일이 어긋난 PR을 머지 전에 막을 수 있다.

도입하지 않은 이유는 **강제력보다 합의 비용이 먼저 들기 때문**이다. 규칙 세트를 고르고 팀이 합의하는 데 시간이 필요하고, 초반에는 "로직은 멀쩡한데 스타일 때문에 PR이 막히는" 상황을 겪는다. 모든 코드가 리뷰를 거치는 만큼, **리뷰에서 짚는 것으로 당분간 충분하다고 봤다.**

**한계 — 알고 있는 것**

강제 수단이 없다. 팀원이 설정을 안 하면 막을 방법이 없다. 리뷰에서 스타일 지적이 반복되기 시작하면 그때가 Checkstyle 도입 시점이다.

### 6-8. Gradle

**결정 근거**

증분 빌드·캐시로 반복 빌드 시간을 줄이고, 테스트·정적 분석·배포 자동화를 태스크로 확장하기 쉽다. Wrapper로 버전을 고정할 수 있어 팀원이 Gradle을 따로 설치할 필요도 없다 ([4-3](#4-3-gradle-wrapper-버전-고정)).

**버전을 9.5.1로 고정한 이유**

후보로 둔 9.6.1 / 9.6.0 / 9.5.1 / 8.14.5는 모두 Spring Boot 4.1.0과 JDK 21을 지원한다. 핵심 문법(DSL)은 8.x와 9.x에 차이가 거의 없어 참고할 자료의 양에도 차이가 없다. 최신 정식 릴리스를 고집할 이유가 없다고 보고, 릴리스 후 시간이 지나 검증이 더 쌓인 9.5.1을 골랐다.

**검토한 대안 — Maven**

구조가 정형화돼 단순하고 XML 설정이 명시적이라 읽기 쉽다는 장점이 있으나, 자동화 확장성과 반복 빌드 효율을 고려해 Gradle을 선택했다.

현재 환경이 **해결하지 못한 것**을 명시해둔다. 모르는 게 아니라 **지금은 안 하기로 한 것**이다.

| # | 한계 | 언제 다룰 것인가 |
|---|---|---|
| 1 | 로컬(IDE 실행)과 운영(컨테이너 실행)의 실행 방식이 다르다 | 배포용 `Dockerfile`은 이미 저장소에 있다. 이를 배포에 어떻게 쓸지는 배포 문서에서 |
| 2 | 테스트 간 데이터 격리가 보장되지 않는다 | 문제가 반복되면 Testcontainers로 전환 ([6-5](#6-5-테스트-db-전략)) |
| 3 | 스키마 변경 이력이 남지 않는다 | 실사용자 데이터가 쌓이면 Flyway 도입 ([6-6](#6-6-스키마-관리-ddl-auto)) |
| 4 | 코드 스타일에 강제력이 없다 | 리뷰에서 스타일 지적이 반복되면 Checkstyle 도입 ([6-7](#6-7-코드-스타일)) |
| 5 | 빌드·테스트가 자동 검증되지 않는다 | CI 구축을 자율 요구사항으로 진행 |
| 6 | Spring Boot 4.1의 국내 레퍼런스가 부족하다 | 공식 문서를 1차 출처로 삼고, 해결한 문제를 [9번](#9-트러블슈팅)에 축적 |
| 7 | 배포용 Compose 파일과 `application-prod.yml`이 없다 | 배포 문서에서 `docker-compose.prod.yml`을 작성한다 (아래) |

### 배포 관련 메모

**이 절은 로컬 세팅과 무관하다.** 배포 문서를 쓸 때 출발점으로 삼기 위한 메모이므로, 지금 읽지 않아도 된다.

- **Compose 파일은 로컬용과 배포용을 분리한다.** 현재 `docker-compose.yml`은 로컬 전용(DB 두 개, 앱 없음)이고, 배포용 `docker-compose.prod.yml`(앱 + DB)은 배포 문서에서 작성한다. 자격증명 주입 방식, 이미지 빌드 위치, 호스트 포트 개방 여부, `ddl-auto` 값, 볼륨·백업이 아직 정해지지 않아 미리 쓰면 전부 추측값으로 굳는다.
- **EC2는 ARM64(Graviton)다.** 지정된 `t4g.medium` 이하 인스턴스는 ARM64라, Windows나 Intel Mac에서 빌드한 이미지가 **그대로는 실행되지 않는다.** `docker buildx --platform linux/arm64` / EC2에서 직접 빌드 / CI의 ARM 러너 중 하나를 골라야 한다.
- **운영 DB를 EC2 내 컨테이너로 두기로 했으므로**, 인스턴스를 재생성하면 데이터가 사라진다. 볼륨과 백업 방안이 필요하다.

## 8. 환경 재현 확인 결과

> 요구사항의 완료 기준 *"다른 팀원이 문서를 따라 환경을 재현하고 제품을 실행할 수 있다"* 를 검증하는 항목이다. **팀원이 각자** 직접 해보고 채운다.

### 검증 방법

문서 작성자는 옆에서 알려주지 않는다. 막히는 지점이 곧 문서의 결함이므로, **막힌 곳을 기록하고 문서를 고친 뒤 다음 사람이 다시 시도한다.**

### 확인 체크리스트

각자 아래를 순서대로 수행하고 결과를 적는다.

- [ ] JDK 21 설치 및 `java -version` 확인
- [ ] Docker Desktop 설치 및 `docker compose version` 확인
- [ ] 저장소 클론 및 IntelliJ Gradle 임포트 성공
- [ ] IntelliJ 설정 4가지 적용 (Gradle JVM / 인코딩 / 코드 스타일 / Actions on Save)
- [ ] `docker compose up -d` 후 두 컨테이너 모두 `(healthy)` 확인
- [ ] 애플리케이션 실행 및 로그 3줄 확인 (http://localhost:8080 은 컨트롤러가 없으면 404가 정상)
- [ ] `./gradlew test` 통과 확인
- [ ] `docker compose exec mysql mysql -uroot -proot devica` 로 DB 접속 확인
- [ ] AI 에이전트에 규칙이 주입되는지 확인 ([Step 7](#step-7-ai-에이전트-설정-선택)) — 쓰는 사람만

> DB 접속 항목은 **접속만 확인**한다. 엔티티가 없는 동안에는 `SHOW TABLES;`가 비어 있는 것이 정상이다. 첫 엔티티가 머지되면 이 항목을 "테이블 생성 확인"으로 바꾼다.

### 검증 기록

**팀원 3명이 각자의 환경에서 위 항목을 모두 통과했다.** 팀이 쓰는 Windows와 macOS 양쪽에서 재현되었고, 막힌 지점은 없었다.

|---|---|---|---|---|
| 라텔 | Windows 11 | 2026-08-06 | 없음 | — |
| 밤밤 | macOS | 2026-08-06 | 없음 | — |

## 9. 트러블슈팅

해결한 문제는 여기에 추가한다. 같은 문제로 두 번 시간을 쓰지 않기 위한 것이다.

### 앱 실행 시 `Communications link failure`

DB 컨테이너가 안 떠 있거나 아직 초기화 중이다.

```bash
docker compose ps
```

`(healthy)`가 아니면 기다린다. 컨테이너가 없으면 `docker compose up -d`.

### `./gradlew test` 실행 시 연결 오류

테스트 DB(3307)가 안 떠 있다. `docker compose up -d`는 **두 컨테이너를 모두** 띄운다. `docker compose ps`로 `mysql-test`가 있는지 확인한다.

### 포트 충돌 — `address already in use` / `port is already allocated`

Docker Compose 버전에 따라 메시지가 다르게 나온다. 아래 둘 다 같은 문제다.

```
Error response from daemon: ports are not available: exposing port TCP 0.0.0.0:3306
-> 127.0.0.1:0: listen tcp 0.0.0.0:3306: bind: address already in use
```
```
Error response from daemon: driver failed programming external connectivity:
Bind for 0.0.0.0:3306 failed: port is already allocated
```

로컬에 MySQL이 이미 설치되어 있거나 다른 컨테이너가 포트를 쓰고 있다.

```bash
# Mac
lsof -i :3306

# Windows PowerShell
Get-NetTCPConnection -LocalPort 3306
```

먼저 그 프로세스를 끌 수 있는지 본다. 로컬에 설치된 MySQL 서비스라면 끄는 쪽이 간단하다.

끌 수 없다면 **포트를 바꾼다. 이때 설정 파일은 고치지 않는다.**

1. `docker-compose.yml`에서 호스트 쪽 포트만 바꾼다. 컨테이너 안쪽(`:3306`)은 그대로 둔다.
   ```yaml
   ports:
     - "13306:3306"      # 개발 DB
   ```
2. 앱을 띄울 때 바뀐 포트를 환경변수로 알려준다.
   ```bash
   DB_PORT=13306 ./gradlew bootRun
   ```
   IntelliJ는 `Run > Edit Configurations > Environment variables`에 `DB_PORT=13306` 을 넣는다.

`application-local.yml`은 `${DB_PORT:3306}` 형태라 환경변수가 있으면 그 값을 쓴다([4-5](#4-5-srcmainresourcesapplication-localyml)). **이 파일을 직접 고치면 그 수정이 PR에 섞여 들어가 다른 팀원의 환경을 깨뜨린다.**

테스트 DB(`3307`)가 충돌할 때도 같은 방식이며, 환경변수 이름만 `TEST_DB_PORT`로 다르다.

```bash
TEST_DB_PORT=13307 ./gradlew test
```

> `docker-compose.yml`은 저장소에 공유되는 파일이라, 포트를 바꾼 채로 커밋하지 않도록 주의한다.

### 한글이 `???`로 저장된다

IntelliJ 인코딩이 UTF-8이 아니다. [Step 3 (2)](#2-파일-인코딩을-utf-8로-맞춘다)를 확인한다. 이미 깨진 채로 저장된 데이터는 복구되지 않으므로 DB를 초기화한다.

### 한 글자도 안 고쳤는데 파일 전체가 변경으로 표시된다

줄바꿈 문자(CRLF/LF) 문제다. `.gitattributes`가 있는지 확인하고, 있는데도 발생하면 줄바꿈을 다시 정규화한다.

```bash
git add --renormalize .
git status                        # 어떤 파일이 바뀌었는지 확인
git commit -m "chore: 줄바꿈 문자 LF 로 정규화"
```

> **`git reset --hard`로 해결하라는 자료가 많은데, 그대로 따라 하지 않는다.** 이 명령은 커밋하지 않은 작업을 **전부 삭제**하며 되돌릴 수 없다. 위의 `--renormalize`는 작업 내용을 건드리지 않고 줄바꿈만 고친다.

### 엔티티를 고쳤는데 테이블에 반영이 안 된다

`ddl-auto: update`는 컬럼 삭제와 타입 변경을 반영하지 않는다 ([6-6](#6-6-스키마-관리-ddl-auto)). 로컬 DB를 초기화한다.

```bash
docker compose down -v && docker compose up -d
```

### `Unsupported class file major version` 또는 Gradle 빌드 실패

Gradle JVM이 21이 아니다. [Step 3 (1)](#1-gradle-jvm을-21로-맞춘다)을 확인한다.

### 검색해서 나온 코드가 동작하지 않는다

Spring Boot 3.x 기준 자료일 가능성이 높다. 공식 문서에서 4.1 기준을 확인한다.

- https://docs.spring.io/spring-boot/
- 4.0 변경점: https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Release-Notes
- 4.1 변경점: https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.1-Release-Notes

# 로깅 컨벤션

애플리케이션 로그를 남길 때 지키는 기준이다. 로그 형식을 ECS 로 정한 이유는 [ADR 0033](adr/0033-로그-형식.md)에 있다.

## 0. 용어

| 용어         | 뜻                                                                                                                                     |
|------------|---------------------------------------------------------------------------------------------------------------------------------------|
| ECS        | Elastic Common Schema. 로그 JSON 의 필드 이름을 정해 둔 표준이다. `log.level`, `error.type` 처럼 점으로 묶인 이름을 쓰고, 출력할 때는 `{"log":{"level":...}}` 처럼 중첩된다 |
| 수집기(Alloy) | 서버의 로그 전용 디렉터리에서 파일을 읽어 로그 저장소로 보내는 에이전트                                                                                                 |
| 레이블        | 수집기가 로그 줄마다 붙이는 분류 값. 우리는 `env`(dev·prod), `app`(devica-app) 을 붙인다                                                                        |
| MDC        | SLF4J 기능. 스레드에 값을 넣어 두면 그 스레드가 남기는 모든 로그에 자동으로 붙는다                                                                                    |

## 1. 로그 형식

| 환경        | 형식                         |
|-----------|----------------------------|
| local     | 텍스트 (Spring Boot 기본 콘솔 형식) |
| dev, prod | ECS JSON                   |

로컬은 표준 출력으로 남긴다. dev·prod는 표준 출력과 로그 전용 파일에 ECS JSON으로 남기며, Alloy는 파일을 수집한다([ADR 0036](adr/0036-로그-수집-방식.md)). 파일 출력과 크기·보관량 제한 설정은 `docker-compose.server.yml`에 있다.

JSON 을 켜는 설정은 `src/main/resources/application-{dev,prod}.yml` 의 `logging.structured.format`, JSON 에서 뺄 필드는 공통 `application.yml` 의 `logging.structured.json` 항목에 있다.

- `service.*` 필드는 뺀다. 수집기가 붙이는 `app`·`env` 레이블과 값이 같다.
- 로거를 거치지 않은 출력은 JSON 줄 사이에 섞여 파싱을 깨뜨린다. 그래서 `System.out.println` 은 쓰지 않고, `show-sql` 은 텍스트로 출력하는 로컬에서만 켠다.
- 로컬 텍스트 로그에도 `trace.id` 와 요청 로그 필드가 로거 이름 앞에 붙는다. `application-local.yml` 의 `logging.pattern.correlation` 에서 넣는다.
- 로컬에서 JSON 을 보려면 `--logging.structured.format.console=ecs` 를 붙여 실행한다.

## 2. 출력 레벨

로거마다 다르다. 표의 레벨 이상인 로그만 남는다. 설정은 `src/main/resources/application.yml`(공통)과 `application-{local,dev,prod}.yml` 의 `logging.level` 항목에 있다.

| 로거                                                               | local                     | dev   | prod  |
|------------------------------------------------------------------|---------------------------|-------|-------|
| 기본값                                                              | INFO                      | INFO  | INFO  |
| `com.wrb.devica`                                                 | DEBUG                     | DEBUG | INFO  |
| `org.hibernate.SQL`                                              | INFO (`show-sql` 로 대신 출력) | INFO  | INFO  |
| `org.hibernate.orm.jdbc.bind`                                    | TRACE                     | INFO  | INFO  |
| `org.springframework.web.servlet.PageNotFound` (Spring 의 405 로그) | ERROR                     | ERROR | ERROR |

## 3. 레벨 사용 기준

| 레벨    | 언제                                                      | 예                              |
|-------|---------------------------------------------------------|--------------------------------|
| ERROR | 서버가 처리하지 못한 실패                                          | 처리하지 못한 예외                     |
| WARN  | 요청이 실패했지만 서버는 규칙대로 처리한 경우, 또는 서버 쪽 이상이 있었지만 처리를 이어 간 경우 | 비즈니스 예외, 요청 값 검증 실패, 외부 호출 재시도 |
| INFO  | 정상 흐름에서 남기는 기록                                          | 요청 처리 완료                       |
| DEBUG | 원인을 좁힐 때만 필요한 값. 로컬과 dev 에서만 출력된다                       | 계산 중간값, 분기를 가른 값               |

요청 처리 중 예외의 레벨은 응답 상태 코드를 따른다.

- 5xx 는 ERROR, 4xx 는 WARN 이다.
- 없는 경로(404)는 봇 스캔이 대부분이라 남기지 않고, 요청 로그의 상태 코드로 본다.

ERROR 와 WARN 모두 예외 종류를 `error.type` 필드로 남긴다.

- ERROR 는 예외 객체를 넘긴다. `error.type`, `error.message`, `error.stack_trace` 가 자동으로 채워진다.
- WARN 은 예외 객체를 넘기지 않고 `error.type` 을 직접 넣는다. 예외 메시지에 요청 값이 섞이기 때문이다. 비즈니스 예외는 대신 에러 코드를 `error.code` 로 넣는다.

```java
log.error("처리하지 못한 예외가 발생", exception);
log.atWarn().addKeyValue("error.type", exception.getClass().getName()).log("잘못된 요청");
```

## 4. 로그를 남기는 지점

| 지점    | 레벨              | 어디서                                                                                                |
|-------|-----------------|----------------------------------------------------------------------------------------------------|
| 요청·응답 | INFO            | `RequestLoggingFilter`. 요청마다 한 줄                                                                   |
| 예외    | ERROR·WARN      | `GlobalExceptionHandler`. 레벨은 3절의 상태 코드 규칙을 따른다 |
| 외부 호출 | INFO·WARN·ERROR | 아직 없다. 생기면 호출 대상·소요 시간·결과를 INFO 로 남긴다. 실패해서 요청이 5xx 로 끝나면 ERROR, 재시도나 다른 경로로 처리를 이어 가면 WARN 으로 남긴다 |

### trace.id

`trace.id` 는 한 요청에서 남긴 로그를 묶는 값이다. 요청 로그뿐 아니라 그 요청을 처리하는 동안 남긴 모든 로그(예외 포함)에 붙는다.

`RequestLoggingFilter` 가 요청마다 자동으로 붙이므로 직접 넣지 않는다. 다만 `@Async` 처럼 다른 스레드로 넘긴 작업의 로그에는 붙지 않는다.

같은 값을 응답 헤더 `X-Trace-Id` 로도 돌려준다. 사용자가 오류를 제보하면 이 값으로 해당 요청의 로그를 찾는다.

### 요청·응답 로그의 필드

| 필드 | 값 |
|---|---|
| `http.request.method` | `GET` 등 |
| `url.path` | 쿼리 문자열을 뺀 경로. 예: `/api/faqs/how-to-use` |
| `http.route` | 경로 변수 자리를 남긴 매핑 패턴. API 별로 묶어 볼 때 쓴다. 예: `/api/faqs/{slug}`. 없는 경로는 `/**`. ECS 에 해당 필드가 없어 OpenTelemetry 의 이름을 따랐다 |
| `http.response.status_code` | 응답 상태 코드 |
| `event.duration` | 처리 시간(나노초) |

헬스체크 경로 `/readyz`, `/livez` 는 요청 로그를 남기지 않는다. 운영 ALB 가 주기적으로 호출해 실제 요청 로그를 덮기 때문이다. Actuator 는 dev·prod 에서 관리 포트(8081)로 분리되어 이 필터를 거치지 않는다. Prometheus 의 메트릭 수집 요청도 요청 로그를 남기지 않는다.

새로 필드를 붙일 때는 SLF4J 의 `addKeyValue` 를 쓰고, 이름은 [ECS 필드 목록](https://www.elastic.co/guide/en/ecs/current/ecs-field-reference.html)에서 먼저 찾는다.

## 5. 민감정보

지금은 회원·결제가 없어 개인정보를 받지 않는다. 그래도 아래 값은 로그에 남기지 않는다.

- 요청 헤더 전체. `Authorization`, `Cookie` 가 섞일 수 있다
- 요청 본문과 쿼리 문자열. 요청 로그에는 경로만 남긴다
- DB 접속 정보 등 환경 변수로 받는 비밀값
- 클라이언트 IP. 차단이나 조사에 필요하면 운영 ALB 의 접근 로그로 본다

회원가입·로그인처럼 개인정보를 받는 기능이 생기면 이 목록에 항목을 더하고 마스킹 방식을 정한다.

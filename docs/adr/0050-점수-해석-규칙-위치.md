# 50. 사용 목적별 점수 해석 규칙 중 점수 구간과 Mac CPU 상한을 정의서에 둔다

- 상태: Accepted
- 날짜: 2026-11-02

## 상황 (조건)

- [0046](0046-추천-콘텐츠-위치.md)에서 사용 목적별 점수 해석 규칙은 변경 주기가 길어 파일로 옮겨 얻는 것이 적다고 보고, 백엔드 개발 전용 클래스 `BackendDevelopmentRecommender` 에 두었다.
- UT에서 사용 목적을 하나 더하는 일(#274 의 모바일 개발 등)이 거론되었다. 
- 지금 구조로는 사용 목적을 추가하기 위해선 정의서 파일과 함께 Java 클래스도 추가해야한다.
- 점수 해석 규칙 중 사용 목적에 따라 달라질 것은 점수를 사양 값으로 바꾸는 점수 구간과 Mac CPU 상한이다. 두 권장안(Mac·Windows) 구성, 지금 쓰는 CPU 보다 한 단계 올리기, Mac CPU 별 메모리 맞추기, 결과 문장은 노트북의 판매 구성에서 나와 사용 목적과 관계없다.

## 고려한 대안

**1. 점수 구간을 사용 목적별 클래스에 두고 노트북 공통 부분은 하나로 모은다**

- 구간 값을 Java 타입으로 적어 잘못된 값을 컴파일할 때 잡는다.
- 사용 목적 하나를 더할 때 정의서 파일과 클래스를 함께 만들어야 하고, 상수만 다른 클래스가 늘어난다.

**2. 보정과 결과 문장까지 점수 해석 규칙 전체를 정의서에 둔다**

- 사용 목적마다 보정과 문장도 다르게 정할 수 있다.
- 보정은 조건과 계산이라 YAML 로 표현하려면 해석 코드를 새로 만들어야 한다. 지금은 사용 목적마다 다른 보정이 없다.

## 선택: 점수 구간과 Mac CPU 상한은 정의서의 `interpretation`, 보정과 결과 문장은 노트북 공통 코드

정의서에 `interpretation` 블록을 두고 항목별 점수 구간과 `macCpuLimit` 을 적는다. 점수에 맞는 구간 값을 고르는 코드(`ScoreRange`)와 노트북 보정·결과 문장(`LaptopRecommender`)은 사용 목적과 관계없이 하나만 둔다.

**근거**

1. 사용 목적마다 다른 값만 정의서로 옮기면, 사용 목적을 더할 때 정의서 파일 하나만 만들면 된다.
2. 보정과 결과 문장은 노트북의 판매 구성에서 나오는 것이라 사용 목적이 늘어도 같다.

## 감수하는 것

1. **구간 값 오류를 컴파일이 아니라 서버 시작에서 잡는다**

   정의서에 그 OS 에 없는 CPU 등급이나 판매하지 않는 메모리 용량을 적어도 IDE 가 알려주지 않는다.

   대응: 서버가 시작할 때 구간 모양과 값을 검사해 틀리면 서버가 뜨지 않는다. CPU 는 그 OS 의 등급, 메모리·저장 공간은 `LaptopSpec` 이 가질 수 있는 값, Mac CPU 상한은 Mac 메모리 구성이 있는 등급만 허용한다.

2. **개선 루프가 고치는 파일 안에 루프가 고치면 안 되는 값이 생긴다**

   제품 추천 개선 루프([0049](0049-제품-추천-개선-루프-실행-방식.md))는 정의서의 `rules` 를 고친다. 점수 구간이 같은 파일에 있어 개선기가 지시를 넘어 구간을 고칠 수 있다. 점수 구간은 규칙 점수의 뜻을 정하는 기준이라, 고치면 모든 규칙의 효과가 함께 바뀐다.

   대응: 개선기와 분석기의 범위에서 `interpretation` 을 제외하고, 개선기는 고친 뒤 `interpretation` 이 `develop` 과 같은지 확인한다. 개선 PR 은 팀원이 리뷰한다.

3. **구간을 바꾼 직후에는 그 사용 목적의 지표가 줄어든다**

   구간이 바뀌면 어느 답 조합의 결과든 달라질 수 있어, 바뀌기 전 결과를 본 세션을 답만으로 가를 수 없다. 그 세션을 지금 결과에 대한 반응으로 세면 이미 고친 문제로 개선 지시가 나갈 수 있다.

   대응: 지표 수집기는 `interpretation` 이 배포를 기다리는 동안 그 사용 목적의 세션을 세지 않고, 배포된 뒤에는 배포 전에 시작한 세션을 버린다. 구간은 드물게 바뀌어 줄어드는 기간이 짧다.

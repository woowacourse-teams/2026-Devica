# 4. DB로 MySQL 8.4를 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 현재 확정된 데이터는 제품 리스트의 기기 정보 정도이고, 맞춤 추천 질문·옵션·조정값을 DB로 관리하는 방안을 검토 중이다. 리뷰 기능도 확장 계획에 있다.
- 특히 맞춤 추천 질문은 검증 과정에서 형태가 자주 바뀔 것으로 예상된다.
- 초기에는 컨테이너로 직접 DB를 띄워 운영하고, 서비스가 성장하면 AWS RDS로 이전할 계획이다.

## 고려한 대안

**1. PostgreSQL**

- JSONB 타입을 지원해, 정형 데이터와 형태가 유동적인 데이터를 하나의 DB에서 다룰 수 있다. 스키마 변경이 잦은 데이터도 별도 저장소 없이 수용된다.
- 고급 SQL 문법과 확장 기능을 통해 복잡한 데이터 처리에 강점이 있다.
- 팀원 대부분이 사용 경험이 없어 학습이 필요하다.

> MongoDB 등 문서형 DB는 맞춤 추천 질문에 적합할 가능성이 있으나, 기기 추천 알고리즘이 확정되지 않아 판단을 보류했다. 현재 확정된 데이터(기기 정보)가 정형 데이터이고, 특별한 이유가 없는 한 RDBMS를 기본 선택지로 두는 것이 일반적이므로 RDBMS를 먼저 적용한다.

## 선택: MySQL 8.4 (LTS)

**근거**

1. PostgreSQL의 JSONB는 스키마가 유동적인 맞춤 추천 질문에 유효한 선택지가 될 수 있다. 그러나 기기 추천 알고리즘이 확정되지 않아, JSONB가 적합한 해법인지조차 판단할 수 없다. 확정되지 않은 요구를 위해 팀에 경험이 없는 DB를 택하는 것은 1개월이라는 기간에서 위험이 크다고 판단했다.
2. MySQL 8.x도 JSON 타입과 인덱싱을 지원하므로, 유동적인 데이터를 다뤄야 할 때 최소한의 대응은 가능하다. JSONB만큼은 아니지만 요구가 구체화되기 전까지는 충분하다.
3. 팀원 대부분이 MySQL을 사용해본 경험이 있어, 확정된 기기 정보 관리와 핵심 기능 구현을 시행착오 없이 진행할 수 있다.

**버전: 8.4 (LTS)**

LTS 중에서 고르되(8.0은 2026년 4월 EOL), 9.7이 추가한 JSON Duality Views의 DML 지원, Hypergraph 옵티마이저, 고급 복제·관측 기능은 이번 프로젝트에서 활용할 가능성이 낮다.

9.7은 2026년 4월 릴리스로 운영 사례가 아직 적은 반면, 8.4는 먼저 안정화되어 사례가 축적되었고 향후 AWS RDS로 이전할 때도 표준적인 선택지다. 8.4 LTS를 사용한다.

## 감수하는 것

1. **기기 추천 알고리즘이 MySQL의 정형 스키마에 맞지 않을 가능성**

   추천 질문·옵션·조정값의 구조는 알고리즘이 확정되기 전까지 알 수 없다. 확정된 형태를 MySQL의 스키마로 표현하기 어렵다면, 그 시점에 PostgreSQL 이전이나 별도 저장소 도입을 다시 검토해야 한다.

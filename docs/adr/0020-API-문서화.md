# 20. API 문서화에 springdoc-openapi를 사용한다

- 상태: Accepted
- 날짜: 2026-08-31

## 상황 (조건)

- 개발이 끝난 API를 확인하려면 Controller의 매핑 메서드를 열어 URL과 요청 DTO를 코드에서 직접 읽어야 한다. 팀원 간 공유와 Postman 테스트가 모두 이 경로를 거친다.
- 프론트엔드를 React 기반으로 다시 구현하면서 그 구현을 AI Agent에 맡길 계획이다. 화면을 만들 때마다 백엔드 코드베이스를 탐색해 API를 파악하는 것은 비효율적이다.
- MVP 검증 기간이라 문서화 자체에 쓸 수 있는 시간이 적다.

## 고려한 대안

**1. Spring REST Docs**

- 테스트 코드를 근거로 문서를 만들기 때문에, 문서에 적힌 API가 실제로 동작함이 보장된다.
- 프로덕션 코드에 문서용 코드가 들어가지 않는다.
- 초기 설정이 번거롭고, 테스트 코드에 문서 생성용 코드가 섞인다.
- UI에서 요청을 보내볼 수 없다.

**2. restdocs-api-spec**

- REST Docs로 검증한 내용을 OpenAPI 스펙으로 만들어 Swagger UI로 띄운다. 정확성과 UI 테스트를 모두 얻는다.
- 세 대안 중 설정이 가장 복잡하다.

## 선택: springdoc-openapi

**근거**

1. 의존성 한 줄로 시작할 수 있다. 문서화에 쓸 시간이 적은 지금은 도입 비용이 판단 기준이다.
2. 코드에서 스펙을 뽑으므로, 갱신하는 별도 작업 없이 API가 추가되면 명세에 반영된다. FE 구현 Agent에게 넘길 단일 출처가 이 스펙이 된다.
3. UI에서 바로 요청을 보낼 수 있어, DTO를 코드에서 확인해 Postman에 옮겨 적던 과정이 사라진다.

**버전: 3.1.0**

Spring Boot 4.1.0을 부모로 빌드되어 우리 버전([0002](0002-프레임워크.md))과 맞는다. 2.x는 Boot 3과 Jackson 2 기반이라 쓸 수 없다.

## 감수하는 것

1. **프로덕션 코드에 문서용 어노테이션이 섞인다**

   설명과 예시를 채우려면 Controller와 DTO에 `@Operation`, `@Schema`가 붙는다.

   대응: 코드를 읽기 어려워지는 시점을 REST Docs 계열로 옮길 근거로 삼는다.

2. **문서가 실제 동작과 어긋날 수 있다**

   손으로 적은 설명과 응답 예시는 코드가 바뀌어도 그대로 남고, 이를 검증하는 장치가 없다.

3. **운영 환경 노출을 설정으로 막아야 한다**

   문서와 요청 UI가 애플리케이션에 실려 배포되므로, 끄지 않으면 운영 서버에서 API 구조가 외부에 열린다. `prod` 프로파일에서 비활성화한다. 개발 서버는 팀원 확인용이므로 켜 둔다.

# 40. 성능 테스트는 API 하나씩, 개발 서버에서 잰다

- 상태: Accepted
- 날짜: 2026-10-14

## 상황 (조건)

- 개발 서버와 운영 서버는 EC2·RDS 사양과 실행 구성이 같다([0018](0018-환경-분리.md), [0038](0038-DB-RDS-이전.md)).
- 운영 서버만 ALB를 거친다.
- 테스트 데이터는 적재 SQL로 만든 합성 데이터를 쓴다(`performance/data/`).

## 고려한 대안

**1. 여러 API를 한꺼번에 거는 혼합 부하**

- 같은 서버·DB·커넥션 풀을 나눠 쓰는 실제 상황에 가깝다.
- 여러 API가 같은 서버·DB·커넥션 풀을 나눠 쓰므로, 기준을 넘었을 때 어느 API가 병목을 만들었는지 가려내기 어렵다.

## 선택: API 하나씩, 개발 서버에서 잰다

테스트를 통과했다는 건, 개발 서버에서 이 API 하나만 합성 데이터로 받았을 때 성능 기준을 만족했다는 뜻이다. 운영에서 다른 요청과 함께 받아도 만족한다는 뜻은 아니다.

**근거**

1. API 하나만 부하를 걸면 기준을 넘었을 때 병목의 원인을 분석하기 쉽다.
2. 개발 서버는 운영과 사양과 구성이 같다. ALB는 운영에만 있지만 서버 처리 시간으로 판정하므로([0039](0039-성능-테스트-판정-기준.md)) 영향이 없다.

## 감수하는 것

1. **다른 API와 자원을 나눠 쓰는 상황을 보지 못한다**

   실제로는 상품 목록과 추천·상세·게시판 요청이 같은 서버·DB·커넥션 풀을 쓴다. 단독으로 통과해도 함께 받으면 버티지 못할 수 있다.

   대응: API별 테스트가 갖춰지면 혼합 부하를 따로 결정한다.

2. **합성 데이터의 분포는 실제와 다르다**

   사양과 가격이 고르게 퍼진 합성 값이라, 실제 데이터에서는 조건별로 걸리는 행 수와 인덱스 효율이 달라질 수 있다.

   대응: 측정 전에 데이터를 확인해, 개선 전후가 같은 데이터에서 잰 값임은 보장한다.

3. **측정하는 동안 개발 서버를 독점한다**

   측정 중에는 develop 머지를 보류하고 개발 서버를 쓰지 않아야 한다.

   대응: 측정 전에 시작·종료 시각을 팀에 공지한다.

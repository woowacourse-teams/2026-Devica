# 29. 프론트엔드 하네스로 팀의 최소 작업 기준을 맞춘다

- 상태: Accepted
- 날짜: 2026-09-23

> 하네스: 코딩 에이전트가 따를 팀 기준과, 그 기준을 거친 코드인지 확인하는 장치를 함께 이르는 말이다.

## 상황 (조건)

- 팀원 전원이 프론트엔드에 익숙하지 않아, 사람이 코드를 보고 문제를 찾아내기 어렵다. 그래서 프론트엔드 코드는 코딩 에이전트에 크게 의존해 작성할 계획이다.
- 팀원마다 쓰는 에이전트가 다르다(Claude Code, Codex). 에이전트를 위한 별도 API 비용은 쓰지 않는다.
- 에이전트마다 결과물과 리뷰 지적이 다르다.
- 리뷰어가 AI 로 리뷰한 결과를 PR 코멘트로 옮기고, 작성자가 그 코멘트를 다시 에이전트에 전달해 고친다. 지적 하나에 사람이 두 번 옮겨야 하고, 그 사이에 지적이 빠질 수 있다.
- PR 을 올리기 전에 AI 리뷰를 거치라고 지침을 줘도, 에이전트가 빠뜨리거나 사람이 잊으면 리뷰 없이 PR 이 올라온다.
- 처음에는 마크다운 규칙 문서만으로 하네스를 만들려 했다([#8](https://github.com/woowacourse-teams/2026-Devica/pull/8)). 일정에 밀려 머지되지 못했고, 그사이 작업이 진행되면서 문서 내용이 코드와 금방 어긋났다.
- 기획이 아직 자주 바뀐다.

## 고려한 대안

**1. 마크다운 규칙 문서만으로 에이전트를 이끈다 ([#8](https://github.com/woowacourse-teams/2026-Devica/pull/8) 방식)**

- 도구나 비용 없이 바로 시작할 수 있다.
- Claude Code 와 Codex 가 같은 문서를 읽을 수 있다.
- 에이전트가 문서를 따랐는지 확인할 방법이 없다.
- 기획과 코드가 바뀌면 문서가 금방 어긋나고, 어긋나도 드러나지 않는다.

**2. 에이전트 프레임워크로 팀 공용 에이전트를 만든다 (VoltAgent 등)**

- 리뷰·수정 순서를 코드로 정해 두면 누가 써도 같은 순서로 진행된다.
- 여러 회사의 모델을 섞어 쓸 수 있다.
- 개인 구독 계정으로는 모델을 부를 수 없어, API 사용료를 따로 내야 한다.

**3. 내 컴퓨터에서 돌리는 무료 모델을 쓴다 (Ollama 등)**

- 사용료가 들지 않는다.
- 개인 컴퓨터에서 돌아가는 작은 모델은 리뷰 품질이 낮다.
- 리뷰가 부실할 때, 모델이 약해서인지 리뷰 기준을 잘못 써서인지 알기 어렵다.

**4. PR 이 올라오면 CI 에서 AI 가 리뷰한다**

- 사람이 따로 실행하지 않아도 모든 PR 이 리뷰된다.
- CI 는 공용 서버라, API 키나 팀원 한 명의 계정 정보를 저장소에 넣어야 한다.
- AI 는 같은 코드에도 매번 다르게 답해, 통과·차단의 기준으로 쓰면 결과가 흔들린다.

**5. 커밋이나 push 할 때 Git 훅이 AI 리뷰를 실행한다**

- 각자의 컴퓨터에서 돌아 개인 구독 계정을 그대로 쓸 수 있다.
- 훅은 리뷰 결과를 터미널에 출력만 해서, 사람이 그 내용을 다시 에이전트에 붙여 넣어야 한다.
- 커밋할 때 돌리면 너무 자주 돌고, push 할 때 돌리면 작업을 다 끝낸 뒤라 고치기 늦다.

## 선택: 각자의 에이전트가 팀 기준으로 리뷰하고 결과를 리뷰 기록으로 남기며, Git 훅과 CI 는 그 기록이 올라가는 코드에 대한 것인지 확인한다

**근거**

1. AI 는 각자 로그인한 에이전트 안에서만 돌기 때문에, 개인 구독 계정만으로 되고 API 사용료가 들지 않는다.
2. 리뷰 기준을 두 에이전트가 함께 읽는 문서 하나로 두어, 누가 어느 에이전트를 써도 같은 기준이 적용된다.
3. 리뷰한 에이전트가 같은 대화에서 바로 고치므로, 사람이 지적을 PR 코멘트나 에이전트로 옮길 필요가 없다.
4. 사람이 코드를 보고 찾기 어려운 문제를 에이전트가 리뷰 기준으로 먼저 걸러 내고, 리뷰를 거치지 않은 코드는 PR 전에 막힌다.
5. 리뷰 기준에는 여러 번 반복된 지적만 적고 기획 내용은 넣지 않아, 기획이 바뀌어도 기준을 고칠 일이 적다. 기계적으로 판정할 수 있는 기준(코드 형식, import 순서 등)은 린트 규칙으로 두어, 코드와 어긋나면 커밋과 CI 에서 바로 드러난다.

## 감수하는 것

1. **리뷰의 질까지 보장하지는 못한다**

   Git 훅과 CI 는 리뷰 기록이 지금 코드에 대한 것인지만 확인한다. 리뷰가 꼼꼼했는지는 알 수 없다. AI 는 같은 코드도 실행마다 다르게 리뷰해 지적을 놓칠 수 있고, 리뷰 기준에 없는 부분(화면 흐름 등)은 보지 않는다. 실제로 [#110](https://github.com/woowacourse-teams/2026-Devica/pull/110) 에서는 기준에 적힌 문제가 있는 코드를 세 번 리뷰하는 동안, 앞의 두 번은 그 문제를 지적하지 못했다.

   대응: 사람의 PR 리뷰는 그대로 한다. 자주 나오는 지적은 리뷰 기준이나 린트 규칙으로 옮긴다.

2. **코드가 바뀌면 리뷰를 다시 해야 한다**

   리뷰한 뒤에 코드를 고치면 기록이 지금 코드와 맞지 않아 push 가 막힌다. 다른 PR 위에 쌓은 PR 은 아래 PR 이 바뀔 때도 다시 리뷰해야 한다.

   대응: 리뷰를 거치지 않은 코드가 올라가지 않게 하려는 의도된 동작이다. PR 은 깊게 쌓지 않고, 아래 PR 부터 머지한다.

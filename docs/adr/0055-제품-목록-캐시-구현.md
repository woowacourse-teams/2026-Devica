# 55. 제품 목록 캐시로 Caffeine 로컬 캐시를 사용한다

- 상태: Accepted
- 날짜: 2026-11-08

## 상황 (조건)

- [0054](0054-제품-맞춤-목록-결과-캐시.md)에서 제품 목록의 조회 결과를 캐시하고, 최저가가 바뀌면 모두 비우기로 했다.
- 앱 서버는 환경마다 한 대이고, 배포하면 다시 시작한다. 마이그레이션도 배포 때 실행된다.
- 앱의 최대 힙은 약 460MiB다. 따로 설정하지 않아 JVM 기본값(서버 메모리의 1/4)이다. 2026-11-07~08 용량 테스트 중 힙 사용은 최대 106MiB였다.
- 캐시 효과를 보려고 적중률을 지표로 수집하기로 했다(#397). 앱 지표는 Actuator와 Prometheus 형식으로 Grafana Cloud에 보내고 있다.
- 앱은 목록을 한 페이지 10대씩 요청하고, API는 한 페이지에 100대까지 허용한다.
- 목록 요청의 검색어는 길이 제한이 없는 자유 입력이다.
- 제품 추천이 내는 맞춤 목록 요청은 성능 테스트 시나리오 기준 1,782개다.
- 오퍼를 바꾸는 메서드는 트랜잭션 안에서 실행되고, 호출하는 가격 수집 작업은 트랜잭션 밖에 있다. `ProductService`는 클래스 전체가 읽기 전용 트랜잭션이다.
- 가격 수집은 오퍼마다 2.1초 간격으로 가격 갱신을 부르고, 가격이 그대로인 오퍼에도 부른다.

## 고려한 대안

**1. Redis**

- 여러 앱 서버가 캐시를 함께 쓰고, 한 서버에서 비우면 모든 서버에 반영된다.
- 앱을 다시 시작해도 캐시가 남는다.
- Redis 서버를 따로 운영해야 한다.
- 캐시에서 꺼낼 때도 네트워크를 거치고 직렬화한다.

**2. Spring 기본 캐시(`ConcurrentMapCacheManager`)**

- 의존성을 더하지 않는다.
- 크기 상한과 만료가 없어, 서로 다른 요청이 오는 만큼 메모리를 계속 쓴다.
- 적중률 통계를 남기지 않는다.

**3. HTTP 캐시(`Cache-Control`로 브라우저·CDN에 저장)**

- 요청이 서버까지 오지 않는다.
- 저장된 응답을 서버가 지울 수 없어, 오퍼를 숨겨도 `max-age`가 끝날 때까지 보인다.
- 요청이 서버에 오지 않아 적중률을 서버 지표로 볼 수 없다.

## 선택: Spring Cache와 Caffeine 로컬 캐시

`@Cacheable`·`@CacheEvict`로 캐시를 쓰고, 저장소는 Caffeine으로 한다.

| 설정 | 값 |
|---|---|
| 크기 상한 | 담긴 노트북 수의 합 20,000 (`maximumWeight`, 빈 결과는 1로 센다) |
| 만료 | 넣은 지 10분 (`expireAfterWrite`) |
| 통계 | 적중·미스 기록 (`recordStats`, `cache.gets` 지표) |
| 캐시하지 않는 요청 | 검색어가 있는 요청 |
| 동시 미스 | 같은 키는 한 번만 조회 (`sync = true`) |
| 비우는 조건 | 최저가가 바뀐 갱신·숨김·복구 |
| 실행 순서 | 트랜잭션보다 바깥 (`@EnableCaching(order = HIGHEST_PRECEDENCE)`) |

**근거**

1. 앱 서버가 환경마다 한 대라 여러 서버가 캐시를 함께 쓸 일이 없다. Redis는 그 장점 없이 운영할 서버와 네트워크 왕복만 늘린다.
2. 로컬 캐시는 배포 재시작으로 비워져, 마이그레이션이 바꾼 데이터가 캐시에 남지 않는다. Redis라면 배포 때 캐시를 비우는 절차가 따로 필요하다.
3. Caffeine은 기본 캐시에 없는 크기 상한, 만료, 적중률 통계를 제공하고, Actuator가 통계를 지표로 내보낸다.
4. 캐시 메모리는 대부분 결과에 담긴 노트북 항목이라, 항목 개수 대신 노트북 수로 상한을 잡았다. 20,000은 제품 추천 요청 1,782개 × 10대에 여유를 둔 값이다.
5. 한 페이지 100대 요청이 몰려도 노트북 2만 대분(항목당 1\~1.5KB로 추정해 20\~30MB)을 넘지 않는다. 측정 중 힙 사용 최대 106MiB에 더해도 최대 힙 460MiB 안에 든다.
6. 검색어는 길이 제한이 없어, 결과 없는 긴 검색어를 바꿔 가며 보내면 무게 1짜리 항목의 키만으로 메모리가 커진다. 제품 추천 요청에는 검색어가 없으므로 검색어 요청을 캐시하지 않아도 효과는 그대로다.
7. 만료는 비우기와 겹친 조회가 옛 결과를 다시 넣었을 때([0054](0054-제품-맞춤-목록-결과-캐시.md) 감수 2) 틀린 결과가 남는 시간의 상한이다.
8. 캐시가 빈 직후 같은 조건의 요청이 몰려도 `sync`로 한 번만 조회해, 0043이 걱정한 몰림을 키 단위로 막는다.
9. 가격 수집은 가격이 그대로인 오퍼에도 갱신을 불러, 호출마다 비우면 수집 내내 2초마다 캐시가 비워진다. 최저가가 바뀐 경우에만 비운다.
10. 캐시가 트랜잭션 바깥에 있어, 적중한 요청은 트랜잭션을 열지 않고 비우기는 커밋 뒤에 일어난다. 같은 요청을 세 번 보냈을 때 DB 커넥션을 빌린 횟수는 미스 1회, 적중 0회였다.

## 감수하는 것

1. **캐시가 앱 서버마다 따로 있다**

   앱 서버를 여러 대로 늘리면 서버마다 따로 캐시하고, 가격 수집을 돈 서버의 캐시만 비워져 다른 서버는 만료 때까지 옛 결과를 보여준다.

   대응: 앱 서버를 늘릴 때 Redis나 서버 간 무효화를 다시 검토한다. Redis로 가면 배포 때 캐시를 비우는 절차도 함께 둔다.

2. **크기 상한과 만료 시간은 측정이 아니라 판단으로 정한 값이다**

   노트북 항목 하나의 크기(1~1.5KB)는 재지 않은 추정이다. 무게 합계는 지표로 나오지 않아, 상한을 얼마나 쓰는지는 밀려난 항목 수(`cache.evictions`)로만 간접적으로 본다. 만료를 길게 잡으면 적중률은 오르지만 틀린 결과가 남을 수 있는 시간도 길어진다.

   대응: 적용 후 용량 측정에서 적중률, 밀려난 항목 수, 힙 사용을 함께 본다. 항목 크기는 `jcmd <pid> GC.class_histogram`으로 잰다.

3. **최대 힙은 서버 메모리에 따라 바뀐다**

   최대 힙을 설정하지 않아, 서버 인스턴스를 바꾸면 근거 5의 계산도 달라진다.

   대응: 인스턴스를 줄일 때 최대 힙과 캐시 상한을 함께 확인한다.

# 55. 제품 목록 캐시로 Caffeine 로컬 캐시를 사용한다

- 상태: Accepted
- 날짜: 2026-11-08

## 상황 (조건)

- [0054](0054-제품-맞춤-목록-결과-캐시.md)에서 제품 목록의 조회 결과를 캐싱하고, 최저가가 바뀌면 모두 비우기로 했다.
- 앱 서버는 환경마다 한 대이고, 배포하면 다시 시작한다. 마이그레이션도 배포 때 실행된다.
- 앱의 최대 힙은 약 460MiB로, 따로 설정하지 않은 JVM 기본값이다. 용량 테스트 중 힙 사용은 최대 약 100MiB였다.
- 앱은 목록을 한 페이지 10대씩 요청하고, API는 한 페이지에 100대까지 허용한다.
- 목록 요청의 검색어는 길이 제한이 없는 자유 입력이다.
- 제품 추천이 내는 맞춤 목록 요청은 성능 테스트 시나리오 기준 1,782개다.
- 오퍼를 바꾸는 메서드는 트랜잭션 안에서 실행되고, 호출하는 가격 수집 작업은 트랜잭션 밖에 있다. `ProductService`는 클래스 전체가 읽기 전용 트랜잭션이다.
- 가격 수집은 가격이 그대로인 오퍼에도 가격 갱신을 부른다.

## 고려한 대안

**1. Redis**

- 여러 앱 서버가 캐시를 함께 쓰고, 한 서버에서 비우면 모든 서버에 반영된다.
- 앱을 다시 시작해도 캐시가 남는다.
- Redis 서버를 따로 운영해야 한다.
- 캐시에서 꺼낼 때도 네트워크 왕복(보통 1ms 안팎)과 직렬화·역직렬화를 거친다.

**2. Spring 기본 캐시(`ConcurrentMapCacheManager`)**

- 의존성을 더하지 않는다.
- 크기 상한과 만료가 없어, 서로 다른 요청이 오는 만큼 메모리를 계속 쓴다.
- 적중률 통계를 남기지 않는다.

## 선택: Spring Cache와 Caffeine 로컬 캐시

`@Cacheable`·`@CacheEvict`로 캐시를 쓰고, 저장소는 Caffeine으로 한다.

| 설정         | 값                                                                                                  |
|------------|----------------------------------------------------------------------------------------------------|
| 크기 상한      | 캐시에 든 페이지들의 노트북 수 합계가 20,000을 넘지 않게 한다 (`maximumWeight`). 노트북이 없는 페이지도 1대로 쳐서, 빈 결과가 끝없이 쌓이지 않게 한다 |
| 캐시하지 않는 요청 | 검색어가 있는 요청. 크기 상한이 키의 크기는 세지 않아서다                                                                  |
| 동시 미스      | 같은 키는 한 번만 조회한다 (`sync = true`)                                                                    |
| 실행 순서      | 트랜잭션보다 먼저 (`@EnableCaching(order = HIGHEST_PRECEDENCE)`). 적중한 요청은 트랜잭션을 열지 않기 위함이다                 |
| 비우는 조건     | 최저가가 바뀐 갱신·숨김·복구. 실행 순서 덕분에 트랜잭션이 끝난 뒤 비운다                                                         |
| 만료         | 넣은 지 10분 (`expireAfterWrite`). 비우기와 겹친 조회가 다시 넣은 옛 결과가 남는 시간의 상한이다                                 |
| 통계         | 적중·미스 기록 (`recordStats`, `cache.gets` 지표)                                                          |

**근거**

1. 앱 서버가 한 대라 분산 캐시가 필요 없고, Redis는 운영할 서버만 늘린다.
2. 로컬 캐시는 배포 재시작 때 비워져, 마이그레이션이 바꾼 데이터가 남지 않는다.
3. Caffeine은 기본 캐시에 없는 크기 상한과 만료가 있다.
4. 캐시 메모리는 대부분 노트북 항목이 차지해, 상한을 노트북 수로 잡았다. 20,000은 제품 추천 요청 1,782개 × 10대에 여유를 둔 값이다.
5. 한 페이지 100대 요청이 몰려도 약 20\~30MB(추정)라, 평소 힙 사용 약 100MiB에 더해도 최대 힙 460MiB에 든다.
6. 검색어는 길이 제한이 없어 키만으로 메모리가 커질 수 있다. 제품 추천 요청에는 검색어가 없어 빼도 효과는 같다.
7. 캐시가 빈 직후 같은 요청이 몰려도 DB에는 한 번만 간다.
8. 목록 조회에 읽기 전용 트랜잭션이 걸려 있어 캐시를 그 바깥에 두었다. 적중한 요청은 DB 커넥션을 빌리지 않는다(같은 요청 세 번: 미스 1회, 적중 0회).
9. 가격 수집은 가격이 그대로여도 갱신을 불러, 매번 비우면 수집 내내 캐시가 비워진다. 그래서 최저가가 바뀐 경우에만 비운다.
10. 비우기와 겹친 조회가 옛 결과를 다시 넣을 수 있어([0054](0054-제품-맞춤-목록-결과-캐시.md) 감수 2), 만료로 그 시간을 묶는다.

## 감수하는 것

1. **캐시가 앱 서버마다 따로 있다**

   서버를 스케일 아웃하면 가격 수집을 수행한 서버의 캐시만 비워져, 다른 서버는 만료 때까지 옛 결과를 보여준다.

   대응: 서버를 늘릴 때 Redis나 서버 간 무효화를 다시 검토한다.

2. **크기 상한과 만료 시간은 판단으로 정한 값이다**

   노트북 항목 크기(1~1.5KB)는 추정이고, 상한을 얼마나 쓰는지는 밀려난 항목 수(`cache.evictions`)로만 알 수 있다. 만료를 늘리면 적중률은 오르지만 옛 결과가 남는 시간도 길어진다.

   대응: 적용 후 측정에서 적중률, 밀려난 항목 수, 힙 사용을 보고 조정한다.

3. **최대 힙이 서버 메모리에 따라 바뀐다**

   서버 인스턴스를 바꾸면 근거 5의 계산도 달라진다.

   대응: 인스턴스를 줄일 때 캐시 상한도 함께 확인한다.

4. **가격 갱신을 다른 트랜잭션 안에서 부르면 캐시가 저장보다 먼저 비워진다**

   캐시가 비워진 뒤 저장이 끝나기 전에 목록 요청이 오면, 옛 가격을 다시 캐시에 넣는다. 지금은 그렇게 부르는 코드가 없다.

   대응: 그런 코드가 생기면 저장이 끝난 뒤 비우도록 바꾼다.

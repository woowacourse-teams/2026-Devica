# 55. 제품 목록 캐시로 Caffeine 로컬 캐시를 사용한다

- 상태: Accepted
- 날짜: 2026-11-08

## 상황 (조건)

- [0054](0054-제품-맞춤-목록-결과-캐시.md)에서 제품 목록의 조회 결과를 캐싱하고, 최저가가 바뀌면 모두 비우기로 했다.
- 앱 서버는 환경마다 한 대이고, 배포하면 다시 시작한다. 마이그레이션도 배포 때 실행된다.
- 앱의 최대 힙은 약 460MiB로, 따로 설정하지 않은 JVM 기본값이다. 용량 테스트 중 힙 사용은 최대 약 100MiB였다.
- 앱은 목록을 한 페이지 10대씩 요청하고, API는 한 페이지에 100대까지 허용한다.
- 목록 요청의 검색어는 길이 제한이 없는 자유 입력이다. 브랜드는 저장된 값과 같은 64자까지만 받는다.
- 제품 추천 조건으로 만들어지는 서로 다른 맞춤 목록 요청은 1,782개(297개 조합 × 정렬 2 × 페이지 3)다. 페이지 3은 성능 테스트의 가정이다([0054](0054-제품-맞춤-목록-결과-캐시.md) 감수 5).
- 오퍼를 바꾸는 메서드는 트랜잭션 안에서 실행되고, 호출하는 가격 수집 작업은 트랜잭션 밖에 있다. 목록 조회는 읽기 전용 트랜잭션 안에서 실행된다.
- 가격 수집은 하루 한 번 실행되며, 가격이 그대로인 오퍼에도 가격 갱신을 호출한다.

## 고려한 대안

**1. Redis**

- 여러 앱 서버가 캐시를 함께 쓰고, 한 서버에서 비우면 모든 서버에 반영된다.
- 앱을 다시 시작해도 캐시가 남는다.
- Redis 서버를 따로 운영해야 한다.
- 캐시에서 꺼낼 때도 네트워크 왕복(보통 1ms 안팎)과 직렬화·역직렬화를 거친다.

**2. Spring 기본 캐시(`ConcurrentMapCacheManager`)**

- 의존성을 더하지 않는다.
- 크기 상한과 만료가 없어, 서로 다른 요청이 오는 만큼 메모리를 계속 쓴다.
- 적중률 통계를 남기지 않는다.

## 선택: Spring Cache와 Caffeine 로컬 캐시

Spring Cache로 캐시를 쓰고, 저장소는 Caffeine으로 한다. 적중·미스 통계를 기록한다.

- **읽기 전략: Cache-Aside**
    - 미스면 목록 조회 메서드가 DB를 조회해 결과를 캐시에 넣는다.
    - 키는 카테고리·조건·정렬·페이지다.
    - 같은 키의 동시 미스는 한 번만 조회한다.
    - 캐시를 트랜잭션보다 먼저 실행한다.
    - 검색어가 있는 요청은 캐시하지 않는다.
- **쓰기 전략: Write-Around + 무효화**
    - 오퍼를 바꾸면 DB에만 쓴다.
    - 최저가가 바뀐 갱신·숨김·복구에서 목록 캐시 전체를 비운다.
    - 비우기는 저장 트랜잭션이 끝난 뒤 일어난다.
- **교체 정책: W-TinyLFU**
    - 캐시에 든 페이지들의 노트북 수 합계가 20,000을 넘으면 내보낸다.
    - 노트북이 없는 페이지도 1대로 센다.
    - 내보낼 항목은 Caffeine의 기본 정책(최근 사용과 사용 빈도를 함께 본다)으로 고른다. 다른 정책과 비교해 고르지는 않았다.
- **만료: TTL**
    - 넣은 지 10분이 지나면 버린다.

**근거**

1. 앱 서버가 한 대라 분산 캐시가 필요 없고, Redis는 운영할 서버만 늘린다.
2. 로컬 캐시는 배포 재시작 때 비워져, 마이그레이션이 바꾼 데이터가 남지 않는다.
3. Caffeine은 기본 캐시에 없는 크기 상한과 만료, 적중률 통계가 있다.
4. 같은 키의 동시 미스를 한 번만 조회하면, 캐시가 빈 직후 같은 요청이 몰려도 DB에는 한 번만 간다.
5. 캐시를 트랜잭션 바깥에 두어, 적중한 요청은 트랜잭션을 열지 않고 DB 커넥션도 빌리지 않는다. 비우기도 저장 트랜잭션이 끝난 뒤 일어난다.
6. 검색어는 길이 제한이 없는데 크기 상한은 키의 크기를 세지 않아, 키만으로 메모리가 커질 수 있다. 제품 추천 요청에는 검색어가 없어 빼도 효과는 같다.
7. 가격 변경의 영향을 받는 캐시 키를 특정할 수 없어서, 새 값으로 고치는 Write-Through 대신 Write-Around + 무효화 전략을 채택한다. 캐시에 담긴 것은 목록 결과라, 최저가 하나가 바뀌면 여러 조건·정렬의 순서와 다른 페이지 내용까지 바뀐다.
8. 가격은 하루 한 번 수집 때만 바뀌어, 전체를 비워도 나머지 시간에는 캐시가 유지된다.
9. 가격 수집은 가격이 그대로여도 갱신을 호출해, 갱신마다 비우면 수집 내내 캐시가 비워진다. 그래서 최저가가 바뀐 경우에만 비운다.
10. 캐시 메모리는 대부분 노트북 항목이 차지해, 상한을 항목 수가 아니라 노트북 수로 잡았다. 빈 페이지를 1대로 치는 것은 빈 결과가 끝없이 쌓이지 않게 하기 위해서다.
11. 20,000은 제품 추천 요청 1,782개 × 10대에 여유를 둔 값이다. 항목 하나는 id·최저가, 문자열 3개, 사양 5개를 담아 객체 헤더를 포함해 약 1~1.5KB로 추정한다. 상한까지 차도 약 20~30MB라, 평소 힙 약 100MiB에 더해도 최대 힙 460MiB에 든다.
12. 정합성은 무효화가 맡고, 만료는 비우기와 겹친 조회가 다시 넣은 옛 결과가 남는 시간의 상한이 된다([0054](0054-제품-맞춤-목록-결과-캐시.md) 감수 2).

## 감수하는 것

1. **캐시가 앱 서버마다 따로 있다**

   서버를 스케일 아웃하면 가격 수집을 수행한 서버의 캐시만 비워져, 다른 서버는 만료 때까지 옛 결과를 보여준다.

   대응: 서버를 늘릴 때 Redis나 서버 간 무효화를 다시 검토한다.

2. **크기 상한과 만료 시간은 판단으로 정한 값이다**

   노트북 항목 크기(1~1.5KB)는 필드 구성으로 계산한 추정이고, 상한을 얼마나 쓰는지는 밀려난 항목 수(`cache.evictions`)로만 알 수 있다. 만료를 늘리면 적중률은 오르지만, 옛 결과가 남는 시간도 길어진다. 힙 사용량에는 아직 수거되지 않은 객체가 섞여 있어, 캐시 크기를 재는 근거로 쓸 수 없다.

   대응: 적용 후 측정에서 적중률, 밀려난 항목 수, 힙 사용을 보고 조정한다. 항목 크기는 JOL이나 힙 덤프로 실측해 추정을 확인한다.

3. **최대 힙이 서버 메모리에 따라 바뀐다**

   서버 인스턴스를 바꾸면 교체 정책의 메모리 계산도 달라진다.

   대응: 인스턴스를 줄일 때 캐시 상한도 함께 확인한다.

4. **가격 갱신을 다른 트랜잭션 안에서 호출하면 캐시가 저장보다 먼저 비워진다**

   캐시가 비워진 뒤 저장이 끝나기 전에 목록 요청이 오면, 옛 가격을 다시 캐시에 넣는다. 지금은 그렇게 호출하는 코드가 없다.

   대응: 그런 코드가 생기면 저장이 끝난 뒤 비우도록 바꾼다.

# 24. 권장 사양의 CPU 를 cpu 행이 아니라 등급 enum 으로 표현한다

- 상태: Accepted
- 날짜: 2026-09-14

## 상황 (조건)

- 사용 목적과 맞춤 질문 답변으로 노트북 권장 사양(OS·CPU·메모리·저장 공간)을 계산한다.
- 권장 사양은 두 곳에 쓰인다. 화면에 "이 정도가 필요하다"고 보여주고, 그 조건으로 제품을 검색한다.
- 검색은 `cpu.score` 하한으로 거른다. 점수는 실제 칩의 벤치마크 측정값이고 `cpu` 테이블에 있다.
- **추천 알고리즘은 확정되지 않았고 교체될 예정이다.** 교체 시 변경 전파를 줄이는 것이 이번 설계의
  최우선 가치다. 알고리즘 추가는 구현체 클래스 하나로 끝나야 한다.
- 프로토타입 알고리즘은 등급 사다리를 오르내리는 방식이다 — Java 계열이면 한 단계 위,
  빌드 대기 경험이 있으면 또 한 단계 위, Mac 은 M Pro 칩에서 멈춘다.
- 맞춤 질문의 현재 CPU 선택지가 이미 같은 사다리다. Mac 은 `BASIC`·`PRO`·`MAX`,
  Windows 는 `U`·`P_HS`·`H`·`HX` 네 단계다.
- Windows CPU 는 Intel 과 AMD 가 함께 있어 제조사를 가로질러 줄 세울 수 없다.
- 직전까지 권장 사양의 CPU 는 `"M 칩"` 같은 표시용 문자열이었다. 비교가 불가능해 검색으로 넘길 수 없었다.

## 고려한 대안

**1. `cpu` 테이블의 행(`Cpu` 엔티티)을 그대로 쓴다**

- 이름과 점수가 한 곳에 있어 중복이 없다. 표시에는 실제 모델명이 나가고 비교는 점수가 한다.
- 권장 사양이 특정 모델을 지목하게 된다. "이 정도 급"이라는 요구와 의미가 다르다.
- 사다리를 표현할 수 없다. 점수순으로 다음 행을 집으면 카탈로그에 칩이 하나 등록될 때마다
  추천 결과가 바뀐다.
- 알고리즘이 `Cpu` 를 반환하려면 구현체마다 리포지토리를 들어야 한다. 단위 테스트가 통합 테스트가 된다.

**2. `cpu` 테이블에 등급 컬럼을 두고 알고리즘은 등급을 다룬다**

- 어떤 칩이 몇 등급인지가 데이터에 있어 점수 임계값을 코드에 두지 않아도 된다.
- 검색이 `cpu.tier IN (해당 등급 이상)` 이 되어 점수를 거치지 않는다.
- 등급 자체가 점수대의 이름인데 점수와 등급을 행마다 따로 관리하게 된다.
- 스키마 변경과 시드 정합성 관리가 따라온다.

**3. 등급 enum 을 두고 등급마다 점수대를 선언한다**

- 사다리가 곧 타입이라 알고리즘이 DB 없이 순수하게 남는다.
- 질문의 현재 CPU 선택지와 이름이 1:1 로 대응한다.
- 점수 임계값이 코드에 들어간다. 카탈로그의 점수 척도가 바뀌면 함께 고쳐야 한다.
- 표시에 실제 모델명 대신 등급명이 나간다.

## 선택: 등급 enum(`CpuTier`)을 두고 검색 시 점수 하한으로 바꾼다

`CpuTier` 가 OS·표시명·최소 점수를 갖는다. 권장 사양(`LaptopSpec`)은 등급을 담고,
제품 검색은 `cpu.score >= tier.minScore` 로 거른다.

**근거**

1. 알고리즘의 조정 단위가 등급이다. 한 단계 올리기·두 값 중 높은 등급 고르기가 규칙의 전부인데,
   등급이 타입이면 그대로 표현되고 `Cpu` 행이면 사다리를 따로 만들어 행으로 되돌려야 한다.
2. 알고리즘이 DB 를 타지 않아 교체 비용이 구현체 하나로 유지된다. `Cpu` 를 쓰면 구현체마다
   리포지토리가 붙어 최우선 가치가 깎인다.
3. **제조사가 여럿인 문제를 등급이 흡수한다.** Intel 과 AMD 를 줄 세울 수는 없지만
   같은 점수대인지는 말할 수 있다. 한 등급이 두 제조사의 대표 모델을 함께 이름에 담는다
   (`H` = `Core Ultra 7 255H / Ryzen 7 H 260급`).
4. 벤치마크 점수는 절대 기준이 아니라 상대값이다. 등급을 먼저 정의하고 점수대를 그 등급의 정의로
   두면, 코드의 임계값은 측정값의 복제가 아니라 우리 분류 기준이 된다.
5. 권장 사양은 특정 모델 지목이 아니라 요구다. 화면에 `Apple M4` 라고 찍으면 사용자가 그 모델만
   찾게 된다. 프로토타입이 실제로 내보내던 문구도 등급명이다.
6. 등급 컬럼(대안 2)은 등급 위에 등급을 얹는 셈이다. 배포 없이 바꿀 요구가 없는 값을 컬럼으로
   두지 않는다는 기존 판단과도 어긋난다.

## 감수하는 것

1. **점수대가 잠정값이다**

   시드된 두 행(`Apple M4` 21000, `Intel Core Ultra 7 255H` 24000)에만 맞춰 두었다.
   나머지 다섯 등급은 추정치다. 잘못 잡히면 검색이 너무 넓거나 좁아진다.

   대응: 제품 데이터가 쌓이면 실제 분포를 보고 조정한다. `CpuTier` 한 곳만 고치면 된다.

2. **한 등급이 제조사를 가로지르는 근사다**

   AMD 가 Intel 과 다른 점수 곡선을 그리면, 이름은 `HX` 급인 Ryzen 칩이 실제로는 `H` 점수대에
   앉을 수 있다. 사용자가 현재 CPU 로 `HX` 를 고르면 실제보다 높게 잡힌다.

   대응: 지금은 감수한다. 제조사별로 등급을 나누려면 질문 선택지와 문구까지 함께 바뀐다.

3. **점수 척도가 바뀌면 두 곳을 함께 고친다**

   `cpu.score` 의 기준 벤치마크를 바꾸면 `CpuTier.minScore` 도 따라가야 한다. 어긋나도
   컴파일과 테스트가 잡지 못하고 검색 결과만 조용히 달라진다.

4. **사양 항목 코드가 둘로 갈린다**

   제품은 실제 모델명을 `CPU` 로, 권장 사양은 등급을 `REQUIRED_CPU` 로 내보낸다. 화면 라벨은 둘 다
   "CPU" 지만 클라이언트는 코드 두 개를 알아야 한다.

   응답 코드를 `CPU` 하나로 맞추는 안을 검토했으나 되돌렸다. 값의 종류가 실제로 다른데
   (`Apple M4` 와 `PRO`) 코드만 같아지면 표면상 통일이 의미상 불일치가 되고,
   `SpecItemView` 에 같은 코드를 가진 상수가 둘 생긴다.

5. **현재 CPU 선택지와 등급이 이름으로 이어진다**

   알고리즘이 `CurrentWindowsCpu.H` 를 `CpuTier.H` 로 잇는 근거는 이름이 같다는 것뿐이다.
   선택지를 추가하거나 이름을 바꾸면 컴파일이 아니라 런타임에 깨진다.

   대응: `CpuTierTest` 가 두 선택지 enum 의 이름마다 같은 이름의 등급이 있는지 확인한다.

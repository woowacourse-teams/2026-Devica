# 54. 제품 목록의 조회 결과를 캐시한다

- 상태: Accepted
- 날짜: 2026-11-08

## 상황 (조건)

- 제품 목록의 용량은 예상 트래픽의 1.6배 이상 2배 미만이다([0053](0053-성능-테스트-용량-판정.md)).
- 개발 서버에서 예상 트래픽의 2배를 걸면 서버 처리 시간 p95가 246ms로 SLO(200ms)를 넘는다.
- 예상 트래픽은 홍보글 한 건으로 추정한 값이고, 정한 목표 배수는 없다.
- 병목은 맞춤 목록 쿼리다. 맞춤 목록은 제품 추천 결과의 사양을 조건으로 거는 목록이다.
    - 전체 목록은 최저가 인덱스를 앞에서부터 순차적으로 탐색하며, 한 페이지 분량(10대)과 다음 페이지 확인용 1대를 확보하면 탐색을 종료한다(조기 종료). 최저가 순서로 읽으므로, 먼저 읽은 11대가 최저가 상위 11대임이 보장된다.
    - 맞춤 목록은 필터링 조건(사양)과 정렬 기준(최저가)이 서로 다른 테이블에 있어, 하나의 인덱스로 필터링과 정렬을 함께 처리할 수 없다. 그래서 옵티마이저는 조건에 맞는 노트북을 모두 읽은 뒤 정렬하는 계획을 고른다.
    - 이 때문에 조건이 넓을수록 느리고, 가장 넓은 Windows 기본 조합은 노트북 9,158대를 읽어 개발 RDS에서 135ms가 걸린다.
- 2배 부하에서도 개발 RDS의 CPU 최대 사용률은 38.3%로, DB는 포화되지 않았다.
- 제품 추천이 내는 조건은 297개 조합이다.
- 앱은 목록을 한 페이지 10대씩, 스크롤하면 다음 페이지를 이어서 요청한다.
- 조건에 맞는 노트북이 가장 적은 조합은 디자인 목적으로, 성능 테스트 데이터에서 78대다.
- 목록 결과를 바꾸는 앱 코드는 가격 수집이 하루 한 번 호출하는 오퍼 갱신뿐이다. 그 밖의 변경은 배포 때의 마이그레이션이다.
- 앱은 배포하면 다시 시작한다.
- [0043](0043-제품-목록-최저가-사전-계산.md)은 갱신 주기가 다른 가격과 사양을 섞지 않으려고, 최저가를 노트북 테이블과 나눈 별도 테이블에 두었다.
- 0043은 두 가지 이유로 캐시를 기각했다. 캐시에 없는 요청은 비싼 쿼리를 그대로 실행해 피크에 DB가 포화될 수 있고(0043 근거 3), 조합이 많아 캐시가 거의 맞지 않는다(0043 근거 4)는 것이다. 그때는 1배에서 RDS CPU가 99%였고, 맞춤 목록의 조건이 제품 추천 조합에서 온다는 점은 따지지 않았다.

## 고려한 대안

쿼리 시간은 로컬 MySQL에서 같은 성능 테스트 데이터(노트북 20,020대)로 잰 값이다. 로컬은 개발 RDS보다 약 4배 빠르므로 전후 비율로 읽는다. 같은 요청도 측정 회차마다 수 ms씩 달라, 전후는 같은 회차 안에서 비교했다.

**1. 가격순 쿼리에서 노출 여부 검사 빼기**

- 쿼리 한 곳만 고치면 된다.
- Windows 기본 조합이 29.6ms에서 20.2ms로 약 30% 줄어든다.
- 숨김 처리한 제품을 목록에서 제외하는 책임이 최저가 계산 로직으로 넘어간다. 이 로직에 오류가 생기면 숨김 처리한 제품이 사용자에게 노출된다.

**2. 최저가 인덱스 순 조기 종료 (필터링 값을 최저가 테이블에 복제)**

- 필터링 값(OS·CPU 점수·메모리 등)을 `product_min_price`에 복제해, 필터링 조건과 정렬 기준을 한 테이블에 둔다. 그러면 최저가 인덱스 순서로 탐색하면서 같은 행에서 조건을 바로 검사할 수 있어, 한 페이지 분량을 확보하는 즉시 탐색을 종료할 수 있다.
- 필터링 조건 쪽에 인덱스를 거는 방법도 있지만, 조건에 맞는 노트북을 빨리 찾을 뿐 결과가 최저가 순서가 아니다. 그래서 결국 모두 읽고 정렬해야 한다.
- 297개 조합의 가격 낮은순 첫 페이지에서 가장 느린 요청이 26.8ms에서 0.55ms로 줄었고, 느려진 조합은 없었다.
- 캐시와 달리 처음 오는 요청도 빠르다.
- 노트북 사양이 바뀌면 최저가 테이블에 복사한 값도 함께 고쳐야 한다. 빠뜨리면 옛 사양을 기준으로 필터링된다.
- 갱신 주기가 다른 가격과 사양이 한 테이블에 섞인다.

**3. 최저가 인덱스 순 조기 종료 (조인 순서 고정)**

- 옵티마이저는 조건 쪽(`laptop`·`cpu`)부터 읽는 순서를 고른다. 쿼리 힌트(`STRAIGHT_JOIN`, `FORCE INDEX`)로 `product_min_price`를 최저가 인덱스 순서로 먼저 읽게 강제하고, 행마다 `laptop`·`cpu`를 조인해 조건을 검사하다가 한 페이지가 차면 멈춘다. 데이터는 바꾸지 않는다.
- 쿼리 힌트만 더하면 된다.
- 조건에 맞는 노트북이 많은 요청이 빨라진다. Windows 기본 조합이 27.7ms에서 0.1ms로 줄었다.
- 조건에 맞는 노트북이 적은 요청은 한 페이지를 채울 때까지 최저가 순서로 오래 읽으며 조인해야 해서 느려진다. 디자인 목적 Windows 3페이지는 4.9ms에서 11.4ms로, 맞는 노트북이 없는 조건은 0.02ms에서 40ms로 늘었다.
- 데이터 분포가 바뀌어도 옵티마이저가 계획을 고를 수 없다.

**4. DB 사양 올리기**

- 코드를 바꾸지 않는다.
- 비용이 늘어난다. `db.t4g.micro`에서 `large`까지 vCPU는 모두 2개라, CPU를 늘리려면 인스턴스 계열을 바꿔야 한다.

## 선택: 제품 목록의 조회 결과를 앱에서 캐시하고, 최저가가 바뀌면 모두 비운다

제품 목록의 조회 결과를 카테고리·조건·정렬·페이지를 키로 캐시한다. 맞춤 목록과 전체 목록은 같은 조회를 쓰므로 함께 캐시한다. 오퍼의 가격 갱신·숨김·복구로 최저가가 바뀌면 목록 캐시 전체를 비운다. 캐시 구현과 크기·만료 설정은 [0055](0055-제품-목록-캐시-구현.md)에서 정한다.

**근거**

1. 정한 목표 배수가 없으니, 홍보글 한 건으로 잡은 추정이 2배 틀려도 버틸 수 있어야 한다. 지금은 2배에서 SLO를 넘는다.
2. DB가 포화되지 않았는데 느린 것은 쿼리 하나가 비싸서다. 캐시에 있는 요청은 이 쿼리를 건너뛴다.
3. 0043 근거 4와 달리, 맞춤 목록의 조건은 제품 추천 조합 안에서 나오므로, 피크 동안 서로 다른 사용자가 같은 조건·정렬로 같은 페이지를 요청한다. 키를 요청 그대로(카테고리·조건·정렬·페이지) 잡으면 이 사용자 사이의 반복이 그대로 적중으로 이어진다. 한 사용자가 다음 페이지로 넘어가는 것은 다른 요청이라 이 키로는 줄지 않는다(감수 4). 적중이 얼마나 될지는 키 수가 아니라 요청이 어느 키에 몰리는지에 달려 있어, 적용 후 측정으로 확인한다(감수 5).
4. 0043 근거 3과 달리, 캐시에 없는 요청이 지금과 같은 쿼리를 실행해도 2배까지 DB가 포화되지 않는다. 그래서 캐시가 비어도 지금보다 나빠지지 않는다. 이는 캐시를 해야 하는 이유가 아니라, 하면 안 되는 이유가 사라졌다는 뜻이다. 다만 2배를 넘는 피크에 캐시가 비면, 그 순간에는 캐시 도입 전처럼 SLO를 넘을 수 있다.
5. 결과를 바꾸는 코드가 한 곳이라 거기서 비우면 되고, 마이그레이션은 재시작으로 비워진다. 가격은 하루 한 번 수집 때만 바뀌어, 비우기는 수집 시간에만 일어난다.
6. 대안 1은 쿼리 시간을 30% 줄일 뿐이지만, 캐시는 적중한 요청에서 쿼리를 없앤다.
7. 대안 2는 0043이 갱신 주기 때문에 나눈 가격과 사양을 다시 한 테이블에 섞는다.
8. 대안 3은 디자인 목적(가장 적은 조합은 78대)처럼 조건에 맞는 노트북이 적은 조합의 요청을 느리게 한다.
9. 대안 4는 CPU를 늘리지만, DB가 포화되지 않았으니 늘어난 CPU가 쿼리 하나의 시간을 줄이지 못한다.

## 감수하는 것

1. **목록 결과를 바꾸는 코드에서 항상 캐시도 비워야 한다**

   빠뜨리면 만료 때까지 옛 가격이나 숨긴 제품이 보인다.

   대응: E2E 테스트가 캐시를 채운 뒤 숨김과 복구가 목록에 반영되는지 확인해, 비우기가 빠지면 실패한다.

2. **비우기와 겹친 조회가 옛 결과를 다시 넣을 수 있다**

   비우기 직전에 시작한 조회가 비운 뒤에 옛 결과를 넣으면, 만료 때까지 남는다.

   대응: 만료 시간으로 그 시간을 묶는다([0055](0055-제품-목록-캐시-구현.md)).

3. **캐시에 없는 요청은 지금처럼 느리다**

   조건마다 첫 요청, 캐시가 비워진 직후, 사용자가 직접 거는 필터가 그렇다.

   대응: 적중률을 보고, 낮으면 대안 2·3을 다시 검토한다.

4. **같은 조건의 다음 페이지도 처음에는 쿼리를 다시 실행한다**

   쿼리는 1페이지를 만들 때 조건에 맞는 노트북을 모두 정렬하지만 10대만 남긴다. 키가 페이지마다 달라, 2·3페이지는 같은 정렬을 처음부터 다시 한다.

   대응: 적용 후 측정에서 미스가 2페이지 이후에 몰리면, 조건·정렬을 키로 정렬된 ID 목록 전체를 캐시하는 방식을 검토한다.

5. **적용 후 측정의 적중률은 시나리오 가정에 기댄다**

   시나리오는 조건 분포(사용 목적별 균등, 맞춤 목록 : 전체 목록 = 1 : 1)와 스크롤 깊이(3페이지)를 근거 없이 가정했다([성능 테스트 가정](../../performance/k6/product-list/README.md)). 3페이지는 RPS를 넉넉히 잡기 위한 보수적인 값으로, 이 가정에서 맞춤 목록의 서로 다른 요청은 1,782개(297 × 정렬 2 × 페이지 3)다. 조건이 더 흩어지면 실제 적중률은 더 낮고, 사용자가 앞쪽 페이지에서 멈추면 더 높을 수 있다. 측정하는 전체 적중률에는 키가 6개(정렬 2 × 페이지 3)뿐인 전체 목록이 절반 포함되어, 맞춤 목록만의 적중률보다 높게 나온다. 시나리오가 같은 순서로 요청하므로, 앞 회차의 캐시가 남으면 측정이 유리해진다.

   대응: 회차마다 앱을 다시 시작하고, 운영 적중률은 지표로 따로 본다. 맞춤 목록의 적중률과 페이지별 요청 수도 나눠 본다. 페이지별 요청 수는 감수 4의 키 변경을 판단하는 데도 쓴다.

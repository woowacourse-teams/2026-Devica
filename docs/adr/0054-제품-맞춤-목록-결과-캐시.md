# 54. 제품 목록의 조회 결과를 캐시한다

- 상태: Accepted
- 날짜: 2026-11-08

## 상황 (조건)

용어: 맞춤 목록은 제품 추천 결과에서 들어와 OS·CPU 점수·메모리·저장 용량(디자인 목적이면 색 영역·GPU 점수까지)을 조건으로 거는 목록이고, 전체 목록은 조건 없는 목록이다. Windows 기본 조합은 `os='WINDOWS'`, CPU 점수 20000 이상, 16GB, 256GB다.

- 2026-11-07~08 개발 서버에서 잰 제품 목록의 용량은 예상 트래픽의 1.6배 이상 2배 미만이다([0053](0053-성능-테스트-용량-판정.md)). 서버 처리 시간 p95는 1.6배에서 176ms(3회 중앙값), 2배에서 246ms였다.
- 예상 트래픽은 홍보글 한 건을 기준으로 추정한 값이고, 따로 정한 홍보 계획이나 목표 배수는 없다.
- 2배에서도 앱 CPU(최대 9.2%), DB 커넥션 대기(0), RDS 읽기 IOPS(최대 0.5)는 여유가 있었다. 부하에 따라 늘어난 것은 RDS CPU(1분 평균 최대 38.3%)뿐이었다.
- 늘어난 지연은 피크 2분에 몰렸다.
- 느린 것은 맞춤 목록이다. 개발 RDS에서 쿼리 실행 시간은 Windows 기본 조합이 135ms, 전체 목록이 0.24ms다.
- 맞춤 목록은 거르는 조건과 정렬 기준(최저가)이 다른 테이블에 있어, 조건에 맞는 노트북을 모두 읽고 정렬한다. Windows 기본 조합은 9,158대를 읽는다.
- 제품 추천이 내는 조건은 297개 조합이다. 성능 테스트 시나리오는 맞춤 목록을 이 조건으로 보내고, 정렬 2가지 × 3페이지까지 세면 서로 다른 요청은 1,782개다.
- 운영 요청 로그에는 쿼리 문자열이 없어, 실제 조건 분포는 확인하지 못했다.
- 목록 결과를 바꾸는 앱 코드는 `ProductOfferService`뿐이다. 운영에서 호출되는 것은 가격 수집이 부르는 가격 갱신(복구 포함)이고, 숨김은 아직 호출하는 곳이 없다. 그 밖의 변경은 배포 때 실행되는 마이그레이션이다.
- 가격 수집은 하루 한 번(04:00) 돈다.
- 앱 서버는 환경마다 한 대이고, 배포하면 다시 시작한다.
- [0043](0043-제품-목록-최저가-사전-계산.md)은 캐시를 기각했다. 캐시가 비면 비싼 쿼리가 몰려 DB가 포화될 수 있고(근거 3), 조합이 많아 캐시가 거의 맞지 않는다(근거 4)는 이유였다. 그때와 지금은 다음이 다르다.
  - 개발 DB에서 가장 비싼 목록 쿼리는 그때 301ms(전체 목록), 지금 135ms(Windows 기본 조합)다.
  - RDS CPU는 그때 1배에서 99%로 포화됐고, 지금은 2배에서 최대 38.3%다.
  - 0043은 맞춤 목록의 조건이 제품 추천이 내는 유한한 조합에서 온다는 점을 따지지 않았다.

## 고려한 대안

쿼리 시간은 로컬 MySQL에서 같은 성능 테스트 데이터(노트북 20,020대)로 잰 값이다. 로컬은 개발 RDS보다 약 4배 빠르므로 전후 비율로 읽는다. 기준값은 측정 회차마다 조금씩 다르다(Windows 기본 조합 27.7~32.6ms).

**1. 가격순 쿼리에서 노출 여부 검사 빼기**

- 쿼리 한 곳만 고치면 된다.
- Windows 기본 조합이 29.6ms에서 20.2ms로 약 30% 줄어든다.
- 숨긴 제품이 목록에 나오지 않는 것을 최저가 계산 로직이 보장하게 되어, 그 로직에 실수가 생기면 숨긴 제품이 보인다.

**2. 최저가 테이블에 거르는 값을 복사해 최저가 순서로 읽기**

- 모든 조건에서 최저가 인덱스 순서로 한 페이지 분량만 읽는다. 297개 조합의 가격 낮은순 첫 페이지에서 가장 느린 요청이 26.8ms에서 0.55ms로 줄었고, 느려진 조합은 없었다.
- 캐시와 달리 처음 오는 요청도 빠르다.
- 사양이 바뀔 때마다 최저가 테이블도 고쳐야 한다.
- 갱신 주기가 다른 가격과 사양이 한 테이블에 섞인다.

**3. 조인 순서를 고정해 최저가 순서로 읽기**

- 쿼리 힌트(`STRAIGHT_JOIN`, `FORCE INDEX`)만 더하면 된다.
- 넓은 조건이 빨라진다. Windows 기본 조합이 27.7ms에서 0.1ms로 줄었다.
- 좁은 조건은 최저가 순서로 한참 읽어야 한 페이지를 채워 느려진다. 디자인 목적 Windows 3페이지는 4.9ms에서 11.4ms로, 맞는 노트북이 없는 조건은 0.02ms에서 40ms로 늘었다.
- 데이터 분포가 바뀌어도 옵티마이저가 계획을 고를 수 없다.

**4. 제품 추천 조합의 결과를 미리 채워 두기**

- 기동 때와 가격 수집 뒤에 1,782개 요청을 미리 조회해 두면, 첫 요청도 캐시에서 나간다.
- 미리 채우는 동안 쿼리 1,782번이 한꺼번에 실행된다.
- 제품 추천 조합이나 페이지 크기가 바뀌면 채우는 목록도 함께 고쳐야 한다.

**5. DB 사양 올리기**

- 코드를 바꾸지 않는다.
- 비용이 늘어난다. `db.t4g.micro`에서 `large`까지 vCPU는 모두 2개라, CPU를 늘리려면 인스턴스 계열을 바꿔야 한다.

거르는 컬럼에 복합 인덱스를 두는 방법은 후보로 올리지 않았다. Windows 기본 조합처럼 조건에 맞는 노트북이 9,158대면 인덱스로 찾아도 읽는 행이 줄지 않는다.

## 선택: 제품 목록의 조회 결과를 앱에서 캐시하고, 최저가가 바뀌면 모두 비운다

`ProductService.findProductsByCategory`의 결과를 카테고리·조건·정렬·페이지를 키로 캐시한다. 맞춤 목록과 전체 목록은 같은 메서드라 함께 캐시한다. 오퍼의 가격 갱신·숨김·복구로 최저가가 바뀌면 목록 캐시 전체를 비운다. 캐시 구현과 크기·만료 설정은 [0055](0055-제품-목록-캐시-구현.md)에서 정한다.

**근거**

1. 따로 정한 목표가 없으니 용량은 추정이 틀릴 수 있는 폭으로 판단한다. 지금은 추정이 2배만 틀려도 기준을 넘는데, 홍보글 한 건으로 잡은 추정에서 2배는 충분히 생길 수 있는 오차다.
2. 자원에 여유가 있는데 느린 것은 쿼리 하나의 비용이 크고, 부하가 늘면 그 위에 DB CPU를 나눠 쓰는 대기가 더해지기 때문이다. 캐시에 있는 요청은 이 쿼리를 실행하지 않으므로 두 몫이 함께 줄어든다.
3. 맞춤 목록의 조건이 제품 추천의 297개 조합 안에서 나오면, 서로 다른 요청이 1,782개뿐이라 피크 동안 반복된다. 조건마다 첫 요청만 DB에 가고 나머지는 캐시에서 돌려준다.
4. 캐시가 비어도 지금보다 나빠지지 않는다. 0043이 걱정한 포화는 캐시가 빈 순간 비싼 쿼리가 몰리는 경우였지만, 지금은 캐시 없이도 2배 부하에서 DB가 포화되지 않는다.
5. 목록 결과를 바꾸는 앱 코드가 한 클래스뿐이라, 거기서 비우면 결과가 맞게 유지된다. 마이그레이션은 배포 재시작으로 캐시가 비워져 따로 비우지 않아도 된다.
6. 대안 1은 2배에서 246ms인 지연을 30% 줄이는 데 그치고, 숨긴 제품을 가리는 장치를 약하게 한다.
7. 대안 2는 0043이 갱신 주기 때문에 나눈 가격과 사양 테이블을 다시 섞고, 대안 3은 좁은 조건을 느리게 한다.
8. 대안 4는 첫 요청까지 빠르게 하지만, 캐시가 비어도 지금보다 나빠지지 않으므로(근거 4) 채우는 코드와 그때의 부하를 더할 만큼 급하지 않다.
9. 대안 5는 DB CPU가 포화되지 않은 상태라 쿼리 하나의 시간을 줄이지 못한다.

## 감수하는 것

1. **최저가나 목록에 나오는 값을 바꾸는 코드를 더하면 캐시도 비워야 한다**

   비우는 일을 빠뜨리면 만료 시간 동안 옛 가격이나 숨긴 제품이 목록에 보인다. 노트북 사양을 바꾸는 앱 기능이 생길 때도 마찬가지다.

   대응: 오퍼를 바꾸는 메서드에 `@CacheEvict`를 둔다. E2E 테스트에서 목록을 먼저 조회해 캐시를 채운 뒤 숨김과 복구가 목록에 반영되는지 확인해, 비우는 일이 빠지면 테스트가 실패한다.

2. **비우기와 겹친 조회가 옛 결과를 다시 넣을 수 있다**

   캐시에 없는 요청이 최저가가 바뀌기 전 데이터로 조회를 시작하고, 그 사이 갱신이 커밋되어 캐시가 비워지면, 그 요청이 끝나며 옛 결과를 캐시에 넣는다. 그 결과는 만료 때까지 남는다. 겹칠 수 있는 시간은 쿼리 한 번(개발 RDS 최대 약 135ms)이고, 가격 수집은 04:00에 돈다.

   대응: 만료 시간을 틀린 결과가 남는 시간의 상한으로 둔다([0055](0055-제품-목록-캐시-구현.md)).

3. **캐시에 없는 요청은 지금과 같다**

   조건마다 첫 요청, 캐시가 비워진 직후(배포, 가격 변경, 만료), 사용자가 직접 거는 필터는 지금처럼 조건에 맞는 노트북을 모두 읽는다. 노트북이 늘면 이 요청들은 함께 느려진다.

   대응: 적중률(`cache.gets`)을 지표로 수집한다. 적용 후 같은 방법으로 용량을 재고, 적중률이 낮거나 용량이 늘지 않으면 대안 2·3을 다시 검토한다.

4. **적용 후 측정의 적중률은 시나리오의 가정에 기댄다**

   성능 테스트 시나리오는 사용 목적과 조합을 정해진 비율로 고른다. 실제 사용자의 조건이 더 흩어지면 적중률은 측정보다 낮다. 또 시나리오가 같은 순서로 요청하므로, 앞 회차가 채운 캐시가 남아 있으면 측정이 유리하게 나온다.

   대응: 회차마다 측정 전에 앱을 다시 시작한다. 운영의 적중률은 `cache.gets` 지표로 따로 확인한다.

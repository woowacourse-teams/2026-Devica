# 11. 보일러플레이트 제거에 Lombok을 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- Java는 getter, 생성자, `toString` 등 반복적으로 작성해야 하는 코드가 많다.
- 영속성 엔티티부터 서비스 계층까지 전반에 걸쳐 이런 코드가 발생한다.

## 고려한 대안

실질적으로 검토한 대안은 없다.

Lombok 대신 IDE의 코드 생성 기능을 쓸 수도 있으나, 필드가 바뀔 때마다 생성된 코드를 함께 고쳐야 한다. 보일러플레이트를 제거한다는 이점이 명확해 다른 선택지를 검토하지 않았다.

## 선택: Lombok

**근거**

1. 반복 코드를 애노테이션으로 대체하면, 클래스에 실제 의미를 갖는 부분만 남는다.
2. 필드가 바뀌어도 생성자나 getter를 함께 고칠 필요가 없다. 스키마와 구조가 자주 바뀌는 이번 프로젝트에서 수정 범위를 줄여준다.

## 감수하는 것

1. **JPA 엔티티에서 Lombok 사용 시의 위험**

   Lombok을 엔티티에 무분별하게 적용하면 다음과 같은 문제가 생길 수 있다.

    - `@ToString`이 연관 엔티티를 참조하면서 의도치 않은 지연 로딩이 발생하거나, 양방향 관계에서 무한 순환이 일어날 수 있다.
    - `@EqualsAndHashCode`가 모든 필드로 동등성을 판단해, JPA가 전제하는 식별자 기반 동등성과 어긋난다.
    - `@Setter`를 열어두면 엔티티 상태를 어디서든 바꿀 수 있어, 변경 지점을 추적하기 어렵다.

   현재 팀 차원의 사용 규칙은 정하지 않았다. 엔티티가 여러 개 만들어진 뒤에는 규칙을 적용하는 비용이 커지므로, 첫 엔티티를 작성하는 시점에 논의해 정한다.

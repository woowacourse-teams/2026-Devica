# 7. 개발 중에는 DB만 컨테이너로 실행한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 실행 환경으로 Docker/Compose를 사용하기로 했으므로, 무엇을 컨테이너로 실행할지 정해야 한다.
- 테스트를 작성하며 개발하므로, 코드를 수정하고 실행하는 주기가 짧고 반복 횟수가 많다.

## 고려한 대안

**1. DB와 애플리케이션을 모두 컨테이너로 실행**

- 애플리케이션의 실행 방식과 네트워크 구성이 배포 환경과 같아져, 환경 차이로 생기는 문제를 개발 단계에서 미리 발견할 수 있다.
- JDK를 포함한 실행 환경이 컨테이너에 고정되어, 팀원의 로컬 설치 상태와 무관하게 같은 환경에서 애플리케이션이 실행된다.
- 코드를 수정할 때마다 이미지를 다시 빌드하고 컨테이너를 재시작해야 한다.
- IDE의 실행·디버깅 기능을 그대로 사용하기 어렵다.

## 선택: DB만 컨테이너로 실행

애플리케이션은 각자의 로컬에서 IDE로 직접 실행한다.

**근거**

1. 테스트를 작성하며 개발하는 방식에서는 실행 주기가 짧고 반복 횟수가 많다. 애플리케이션을 컨테이너에 넣으면 수정할 때마다 이미지를 다시 빌드해야 하고, 그 비용이 그대로 검증 속도의 저하로 이어진다.
2. 배포 환경과의 일치는 배포 단계에서 확보한다. 개발 단계에서는 반복 속도를 우선하고 환경 일치는 배포 파이프라인에서 다루는 편이, 비용 대비 효과가 크다고 판단했다.
3. 애플리케이션은 JVM 위에서 실행되어 OS에 종속되지 않으며, JDK 버전도 Gradle 툴체인 설정으로 고정되어 있다. 따라서 컨테이너에 넣지 않아도 팀원 간 실행 환경이 통일된다. 대안이 가진 이점 중 실행 환경 통일은 컨테이너 없이도 이미 확보된 셈이다.

## 감수하는 것

1. **개발 환경과 배포 환경의 실행 방식이 다르다**

   애플리케이션이 컨테이너 밖에서 실행되므로, 컨테이너 환경에서만 드러나는 문제(네트워크 구성, 파일 경로, 타임존 등)는 개발 중에 발견되지 않는다. 이런 문제는 배포 단계에서 처음 확인하게 된다.

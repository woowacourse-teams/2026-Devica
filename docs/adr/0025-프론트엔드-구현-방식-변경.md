# 25. 프론트엔드를 React로 구현한다

- 상태: Accepted
- 날짜: 2026-09-16

[ADR 0010](0010-프론트엔드-구현-방식.md)을 대체한다.

## 상황 (조건)

0010의 조건 중 세 가지가 달라졌다.

- **MVP 1개월이라는 기간이 끝났다.** 0010은 "화면 구현에 드는 시간이 늘어날수록 검증 시간이 줄어든다"를 전제로 했다. V0 검증이 끝나 이 압박이 사라졌다.
- **0010이 감수하기로 한 비용이 실측됐다.** 프로토타입은 "JavaScript를 직접 작성"하는 쪽을 택했고, 결과는 프레임워크 없는 수동 DOM 상태 머신 약 87KB(`probe-app.js` 38KB
  포함)였다. 그 프로토타입은 `develop`에 병합되지 못했다.
- **인프라 담당자가 생겼다.** 0010이 "관리할 지점이 늘어난다"고 본 별도 배포 파이프라인이, 담당자가 있는 지금은 같은 무게가 아니다.

달라지지 않은 조건도 있다. 팀에 프론트엔드 개발 경험이 부족하다는 점은 그대로다.

한편 `develop`은 이미 순수 REST API다. 템플릿과 정적 자원이 없고 뷰를 반환하는 컨트롤러도 없어, 옮길 서버 렌더링 코드가 없다.

## 고려한 대안

**1. Thymeleaf 유지**

- 서버와 화면이 한 애플리케이션에 있어 배포 대상이 하나다.
- 이미 팀이 한 번 다뤄 봤다.
- 화면 상태가 자주 바뀌는 흐름에서는 JavaScript를 직접 작성하게 된다. 그 비용이 프로토타입에서 확인됐다.

**2. Next.js**

- 라우팅·서버 렌더링이 기본 제공된다.
- 서버 런타임이 필요해 배포 대상이 정적 파일보다 무겁다.
- 서버 렌더링이 필요한 요구가 아직 없다.

## 선택: React

빌드 도구는 Vite를 쓴다.

**근거**

1. 기기 추천은 질문과 응답을 반복하는 흐름이라 화면 상태가 자주 바뀐다. 프로토타입에서 이 흐름을 직접 구현해 본 결과가 87KB의 수동 DOM 조작이었고, 이는 0010이 "감수한다"고 적은 항목이 실제로
   비용이 됨을 보여준다.
2. 백엔드가 이미 순수 REST API라 전환 비용이 낮다. 버릴 서버 렌더링 코드가 없다.
3. 서버 렌더링이 필요한 요구가 없으므로 Next.js의 런타임을 떠안을 이유가 없다. 정적 파일만 내보내면 배포 대상이 가볍다.

**버전: React 19.3.0 / Vite 8.3.0 / TypeScript 7.0.2**

TypeScript를 함께 쓴다. 백엔드 응답 형식이 6종이고 앞으로 늘어나므로, 나중에 전환하는 비용이 지금 설정하는 비용보다 크다.

## 감수하는 것

1. **동일 오리진이 더 이상 공짜가 아니다**

   0010의 근거 2번("CORS 설정이 발생하지 않는다")이 무효가 된다. 프론트엔드가 API를 상대 경로로 호출하므로, 프론트엔드를 서빙하는 쪽이 `/api`와 `/actuator`를 백엔드로 넘겨야 한다.

   대응: 넘기지 못하는 구성으로 가게 되면 백엔드에 CORS 설정을 추가한다. 프론트엔드 코드는 `VITE_API_BASE_URL` 하나로 양쪽을 모두 지원한다.

2. **배포 대상이 둘이 된다**

   프론트엔드를 별도 인스턴스에 올리면 EC2·CodeBuild·CodePipeline·타깃 그룹·보안 그룹 규칙이 환경마다 따라붙는다. 배포 실패 지점도 둘이 된다.

   대응: 토폴로지는 인프라 담당자와 합의한 뒤 별도 ADR로 남긴다. 이 문서는 구현 방식만 정한다.

3. **팀의 프론트엔드 경험 부족은 그대로다**

   0010이 적은 이 조건은 달라지지 않았다. 학습 비용은 여전히 든다. 다만 그 비용을 Thymeleaf + 수동 JavaScript 쪽에서 이미 치르고 있었다는 것이 프로토타입에서 확인됐다.

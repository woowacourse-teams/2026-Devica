# 53. 성능 테스트의 용량을 예상 트래픽의 몇 배까지 성능 기준을 지키는지로 잰다

- 상태: Accepted
- 날짜: 2026-11-07

## 상황 (조건)

- 성능 테스트는 예상 트래픽에서 성능 기준을 만족하는지 확인하고, 결과는 개선 전후를 비교하는 데 쓴다([0040](0040-성능-테스트-판정-기준.md)). 
- 예상 트래픽은 홍보글이 노출된 직후 10분이고, 첫 2분에 평균의 3배(피크 약 19.5 RPS)가 몰리는 모양이다([0042](0042-성능-테스트-예상-트래픽.md)).
- 예상 트래픽은 실측이 아니라 추정한 값이다. 홍보글 한 건이 잘 됐을 때를 기준으로 조회 수와 몰리는 시간을 가정했고, 여러 채널에 동시에 올리는 경우는 반영하지 않았다([0042](0042-성능-테스트-예상-트래픽.md) 감수 항목 1, 2).
- 앱 서버는 환경마다 한 대이고, 트래픽에 따라 서버를 자동으로 늘리지 않는다([0043](0043-제품-목록-최저가-사전-계산.md)).
- 측정은 개발 서버에서 하므로([0041](0041-성능-테스트-측정-범위.md)), 측정하는 동안 개발 서버를 다른 일에 쓸 수 없다.

## 고려한 대안

**1. 예상 트래픽의 부하 테스트로 끝낸다**

- 이미 정해진 절차 하나로 측정이 끝난다.
- 예상 트래픽에서의 결과만 알 수 있다.

**2. 목표 배수를 정해, 그 부하에서 통과·실패로 판정한다**

- 결과가 통과·실패로 나와 판단하기 쉽다.
- 목표 배수를 정할 근거가 따로 필요하다.

**3. 배수를 2배씩 올린다 (2 → 4 → 6 → 8)**

- 적은 단계로 넓은 범위를 볼 수 있다.
- 용량이 낮으면 첫 단계에서 기준을 넘어, 용량을 "2배 미만"으로밖에 말하지 못한다.

**4. 다음 홍보 때 실제 유입을 재서 예상 트래픽을 고친다**

- 추정 대신 실측으로 예상 트래픽을 정할 수 있다.
- 실측할 기회가 생길 때까지 기다려야 하고, 잰 값도 그 한 번의 결과다.

**5. 미리 재지 않고, 모니터링과 알림으로 트래픽이 몰릴 때 대응한다**

- 측정 없이 실제 트래픽에 맞춰 대응할 수 있다.
- 알림을 받고 대응하는 사이에는 성능이 떨어진 채로 서비스된다.

## 선택: 예상 트래픽의 부하를 배수로 키워 배수마다 1회 재고, 기준을 지키는 가장 큰 배수를 용량으로 본다

확장성(사용자와 데이터가 늘어도 같은 성능을 지키는가) 중 트래픽이 늘어나는 경우만 다룬다. 데이터는 성능 테스트 데이터 그대로 두고, 데이터가 늘어나는 경우는 다루지 않는다.

| 구분    | 내용                                                          |
|-------|-------------------------------------------------------------|
| 부하    | 예상 트래픽의 부하 모양(워밍업 1분 → 피크 2분 → 꼬리 8분)을 `LOAD_SCALE` 배수로 키운다 |
| 단계    | 1.5 → 2 → 3 → 4배. 기준이 처음 깨지면 멈추고, 필요하면 직전 배수와의 사이를 1회 더 잰다  |
| 판정    | 배수마다 1회. 기준은 0040과 같다(서버 처리 시간 p95 200ms 이하, 오류율 1% 이하)     |
| 무효 조건 | 0040과 같다. 다만 `dropped_iterations`는 무효가 아니라 기준을 지키지 못한 것으로 본다. 서버가 느려져 세션이 밀린 결과다 |
| 용량    | 기준을 지킨 가장 큰 배수. 피크 RPS(약 19.5 × 배수)로 함께 적는다                 |
| 함께 기록 | k6 p95, 앱 CPU, 커넥션 대기, RDS CPU. 무엇이 먼저 차는지 남긴다              |

**근거**

1. 성능 기준 통과는 추정한 트래픽에서만 확인한 결과라, 추정보다 트래픽이 늘었을 때 같은 성능을 지키는지는 따로 재야 한다. 예상 트래픽과 같은 모양으로 키우면 용량을 "추정이 몇 배까지 틀려도 버티는가"로 읽을 수 있고, 개선 전후도 같은 요청 분포에서 비교할 수 있다.
2. 데이터가 늘어나는 경우는 다루지 않는다. 불확실한 것은 트래픽 추정이고, 성능 테스트 데이터의 규모는 시중에 판매 중인 노트북 상품 수로 정해 두었다([성능 테스트 데이터](../../performance/data/README.md)).
3. 실측(대안 4)과 운영 중 대응(대안 5)으로는 대신하지 않는다. 실측은 다음 홍보까지 기다려야 하고 그 한 번의 값만 알려 준다. 운영 중 대응은 서버를 자동으로 늘릴 수 없어 사람이 대응해야 하는데, 홍보 피크는 10분이라 대응하기 전에 지나간다.
4. 목표 배수는 정하지 않는다. 예상 트래픽이 이미 추정이라 목표 배수도 추정 위에 세울 수밖에 없다. 대신 용량을 "몇 배"로 남기고, 개선이 필요한지는 용량과 함께 그때의 홍보 계획(채널 수 등)을 보고 판단한다.
5. 단계는 1.5배부터 촘촘히 올린다. 알고 싶은 것은 추정이 몇 배까지 틀려도 버티는가라서 예상 트래픽 근처가 중요하다. 2026-11-07 첫 측정에서 2배씩 올렸을 때는 첫 단계에서 기준을 넘었다.
6. 배수마다 1회로 판정한다. 2026-11-07 예상 트래픽 3회의 서버 처리 시간 p95는 120~130ms로, 회차 간 흔들림(10ms)이 기준과의 거리보다 작았다. 배수마다 3회씩 재면 단계마다 약 36분이 걸려, 그동안 개발 서버를 쓸 수 없다. 기준에 가까운 배수만 다시 잰다(감수 항목 2).
7. 기준이 깨지면 더 높은 배수로 가지 않는다. 측정하는 동안 개발 서버를 다른 일에 쓸 수 없어, 필요 이상으로 길게 부하를 걸지 않는다.

## 감수하는 것

1. **서버 처리 시간이 실제보다 작게 나올 수 있다**

   요청 로그의 처리 시간은 Tomcat 스레드를 기다린 시간을 빼고 잰다([0040](0040-성능-테스트-판정-기준.md) 감수 항목 3). 부하가 커질수록 이 시간이 늘어 용량을 실제보다 크게 볼 수 있다. 2026-11-07 측정에서는 k6 p95와 서버 처리 시간 p95의 차이가 1배 약 50ms, 1.6배 40ms, 2배 43ms로 벌어지지 않았다.

   대응: 배수별로 두 값의 차이를 기록한다. 차이가 1배일 때의 2배를 넘으면 그 배수는 기준을 지키지 못한 것으로 본다.

2. **기준에 가까운 배수는 1회로 판정이 바뀔 수 있다**

   2026-11-07 측정에서 1.6배의 서버 처리 시간 p95는 187ms로 기준에 가까웠다. 1회 값이라 다시 재면 기준을 넘을 수도 있다.

   대응: 서버 처리 시간 p95가 기준의 ±10%(180~220ms) 안이면 그 배수를 2회 더 재 3회 중앙값으로 판정한다.

3. **용량 근처의 정확한 값은 모른다**

   단계 사이를 재지 않으므로 용량은 "2배 이상 3배 미만"처럼 범위로 나온다.

   대응: 범위를 좁혀야 하면 사이 배수를 더 잰다.

4. **부하 발생기가 먼저 한계에 닿을 수 있다**

   부하는 팀원 노트북에서 건다([0041](0041-성능-테스트-측정-범위.md)). 노트북이 먼저 한계에 닿으면 k6 응답 시간이 늘고 `dropped_iterations`가 생겨, 서버의 한계로 잘못 볼 수 있다. 2026-11-07 측정에서는 2배까지 k6의 CPU 사용률이 최대 4.5%였다.

   대응: k6를 실행한 컴퓨터의 CPU 사용률을 함께 기록한다. 80% 이상이었던 배수의 결과는 서버의 한계로 보지 않는다.

5. **데이터가 늘면 용량이 달라질 수 있다**

   용량은 성능 테스트 데이터의 규모에서 잰 값이다. 판매 상품이 늘면 같은 요청에도 DB가 읽는 노트북이 늘어 용량이 줄 수 있다.

   대응: 시중 상품 수가 늘어 성능 테스트 데이터의 규모를 바꾸면 용량을 다시 잰다.

6. **개선이 필요한지에 대한 판단이 사람마다 다를 수 있다**

   목표 배수가 없어, 같은 용량을 두고도 충분한지에 대한 판단이 갈릴 수 있다.

   대응: 개선을 제안할 때 용량과 함께 판단의 근거로 삼은 홍보 계획을 이슈에 적는다.

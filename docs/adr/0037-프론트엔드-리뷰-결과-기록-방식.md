# 37. 프론트엔드 리뷰 결과를 커밋 트레일러로 남긴다

- 상태: Accepted
- 날짜: 2026-10-02

## 상황 (조건)

- [ADR 0029](0029-프론트엔드-하네스.md)에 따라 `frontend/`를 바꾸면 에이전트가 리뷰 결과를 남기고, pre-push 훅과 CI가 그 결과가 올라가는 코드에 대한 것인지 확인한다.
- 리뷰 결과는 브랜치마다 `.review/<브랜치>.md` 파일 하나로 남았고, PR이 머지된 뒤에도 develop에 그대로 남는다. 2026-10-02 기준 17개가 쌓였다.
- 머지된 뒤에는 이 파일을 검사에 쓰지 않는다.
- 검사에 쓰는 값은 `frontend/` diff 해시, 기준 브랜치, 필수 항목이 모두 끝났는지 세 가지다.
- diff 해시는 `frontend/` 아래 코드로만 계산한다.
- CI는 GitHub Actions에서 돌고, 저장소의 git 이력만 읽어 검사한다.

## 고려한 대안

**1. 리뷰 결과를 파일로 계속 남긴다**

- 지적 목록과 상태, 기각 근거가 저장소에 남아 나중에 확인할 수 있다.
- PR 수만큼 develop에 파일이 쌓인다.

**2. PR이 머지되면 develop에서 그 브랜치의 기록을 지운다 ([#122](https://github.com/woowacourse-teams/2026-Devica/issues/122))**

- 진행 중인 브랜치의 기록과 검사에는 영향이 없다.
- PR이 머지될 때마다 정리용 커밋이 develop에 남는다.
- 지우는 워크플로에 develop에 쓸 권한을 줘야 한다.

**3. 검사를 통과하면 CI가 PR 브랜치에서 기록을 지운다**

- 기록이 develop에 들어가지 않는다.
- CI가 작업 중인 브랜치에 커밋을 올려, 작성자와 그 위에 쌓인 PR이 매번 원격 브랜치를 받아 맞춰야 한다.
- 기록을 지운 뒤에는 브랜치에 기록이 없어, 이후 push는 `frontend/`를 고치지 않았어도 검사에 막힌다.

## 선택: 리뷰 결과를 커밋 트레일러로 남긴다

리뷰를 마친 뒤 코드를 커밋할 때 아래 트레일러를 붙인다. `unresolved`는 해결도 기각도 하지 않은 필수 항목 수다. `frontend/`에 변경이 없으면 지금처럼 검사하지 않는다.

```
Frontend-Review: hash=<diff 해시> base=<기준 브랜치> unresolved=<미해결 필수 항목 수>
```

**근거**

1. 리뷰 결과가 파일이 아니라 커밋 메시지에 남아, develop에 기록 파일이 쌓이지 않고 정리용 커밋도 생기지 않는다.
2. 커밋 메시지는 diff 해시에 들어가지 않아, 해시를 계산한 뒤 트레일러를 붙여도 값이 그대로다. 리뷰 뒤에 코드가 바뀌면 막는 기존 검사를 그대로 쓸 수 있다.
3. 트레일러는 git 이력에 있어, pre-push 훅과 CI가 같은 스크립트로 읽을 수 있다.
4. 검사에 쓰는 세 가지 값을 한 줄에 담을 수 있다.

## 감수하는 것

1. **리뷰 내용이 저장소에 남지 않는다**

   어떤 지적이 나왔고 왜 기각했는지를 나중에 저장소에서 확인할 수 없다.

   대응: 에이전트가 리뷰를 마칠 때 지적 목록과 상태, 기각 근거를 작성자에게 보고한다. 사람의 PR 리뷰는 그대로 한다.

2. **필수 항목이 끝났는지를 숫자로만 확인한다**

   파일로 남길 때는 항목마다 상태와 기각 근거가 적혔는지 검사했다. 이제는 에이전트가 센 `unresolved` 값만 확인한다.

   대응: 에이전트가 보고한 지적 목록과 `unresolved` 값이 맞는지 작성자가 확인한다.

3. **커밋할 때 트레일러를 직접 붙여야 한다**

   빠뜨리면 push가 막힌다.

   대응: 에이전트가 리뷰를 마칠 때 붙일 트레일러와 명령을 안내한다. 이미 커밋했다면 `git commit --amend`로 붙이고, push한 뒤라면 빈 커밋(`--allow-empty`)에 붙인다. 트레일러는 브랜치의 어느 커밋에 있어도 된다.

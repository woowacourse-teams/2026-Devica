# 8. 테스트 DB로 운영과 동일한 MySQL 컨테이너를 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- JPA를 사용하므로, 생성되는 쿼리가 의도대로 동작하는지 테스트로 확인해야 한다.
- 운영 DB는 MySQL 8.4다.
- 스키마는 JPA의 DDL 자동 생성으로 관리하므로, 테스트 DB의 종류와 무관하게 스키마 구성에는 추가 작업이 필요 없다.
- 이미 Docker/Compose로 DB 컨테이너를 띄우고 있어, 컨테이너를 하나 더 추가하는 비용이 낮다.

## 고려한 대안

**1. H2 인메모리 DB**

- 컨테이너 없이 동작해 세팅이 간단하고, 테스트 실행 속도가 매우 빠르다.
- MySQL과 SQL 문법·타입·제약 동작이 달라, H2에서 통과한 쿼리가 운영에서 깨질 수 있다.
- MySQL 전용 함수, `ON DUPLICATE KEY UPDATE`, 인덱스 힌트 등을 사용하면 그 부분은 검증할 수 없다.

**2. Testcontainers**

- 테스트 코드가 실행 시점에 운영과 같은 이미지로 컨테이너를 띄우므로, 환경 일치와 테스트 간 격리가 모두 보장된다.
- CI 환경에서 별도 설정이 거의 필요 없다.
- 컨테이너 기동에 회당 8~15초가 소요된다.
- 팀이 사용해본 적 없는 도구라 개념을 익히는 시간이 필요하다.

## 선택: 운영과 동일한 MySQL 8.4 컨테이너 (별도 포트 3307)

**근거**

1. 테스트의 목적은 운영에서 실제로 동작할지를 검증하는 것인데, DBMS가 다르면 그 검증이 성립하지 않는다. 통과하지만 신뢰할 수 없는 테스트는 없느니만 못하다.
2. 이미 Compose로 DB 컨테이너를 관리하고 있어, 테스트용 컨테이너를 하나 더 추가하는 비용이 거의 없다. H2의 이점인 세팅의 간편함이 우리 조건에서는 큰 차이를 만들지 않는다.
3. Testcontainers는 기술적으로 현재 선택보다 낫다. 다만 팀이 아직 겪지 않은 문제를 미리 해결하는 도구이고, 회당 기동 시간과 학습 비용이 지금으로서는 더 크다고 판단해 보류했다.

**Testcontainers 도입 조건**

아래 중 하나라도 발생하면 도입한다. 쓰지 않겠다는 뜻이 아니라, 문제를 먼저 겪고 나서 도입하겠다는 뜻이다.

- 테스트 순서에 따라 결과가 달라지는 일이 반복될 때
- CI 구축 시 테스트 DB 설정을 이중으로 관리하는 부담이 실제로 느껴질 때

전환하게 되면 그 과정(어떤 문제를 겪었고 → 무엇을 근거로 → 무엇을 바꿨고 → 결과가 어땠는지)을 남긴다.

## 감수하는 것

1. **테스트 간 데이터 격리가 보장되지 않는다**

   `@Transactional`로 롤백되지 않는 통합 테스트(`webEnvironment = RANDOM_PORT`)에서는 데이터가 남는다.

   대응: 문제가 발생하면 테이블 초기화 유틸을 만든다.

2. **CI 설정이 이중화된다**

   CI를 붙일 때 `docker-compose.yml`과 별개로 CI용 서비스 컨테이너를 정의해야 한다. 그 결과 테스트 DB 포트가 세 곳에 존재하게 된다.

   | 파일 | 내용 |
      |---|---|
   | `src/test/resources/application.yml` | `TEST_DB_PORT` 기본값 |
   | `docker-compose.yml` | `mysql-test` 포트 매핑 |
   | `.github/workflows/ci.yml` | service container 포트 매핑 |

   포트를 변경하려면 세 곳을 함께 고쳐야 한다. 하나만 고치면 CI에서만 실패하는데, 오류 메시지가 아래 3번과 같은 `Communications link failure`라 원인을 구분하기 어렵다.

3. **컨테이너를 실행하지 않으면 테스트가 실패한다**

   실패 메시지가 `Communications link failure`라, 처음 마주하면 원인을 짐작하기 어렵다.

   대응: 트러블슈팅 문서에 기록해두었다.****

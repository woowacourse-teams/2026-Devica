# 16. HTTPS 처리를 ALB에 맡긴다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 사용자를 유입시키려면 TLS 기반 HTTPS가 필수이므로, 인증서를 발급하고 갱신할 주체가 필요하다.
- 인증서 갱신 실패는 곧 서비스 접속 불가다.
- 지금은 EC2 한 대지만, 무중단 배포로 가려면 트래픽을 옮겨줄 지점이 필요하다. 인프라를 구성하는 지금 함께 넣는 편이 낫다고 판단했다.
- 팀에 인프라를 상시 관리할 시간이 없다.

## 고려한 대안

**1. Nginx 컨테이너**

- EC2 안에서 실행되므로 별도 인프라 비용이 없다.
- 라우팅 커스터마이징의 자유도가 높다.
- Certbot 설정과 갱신을 직접 구성해야 한다.
- 무중단 배포용 설정 파일도 서버 안에서 직접 관리하게 된다.

## 선택: ALB (인증서는 ACM)

ALB가 `:443`에서 TLS를 종료하고 EC2의 `:80`으로 전달한다. **운영 서버에만 적용한다** — 개발 서버는 ALB를 거치지 않는다([0017](0017-서버-환경-분리.md)).

**근거**

1. ACM이 인증서를 발급하고 자동으로 갱신한다. 갱신 실패가 곧 접속 불가인 상황에서, 그 실패 가능성을 EC2 내부의 수동 관리 대상으로 남기지 않는다. 관리 포인트를 늘리는 대신 비용을 지불하기로 했다.
2. TLS를 ALB가 종료하므로 인증서와 키를 서버에 두지 않는다.
3. 나중에 인스턴스를 늘릴 때 타깃 그룹 전환 지점이 이미 있다. Nginx라면 그 시점에 설정을 새로 구성해야 한다.

## 감수하는 것

1. **트래픽이 없어도 시간당 과금이 발생한다**

   Nginx를 택했다면 들지 않았을 고정 비용이다. 검증 단계의 서비스라 트래픽 대비 비용 효율은 좋지 않다.

2. **세밀한 라우팅 제어가 제한적이다**

   대응: 필요해지는 시점에 Nginx를 앞단에 두는 구성을 다시 검토한다.

3. **지금은 무중단 배포에 쓰이지 않는다**

   인스턴스가 하나라 배포 그룹에 로드 밸런서를 연동하지 않았다([0014](0014-CD-파이프라인.md)). 도입 근거 중 하나였던 무중단 전환은 인스턴스를 늘리기 전까지 확보되지 않는다.

4. **개발 서버는 HTTPS가 아니다**

   ALB를 운영에만 두었으므로 개발 서버는 `http`로 접속한다. TLS가 필요한 동작은 개발 서버에서 검증할 수 없고, 운영에 올린 뒤에야 확인된다. 타깃 그룹 `dev-tg`가 만들어져 있으나 라우팅에 쓰이지 않는다.

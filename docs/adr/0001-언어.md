# 1. 언어로 Java 21을 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 팀원 전원이 Java/Spring으로 서비스를 개발하고 배포해본 경험이 있다.
- 프론트엔드 담당자가 따로 없어, 팀원 각자가 백엔드와 프론트엔드를 모두 담당해야 한다.
- MVP까지 약 1개월이며, 이 기간 안에 실사용자를 확보해 가설을 검증해야 한다.
- 따라서 기술 학습에 쓰는 시간은 곧 검증에 쓸 시간을 줄이는 비용이 된다.

## 고려한 대안

**1. Node.js**

- 백엔드와 프론트엔드를 동일한 언어로 개발할 수 있어, 두 영역을 겸하는 팀에서 컨텍스트 스위칭 비용이 낮다.
- 컴파일 단계가 없어 빌드 및 실행 속도가 빠르다.
- 팀원 누구도 실무 경험이 없어, 학습과 시행착오에 시간이 든다.

## 선택: Java 21 (LTS)

**근거**

1. 프론트엔드는 어떤 언어를 택하든 팀에 익숙하지 않아 학습이 필요하다. 반면 Node.js를 택하면 백엔드까지 미숙한 영역이 되어 학습 범위가 두 배가 된다. 1개월이라는 기간에서는 컨텍스트 스위칭 비용보다 학습 비용이 더 크다고 판단했다.
2. 컨텍스트 스위칭 비용은 기간 전체에 분산되고 숙련될수록 줄어드는 반면, 학습 비용은 초반에 집중되어 검증 사이클의 시작 자체를 늦춘다.
3. 익숙한 영역에서는 AI가 생성한 코드를 검토하고 판단할 수 있지만, 미숙한 영역에서는 그대로 받아들이게 된다. 백엔드를 익숙한 스택으로 유지하면 최소한 서버 로직만큼은 팀이 직접 통제할 수 있고, 문제 발생 시 원인 파악도 가능하다.

**버전: 21 (LTS)**

Spring Boot 4.1은 Java 17~26을 지원한다. 이 중 비-LTS 버전은 6개월 주기로 지원이 끊겨 라이브러리와 도구 생태계의 대응이 늦으므로, LTS인 17·21·25만 후보로 뒀다.

21에서만 지원하는 기능을 쓸 계획이 있는 것은 아니지만, 17과 생태계 안정성이 비슷한 이상 더 최신인 21을 택하지 않을 이유가 없다고 판단했다. 25는 호환성 사례가 아직 충분히 축적되지 않아 제외했다.

## 감수하는 것

1. **백엔드와 프론트엔드 간 컨텍스트 스위칭 비용**

   팀원 전원이 두 영역을 겸하므로, 언어가 다른 데서 오는 작업 전환 비용이 프로젝트 기간 내내 발생한다.

   대응: 작업을 기능 단위로 나누어, 한 사람이 한 기능의 백엔드와 프론트엔드를 함께 맡도록 했다. 언어 전환은 여전히 발생하지만 같은 기능 안에서 이루어지므로, 도메인 맥락은 유지된다.

# 38. dev·prod DB를 MySQL 컨테이너에서 RDS로 옮긴다

- 상태: Accepted
- 날짜: 2026-10-07

## 상황 (조건)

- dev·prod 모두 DB가 EC2 안의 MySQL 컨테이너다.
- 데이터가 Docker 볼륨 하나에만 있고, 백업이 없다.
- 운영 DB에 사용자가 질문 게시판에 남긴 글과 댓글이 쌓인다. 사용자가 직접 쓴 내용이라 다시 만들어낼 수 없다.
- 1명이 서버 구성과 유지보수를 맡는다.
- dev·prod 애플리케이션 서버 모두 가용 메모리가 500~600MiB밖에 없다.
- AWS 인프라 비용은 지원된다.
- 스키마는 Flyway로 관리하므로([0028](0028-DB-스키마-마이그레이션-관리.md)), DB를 옮겨도 마이그레이션 이력만 함께 옮기면 이어서 적용할 수 있다.

## 고려한 대안

**1. 컨테이너를 유지하고 `mysqldump`로 주기 백업**

- 지금 구성을 그대로 두고 덤프 파일을 S3에 올리므로 추가 비용이 거의 없다.
- 백업 스크립트, 실행 주기, 보관 정리, 복구 절차를 직접 만들고 유지보수까지 해야 한다.
- 덤프 사이에 쌓인 데이터는 복구할 수 없다.

## 선택: RDS for MySQL 8.4, db.t4g.micro 단일 AZ

dev·prod에 같은 구성으로 하나씩 둔다. 자동 백업을 켜고, 퍼블릭 접근을 막아 VPC 안에서만 접속하게 한다. 보안 그룹은 공용 계정 규칙에 따라 팀 공용인 `project-db`를 쓰므로, 환경 구분은 환경별 계정·비밀번호가 맡는다. 앱은 마스터 계정이 아니라 해당 DB 권한만 가진 앱 전용 계정으로 접속한다.

**근거**

1. 자동 백업과 시점 복구를 RDS가 맡아, 백업 스크립트와 복구 절차를 직접 만들고 유지보수하지 않아도 된다. AWS 비용이 지원되므로 대안의 비용 이점은 판단을 바꾸지 않는다.
2. DB와 애플리케이션 서버의 생명 주기가 분리되어, 앱 서버를 다시 만들거나 서버에 장애가 나도 DB 데이터가 남는다.
3. DB가 EC2에서 빠지면서, 가용 메모리가 부족하던 서버를 앱과 수집기만 나눠 쓰게 된다.
4. dev도 같은 구성으로 옮겨, prod 전환 전에 연결 설정과 이관 절차를 dev에서 먼저 확인한다.

**사양: db.t4g.micro, 단일 AZ**

지금 트래픽은 작은 인스턴스로 충분하고, AZ 장애는 자동 백업으로 복구하는 것으로 감수한다. Multi-AZ는 비용이 약 두 배라 트래픽이나 가용성 요구가 커질 때 다시 판단한다.

## 감수하는 것

1. **AZ 장애와 유지 관리 중에 DB가 멈춘다**

   인스턴스가 하나뿐이라, 그 인스턴스가 있는 가용 영역(AZ)에 장애가 나면 복구될 때까지 기다리거나 자동 백업으로 다른 AZ에 새 인스턴스를 복원해야 한다. 복원한 인스턴스는 엔드포인트가 달라 `DB_HOST`도 바꿔야 한다. RDS가 유지 관리 기간에 엔진 패치를 적용할 때도 인스턴스가 재시작되어 몇 분간 접속이 끊긴다.

   대응: 유지 관리 기간을 트래픽이 적은 시간대로 지정한다.

2. **DB 로그와 상태가 대시보드에서 빠진다**

   [0036](0036-로그-수집-방식.md)은 DB 오류 로그를 EC2의 전용 디렉터리에 남기고 Alloy가 읽게 했다. RDS에서는 이 파일이 EC2에 없어 Alloy가 읽을 수 없고, DB 디스크도 호스트 지표에 잡히지 않는다.

   대응: RDS 상태를 감시하는 방법은 #183에서 정한다. 그 전까지는 RDS 콘솔에서 확인한다.

3. **로컬·테스트 DB와 배포 DB의 실행 방식이 달라진다**

   로컬과 테스트는 MySQL 컨테이너를 그대로 쓴다([0007](0007-컨테이너-적용-범위.md), [0008](0008-테스트-데이터베이스.md)).

   대응: RDS의 MySQL 버전·문자셋·시간대를 컨테이너와 같게 맞춘다.

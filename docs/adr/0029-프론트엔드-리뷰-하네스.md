# 29. 프론트엔드 리뷰를 에이전트 Skill 로 수행하고 Git 훅과 CI 로 강제한다

- 상태: Accepted
- 날짜: 2026-09-23

## 상황 (조건)

- 팀원마다 쓰는 코딩 에이전트가 다르다. Claude Code 와 Codex 를 함께 쓴다.
- 에이전트는 각자의 개인 구독 계정으로 쓴다. 팀 공용 계정이나 API 키는 없고, 별도 API 비용을 쓰지 않는다.
- 프론트엔드 PR 리뷰에서 같은 종류의 문제가 반복해서 지적된다. PR #97 의 리뷰 지적 8건 중 7건이 비동기 요청 처리와 화면 상태 관리 문제였다.
- 에이전트마다 리뷰에서 지적하는 내용이 달라 팀 공통 기준이 없다. AI 리뷰 결과를 사람이 옮겨 반영하는 일이 반복된다.
- 기획과 기술 스택이 자주 바뀐다. V0 에서 V1 으로 유스케이스가 바뀌었고, 프론트엔드는 Thymeleaf 에서 React 로 바뀌었다([0025](0025-프론트엔드-구현-방식-변경.md)).
- 프론트엔드와 백엔드가 한 저장소에 있고, 백엔드만 다루는 팀원도 있다.
- CI 는 GitHub Actions 를 쓴다([0013](0013-CI-도구.md)).

## 고려한 대안

**1. 에이전트 프레임워크로 팀 공용 리뷰 에이전트 구축 (VoltAgent 등)**

- 리뷰 흐름을 에이전트 그래프로 코드에 고정할 수 있다.
- 여러 회사의 모델을 섞어 쓸 수 있다.
- 외부 프레임워크는 구독 계정으로 모델을 호출할 수 없어 API 키와 사용량 비용이 필요하다.

**2. 로컬 모델로 리뷰 (Ollama 등)**

- 비용이 들지 않고, 1번의 구조를 그대로 쓸 수 있다.
- 개인 PC 에서 돌릴 수 있는 크기의 모델은 리뷰 품질과 도구 호출 정확도가 떨어진다.
- 결과가 나쁠 때 모델의 한계인지 규칙 설계의 문제인지 구분하기 어렵다.

**3. CI 에서 LLM 리뷰 실행**

- PR 마다 사람 손을 거치지 않고 리뷰가 돈다.
- 공용 서버라 인증 정보를 저장소 시크릿에 넣어야 한다. API 키(비용)나 특정 개인의 구독 토큰이 필요하다.
- LLM 결과는 실행마다 달라, 통과 조건으로 쓰면 같은 코드가 통과와 차단을 오간다.

**4. Git 훅에서 LLM 리뷰 실행**

- 로컬에서 각자의 계정으로 돌 수 있다.
- pre-push 에서 돌면 리뷰가 너무 늦고, 훅은 대화형이 아니라 지적 사항을 사람이 다시 에이전트에 옮겨야 한다.
- pre-commit 에서 돌면 너무 자주 실행되고, 커밋 단위가 리뷰 단위(PR)와 맞지 않는다.

## 선택: 에이전트 세션 안의 리뷰 Skill + Git 훅·CI 의 리뷰 기록 검사

LLM 리뷰는 각자의 에이전트 세션 안에서 `frontend-review` Skill 로 하고, Git 훅과 CI 는 "리뷰를 거쳤는가"만 LLM 없이 검사한다.

| 구성 | 역할 |
|---|---|
| `AGENTS.md` | 작업 흐름을 에이전트에 안내한다. Claude Code 는 `CLAUDE.md` 의 `@AGENTS.md` 로 같은 원본을 읽는다 |
| `docs/review-rules/*.md` | AI 판단이 필요한 리뷰 기준. 반복된 지적에서만 만든다 |
| `.agents/skills/frontend-review` | 규칙 파일마다 리뷰어를 병렬로 띄워 리뷰 → 반영 → 린트 → `.review/` 기록. Claude Code 쪽은 심볼릭 링크로 같은 원본을 쓴다 |
| Biome (`frontend/biome.json`) | 기계적으로 판정할 수 있는 기준. TypeScript 7 을 typescript-eslint 가 지원하지 않아 ESLint 대신 쓴다 |
| pre-commit | 스테이징된 `frontend/` 파일에 Biome 안전 수정과 타입 검사 |
| pre-push, CI | 리뷰 기록의 diff 해시가 PR base 와의 merge-base 대비 `frontend/` diff 와 같은지, 미해결 필수 지적이 없는지 검사 |

다시 검토할 조건:

- 팀 공용 API 예산이 생길 때. 1번이나 3번으로 흐름을 코드에 고정할 수 있다.
- 리뷰가 필수 규칙을 놓치는 일이 반복될 때. 리뷰어를 늘리거나 규칙을 린트로 옮긴다.

**근거**

1. 에이전트 세션 안에서 리뷰하므로 각자의 구독 계정으로 돌고 API 비용이 들지 않는다. 훅과 CI 에는 LLM 호출이 없어 인증 정보가 필요 없다.
2. 규칙·Skill·지침의 원본이 하나이고 Claude Code 쪽은 참조만 하므로, 팀원이 어느 에이전트를 써도 같은 기준으로 리뷰한다.
3. 규칙을 PR #97 처럼 반복된 지적에서만 만들고 기획·스택 내용을 넣지 않아, 요구사항이 바뀌어도 규칙이 낡지 않는다. 기계적인 기준은 린트로 옮겨 코드와 함께 관리된다.
4. 리뷰 결과를 에이전트가 같은 세션에서 바로 반영하므로, AI 리뷰를 사람이 옮기는 일이 없어진다.
5. 비싼 LLM 판단은 한 번, 결정적인 검사는 여러 번 한다. 같은 코드면 CI 결과가 항상 같다.
6. 검사 범위를 `frontend/` 로 한정해, 백엔드만 다루는 팀원과 백엔드 PR 에는 영향이 없다.

## 감수하는 것

1. **흐름을 완전히 강제하지는 못한다**

   에이전트가 Skill 을 쓰지 않거나 사람이 `--no-verify` 로 pre-push 를 건너뛸 수 있다. 검사가 보는 것은 "기록의 해시가 코드와 맞는가"이지, 리뷰가 실제로 충실했는지가 아니다.

   대응: CI 가 같은 검사를 다시 해 PR 단계에서 막는다. 리뷰 기록이 PR 에 남아 사람 리뷰에서 확인할 수 있다.

2. **리뷰 품질이 실행마다 다르다**

   같은 코드를 세 번 리뷰했을 때, 규칙에 명시된 패턴을 세 번째에서야 잡은 적이 있다(#110). 규칙이 다루지 않는 관점(화면 흐름 등)은 보지 못한다(#112).

   대응: 사람의 PR 리뷰는 그대로 둔다. 반복되는 지적은 규칙이나 린트로 옮긴다.

3. **리뷰 뒤에 코드를 고치면 다시 리뷰해야 한다**

   해시가 달라져 push 가 막힌다. 수정이 작아도 Skill 을 다시 돌려야 한다.

   대응: 의도된 동작이다. 린터 자동 수정은 Skill 이 기록 전에 먼저 돌려, 커밋할 때 코드가 바뀌어 해시가 어긋나지 않게 한다.

4. **훅은 `npm install` 을 해야 설치된다**

   `frontend/` 에서 `npm install` 을 하지 않은 사람에게는 pre-commit·pre-push 가 없다.

   대응: [프론트엔드 개발 환경 가이드](../프론트엔드_개발_환경_가이드.md)에 설치 절차를 적었다. 훅이 없어도 CI 가 막는다.

5. **작업 트리의 untracked 파일도 해시에 들어간다**

   새로 만든 파일을 리뷰에 포함하려는 동작이지만, 저장소 안에 의도하지 않은 파일이 생기면 리뷰 해시와 커밋 해시가 달라진다. iCloud 동기화 폴더에서 충돌 사본이 생겨 push 가 막힌 적이 있다(#118).

   대응: 저장소를 동기화되지 않는 위치에 둔다. 해시 불일치로 막히면 `git status` 로 의도하지 않은 파일부터 확인한다.

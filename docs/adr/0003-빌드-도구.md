# 3. 빌드 도구로 Gradle 9.5.1을 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 언어가 Java이므로 후보는 Gradle과 Maven으로 좁혀진다.
- 팀원 모두 두 도구를 사용해본 적은 있으나, AI나 문서의 도움을 받아 동작 원리를 이해하지 못한 채 사용했다. 두 도구 사이에 숙련도 차이는 없다.
- 인증/인가를 비롯해, 개발 과정에서 의존성을 추가할 일이 반복될 것으로 예상된다.
- 팀원의 로컬 OS가 혼재되어 있어, 각자 설치한 빌드 도구의 버전이 달라질 여지가 있다.

## 고려한 대안

**1. Maven**

- 구조가 정형화되어 있어 프로젝트마다 빌드 파일의 형태가 크게 다르지 않다.
- XML 기반이라 설정이 명시적이고, 문서·예제와 형태가 거의 일치한다.
- 유연성이 낮고 설정이 길어진다.

## 선택: Gradle 9.5.1

**근거**

1. 두 도구 모두 팀의 숙련도가 낮아 학습 비용에 차이가 없고, 의존성 추가는 공식 문서를 참고해 진행하므로 설정 방식의 차이도 실질적인 부담이 되지 않는다.
2. Gradle의 증분 빌드와 스크립트 확장성은 흔히 언급되는 장점이지만, 1개월 규모의 MVP에서는 체감되지 않는다고 판단했다.
3. 결국 이 프로젝트의 조건에서 두 도구를 가르는 결정적 차이는 없었다. 팀원 전원이 이전 미션을 Gradle 기반으로 진행해 빌드 스크립트의 형태에 익숙하므로, 익숙한 쪽을 유지하는 편이 합의 비용이 낮다고 판단했다.

**버전: 9.5.1 (Wrapper로 고정)**

후보로 둔 9.6.x, 9.5.1, 8.14.5는 모두 Spring Boot 4.1.0과 JDK 21을 지원하며, 빌드 스크립트 문법도 8.x와 9.x 간 차이가 거의 없어 참고 자료의 양에도 차이가 없다.

팀이 Gradle의 동작 원리를 깊이 이해하지 못한 상태이므로, 빌드 도구 자체에서 문제가 생기면 해결에 시간이 걸린다. 1개월이라는 기간에서 이는 검증 시간을 그대로 잠식한다. 따라서 최신 릴리스보다는 출시 이후 시간이 지나 알려진 이슈가 정리된 버전이 낫다고 보고 9.5.1을 골랐다.

Gradle Wrapper로 버전을 저장소에 포함시켜, 팀원의 로컬 설치 상태와 무관하게 같은 버전으로 빌드되도록 했다.

## 감수하는 것

없다. Maven의 장점인 정형화된 구조는 빌드 설정을 깊이 손댈 계획이 없는 이 프로젝트에서 실질적인 손실로 이어지지 않는다.

# 13. CI 도구로 GitHub Actions를 사용한다

- 상태: Accepted
- 날짜: 2026-08-13

## 상황 (조건)

- 저장소가 GitHub에 있고, 모든 변경은 `main`·`develop`으로 향하는 PR을 거친다.
- 빌드와 테스트를 각자 로컬에서 확인하는 방식에서는 컴파일되지 않는 코드가 통합 브랜치에 들어갈 수 있다. 배포 서버는 이 브랜치를 기준으로 빌드하므로, 통합 시점의 검증이 빠지면 곧 배포 실패가 된다.
- 테스트는 운영과 동일한 MySQL 8.4 컨테이너를 요구한다([0008](0008-테스트-데이터베이스.md)). CI 환경에도 같은 DB가 있어야 한다.
- 팀 AWS 계정은 액세스 키 발급이 막혀 있고, IAM 자격증명 공급자(OIDC)와 역할을 새로 만들 권한도 없다.
- 1개월이라는 기간에서 CI 인프라 자체를 운영하는 데 쓸 시간이 없다.

## 고려한 대안

**1. Jenkins**

- 플러그인이 많고 파이프라인 구성의 자유도가 높다.
- 빌드 서버를 따로 띄우고 직접 운영해야 한다. 서버 비용과 관리 대상이 늘어난다.

**2. AWS CodeBuild**

- CD를 AWS에서 구성한다면 빌드 도구를 하나로 통일할 수 있다.
- PR 이벤트와의 결합이 약하다. 검증 결과가 PR 화면에 표시되지 않아, 머지 전에 확인하도록 강제하기 어렵다.

## 선택: GitHub Actions

**근거**

1. 검증 대상이 PR이고 저장소가 GitHub에 있다. PR 이벤트에 직접 붙고 결과가 PR 화면에 체크로 나타나므로, 머지 전 검증이 협업 흐름 안에서 강제된다. 검증을 사람의 성실함에 의존하지 않게 만드는 것이 목적이므로 이 결합이 가장 중요하다.
2. service 컨테이너로 MySQL 8.4를 띄울 수 있어, 별도 인프라 없이 [0008](0008-테스트-데이터베이스.md)에서 정한 "운영과 같은 DBMS로 검증한다"를 그대로 지킨다.
3. 러너를 팀이 관리하지 않는다. Jenkins와 달리 빌드 서버 운영에 시간을 쓰지 않아도 된다.
4. CI는 AWS 리소스를 조작하지 않으므로, 액세스 키를 발급받을 수 없다는 제약이 걸리지 않는다. 같은 제약 때문에 CD는 다른 도구로 분리한다([0014](0014-CD-파이프라인.md)).

**트리거 범위: `main`·`develop`의 PR과 Push**

PR만으로 충분해 보이지만 Push도 포함했다. 머지 커밋 자체나 직접 푸시된 커밋은 PR 이벤트로 잡히지 않아, 통합된 결과물이 검증되지 않은 채 남는다.

## 감수하는 것

1. **CI와 CD의 설정이 서로 다른 곳에 나뉜다**

   CI는 저장소의 워크플로 파일에, CD는 AWS 콘솔과 spec 파일에 있다. 파이프라인 전체를 한 곳에서 볼 수 없고, 어느 단계가 무엇을 검증하는지 문서로 이어 붙여야 한다.

2. **테스트 DB 포트가 세 곳에 존재하게 된다**

   `src/test/resources/application.yml`, `docker-compose.yml`, `.github/workflows/ci.yml`의 값이 서로 맞아야 한다. [0008](0008-테스트-데이터베이스.md)에서 예상한 이중화가 실제로 발생했고, `buildspec.yml`의 `TEST_DB_PORT`까지 네 곳이 되었다.

3. **검증 단계가 `./gradlew build` 하나뿐이다**

   정적 분석, 커버리지 리포트, 알림 연동이 없다. 의도한 범위이며, 실제로 불편을 느낀 시점에 추가한다.

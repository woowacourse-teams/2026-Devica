# 34. 로그 저장소로 Grafana Cloud(관리형 Loki)를 사용한다

- 상태: Accepted
- 날짜: 2026-09-30

## 상황 (조건)

- 스프린트 1 기간 안에 1명이 구축하고 유지보수한다.
- 애플리케이션 서버는 dev·prod 각각 AWS t4g.small(메모리 2GiB)이다.
- AWS 인프라 비용은 지원된다.
- 알림은 Grafana Cloud에서 관리한다.
- 스프린트 2부터 부하 테스트를 진행한다.

## 고려한 대안

**1. Loki 자체 구축 (AWS)**

- 로그를 AWS 스토리지에 저장해 보관 기간을 직접 정할 수 있다.
- 로그 저장소를 애플리케이션과 다른 서버에서 운영하므로, 저장소의 자원 사용이 부하 테스트 결과에 영향을 주지 않는다.
- 로그 저장소용 서버의 보안 패치, 업그레이드, 장애 대응을 직접 맡아야 한다.

**2. Elasticsearch 계열 (Elasticsearch / OpenSearch)**

- 로그 필드를 인덱싱해 전문 검색과 분석이 강력하다.
- JVM 메모리 설정과 인덱스 관리 등 운영할 요소가 많아 유지보수 부담이 크다.

**3. ClickHouse 기반 (SigNoz, ClickStack 등)**

- 대용량 로그의 압축과 집계가 강하다.
- 여러 컨테이너로 구성되어 유지보수 부담이 크고, 현재 규모에서는 강점이 드러나지 않는다.

**4. Graylog (Graylog Open)**

- 수집·검색·알림을 하나의 UI로 제공한다.
- MongoDB와 Data Node(OpenSearch)까지 함께 운영해야 해 유지보수 부담이 크다.

## 선택: Grafana Cloud 무료 플랜 (관리형 Loki)

dev·prod 로그를 하나의 스택에 모으고, `env` 레이블로 구분한다.

**근거**

1. 저장소 운영을 Grafana Labs가 맡아, 로그 저장소용 서버를 따로 유지보수할 필요가 없다.
2. 저장소가 애플리케이션 서버 밖에 있어, 저장소의 자원 사용이 부하 테스트 결과에 영향을 주지 않는다. 서버에서 실행하는 수집기의 부하는 별도로 확인한다.
3. 무료 한도(월 50GB 수집) 안에서 운용할 수 있을 것으로 예상한다. 1,000 RPS로 1시간 부하 테스트를 하면 약 5GB로 추정한다. 이는 요청당 평균 약 1.4KB의 로그를 가정한 값이며, 실제 수집량과 테스트 횟수, 평상시 dev·prod 로그를 합쳐 한도를 확인한다.
4. 알림을 관리하는 Grafana에서 로그를 함께 조회할 수 있다.
5. 내부가 Loki라, 자체 구축으로 옮겨도 LogQL 쿼리와 수집 파이프라인을 재사용할 수 있다. 전송 주소와 인증 설정은 변경한다.

## 감수하는 것

1. **14일이 지난 로그는 조회할 수 없다**

   무료 플랜의 보관 기간이 14일이다.

   대응: 장기 통계는 메트릭이나 DB로 집계한다. 원본 장기 보관이 필요해지면 수집기에서 AWS 스토리지로 사본을 함께 보낸다.

2. **전문 검색이 약하다**

   Loki는 본문을 인덱싱하지 않아, 넓은 범위를 검색하면 느리다.

   대응: 로그를 JSON 구조로 남긴다. 시간과 `env`·`app`으로 검색 범위를 좁힌 뒤 ECS의 `trace.id` 본문 필드로 요청을 찾는다([ADR 0033](0033-로그-형식.md)).

3. **레이블 설계를 잘못하면 느려진다**

   값이 다양한 필드를 레이블로 쓰면 로그 스트림이 급격히 늘어난다.

   대응: 레이블은 `env`, `app`처럼 값의 종류가 적은 필드로 제한하고, 나머지는 본문 필드로 남긴다.

4. **외부 서비스에 의존한다**

   Grafana Cloud 장애나 무료 정책 변경의 영향을 받는다.

   대응: AWS에 Loki를 자체 구축해 옮길 수 있다.

# 36. Alloy가 Docker 로그 파일을 직접 읽는다

- 상태: Proposed
- 날짜: 2026-10-01
- 관련 이슈: [#134](https://github.com/woowacourse-teams/2026-Devica/issues/134)

## 상황 (조건)

- dev·prod의 Docker는 컨테이너 표준 출력 로그를 호스트 파일에 저장한다. 
- 기존 Alloy는 일반 계정으로 실행되며, 추가 권한과 권한 상승이 차단되어 있다. 
- 기존 구성은 `docker.sock`과 호스트 루트 디렉터리를 마운트하지 않는다.
- 로그 디렉터리의 그룹 권한이 목록 조회를 허용하지 않는다.

## 고려한 대안

**1. Docker 소켓을 통한 수집**

- Docker API로 컨테이너를 발견하고 로그를 읽을 수 있어, 파일 탐색과 컨테이너 식별 설정이 간단하다.
- Docker가 제공하는 API를 사용하므로 로그 파일의 저장 경로에 의존하지 않는다.
- 수집기에 Docker 데몬 제어 권한이 생긴다. 수집기를 해킹되면 호스트 파일에 접근하거나 컨테이너를 실행해 서버 전체를 장악할 수 있다.

## 선택: capability를 모두 제거한 root 계정으로 Docker 로그 파일 직접 읽기

Alloy를 컨테이너 내부 root 계정으로 실행하고, Docker 로그 디렉터리를 읽기 전용으로 마운트한다. `cap_drop: [ALL]`과 `security_opt: ["no-new-privileges:true"]`를 유지한다. `docker.sock`, 호스트 루트 디렉터리, privileged 모드와 호스트 PID·네트워크 네임스페이스는 사용하지 않는다.

**근거**

1. Docker 데몬 제어 권한을 수집기에 부여하지 않고 로그를 읽을 수 있다.
2. dev·prod 모두 capability를 제거한 root 계정의 임시 컨테이너에서 로그 목록과 내용을 읽을 수 있다.
3. 로그 디렉터리를 읽기 전용으로 제공해, 수집기가 호스트 로그 파일을 변경하지 못하게 할 수 있다.
4. 기존 capability 제거와 권한 상승 차단 설정을 유지할 수 있다.

## 감수하는 것

1. **Alloy의 실행 계정을 일반 계정에서 root로 변경해야 한다**

   기존 일반 계정 실행 구조가 바뀐다. capability 제거와 읽기 전용 마운트를 적용해도, 침해된 수집기가 접근 가능한 로그·인증 정보를 유출하거나 네트워크와 쓰기 가능한 컨테이너 경로를 악용할 위험은 남는다.

   대응: 권한 제한을 유지하고 마운트 범위를 최소화한다. 적용 전에 모니터링 담당에게 실행 계정 변경과 검증 결과를 공유한다.

2. **Docker 로그 저장 구조에 의존한다**

   Docker 업데이트나 로깅 드라이버 변경으로 경로·형식이 달라지면 수집이 중단될 수 있다. 메트릭이 정상 수집되어도 로그만 끊길 수 있다.

   대응: Docker 설정 변경 후 dev에서 로그 수집을 확인하고 prod에 적용한다. 로그 수집 중단 알림을 추가한다. 정상적인 무로그 구간과 구분할 수 있도록 수집기 오류·전송 실패 지표나 주기적으로 발생하는 로그를 기준으로 감지 조건을 정한다.

3. **파일 탐색과 파싱 설정을 직접 관리한다**

   Docker 로그 파싱과 컨테이너 식별 설정이 필요하다. 컨테이너 재생성·로그 회전 후에도 수집이 이어지는지 확인해야 한다.

   대응: Docker 로그 파일의 최대 크기와 보관 개수를 설정하고, dev·prod에서 컨테이너 재생성·로그 회전 후 수집과 `env`·`app` 레이블을 검증한다.

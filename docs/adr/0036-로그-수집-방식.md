# 36. 앱·DB 로그를 전용 디렉터리에 저장하고 Alloy가 읽는다

- 상태: Accepted
- 날짜: 2026-10-01

## 상황 (조건)

- 앱·DB는 Docker 컨테이너로 실행되며, 환경변수로 DB 인증 정보를 전달받는다.
- Docker 로그 디렉터리에는 컨테이너 환경변수가 담긴 설정 파일도 있다.
- 기존 Alloy는 일반 계정으로 실행되며, 추가 권한과 권한 상승이 차단되어 있다.
- 기존 구성은 `docker.sock`과 호스트 루트 디렉터리를 마운트하지 않는다.

## 고려한 대안

**1. Docker 로그 디렉터리 직접 읽기**

- 앱·DB의 표준 출력 방식을 유지할 수 있다.
- 컨테이너 설정 파일까지 Alloy에 노출된다. 읽기 전용 설정은 인증 정보 유출을 막지 못한다.
- 로그 파일 하나만 마운트하면, 로그가 새 파일에 기록되기 시작했을 때 Alloy가 그 파일을 읽지 못한다.

**2. journald 수집**

- Docker 설정 파일을 노출하지 않고 컨테이너 표준 출력 로그를 수집할 수 있다.
- 공용 journal을 연결하면 다른 시스템 로그도 읽을 수 있다. 수집 필터는 파일 접근 권한을 제한하지 않는다.
- 시스템 로그와 보관 용량을 공유하며, 발생량 제한과 서버 설정을 추가로 관리해야 한다.

**3. Docker 소켓을 통한 수집**

- Docker API로 컨테이너를 발견하고 로그를 읽을 수 있어, 파일 탐색과 컨테이너 식별 설정이 간단하다.
- Docker가 제공하는 API를 사용하므로 로그 파일의 저장 경로에 의존하지 않는다.
- 수집기에 Docker 데몬 제어 권한이 생긴다. 수집기가 해킹되면 호스트 파일에 접근하거나 컨테이너를 실행해 서버 전체를 장악할 수 있다.

## 선택: 로그 전용 디렉터리의 파일 수집

앱·DB 로그를 전용 디렉터리에 저장하고, Alloy에 읽기 전용으로 마운트한다. Alloy는 컨테이너 내부 root 계정으로 실행하며, 기존 capability 제거와 권한 상승 차단 설정을 유지한다.

**근거**

1. 로그만 저장하는 경로를 연결해 DB 인증 정보가 담긴 Docker 설정 파일과 다른 시스템 로그의 접근을 제외할 수 있다.
2. Spring Boot와 MySQL의 파일 출력 기능을 사용해 별도 로그 저장 서비스를 운영하지 않아도 된다.
3. 디렉터리를 연결하므로 회전으로 새로 만들어진 로그 파일도 같은 경로에서 읽을 수 있다.
4. Docker 소켓을 노출하지 않고 기존 capability 제거·권한 상승 차단을 유지할 수 있다.

## 감수하는 것

1. **파일 출력과 회전을 직접 관리한다**

   앱은 Spring Boot의 회전 정책을 설정하고, MySQL은 systemd 타이머에서 오류 로그를 옮긴 뒤 파일을 다시 열게 해야 한다.

   대응: 배포 시 디렉터리 소유권과 회전 설정을 준비하고, 파일 크기와 보관량을 제한한다. DB는 주기적으로 크기를 검사하므로 검사 사이에는 기준 크기를 초과할 수 있다.

2. **파일 쓰기가 서버 디스크 공간을 사용한다**

   앱은 표준 출력과 파일에 로그를 남겨 사본이 생긴다. 파일 출력이 실패하거나 Alloy가 읽기 전에 보관 파일이 삭제되면 일부 로그가 전송되지 않을 수 있다.

   대응: Docker 표준 출력 사본도 크기와 개수를 제한한다. dev에서 디스크 사용량·로그 회전·컨테이너 재생성 후 수집을 검증하고 prod에 적용한다. Alloy 읽기 위치는 별도 볼륨에 보존한다.

3. **Alloy가 컨테이너 내부 root로 실행된다**

   접근 가능한 앱·DB 로그와 Alloy 자체 인증 정보가 유출될 위험은 남는다.

   대응: 로그 전용 경로 외에 Docker 설정·DB 데이터·호스트 루트·Docker 소켓을 연결하지 않는다. 로그 본문에 민감정보를 남기지 않는 기존 컨벤션을 유지한다.

# 36. 앱·DB 로그를 전용 디렉터리에 저장하고 Alloy가 읽는다

- 상태: Accepted
- 날짜: 2026-10-01

## 상황 (조건)

- 앱·DB는 Docker 컨테이너로 실행되며, 환경변수로 DB 인증 정보를 전달받는다.
- Docker 로그 디렉터리에는 컨테이너 환경변수가 담긴 설정 파일도 있다.
- 기존 Alloy는 일반 계정으로 실행되며, 추가 권한과 권한 상승이 차단되어 있다.
- 기존 구성은 `docker.sock`과 호스트 루트 디렉터리를 마운트하지 않는다.

## 고려한 대안

**1. Docker 로그 디렉터리 직접 읽기**

- 앱·DB의 표준 출력 방식을 유지할 수 있다.
- root로 디렉터리 전체를 읽으면 인증 정보가 담긴 설정 파일도 읽을 수 있다. 읽기 전용 마운트로도 막지 못한다.
- Docker는 내부 로그 파일을 외부 도구로 직접 읽는 방식을 권장하지 않는다.
- 로그 파일 하나만 마운트하면, 로그가 새 파일에 기록되기 시작했을 때 Alloy가 그 파일을 읽지 못한다.

**2. journald 수집**

- Docker 설정 파일을 노출하지 않고 컨테이너 표준 출력 로그를 수집할 수 있다.
- 공용 journal을 연결하면 다른 시스템 로그도 읽을 수 있다. 수집 필터는 파일 접근 권한을 제한하지 않는다.
- 시스템 로그가 많이 쌓이면 앱 로그가 더 빨리 삭제될 수 있다.
- 로그가 한꺼번에 많이 발생하면 일부는 저장되지 않을 수 있다.

**3. Docker 소켓을 통한 수집**

- Docker API로 컨테이너를 발견하고 로그를 읽을 수 있어, 파일 탐색과 컨테이너 식별 설정이 간단하다.
- Docker가 제공하는 API를 사용하므로 로그 파일의 저장 경로에 의존하지 않는다.
- 수집기에 Docker 데몬 제어 권한이 생긴다. 수집기가 해킹되면 호스트 파일에 접근하거나 컨테이너를 실행해 서버 전체를 장악할 수 있다.

## 선택: 로그 전용 디렉터리의 파일 수집

앱·DB 로그를 전용 디렉터리에 저장하고, Alloy에 읽기 전용으로 마운트한다. Alloy는 일반 계정(`473:473`)으로 실행하며, 기존 Alloy에 적용된 capability 제거와 권한 상승 차단 설정을 유지한다. 로그 디렉터리는 공통 그룹에 읽기·탐색 권한을 주고, 새 파일에도 같은 그룹이 상속되도록 설정한다.

이 결정의 승인 범위는 로그를 저장할 경로와 Alloy의 접근 권한이다. 중단 중 보관 파일로 넘어간 로그까지 수집할지, 그 로그의 누락을 허용할지는 아직 결정하지 않았다.

**근거**

1. Alloy에 앱·DB 로그만 제공해, 인증 정보가 담긴 Docker 설정 파일이나 다른 시스템 로그를 읽지 못하게 할 수 있다.
2. 로그 전용 디렉터리에 읽기 권한을 부여하므로, Docker 내부 디렉터리의 권한을 바꾸거나 Alloy에 root 권한을 줄 필요가 없다.
3. Docker 데몬 제어 권한을 부여하지 않고 기존 capability 제거·권한 상승 차단 설정을 유지할 수 있다.

## 감수하는 것

1. **로그 파일이 계속 커지지 않도록 직접 관리해야 한다**

   앱과 DB가 로그를 파일에 쓰도록 설정하고, 파일이 커지면 새 파일에 기록하게 해야 한다. 앱은 Spring Boot 설정을 사용하지만, DB는 서버에 주기적으로 실행되는 작업을 따로 설치해야 한다. 앱을 이전 버전으로 되돌려도 이 작업은 남는다.

   대응: 파일 크기와 보관할 로그의 양을 제한한다. DB는 일정 간격으로 크기를 확인하므로, 다음 확인 전까지는 정한 크기를 넘을 수 있다. DB가 파일에 로그를 쓸 때만 작업을 실행하고, 더 이상 필요하지 않을 때의 제거 방법은 [배포 가이드](../백엔드_배포_가이드.md)에 적는다.

2. **같은 로그가 두 곳에 저장된다**

   앱이 실행 중에 내보내는 로그를 Docker가 파일로 저장한다. 앱도 같은 로그를 별도 파일에 저장하므로, 서버에 같은 로그의 사본이 생긴다.

   대응: 앱이 저장하는 로그와 Docker가 저장하는 로그의 크기·보관량을 각각 제한한다. dev에서 디스크 사용량을 확인한 뒤 prod에 적용한다.

3. **일부 로그가 Grafana Cloud에 전달되지 않을 수 있다**

   파일에 로그를 쓰지 못하면 Alloy가 그 로그를 보낼 수 없다. 또 Alloy가 멈춘 사이 기존 파일을 보관하고 새 파일에 기록하기 시작하면, 다시 실행된 Alloy는 현재 파일만 읽는다. 이전 파일에 남은 로그는 자동으로 보내지 않는다.

   대응: 파일이 바뀌거나 컨테이너를 다시 만든 뒤에도 수집되는지 확인한다. Alloy가 어디까지 읽었는지는 따로 저장해 재시작 후에도 기억하게 한다. 다만 이것만으로 이전 파일의 로그까지 보낼 수는 없다. 이 누락을 허용할지, 이전 파일도 읽게 할지는 추가로 결정해야 한다.

4. **새 로그 파일도 Alloy가 읽을 수 있도록 권한을 맞춰야 한다**

   앱과 DB가 새로 만든 파일을 Alloy가 읽지 못하면 로그 수집이 멈춘다. 어디까지 읽었는지 기록하는 저장 공간에도 Alloy가 쓸 수 있어야 한다.

   대응: 새 파일도 Alloy가 속한 그룹을 그대로 사용하도록 디렉터리를 설정한다. 기존 파일의 읽기 권한과 읽은 위치를 기록할 저장 공간의 쓰기 권한도 배포할 때 맞춘다. 새 파일이 생긴 뒤에도 Alloy가 읽을 수 있는지 확인한다.

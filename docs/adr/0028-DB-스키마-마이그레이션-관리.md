# 28. DB 스키마 변경을 Flyway 마이그레이션으로 관리한다

- 상태: Accepted
- 날짜: 2026-09-19

## 상황 (조건)

- Flyway 도입 전에는 `schema.sql`에 제품 추천 기능을 위한 8개 테이블이 있었고, 로컬·개발 환경에서는 Hibernate의 `ddl-auto: update`와 SQL 초기화로 스키마를 만들었다.
- 개발 서버는 `develop` 브랜치를 배포한다. 정식 운영 배포의 기준 브랜치는 `main`으로 정했지만, 아직 정식 버전 개발이 완료되지 않아 현재 운영 서버에는 `prototype` 브랜치의 V0를
  테스트용으로 배포하고 있다.
- 정식 버전 개발이 완료되면 운영 배포의 소스 브랜치를 `main`으로 전환하고, 이후 `develop`의 변경을 `main`에 병합해 운영에 배포한다.
- V0 DB에 저장된 테스트 데이터는 정식 버전으로 이관할 필요가 없다. 정식 운영 환경은 기존 V0 DB를 재사용하지 않고 새 빈 DB에서 시작할 수 있다.
- FAQ 기능이 병합되는 등 개발 과정에서 테이블, 컬럼, 제약 조건의 추가·변경이 계속 발생할 예정이다.
- 개발·운영 환경에서 같은 버전의 스키마를 재현하고, 어떤 변경이 언제 적용되었는지 확인할 수 있어야 한다.
- DB는 [ADR 0004](0004-데이터베이스.md)에서 결정한 MySQL 8.4를 사용하며, 애플리케이션은 Spring Boot 4.1.0과 Gradle 의존성 관리를 사용한다.

## 고려한 대안

**1. Hibernate의 `ddl-auto: update`와 `schema.sql`을 계속 사용한다**

- 엔티티 변경이나 초기 테이블 생성에 별도 마이그레이션 파일을 작성하지 않아 초기 개발 속도가 빠르다.
- SQL 파일 하나로 빈 DB의 초기 스키마를 만들 수 있다.
- `update`가 적용한 변경 이력과 적용 순서를 DB에서 확인할 수 없고, 환경마다 엔티티와 기존 스키마의 상태에 따라 결과가 달라질 수 있다.
- 이미 배포된 DB에 필요한 데이터 변환, 제약 조건 변경, 인덱스 추가를 안전하고 재현 가능하게 적용하기 어렵다.

## 선택: Flyway 마이그레이션

애플리케이션 시작 시 Flyway가 마이그레이션을 적용하도록 `spring-boot-starter-flyway`와 MySQL 전용 모듈 `flyway-mysql`을 사용한다. 버전은 Spring Boot의 의존성
관리에 맡긴다.

스키마 관리에 관한 [ADR 0008](0008-테스트-데이터베이스.md)·[ADR 0014](0014-CD-파이프라인.md)·[ADR 0019](0019-환경별-설정-관리.md)의 후속 결정이다. MySQL
컨테이너와 프로파일 기반 환경 분리는 유지한다.

마이그레이션은 `src/main/resources/db/migration/`에 `V<버전>__<설명>.sql` 형식으로 둔다.

- `V1.1__create_initial_schema.sql`에는 현재 초기 스키마의 9개 테이블을 모두 생성한다.
- `V1.2__insert_reference_data.sql`에는 제품 종류·사용 목적·질문·선택지 기준 데이터를 등록한다.
- Flyway가 공유 환경에 최초 적용된 이후 발생하는 스키마 변경은 기존 migration을 수정하지 않고 새로운 버전의 migration으로 추가한다.
- 운영 또는 공유 환경에 적용된 마이그레이션 파일은 수정·삭제하지 않는다. 수정이 필요하면 다음 버전의 새 마이그레이션을 추가한다.

초기 구성을 `1.x`로 표현하되 각 파일의 적용 이력은 별도로 관리한다. 예상하지 못한 테이블·데이터 중복이 오류로 드러나도록 `IF NOT EXISTS`와 `ON DUPLICATE KEY UPDATE`는 사용하지
않는다.

**첫 배포와 DB 전환 정책**

- 정식 운영의 첫 배포는 새 빈 DB를 대상으로 하며, Flyway가 `V1.1`부터 순서대로 스키마와 기준 데이터를 적용한다. 서비스의 V0·정식 버전과 Flyway 파일의 `V1.1`, `V1.2`는 서로 다른
  버전 체계다.
- V0 데이터 이관, 기존 V0 DB baseline, baseline 시나리오 테스트는 이번 도입 범위에서 제외한다. `baseline-on-migrate`도 활성화하지 않는다.
- 로컬·개발 환경에 Flyway 이력이 없는 기존 테이블이 남아 있다면 별도 빈 DB를 준비해 전환한다. 데이터를 보존해야 하는 환경이 생기면 그 환경의 전환 정책과 baseline 필요성을 별도로 결정한다.
- 도입 검증은 빈 DB에서의 마이그레이션 적용, 기준 데이터 등록, `ddl-auto: validate` 통과 및 애플리케이션 정상 기동을 기준으로 한다. 재기동 시 적용된 마이그레이션이 다시 실행되지 않는지도
  확인한다.
- 정식 배포 이후에는 데이터를 유지하면서 새 버전의 마이그레이션을 누적 적용한다. 빈 DB에서 시작하는 정책은 이번 최초 전환에만 적용한다.

**테스트 방식**

- 일반 테스트는 `devica_test`에서 Hibernate의 `create-drop`을 사용한다.
- 마이그레이션·기준 데이터 검증은 `flyway-test` 프로파일의 `devica_flyway_test`에서 수행한다. 컨텍스트 시작 시 `clean` → `migrate` 후 Hibernate의
  `validate`로 엔티티 매핑을 검증한다.
- `FlywayMigrationTest`는 미적용 마이그레이션이 없는지, 시드·질문 테스트는 등록된 기준 데이터가 맞는지 확인한다. 실행
  방법은 [개발 환경 가이드](../개발_환경_가이드.md#4-6-srctestresourcesapplicationyml)에 있다.

**근거**

1. FAQ처럼 기능이 순차적으로 합류하는 현재 상황에서는 전체 스키마를 반복 생성하는 방식보다 변경분을 누적하는 방식이 충돌 원인을 좁히고 리뷰하기 쉽다.
2. 로컬·개발·운영 DB가 서로 다른 시점에 생성될 수 있으므로, SQL 초기화나 Hibernate 자동 변경만으로는 같은 스키마임을 보장하기 어렵다. Flyway 이력은 각 DB가 어느 변경까지 적용됐는지
   확인하게 한다.
3. MySQL을 계속 사용하므로 MySQL 전용 Flyway 모듈을 함께 추가해 해당 DB 지원을 명시한다. Spring Boot가 검증한 Flyway 버전을 사용해 별도 버전 호환성 관리를 줄인다.
4. 현재 배포된 V0는 테스트용이며 데이터를 이관할 필요가 없다. 새 빈 DB에 초기 마이그레이션을 실제로 적용하는 경로로 정식 배포를 시작하면, 기존 DB 상태와 baseline 버전의 정합성을 맞추는 전환
   작업을 줄일 수 있다.

**버전: Spring Boot 관리 버전**

`io.spring.dependency-management` 플러그인이 Spring Boot 4.1.0의 BOM을 적용하므로 Flyway 관련 의존성에 버전을 직접 고정하지 않는다. Spring Boot 업그레이드
시 호환되는 버전으로 함께 갱신한다.

## 감수하는 것

1. **마이그레이션 파일과 스키마 변경의 동기화 책임**

   엔티티만 수정하거나 적용된 SQL 파일을 고치면 환경 간 스키마가 달라지거나 Flyway 검증이 실패할 수 있다.

   대응: 스키마 변경 PR에는 해당 버전의 마이그레이션을 포함하고, 이미 적용된 파일은 새 버전 파일로 보완한다.

2. **첫 배포 시 DB 연결 대상 확인**

   운영 배포 브랜치를 `prototype`에서 `main`으로 바꾸더라도 DB 연결 대상이나 DB 볼륨이 자동으로 새로 만들어지는 것은 아니다. V0 DB를 그대로 연결하면 이번 결정의 빈 DB 전제가 성립하지
   않는다.

   대응: 정식 운영용 새 DB를 준비하고 연결 설정을 함께 확인한다. 기존 V0 DB의 삭제나 초기화는 이 변경에 포함하지 않는다. 보존 중인 V0로 되돌려야 한다면 애플리케이션과 DB 연결 대상을 함께
   복구하며, 새 정식 DB에 V0 애플리케이션만 연결하는 방식을 롤백으로 간주하지 않는다.

3. **기존 초기화 방식의 정리 필요**

   `schema.sql` 초기화와 `ddl-auto: update`를 Flyway와 함께 유지하면 동일한 DDL이 중복 적용되거나 Hibernate가 이력 밖의 스키마를 변경할 수 있다.

   대응: 애플리케이션은 SQL 초기화를 끄고 Hibernate를 `validate`로 설정한다. 테스트는 위의 두 구성으로 나누고, `clean`은 Flyway 전용 테스트 DB에서만 실행한다.

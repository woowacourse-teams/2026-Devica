# 27. API 요청을 Vercel rewrite로 백엔드에 넘긴다

- 상태: Accepted
- 날짜: 2026-09-18

## 상황 (조건)

- 프론트엔드는 Vercel(HTTPS)에, 백엔드는 EC2에 있어 오리진이 다르다([0026](0026-프론트엔드-배포처.md)).
- 지금 연결하는 백엔드는 개발 서버이고, 개발 서버는 ALB를 거치지 않아 HTTP로만 받는다([0016](0016-HTTPS-처리-지점.md)).
- 개발 서버 연결은 운영 서버로 바꿀 때까지의 임시 연결이다.
- 백엔드에 CORS 설정이 없다.
- 프론트엔드 코드는 API를 상대 경로로 호출하고, `VITE_API_BASE_URL`을 채우면 백엔드를 직접 호출하도록 짜여 있다([0025](0025-프론트엔드-구현-방식-변경.md)).

## 고려한 대안

**1. 브라우저가 백엔드를 직접 호출 (`VITE_API_BASE_URL` + CORS)**

- 요청이 중간 서버를 거치지 않는다.
- 백엔드가 HTTPS여야 한다. HTTPS 페이지에서 HTTP를 호출하면 브라우저가 mixed content로 막는다.
- 백엔드에 CORS 설정을 추가해야 한다.
- 주소가 바뀌면 다시 빌드해야 한다.

## 선택: Vercel rewrite

Vercel 대시보드의 Routing Rules로 `/api` 요청을 백엔드로 넘긴다.

규칙은 `vercel.json`이 아니라 대시보드에 둔다. 목적지를 바꿀 때 커밋과 재배포 없이 Publish만으로 반영된다.

다시 검토할 조건:

- 운영 서버를 연결할 때. 백엔드가 HTTPS가 되어 브라우저가 직접 호출할 수 있다.

**근거**

1. 개발 서버가 HTTP라서 브라우저가 직접 호출할 수 없다. rewrite는 Vercel 서버가 호출하므로 mixed content가 생기지 않는다.
2. 백엔드를 고치지 않는다. 같은 오리진으로 요청하므로 CORS 설정이 필요 없다.
3. 연결 대상이 임시라 곧 바뀐다. 대시보드에서 목적지만 바꾸면 되고 다시 빌드하지 않는다.

## 감수하는 것

1. **설정이 저장소 밖에 있다**

   규칙이 코드 리뷰를 거치지 않고, 변경 이력은 대시보드의 History 탭에만 남는다. 코드만 봐서는 요청이 어디로 가는지 알 수 없다.

   대응: [프론트엔드 배포 가이드](../프론트엔드_배포_가이드.md)에 규칙 값을 기록하고, 규칙을 바꾸면 문서도 함께 고친다.

2. **Vercel과 개발 서버 사이 구간은 암호화되지 않는다**

   브라우저에서 Vercel까지는 HTTPS지만, Vercel에서 개발 서버까지는 HTTP다. 개발 서버에는 실제 사용자 데이터가 없어 지금은 비용이 되지 않는다.

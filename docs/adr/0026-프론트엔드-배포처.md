# 26. 프론트엔드를 우선 Vercel에 배포한다

- 상태: Accepted
- 날짜: 2026-09-18

## 상황 (조건)

- 백엔드는 [0014](0014-CD-파이프라인.md)에 따라 CodePipeline으로 배포한다. 파이프라인과 빌드 프로젝트가 환경마다 한 벌씩 있다.
- 팀 AWS 계정은 액세스 키와 OIDC 역할을 만들 수 없다.
- 프론트엔드를 별도 EC2에 올리면 이 구조가 한 벌 더 붙는다. EC2·CodeBuild·CodePipeline·타깃 그룹·보안 그룹 규칙이 환경마다 따라온다([0025](0025-프론트엔드-구현-방식-변경.md)).
- 당장은 간단하게 배포할 수 있는 것이 우선이다.

## 고려한 대안

**1. 별도 EC2**

- 서버 설정을 직접 다룰 수 있어 커스터마이징이 쉽다.
- 인스턴스를 늘려 ALB 뒤에 두는 식으로 확장에 유연하다.
- 백엔드와 같은 도구(CodePipeline)와 같은 콘솔에서 관리된다.
- 배포하려면 0014의 파이프라인 구조를 프론트엔드용으로 한 벌 더 만들어야 해 구조가 복잡해진다.

## 선택: Vercel

`develop` 브랜치의 `frontend/` 디렉터리를 배포한다. 이 문서는 배포처만 정한다. 백엔드처럼 개발과 운영을 나눌지는 별도 ADR로 남긴다.

다시 검토할 조건:

- 서버 쪽 설정(프록시, 응답 헤더 등)을 직접 다뤄야 할 때
- Vercel 요금제의 한도에 걸릴 때

**근거**

1. 저장소를 연결하고 Root Directory만 지정하면 빌드와 배포가 자동으로 이뤄진다. 별도 파이프라인을 만들고 관리할 필요가 없다.
2. GitHub 연동으로 배포하므로 팀 AWS 계정의 권한 제약과 무관하다.

## 감수하는 것

1. **프론트엔드와 백엔드의 오리진이 분리된다**

   0025가 감수한 "동일 오리진이 더 이상 공짜가 아니다"가 실제 비용이 된다. 프론트엔드는 `*.vercel.app`, 백엔드는 EC2라서, 둘을 잇는 설정을 따로 관리해야 한다.

   대응: Vercel의 Routing Rules로 `/api` 요청을 백엔드로 넘긴다([0027](0027-API-요청-연결-방식.md)).

2. **무료(Hobby) 요금제의 제약을 받는다**

   Hobby 요금제는 약관상 상업적 사용을 허용하지 않고, 대역폭과 빌드 시간에 한도가 있다. 실제 사용자에게 서비스를 열거나 트래픽이 늘면 이 제약에 걸린다.

   대응: 서비스를 공개하기 전에 Pro 요금제로 전환할지, 별도 EC2로 옮길지 다시 판단한다.

3. **프로젝트 설정이 저장소 밖에 있다**

   Root Directory와 배포 브랜치는 Vercel 대시보드에만 있어 변경 이력이 남지 않는다.

   대응: [프론트엔드 배포 가이드](../프론트엔드_배포_가이드.md)에 값을 기록한다.

4. **배포를 확인하는 곳이 둘이 된다**

   백엔드는 AWS 콘솔에서, 프론트엔드는 Vercel 대시보드에서 배포 상태와 로그를 본다. 화면이 깨졌을 때 원인이 프론트엔드 배포인지 백엔드 배포인지 두 곳을 모두 확인해야 한다.

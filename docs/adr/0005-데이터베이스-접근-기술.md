# 5. DB 접근 기술로 Spring Data JPA를 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 팀원 전원이 JPA를 동작 방식까지 이해한 상태로 사용해본 경험이 있다.
- 데이터 구조가 확정되지 않아, 개발 과정에서 스키마 변경이 반복될 것으로 예상된다.
- 기기 추천 기능에는 조건 조합에 따른 필터링이 필수이므로 복잡한 조회 쿼리가 필요하다.

## 고려한 대안

**1. Spring Data JDBC**

- SQL이 코드에 명시적으로 드러나, 실행되는 쿼리를 예측하기 쉽다.
- 영속성 컨텍스트나 지연 로딩 같은 개념이 없어 학습·이해 부담이 적다.
- AI 도구가 SQL을 직접 읽고 다룰 수 있어, AI를 적극 활용하는 환경에서 유리하다는 평가를 받는다.
- 연관관계 매핑이나 변경 감지를 지원하지 않아, 스키마·엔티티 변경 시 수정할 코드가 많다.

## 선택: Spring Data JPA (Hibernate)

**근거**

1. Spring Data JDBC의 이점으로 언급되는 "AI가 SQL을 직접 읽고 다루기 쉽다"는 점은 AI에 구현을 위임하는 것을 전제로 한다. 그러나 이번 프로젝트는 백엔드만큼은 팀이 직접 판단하고 AI는 보조적으로만 활용한다는 방침을 세웠다. 따라서 이 이점은 우리 조건에서 유효하지 않다.
2. 스키마 변경이 반복될 상황에서 JPA의 DDL 자동 생성과 변경 감지는 수정 범위를 줄여준다. Spring Data JDBC였다면 스키마가 바뀔 때마다 SQL과 매핑 코드를 함께 고쳐야 한다.
3. 팀원 전원이 JPA를 동작 방식까지 이해한 상태로 사용해봤으므로, 학습 없이 착수할 수 있다.

**QueryDSL 도입 보류**

기기 추천의 동적 쿼리를 처리하기 위해 도입을 검토했으나, 모든 팀원에게 익숙한 도구가 아니어서 보류했다. 우선 Spring Data JPA의 쿼리 메서드와 JPQL로 구현하고, 조건 조합이 복잡해져 필요성이 체감되는 시점에 도입한다.

## 감수하는 것

1. **실행되는 SQL이 코드에 드러나지 않는다**

   JPA는 쿼리를 자동으로 생성하므로, 의도치 않은 쿼리(N+1 등)가 나가도 알아차리기 어렵다. 조건 조합이 많은 기기 추천 기능에서 특히 위험하다.

   대응: 테스트로 동작을 확실히 검증하고, 성능 문제는 이후 쿼리 튜닝 단계에서 다룬다.

2. **동적 쿼리를 QueryDSL 없이 처리해야 한다**

   조건 조합이 늘어나면 쿼리 메서드와 JPQL만으로는 관리하기 어려워진다. 그 시점에 QueryDSL 도입을 다시 검토한다.

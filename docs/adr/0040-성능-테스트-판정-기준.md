# 40. 성능 테스트의 통과 기준을 서버 처리 시간 p95 200ms, 오류율 1%로 정한다

- 상태: Accepted
- 날짜: 2026-10-14

## 상황 (조건)

- 화면 하나를 1초 안에 보여주는 것을 목표로 한다.
- k6는 팀원 각자의 노트북에서 돌린다.
- 앱은 요청마다 서버 처리 시간을 로그로 남기고, Grafana Cloud에서 조회할 수 있다([0033](0033-로그-형식.md), [0034](0034-로그-저장소.md)). 요청 시간 히스토그램 지표도 60초마다 수집된다.
- 테스트 스크립트는 요청 조건을 모두 유효한 조합으로 만든다.
- 성능 테스트 결과는 개선 전후를 비교하는 데 쓴다.

## 고려한 대안

**1. k6가 잰 응답 시간의 p95**

- k6 결과만 보면 되어 따로 조회할 필요가 없다.
- 측정 장소의 네트워크 시간이 들어간다. 200ms는 네트워크 시간을 빼고 API에 배정한 시간이라 그대로 비교할 수 없고, 장소가 바뀌면 개선 전후도 비교할 수 없다.

**2. 요청 시간 히스토그램 지표의 p95**

- 대시보드에서 바로 볼 수 있다.
- 구간(버킷) 안에서 값을 추정해 실제보다 크게 나온다. 2026-10-12 측정에서 같은 구간의 히스토그램 p95는 268~274ms, 요청 로그 p95는 163~175ms였다.
- 가장 큰 버킷보다 느린 요청은 값을 나타내지 못한다. 2026-10-14 측정에서 히스토그램 p95는 세 회차 모두 가장 큰 버킷인 5초에 걸렸고, 요청 로그 p95는 7.3~8.0초였다.

**3. 4xx도 오류율에 포함**

- 실패한 응답을 모두 한 숫자로 본다.
- 4xx는 검증 단계에서 바로 끝나 응답이 빨라서 p95를 왜곡한다.

**4. 5xx와 타임아웃도 측정 무효 조건에 포함**

- 오류가 난 회차를 판정에서 빼고 다시 잴 수 있다.
- 오류율 기준(1%)이 허용한 오류 한 건으로도 회차 전체가 무효가 된다.

## 선택: 서버 처리 시간 p95와 오류율로 판정하고, 측정이 잘못된 회차는 무효로 한다

| 구분       | 기준                                                                               |
|----------|----------------------------------------------------------------------------------|
| 성능 기준    | 서버 처리 시간(요청 로그) p95가 3회의 중앙값으로 200ms 이하. 오류율(5xx, 5초 타임아웃, 연결 오류)이 모든 회차에서 1% 이하 |
| 측정 무효 조건 | 3xx·4xx 응답, 200 응답의 형식 검사 실패, `dropped_iterations`가 0이 아님, 측정 중 배포               |
| 측정 방법    | 한 회차는 워밍업 1분 → 측정 10분. 같은 조건으로 3회                                                |

**근거**

1. 화면을 1초 안에 보여주려면 네트워크 왕복과 렌더링에 쓸 시간을 남겨야 해서, API 하나에는 200ms를 배정했다.
2. 200ms는 네트워크 시간을 빼고 API에 배정한 시간이라, 네트워크 시간이 들어가지 않는 서버 처리 시간과 비교해야 한다. 서버 처리 시간은 측정 장소에 따라 달라지지 않아 개선 전후 비교에도 쓸 수 있다.
3. 요청 로그는 요청마다 실제로 잰 값이라 추정이 끼지 않는다.
4. 3xx·4xx나 형식 검사 실패가 나왔다면 서버가 아니라 측정이 잘못된 것이다. 오류율에 섞지 않고 회차를 무효로 해서 다시 잰다.
5. `dropped_iterations`가 0이 아니면 k6가 계획한 부하를 다 걸지 못해 예상 트래픽을 검증한 것이 아니다. 측정 중에 배포되면 측정 도중에 서버가 바뀐다. 둘 다 결과를 판정에 쓸 수 없다.
6. 5xx와 타임아웃은 측정 무효 조건에 넣지 않는다. 넣으면 오류율 기준이 허용한 오류 한 건으로도 회차 전체가 무효가 된다.
7. 한 회차의 p95는 네트워크나 서버 상태에 따라 흔들려 3회의 중앙값으로 판정한다. 오류율은 한 번이라도 1%를 넘으면 그 부하를 감당하지 못한 것으로 본다.
8. 워밍업 1분은 2026-10-14 첫 측정에서 확인했다. 워밍업 첫 10초의 k6 p95가 이후보다 높지 않아 콜드 스타트의 영향이 보이지 않았다.

## 감수하는 것

1. **판정 값을 Grafana에서 직접 조회한다**

   k6 결과만으로는 판정할 수 없다. 회차마다 측정 구간을 계산해 Grafana에서 쿼리를 실행해야 한다.

   대응: 성능 테스트 안내(`performance/README.md`)에 쿼리와 시간 설정 순서를 둔다.

2. **요청 로그에서 테스트 요청만 골라내지 못한다**

   k6는 `User-Agent: devica-k6/<테스트 이름>`을 붙이지만 요청 로그에 User-Agent가 남지 않는다. 측정 중 다른 요청이 들어오면 판정 값에 섞인다.

   대응: 측정 중에는 개발 서버를 함께 쓰지 않는다. 요청 로그에 User-Agent를 남기면 해소된다.

3. **Tomcat 스레드를 기다린 시간이 빠진다**

   로그의 처리 시간은 요청 필터에 들어온 뒤부터 잰다. 동시 요청이 많은 높은 부하에서는 실제보다 작게 나올 수 있다. 커넥션 풀을 기다린 시간은 들어간다.

   대응: 오류율과 k6 응답 시간을 함께 기록해 서버 처리 시간만으로 판단하지 않는다.

4. **로그와 k6의 구간 경계가 조금 다르다**

   로그는 측정 구간을 시각으로 자르고, k6는 측정 시나리오로 나눈다. 구간 경계에 걸친 세션 몇 개만큼 두 값이 다른 요청을 포함한다.

# 18. 개발 환경과 운영 환경을 분리한다

- 상태: Accepted
- 날짜: 2026-08-27

## 상황 (조건)

- 운영 환경에 실사용자를 받는 프로토타입 버전(`V0`)이 배포되어 있고, 그와 별개로 새 버전(`V1`)을 개발해야 한다.
- `V1` 개발 과정에서 스키마 변경과 데이터 입력·수정·삭제가 빈번하게 발생한다.
- 운영 DB에 쌓이는 것은 사용자 실험 이벤트뿐이다. 제품 데이터는 코드에 하드코딩되어 있어 DB에 없다.
- 운영 DB는 EC2 안의 MySQL 컨테이너이고, 데이터의 전부가 볼륨 하나에 들어 있다. 백업도 스냅샷도 없다.
- `V1`에서는 제품 데이터를 DB로 옮기고 수집을 자동화할 예정이다.
- 로컬은 앱을 IDE에서 직접 실행하므로([0007](0007-컨테이너-적용-범위.md)), 컨테이너로 배포된 상태와 실행 방식이 다르다.
- AWS 비용이 지원되고, 기존 EC2와 CodePipeline의 설정을 모두 기록해두었다.

> [0017](0017-서버-환경-분리.md)은 나눈 두 서버를 어느 subnet에 둘지를 정했다. 이 문서는 그보다 앞선 결정인 환경을 나눌 것인가 자체를 기록한다. 당시 별도 문서로 남기지 않아 뒤늦게 적는다.

## 고려한 대안

실질적으로 검토한 대안은 없다.

환경을 겸용하는 방안은 나누는 비용이 크지 않아 비교가 성립하지 않았다. 운영 데이터를 복제하는 방안은 운영 DB에 사용자 이벤트만 있어 복제할 것이 없다.

## 선택: 서버와 DB를 따로 둔 개발 환경을 만든다

**근거**

1. 운영에 쌓인 이벤트를 되돌릴 수단이 없다. 백업이 없고, 이벤트는 사용자가 실제로 한 행동의 기록이라 다시 만들어낼 수도 없다.
2. 자동화 도입 과정에서 잘못된 데이터가 한 번에 대량으로 적재될 수 있다.
3. 배포된 상태에서만 드러나는 문제를 확인할 곳이 필요하다. 로컬은 IDE 실행이라 컨테이너 환경과 다르고, 그 차이는 지금까지 배포 단계에서 처음 확인됐다.
4. 분리하는 비용이 크지 않다. AWS 비용이 지원되고 기존 설정이 기록되어 있어, 같은 구성을 반나절 만에 다시 만들 수 있다.

## 감수하는 것

1. **AWS 리소스의 유지보수 비용 증가**

   EC2·파이프라인·빌드 프로젝트가 환경마다 하나씩이라 비용과 콘솔 설정 대상이 두 배다. 한쪽만 고쳐 두 환경이 어긋날 수 있다.

2. **개발 환경에서 확인할 수 없는 운영 이벤트**

   사용자 반응을 집계하거나 분석하는 작업은 운영 환경에서만 가능하다. 지금은 이벤트가 전부라 영향이 작지만, `V1`에서 제품 데이터가 DB로 들어오면 양과 분포에서 비롯되는 문제(느린 쿼리, 인덱스 부재 등)가 개발 환경에서 재현되지 않는다.

   대응: 그 시점에 익명화한 샘플 데이터를 생성하는 방안을 검토한다. 운영 데이터를 그대로 가져오지는 않는다.

3. **두 환경 사이에 남는 차이**

   개발 환경은 ALB를 거치지 않아 HTTPS가 아니다([0016](0016-HTTPS-처리-지점.md), [0017](0017-서버-환경-분리.md)). TLS가 필요한 동작은 운영에 올린 뒤에야 확인된다.

# 31. 라우팅에 wouter 를 사용한다

- 상태: Accepted
- 날짜: 2026-09-30

## 상황 (조건)

- 화면은 경로로, 화면이 쓰는 값은 쿼리로 나타낸다([0030](0030-화면-주소-방식.md)).
- 목록은 화면을 먼저 띄운 뒤 데이터를 받아 채운다.
- 프론트엔드의 런타임 의존성은 `react`와 `react-dom`뿐이다.
- 빌드된 JS는 gzip 기준 약 76KB다.

## 고려한 대안

**1. React Router 8**

- 가장 널리 쓰여 자료와 사용 사례가 많다.
- 스크롤 복원 컴포넌트를 제공한다.
- 데이터 로딩과 서버 렌더링까지 다루는 프레임워크 기능을 함께 담고 있다.
- 약 33KB(gzip)가 늘어난다.

**2. History API 직접 구현**

- 의존성이 늘지 않는다.
- 경로 매칭, 링크, 방문 기록 구독을 직접 작성하고 관리한다.

## 선택: wouter

**근거**

1. 경로와 쿼리로 화면을 나타내는 데 필요한 기능을 모두 갖췄다.
2. 늘어나는 크기가 약 3KB로, 지금 번들(약 76KB)에 비해 작다.
3. 데이터 로딩·서버 렌더링 같은 쓰지 않는 기능이 없다.
4. 경로 매칭과 방문 기록 구독을 라이브러리가 맡아, 이 부분을 직접 작성하지 않는다.

**버전: 3.12.0**

도입 시점의 최신 버전이다.

## 감수하는 것

1. **스크롤 복원을 직접 구현한다**

   뒤로 가기로 목록에 돌아왔을 때 보던 위치를 되살리는 기능이 없다. 목록은 데이터를 받은 뒤 그려지므로, 복원 시점도 목록이 그려진 뒤로 맞춰야 한다.

2. **쿼리 값 검증을 직접 한다**

   주소는 누구나 고칠 수 있다. `sort=abc` 같은 잘못된 값은 주소를 읽는 쪽에서 기본값으로 바꿔야 한다.

3. **자료가 React Router 보다 적다**

   막혔을 때 찾을 수 있는 사례가 적다.

   대응: 소스가 680줄이라 직접 읽어 동작을 확인할 수 있다.

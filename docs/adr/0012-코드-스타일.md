# 12. 코드 스타일로 우테코 IntelliJ 스타일과 .editorconfig를 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 팀원의 로컬 OS가 Windows와 macOS로 나뉘어 있어, 줄바꿈 문자나 인코딩이 서로 다르게 적용될 수 있다.
- 팀 규모가 작고 1개월 안에 검증을 마쳐야 하므로, 컨벤션을 직접 설계할 여력이 없다.
- 팀원 전원이 이전 미션에서 우테코 IntelliJ 스타일을 사용해왔다.

## 고려한 대안

**1. 다른 공개 스타일 (Google Java Style, 네이버 스타일, Palantir Java Format)**

- 널리 검증된 표준이며, 문서와 사용 사례가 풍부하다.
- 팀이 사용해본 적이 없어, 규칙을 익히고 적응하는 시간이 필요하다.

**2. 컨벤션 직접 설계**

- 팀의 선호와 프로젝트 특성에 맞게 규칙을 정할 수 있다.
- 규칙을 정하고 합의하는 데 시간이 든다.

## 선택: 우테코 IntelliJ 스타일 XML + `.editorconfig`

두 파일은 역할이 다르다.

| 도구 | 역할 | 적용 방식 |
|---|---|---|
| 우테코 스타일 XML | 상세한 포맷 규칙 (줄바꿈, 중괄호 위치 등) | 각자 IntelliJ에 임포트 |
| `.editorconfig` | 기본 규칙 (들여쓰기, 줄바꿈 문자, 인코딩) | 클론하면 자동 적용 |

**근거**

1. 검증된 공개 스타일이면서 팀 전원이 이미 사용해본 것이므로, 규칙을 익히는 비용이 사실상 없다. 컨벤션을 직접 설계할 여력이 없는 상황에서 가장 빠르게 적용할 수 있다.
2. 스타일 XML만 사용하면 임포트하지 않은 팀원의 코드가 전혀 다른 형태가 된다. `.editorconfig`를 함께 두면 클론만으로 최소한의 일관성이 확보되고, OS별로 달라지는 줄바꿈 문자와 인코딩도 통일된다. 추가 비용은 파일 하나를 커밋하는 것뿐이다.

**Checkstyle 도입 보류**

규칙 위반 시 빌드를 실패시켜 스타일을 강제하는 도구다. CI에서 검사하면 스타일이 어긋난 PR을 머지 전에 차단할 수 있다.

도입하지 않은 이유는 강제력을 얻기 전에 합의 비용이 먼저 들기 때문이다. 규칙 세트를 고르고 팀이 합의하는 데 시간이 필요하고, 초반에는 로직에 문제가 없는데도 스타일 때문에 PR이 막히는 상황을 겪게 된다. 모든 코드가 리뷰를 거치므로 당분간은 리뷰에서 짚는 것으로 충분하다고 봤다.

리뷰에서 스타일 지적이 반복되기 시작하면 그 시점에 도입한다.

## 감수하는 것

1. **스타일 규칙을 강제할 수단이 없다**

   팀원이 스타일 XML을 임포트하지 않아도 막을 방법이 없다. `.editorconfig`가 들여쓰기와 줄바꿈 문자 정도는 자동으로 맞춰주지만, 상세한 포맷 규칙은 각자의 설정에 달려 있다.

   대응: 리뷰에서 확인하고, 지적이 반복되면 Checkstyle 도입을 논의한다.

# 22. 동적 쿼리를 QueryDSL 로 작성한다

- 상태: Accepted
- 날짜: 2026-09-02

## 상황 (조건)

- 목록 조회의 사양 조건 네 개가 모두 선택이고 AND 로 결합된다. 지정하지 않은 조건은 조회에서 빠져야 한다.
- 검색어와 가격·브랜드 조건이 추가될 예정이다.
- 조회 조건은 엔티티의 필드를 가리킨다. 필드 이름이 바뀌면 조회도 함께 바뀌어야 한다.
- 응답에 CPU 정보가 들어가므로 노트북과 CPU 를 한 번에 읽어야 하고, 판매 중인 오퍼가 있는 제품만 골라야 한다.
- 전체 개수를 내려주지 않는다. 한 건 더 읽어 다음 페이지 여부만 판단한다.

> [0005](0005-데이터베이스-접근-기술.md) 가 "조건 조합이 늘어나면 그 시점에 QueryDSL 도입을 다시 검토한다"고 남겨두었다. 이 문서가 그 검토 결과다.

## 고려한 대안

**1. Specification 과 Criteria API**

- 별도 의존성 없이 Spring Data JPA 만으로 조건을 조립할 수 있다.
- 필드를 문자열로 참조한다. 이름이 틀려도 컴파일에 걸리지 않고 실행할 때 드러난다.
- 연관을 함께 읽으면서 조건에도 쓰려면 `Fetch` 를 `Join` 으로 캐스팅해야 한다.

**2. JPQL 문자열을 조건에 따라 이어 붙이기**

- 생성되는 쿼리를 그대로 눈으로 볼 수 있다.
- 조건을 붙이는 곳과 파라미터를 바인딩하는 곳이 나뉘어, 한쪽만 고치면 어긋난다.

**3. 조건을 항상 넣고 값이 없으면 무시하도록 쓰기 (`:param is null or ...`)**

- 쿼리가 하나로 고정되어 읽기 쉽다.
- 지정하지 않은 조건도 SQL 에 남아 실행 계획에 영향을 준다.

## 선택: QueryDSL

조건 하나를 메서드 하나로 표현하고, 값이 없으면 `null` 을 돌려준다. `where` 절은 `null` 을 조건이 없는 것으로 취급한다.

**근거**

1. 필드 참조가 컴파일 시점에 검증된다. 이름이 바뀌면 빌드가 깨져 조회를 함께 고치게 된다.
2. 조건이 늘어도 메서드가 하나 늘 뿐이다. 조합을 나열하거나 분기를 중첩하지 않는다.
3. 연관을 함께 읽는 것과 서브쿼리를 우회 없이 표현한다. 캐스팅이나 문자열 조립이 필요 없다.
4. 페이징을 직접 조립할 수 있어, 전체 개수를 세지 않는 방식을 그대로 쓴다.

## 감수하는 것

1. **빌드 단계에서 생성되는 질의 타입**

   엔티티마다 Q 클래스가 생성되므로 빌드가 그만큼 늘어나고, 엔티티를 바꾸면 다시 생성해야 한다. IDE 가 생성 경로를 소스로 인식하도록 설정해야 한다.

2. **의존성 관리 대상 증가**

   Spring Boot 가 버전을 관리하지만 Jakarta 용 분류자를 직접 지정해야 한다. Boot 를 올릴 때 함께 확인할 항목이 하나 늘었다.

3. **페이징 조립의 직접 구현**

   `Slice` 를 만들어 주는 지원이 없어, 한 건 더 읽고 잘라내는 처리를 코드로 둔다.

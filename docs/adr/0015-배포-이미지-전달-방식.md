# 15. 배포 이미지를 레지스트리 없이 배포 번들로 전달한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- CodeDeploy를 사용하므로([0014](0014-CD-파이프라인.md)), 배포 번들이 이미 S3를 거쳐 EC2로 전달된다.
- CodeBuild가 만든 컨테이너 이미지를 EC2까지 옮길 방법이 필요하다.
- 이미지 크기는 126MB 수준이고, 배포 빈도가 높지 않다.
- 파이프라인 아티팩트 버킷이 계정 공용이라, 팀이 수명 주기 규칙을 직접 걸 수 없다.

## 고려한 대안

**1. ECR**

- 같은 계정·같은 리전이라 별도 비밀값이 없고 전송료도 들지 않는다.
- 배포 번들이 가벼워지고, 이미지 이력이 레지스트리에 남는다.
- EC2 인스턴스 역할과 CodeBuild 역할 양쪽에 ECR 권한을 붙여야 한다.

**2. GHCR**

- 저장소와 같은 곳에서 이미지를 관리할 수 있다.
- EC2에 GitHub 자격증명을 두어야 한다. 서버에 외부 서비스의 비밀값이 생긴다.

## 선택: `docker save`로 만든 `image.tar`를 배포 번들에 실어 보내고 EC2에서 `docker load`

이미지 태그는 커밋 SHA 앞 7자리를 쓴다.

**근거**

1. 통로가 이미 있다. CodeDeploy가 S3를 거쳐 번들을 나르는데 이미지만 따로 창고를 두면, 자격증명과 관리 대상이 하나 늘어난다. 늘어난 만큼의 이득이 지금 규모에서는 없다.
2. EC2가 S3하고만 통신하면 된다. GitHub 자격증명도, 소스도, 빌드 도구도 서버에 두지 않는다.
3. 태그를 커밋 SHA로 하면 실행 중인 컨테이너와 커밋이 1:1로 대응한다. `latest`는 어떤 코드가 돌고 있는지 서버에서 확인할 방법이 없고 롤백 대상도 지정할 수 없다. CodePipeline이 넘겨주는 `COMMIT_ID`를 `buildspec.yml`이 `image-tag.txt`에 적어 번들에 싣고, SHA를 알 수 없으면 빌드를 중단한다.
4. 롤백이 재빌드 없이 성립한다. 이전 성공 리비전의 번들에 그때의 `image.tar`와 `image-tag.txt`가 그대로 들어 있어, CodeBuild를 다시 돌리지 않고도 정확히 이전 이미지로 돌아간다. 재빌드가 깨져서 되돌아가지 못하는 상황이 없다.

## 감수하는 것

1. **번들이 무겁고 배포가 느려진다**

   `image.tar`가 126MB라 S3를 두 번 왕복한다(빌드가 올리고, 배포가 내려받는다). 배포 시간이 십수 초 늘어난다.

2. **S3에 번들이 계속 쌓인다**

   버킷이 계정 공용이라 팀이 정리 규칙을 걸 수 없다.

   대응: 계정 관리자에게 파이프라인 이름 접두사(`devica-dev-pipe/`, `devica-prod-pipe/`)에 한정한 수명 주기 규칙을 요청한다.

**ECR 전환 조건**

이미지가 커지거나 배포가 잦아져 위 두 항목이 실제 부담이 되면 ECR로 옮긴다. 같은 계정·같은 리전이라 비밀값도 전송료도 없고, 양쪽 역할에 ECR 권한을 붙이는 것으로 끝난다.

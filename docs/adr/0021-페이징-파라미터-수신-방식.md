# 21. 페이징 파라미터를 Pageable 대신 page·size 로 직접 받는다

- 상태: Accepted
- 날짜: 2026-09-01

## 상황 (조건)

- 목록 조회 스펙이 페이지 크기의 기본값 20, 최대 100 을 요구한다. 잘못된 파라미터는 400 으로 응답하기로 되어 있다.
- 정렬은 `id` 오름차순으로 고정한다. 앞으로 추가될 정렬(UC-09)도 추천순·가격 낮은 순·가격 높은 순 셋으로 닫혀 있으며, 추천순은 여러 값을 조합해 산출한다.
- 프런트엔드가 아직 개빌되지 않아, 파라미터와 응답 계약을 맞춰볼 클라이언트가 없다.

## 고려한 대안

**1. `Pageable` 을 그대로 받는다**

- 페이지 번호·크기의 바인딩과 기본값을 Spring 이 처리한다. 레포지토리까지 그대로 넘길 수 있다.
- 페이지 크기 상한은 전역 설정(`spring.data.web.pageable.max-page-size`)으로만 지정할 수 있고, 초과 요청을 거부하지 않고 상한으로 보정한다.
- `sort` 파라미터가 함께 열린다. 정렬 키가 엔티티 필드 이름이라 필드명을 바꾸면 API 가 깨진다.

**2. `Pageable` + 전역 `max-page-size` 설정**

- 설정 한 줄로 상한이 적용된다.
- 상한이 모든 API 에 공통으로 걸리고, 초과 요청은 여전히 보정된다.

## 선택: `page`·`size` 를 `@RequestParam` 으로 직접 받는다

정렬은 클라이언트에서 받지 않고 서버가 조립해 `PageRequest` 로 만든다.

**근거**

1. 상한 위반을 400 으로 알린다. 조용히 100 개로 잘리면 클라이언트는 왜 그만큼만 오는지 모른 채 원인을 찾게 된다.
2. 기본값과 상한이 컨트롤러 시그니처에 드러난다. 전역 설정에 두면 코드를 봐도 몇 개까지 되는지 알 수 없다.
3. 정렬을 열지 않는다. 추천순은 `Sort` 로 표현되지 않으므로, 클라이언트 정렬을 받으면 UC-09 의 세 가지와 별개인 정렬 경로가 하나 더 생긴다.

## 감수하는 것

1. **페이징 파라미터의 중복 선언**

   페이징이 있는 API 가 늘어나면 `page`·`size` 선언이 컨트롤러마다 반복된다.

   대응: 세 번째 API 가 생기는 시점에 공통 파라미터 객체나 커스텀 리졸버로 묶는다.

2. **Spring 관례와 다른 형태**

   `Pageable` 을 기대하고 코드를 여는 사람에게는 낯설고, 되돌리려는 시도가 반복될 수 있다. 이 문서가 그 판단의 근거다.

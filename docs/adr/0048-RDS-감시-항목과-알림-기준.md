# 48. RDS는 저장 공간·CPU 크레딧·수집 끊김에만 알림을 걸고 나머지는 대시보드로 본다

- 상태: Accepted
- 날짜: 2026-10-23

## 상황 (조건)

- dev·prod DB는 RDS(t4g, Unlimited 모드)이고, 저장 공간은 둘 다 200GiB다([ADR 0038](0038-DB-RDS-이전.md)).
- RDS 지표는 Alloy가 CloudWatch에서 1분 단위로 읽어 Grafana Cloud로 보낸다([ADR 0047](0047-RDS-지표-수집-방식.md)).
- 기존 알림은 "울리면 바로 할 일이 있는 것만 건다", "데이터 없음은 App Down만 알림으로 본다"는 원칙을 따른다.
- DB가 앱 서버 안의 컨테이너였을 때는 아래 알림이 DB도 함께 감시했다.
  - 서버 디스크 알림 Disk Almost Full(80% 초과 30분): DB 데이터도 같은 디스크에 있었다.
  - 서버 메모리 알림 Low Memory: 앱과 DB가 같은 메모리를 나눠 썼다.
  - MySQL 오류 로그 알림 DB Error Log
- `/readyz` 헬스 체크가 DB 연결까지 검사하고, prod에서는 Synthetics가 이 경로의 실패를 알린다.
- 우아한테크코스 정책 상 IAM을 사용할 수 없어, 주어진 인스턴스 역할에 없는 권한은 추가할 수 없다([ADR 0047](0047-RDS-지표-수집-방식.md)).
- DB 로그는 RDS 콘솔에서 본다([ADR 0038](0038-DB-RDS-이전.md)).
- 응답 지연은 High Latency 알림이 감시한다. 1초 넘는 요청이 10%를 넘으면 울린다.
- 환경마다 앱이 하나이고, 커넥션 풀은 Hikari 기본값(최대 10개)이다.
- RDS의 최대 커넥션 수(`max_connections`)는 60이다.
- RDS 여유 메모리는 평소에도 130MiB 안팎이다. MySQL이 메모리 대부분을 버퍼 풀로 미리 잡아 두기 때문이다.
- 성능 테스트에서 피크 때 RDS CPU가 99%까지 올랐지만([ADR 0043](0043-제품-목록-최저가-사전-계산.md)), RDS 내에서 어느 지점이 병목이었는지는 알 수 없었다.

## 고려한 대안

**1. RDS 여유 메모리(Freeable Memory)에 알림 걸기**

- DB가 앱 서버 안의 컨테이너였을 때처럼 DB 메모리 부족을 알 수 있다.
- MySQL은 메모리 대부분을 버퍼 풀로 미리 잡아 두므로 여유 메모리가 평소에도 낮기 때문에, 숫자만으로 이상인지 판단하기 어렵다.

**2. RDS 오류 로그를 모니터링 패널에 두기**

- DB가 앱 서버 안의 컨테이너였을 때처럼 MySQL 자체 오류를 직접 알 수 있다.
- RDS 로그를 CloudWatch Logs로 내보내도록 바꾸고, Alloy에 CloudWatch Logs 수집을 새로 붙여야 한다.

**3. 수집 끊김의 기준을 RDS 알림의 "데이터 없음"으로 잡기**

- 알림을 새로 만들지 않고 기존 RDS 알림의 설정만 바꾸면 된다.
- 서버나 Alloy가 멈춰도 울려, 같은 원인으로 App Down과 알림이 겹친다.

## 선택: 알림 3개, 패널 8개

| 알림                  | 기준                               |
|---------------------|----------------------------------|
| RDS Storage Low     | 남은 공간 40GiB(사용률 80%) 미만 30분 지속   |
| RDS CPU Credits Low | 크레딧 1 미만 30분 지속                  |
| RDS Metrics Missing | 앱 지표는 들어오는데 RDS 지표가 없는 상태 30분 지속 |

| 패널               | 보는 것                  |
|------------------|-----------------------|
| CPU Usage        | CPU 사용률               |
| IOPS             | 초당 디스크 읽기·쓰기 횟수       |
| I/O Latency      | 디스크 읽기·쓰기 한 번에 걸리는 시간 |
| Disk Queue Depth | 처리를 기다리는 디스크 요청 수     |
| Free Storage     | 남은 저장 공간 (40GiB 기준선)  |
| Freeable Memory  | 남은 메모리                |
| CPU Credits      | CPU 크레딧 잔량 (1 기준선)    |
| Connections      | 연결 수                  |

대시보드 RDS 행의 위 줄에 앞의 4개를, 아래 줄에 뒤의 4개를 둔다.

**근거**

1. 저장 공간 알림 기준은 컨테이너 시절 DB 디스크를 감시하던 Disk Almost Full과 같은 80% 기준으로 둔다.
2. CPU 크레딧이 바닥났다는 것은 기준 이상의 CPU 사용이 쌓인 크레딧을 다 쓸 만큼 이어졌다는 뜻이므로, 바닥난 시점(1 미만)에 알린다. Unlimited 모드라 바닥나도 느려지지 않고 그 뒤 붙는 추가 요금은 작아, 바닥나기 전에 미리 알릴 필요는 없다.
3. 수집 끊김 알림은 앱 지표가 들어올 때만 울려, 서버·Alloy가 멈춘 경우는 App Down에 맡긴다.
4. 세 알림은 늦게 울려도 그 사이 피해가 없어 지속 시간을 짧게 둘 필요가 없다. 남은 40GiB가 30분 만에 찰 만큼 데이터가 늘지 않고, 크레딧이 바닥나도 느려지지 않는다. 그래서 값이 잠깐 기준을 넘었다 돌아오는 경우는 알리지 않도록 Disk Almost Full과 같은 30분으로 둔다.
5. 메모리는 평소에도 낮아 알림 기준을 정할 수 없다. 메모리가 실제로 모자라면 쿼리가 느려져 High Latency 알림이 먼저 울린다.
6. 연결 수 알림은 최대 커넥션 수(60)를 초과해 새 연결이 거부되는 것을 방지하는 용도다. 앱은 Hikari 풀 때문에 연결을 10개까지만 열어 60을 초과할 일이 없다. 풀이 모자라면 JVM / DB 행의 커넥션 대기로 드러난다.
7. DB 로그 패널은 두지 않는다. DB가 멈추면 `/readyz` 실패로 Synthetics가 먼저 알리고, 그 뒤 원인은 RDS 콘솔의 로그로 찾을 수 있어 패널이 더해 주는 것이 없다. 패널로 가져오려면 RDS 로그 내보내기를 켜고 Alloy에 CloudWatch Logs 수집을 새로 붙여야 한다.
8. CPU와 디스크 I/O는 DB가 느릴 때 원인이 연산인지 I/O인지 추적하기 위해 대시보드에 둔다. 정상 범위를 아직 모르고 DB가 느려지면 High Latency가 먼저 울리므로 알림은 걸지 않는다.

## 감수하는 것

1. **DB 성능 지표에 알림이 없어, 응답이 느려진 뒤에야 안다**

   DB의 CPU·메모리·디스크 I/O에 알림이 없어서, DB가 느려지면 High Latency가 울린 뒤에야 RDS 행을 본다.

   대응: 성능 테스트 기록에 RDS CPU와 I/O 값을 남겨 정상 범위를 쌓는다. 범위가 잡히면 알림을 다시 검토한다.

2. **저장 공간 알림 기준이 할당 크기에 의존한다**

   40GiB는 200GiB의 20%라서, 스토리지를 늘리거나 줄이면 기준이 뜻하는 사용률이 달라진다.

   대응: 할당 크기를 바꿀 때 RDS Storage Low 기준도 함께 고친다.

3. **연결 수 판단이 Hikari 기본값에 기대고 있다**

   풀 크기가 설정 파일에 드러나 있지 않다. 풀 크기를 바꾸거나 앱을 여러 대로 늘리면 근거 6이 달라진다.

   대응: 풀 크기나 앱 수를 바꿀 때 연결 수 알림이 필요한지 다시 본다.

4. **수집 끊김은 늦게 안다**

   지표가 끊긴 뒤 "없음"으로 판정되기까지 최대 5분, 그 상태가 30분 이어져야 알린다. 그동안 저장 공간·크레딧 알림은 동작하지 않는다.

   대응: 남은 40GiB가 수십 분 만에 찰 만큼 데이터가 늘지 않고 크레딧이 바닥나도 느려지지 않아(근거 4), 그대로 둔다.

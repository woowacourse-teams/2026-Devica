# 14. CD 파이프라인으로 AWS CodePipeline과 CodeDeploy를 사용한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- CD가 없으면 배포는 EC2에 접속해 코드를 내려받고 빌드하고 컨테이너를 재기동하는 일을 매번 반복하는 것이다.
- 운영 서버는 private subnet에 있어 AWS 콘솔의 SSM으로만 접근할 수 있고, 그 권한도 인스턴스를 생성한 계정에 묶여 있다. 그 한 사람이 자리에 없으면 팀 전체의 배포가 멈춘다. 스크립트로 절차를 줄여도 "서버에 접속해야 한다"는 제약은 남는다.
- 팀 AWS 계정은 액세스 키 발급이 막혀 있고, IAM 자격증명 공급자(OIDC)와 역할을 새로 만들 권한도 없다.
- 배포 대상 EC2가 ARM64(Graviton)이고 OS는 Ubuntu 26.04 LTS다. `docker build`는 빌드하는 머신의 아키텍처로 이미지를 고정하므로, 이미지를 만드는 환경도 ARM이어야 한다.
- CI는 GitHub Actions에서 돌고 있다([0013](0013-CI-도구.md)).

## 고려한 대안

**1. GitHub Actions로 CD까지 처리**

- CI와 도구가 통일되고, 파이프라인 설정 전체가 저장소에 남아 변경 이력이 추적된다.
- AWS를 조작하려면 액세스 키 또는 OIDC 역할이 필요하다. 팀 계정에서는 둘 다 만들 수 없다.
- 러너가 x86이라 arm64 이미지를 만들려면 QEMU 에뮬레이션을 거쳐야 한다.

**2. SSM Send-Command로 배포를 밖에서 밀어 넣기**

- 서버에 인바운드 포트를 열지 않아도 된다.
- 호출하는 쪽에 AWS 자격증명이 필요하다. 1번과 같은 벽에 부딪힌다.

**3. SSH + GitHub Actions**

- 구성이 단순하고 익숙하다. 
- 22번 포트를 열고 개인 키를 Secrets에 넣어야 한다. 그런데 우테코의 AWS 리소스 보안 규칙상 private 서브넷은 22번 포트 접속이 차단되고, public 서브넷도 우테코 IP에서만 SSH 접속을 허용한다. GitHub Actions 러너의 IP는 매번 달라지므로 이 조건을 만족할 수 없다.

**4. EC2에 GitHub Actions self-hosted runner 설치**

- 러너가 GitHub를 아웃바운드로 폴링하므로 인바운드 포트도, AWS 자격증명도 필요 없다. 1~3번이 막힌 벽을 모두 우회한다.
- ARM64 EC2에서 도니 `docker build`가 네이티브로 동작한다.
- 러너 운영이 팀 몫이 된다. [0013](0013-CI-도구.md)에서 관리형 러너를 택한 근거를 되돌리는 셈이다.
- 배포 대상이 곧 빌드 서버가 되어 빌드가 운영 인스턴스의 자원을 쓴다.
- 실행 로그가 GitHub에 남지만, 러너 자체가 죽거나 큐에 걸리면 워크플로가 시작조차 안 돼 화면에 아무것도 안 뜬다. 결국 EC2에 들어가 러너 상태를 봐야 하는데, 이는 서버 접속을 없애려던 애초의 목적과 어긋난다.

## 선택: AWS CodePipeline (Source → CodeBuild → CodeDeploy)

배포는 EC2의 CodeDeploy 에이전트가 S3에서 번들을 내려받아 `appspec.yml`의 훅을 실행하는 방식이다. 파이프라인은 배포 환경마다 하나씩 두고, `buildspec.yml`·`appspec.yml`·`scripts/`는 두 환경이 공유한다.

**근거**

1. AWS 안에서 도는 서비스라 자격증명 문제가 없다. 각 단계가 자기 서비스 역할로 움직이므로, 발급받을 수 없는 키를 전제하지 않는다.
2. 에이전트가 번들을 당겨오는 방식이라 인바운드 포트를 열지 않는다. 동시에 배포 권한이 개인 계정에서 인스턴스 역할로 옮겨가, 특정 팀원이 없으면 배포가 멈추는 병목이 사라진다. 자동화의 목적이 반복 작업 제거보다 이 병목 해소에 있으므로 이 점이 결정적이다.
3. CodeBuild가 ARM 네이티브 환경 이미지를 제공해, 배포 대상의 아키텍처 제약을 에뮬레이션 없이 만족한다. 프로젝트의 환경 이미지를 `aws/codebuild/amazonlinux-aarch64-standard`로 지정하면 된다(기본값이 x86_64라 명시적으로 바꿔야 한다).
4. 배포 이력과 롤백을 CodeDeploy가 관리한다. 실패하면 이전 성공 리비전을 재배포하므로, 롤백을 직접 구현하지 않아도 된다.

**CI는 GitHub Actions에 그대로 둔다**

PR 단계의 검증은 GitHub 이벤트와 붙어 있는 편이 자연스럽다. 도구를 통일하려고 CI까지 옮기면 [0013](0013-CI-도구.md)에서 얻은 이점을 잃는다.

**배포 그룹 설정**

| 항목 | 값 | 이유 |
|---|---|---|
| 배포 유형 | 현재 위치(In-place) | 블루/그린은 인스턴스가 둘 이상이어야 의미가 있다 |
| 배포 구성 | `CodeDeployDefault.AllAtOnce` | 환경마다 인스턴스가 하나라 다른 구성과 결과가 같다 |
| 로드 밸런서 | 사용 안 함 | 켜면 배포 중 타깃 그룹에서 인스턴스를 뺐다 넣는데, 등록 해제 대기(기본 300초)가 더해져 중단 시간이 오히려 길어진다 |
| 실패 시 롤백 | 사용 | `validate.sh`가 스스로 롤백하지 않으므로 필수다 |

`ApplicationStop` 훅은 두지 않는다. 컨테이너를 미리 내리면 헬스체크 실패로 롤백하는 동안 서비스가 더 오래 죽어 있다.

## 감수하는 것

1. **설정이 저장소와 콘솔에 나뉜다**

   `buildspec.yml`과 `appspec.yml`은 코드로 남지만, 빌드 이미지·권한·트리거 브랜치는 콘솔에만 있어 변경 이력이 남지 않는다. 누가 언제 무엇을 바꿨는지 추적할 수 없다. 환경마다 파이프라인과 빌드 프로젝트가 따로 있으므로 이 대상도 두 벌이고, 한쪽만 고치면 두 환경이 어긋난다.

   대응: 관리 대상이 늘어나면 IaC(CloudFormation, Terraform) 도입을 검토한다.

2. **CodeBuild 로그가 꺼져 있다**

   서비스 역할에 CloudWatch Logs 권한이 없어, 로그를 켜면 빌드가 실패한다. 지금은 빌드가 깨져도 `exit status 1`만 보인다.

   대응: 계정 관리자에게 `logs:CreateLogGroup`, `logs:CreateLogStream`, `logs:PutLogEvents` 권한을 요청한다.

3. **무중단 배포가 아니다**

   `docker compose up -d`로 컨테이너를 교체하는 동안 요청이 끊긴다. 환경마다 인스턴스가 하나라 로드 밸런서 연동을 켜는 편이 오히려 중단 시간을 늘린다.

   대응: 인스턴스를 늘리고 ALB 타깃 그룹 전환 방식으로 바꾼다([0016](0016-HTTPS-처리-지점.md)).

4. **스키마 변경이 포함된 배포는 롤백되지 않는다**

   애플리케이션만 이전 버전으로 돌아가고 스키마는 새 상태로 남는다.

   대응: 마이그레이션 도구(Flyway) 도입을 검토한다.

5. **의존성을 추가할 때마다 arm64 지원 여부를 확인해야 한다**

   arm64 매니페스트를 제공하지 않는 이미지는 쓸 수 없다. 지금 쓰는 `temurin`과 `mysql`은 모두 지원하지만, 확인해야 할 항목이 하나 늘었다. 빌드 환경을 x86으로 되돌리면 이미지가 EC2에서 `exec format error`로 실행되지 않는데, 이 실패는 빌드가 성공한 뒤 배포 단계에서 드러나 원인을 찾기 어렵다.

6. **Ubuntu 26.04는 CodeDeploy 에이전트의 공식 지원 목록에 없다**

   설치와 동작은 확인했으나 보장된 조합이 아니다. 다음 우분투 버전에서 다시 막힐 수 있다.

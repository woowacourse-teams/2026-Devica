# 10. 프론트엔드를 Thymeleaf로 구현한다

- 상태: Accepted
- 날짜: 2026-08-17

## 상황 (조건)

- 프론트엔드 전담자가 없어, 팀원 각자가 백엔드와 함께 화면까지 담당한다.
- 팀에 프론트엔드 개발 경험이 부족해 어떤 방식을 택하든 학습이 필요하다.
- MVP까지 1개월이므로, 화면 구현에 드는 시간이 늘어날수록 검증 시간이 줄어든다.

## 고려한 대안

**1. React / Next.js**

- 동적 인터랙션 구현이 자유로워, 복잡한 화면 흐름을 다루기 쉽다.
- 프론트엔드와 백엔드를 독립적으로 배포·확장할 수 있다.
- AI 도구가 React/Next.js 코드에 익숙해, AI를 활용하면 구현 속도가 빠르다.
- 별도 서버로 분리되므로 CORS 설정, 빌드 파이프라인 등 관리할 지점이 늘어난다.
- 학습 범위가 넓다.

## 선택: Thymeleaf

**근거**

1. 어느 쪽을 택하든 학습이 필요하지만, Thymeleaf는 HTML에 문법을 얹는 방식이라 학습 범위가 좁다. 또한 서버 사이드 렌더링이므로 이미 익숙한 Spring 코드 안에서 화면을 다룰 수 있다.
2. 하나의 애플리케이션에서 화면과 API를 함께 제공하므로, CORS 설정이나 별도 배포 파이프라인 같은 관리 지점이 발생하지 않는다.
3. React/Next.js의 장점인 "AI를 활용하면 구현이 빠르다"는 점은, 프론트엔드가 팀이 직접 통제하기 어려운 영역이라는 전제에서는 유효하다. 다만 이 이점을 얻자고 관리할 지점까지 늘리는 것은 1개월이라는 기간에서 부담이 크다고 판단했다.

## 감수하는 것

1. **클라이언트 상태 기반의 화면 구현이 어렵다**

   기기 추천은 질문과 응답을 반복하는 흐름이라 화면 상태가 자주 바뀐다. Thymeleaf는 서버가 화면을 그리는 방식이므로, 상태 변화를 페이지 전환으로 처리하거나 JavaScript를 직접 작성해야 한다.

   상태 전환에 연동된 애니메이션처럼 사용자 경험을 다듬는 작업도 React에 비해 손이 많이 간다. 검증 단계에서는 흐름이 동작하는 것을 우선하고, 표현은 최소한으로 가져간다.

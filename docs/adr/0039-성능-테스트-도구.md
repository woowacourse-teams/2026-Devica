# 39. 성능 테스트 도구로 k6를 사용한다

- 상태: Accepted
- 날짜: 2026-10-07

## 상황 (조건)

- 목표 데이터는 제품 2만 건 이상, 제품당 판매처 3곳 이상(오퍼 최소 6만 건), 게시글 100만 건 이상이다. 현재 제품 시드는 20건이므로 목표 규모의 테스트 데이터를 별도로 준비해야 한다.
- 목표 부하는 서비스 전체 1,000 RPS다. 경로별 실제 요청 비율과 허용 응답시간은 아직 정해지지 않았다.
- 제품 목록 조회는 CPU·판매처를 조인하고 최저가를 집계한 뒤 정렬·페이징한다. 게시글 목록 조회는 정렬·페이징과 글별 댓글 수 조회를 수행한다. 검색 조건과 페이지 깊이에 따라 비용이 달라질 수 있다.
- 현재 모니터링은 Actuator·Alloy의 앱·호스트 지표를 60초마다 Grafana Cloud Prometheus로 보내고, 요청·오류 로그를 Loki에서 본다. MySQL 내부 지표와 트레이스는 수집하지 않는다.
- 부하 발생기는 앱·DB가 실행되는 서버와 분리해야 한다.

## 고려한 대안

**1. nGrinder**

- JVM 기반 에이전트를 여러 대 사용하고, 웹 UI에서 테스트·결과·대상 서버 모니터링을 관리할 수 있다.
- 기본 설정이 가상 사용자 수 중심이므로 목표 RPS 유지 여부를 별도로 확인해야 한다. 컨트롤러와 에이전트 운영도 필요하다. 스크립트는 Jython·Groovy를 사용한다. 공식 저장소는 2025-09-24부터 읽기 전용이다.

**2. Gatling Community Edition**

- 팀에 익숙한 Java DSL을 사용할 수 있다. `constantUsersPerSec`로 일정한 사용자 유입률을 만들 수 있다.
- 사용자 한 명이 여러 요청을 보내면 사용자/초가 요청/초와 같지 않다. 기본 결과는 실행별 정적 HTML 보고서이며, 공식 OpenTelemetry 결과 연동은 Enterprise Edition 기능이다.

## 선택: 별도 부하 발생기에서 k6를 실행한다

k6는 `constant-arrival-rate`로 반복 시작률을 정하고, `http_reqs`와 `dropped_iterations`로 설정한 부하가 실제로 발생했는지 확인할 수 있다. 반복당 요청 하나로 구성하면 반복/초를 목표 RPS에 대응시킬 수 있다. 결과는 필요할 때 Prometheus remote write로 현재 Grafana 지표와 같은 시간축에 놓을 수 있다.

**근거**

1. 이번 테스트의 기준은 동시 사용자 수보다 실제 1,000 RPS 유입과 그때의 응답이다. k6는 목표 유입률과 실제 요청 수, 발생하지 못한 반복을 함께 확인하기 쉽다.
2. 팀이 이미 Grafana에서 경로별 요청량·지연, JVM·DB 커넥션, 호스트 자원과 로그를 본다. k6 결과를 같은 시간대에 대조하면 발생기에서 본 지연과 서버 증상을 연결할 수 있다.
3. 현재 필요한 것은 조회 병목을 반복 재현하는 것이다. nGrinder의 별도 컨트롤러 운영보다 코드로 시나리오를 관리하는 쪽이 간결하다. Gatling도 유효한 대안이지만, 현재 모니터링과 결과를 연결하는 경로에서 k6가 더 직접적이다.

**적용·검증 범위**

- 목표 규모 데이터를 넣은 비운영 환경에서 제품 목록·상세, 게시글 목록·상세를 개별 측정한 뒤 혼합 부하를 준다. 목록은 필터·검색·가격순·깊은 페이지를 포함하고, ID와 검색 조건을 분산한다.
- 경로별 비중은 임시값을 기록해 시작하고 실제 유입 로그를 확인한 뒤 조정한다. 반복당 요청 하나로 총 1,000 RPS를 설정하며, 단계적으로 올린 뒤 10분 이상 안정 구간을 유지한다.
- 판정에는 설정값뿐 아니라 실제 요청/초, `dropped_iterations`, 경로별 p95·p99, 1초 초과 비율, 실패율을 사용한다. 허용 지연·오류율은 팀의 SLO가 정해진 뒤 확정한다. 현재 Grafana의 '1초 초과 요청 10%' 알림은 참고 기준이다.
- 발생기 CPU·네트워크가 먼저 포화되면 그 결과를 서비스 최대 처리량으로 해석하지 않는다. 특정 SQL이 의심되면 실행 계획과 쿼리 시간을 별도로 확인한다.

이 선택은 1,000 RPS를 달성했다는 뜻이 아니다. 목표 규모 데이터와 별도 발생기를 준비해 실제 요청률을 검증한 뒤 상태를 Accepted로 바꾼다.

## 감수하는 것

1. **JavaScript 시나리오 유지 비용**

   시나리오를 JavaScript로 관리해야 한다.

   대응: API별 짧은 시나리오로 나누고 테스트 데이터·부하 조건을 코드와 함께 기록한다.

2. **부하 발생기 자체의 한계**

   목표율을 설정해도 VU나 발생기 자원이 부족하면 반복이 누락된다. 오픈소스 로컬 실행에서 여러 발생기를 자동 지휘하는 기본 컨트롤러는 없다.

   대응: 발생기 자원과 `dropped_iterations`를 함께 확인한다.

3. **Grafana 연동의 실험적 기능과 메트릭 사용량**

   Prometheus remote write 출력은 현재 실험적 기능이다.

   대응: 우선 로컬 결과를 보관한다. 원격 전송이 필요해지면 버전을 고정하고, 동적 제품 ID·게시글 ID 대신 경로명처럼 값의 종류가 적은 태그를 사용한다.

4. **SQL별 병목 관측의 한계**

   현재 Grafana 지표만으로 느린 SQL을 바로 특정할 수 없다.

   대응: 병목 후보가 드러난 조회는 DB 실행 계획과 쿼리 시간을 별도로 측정한다.

## 이후 변경

- 2026-10-14: 상품 목록 테스트를 실제로 진행하면서 조건 일부를 뒤의 ADR로 다시 정했다.
  판정 기준은 [0040](0040-성능-테스트-판정-기준.md)에서 서버 처리 시간 p95 200ms, 오류율 1%로 정했다.
  측정 범위는 [0041](0041-성능-테스트-측정-범위.md)에서 API 하나씩 개발 서버에서 재기로 하고, 혼합 부하는 미뤘다.
  목표 부하는 [0042](0042-성능-테스트-예상-트래픽.md)에서 서비스 전체 1,000 RPS 대신 홍보 직후 10분간 약 260명으로 정했다.
  부하 발생기는 별도 서버를 두지 않고 팀원 노트북에서 실행했다.
- 2026-10-14: 상태를 Accepted로 바꿨다. 1,000 RPS는 검증하지 않았지만, 상품 목록 테스트에서 k6로 정한 유입률을 걸고 3회 모두 `dropped_iterations`가 0이어서 계획한 부하가 실제로 발생한 것을 확인했다.

# 17. 개발 서버는 public subnet에, 운영 서버는 private subnet에 둔다

- 상태: Accepted
- 날짜: 2026-08-26

## 상황 (조건)

- 실사용자를 받는 서버에 직접 배포해 확인하면, 검증 중인 변경이 그대로 사용자에게 노출된다. 배포된 상태에서만 드러나는 문제를 확인할 별도의 서버가 필요하다.
- 개발 중에는 로그를 보고 컨테이너를 다시 띄우는 일이 잦다. 반면 운영 서버에 사람이 접속할 일은 사고 대응에 한정된다.
- private subnet의 인스턴스에는 AWS 콘솔의 SSM 세션 매니저로만 접근할 수 있다. 팀 IAM 권한으로는 그 밖의 경로를 열 수 없다. 콘솔을 거치는 접속은 파일 전송이나 툴 연동이 불편하다.
- 두 서버 모두 CodeDeploy로 배포되므로([0014](0014-CD-파이프라인.md)), 서버가 인터넷에서 들어오는 연결을 받지 않아도 배포는 성립한다.

## 고려한 대안

**1. 서버 한 대로 개발과 운영을 겸용**

- 인스턴스와 파이프라인이 하나뿐이라 비용과 관리 대상이 절반이다.
- 검증 중인 변경이 사용자에게 그대로 보인다. 배포 실패가 곧 서비스 중단이다.

**2. 두 대 모두 private subnet**

- 인바운드 경로가 하나도 열리지 않아 구성이 일관되고 보안 면에서 낫다.
- 개발 서버까지 콘솔 SSM으로만 접근하게 되어, 잦은 확인 작업의 비용이 계속 발생한다.

## 선택: 개발 서버는 public subnet + SSH, 운영 서버는 private subnet + SSM

운영 서버는 ALB를 통해서만 트래픽을 받는다([0016](0016-HTTPS-처리-지점.md)).

**근거**

1. 두 서버의 접근 빈도와 위험이 다르다. 개발 서버는 자주 들여다보지만 잃을 것이 없고, 운영 서버는 드물게 접근하지만 사용자 데이터가 있다. 같은 기준을 적용하면 한쪽이 반드시 손해를 본다.
2. 콘솔 SSM의 불편은 운영 서버에서는 사고 대응 시에만 발생하지만, 개발 서버에서는 매일 발생한다. 개발 서버에 SSH를 여는 대가로 얻는 시간이 더 크다.
3. 운영 서버를 private에 두어도 배포는 막히지 않는다. CodeDeploy 에이전트가 S3에서 번들을 당겨오는 구조라 인바운드 경로가 필요 없다.

## 감수하는 것

1. **개발 서버에 SSH 포트가 열려 있다**

   인터넷에서 접근 가능한 인바운드 경로가 하나 생겼다. 보안 그룹의 허용 대역을 좁게 유지하지 않으면 그대로 공격면이 된다.

2. **개발 서버는 HTTPS가 아니다**

   ALB를 거치지 않아 `http://<EC2 주소>`로 접속한다. TLS가 필요한 동작(보안 쿠키, 외부 서비스 콜백 등)은 개발 서버에서 검증할 수 없다.

3. **AWS 리소스가 두 벌이 된다**

   EC2·파이프라인·빌드 프로젝트가 환경마다 하나씩이라 비용과 콘솔 설정 대상이 두 배다. 한쪽만 고쳐 두 환경이 어긋나는 일이 생길 수 있다.

4. **두 환경이 같은 `docker-compose.prod.yml`을 쓴다**

   개발 서버도 `SPRING_PROFILES_ACTIVE=prod`로 실행된다. 환경별 설정을 다르게 주려면 compose 파일을 나누고 `buildspec.yml`과 `scripts/deploy.sh`가 환경을 구분하도록 고쳐야 한다.

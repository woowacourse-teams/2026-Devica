# 13. 제품 지표 수집에 PostHog Cloud를 프론트엔드로 붙인다

- 상태: Accepted
- 날짜: 2026-08-19

## 상황 (조건)

- MVP 유스케이스가 실제로 동작하는지 두 지표로 확인해야 한다. 추천 플로우 완주율 60% 이상, 제품 열람률 50% 이상.
- `experiment_event` 테이블에 이미 12종의 행동 이벤트가 쌓이고 있다. **절대 수치는 이 테이블에서 정확히 셀 수 있다.**
- 화면 전환이 URL을 바꾸지 않는다. 템플릿은 `index.html` 하나이고 뷰 5개를 클래스 토글로 전환한다. 따라서 **이탈 지점을 주소로 되짚을 수 없다.**
- 검증 기간의 트래픽은 소규모다.

## 고려한 대안

**1. 자체 DB 집계만 유지한다 (`experiment_event` 쿼리)**

- 광고 차단기의 영향을 받지 않아 수치가 정확하다.
- 이미 구축되어 있어 추가 비용이 없다.
- 숫자가 목표에 미달했을 때 원인을 볼 수단이 없다. 쿼리로는 어느 단계에서 끊겼는지만 알 뿐, 그 화면에서 무슨 일이 있었는지는 알 수 없다.
- 퍼널 같은 분석을 직접 만들어야 한다.

**2. PostHog 서버 사이드 수집 (`posthog-java`)**

- 컨트롤러에서 직접 보내므로 광고 차단기의 영향을 받지 않는다.
- 퍼널 등 분석 기능을 그대로 쓸 수 있다.
- 세션 리플레이가 동작하지 않는다. 브라우저에서만 수집할 수 있는 기능이다.

**3. Google Analytics 4**

- 무료이고 참고 자료가 많다.
- 세션 리플레이가 없다.
- 커스텀 이벤트 기반 퍼널 구성이 PostHog보다 번거롭다.

## 선택: PostHog Cloud (US) + 프론트엔드 수집(posthog-js)

`experiment_event` 적재는 그대로 두고 PostHog를 병행한다. 정확한 절대 수치는 DB에서, 원인 파악은 PostHog에서 본다.

**근거**

1. 지금 필요한 것은 정확한 수치가 아니라 "목표에 미달했을 때 어디서 막혔는가"다. 정확한 절대 수치는 이미 `experiment_event`에서 얻을 수 있으므로, PostHog에 요구하는 것은 원인 파악 수단 하나뿐이다.
2. URL이 바뀌지 않는 구조라 이탈 지점을 주소로 되짚을 수 없고, 세션 리플레이가 사실상 유일한 단서다. 이 기능이 브라우저에서만 동작하므로 대안 2·3이 탈락한다.
3. 검증 기간의 트래픽 규모에서는 무료 티어 안에서 끝난다.

**버전: posthog-js HTML 스니펫, `defaults: '2026-05-30'`**

스니펫 방식은 PostHog가 로더를 자동 갱신하므로 SDK 버전을 직접 관리하지 않는다. 대신 `defaults`에 설정 스냅샷 날짜를 고정해, SDK가 갱신돼도 수집 동작이 말없이 바뀌지 않게 한다.

## 감수하는 것

1. **광고 차단기를 쓰는 사용자의 이벤트가 누락된다**

   PostHog의 "총 방문자 수"를 정확한 값으로 신뢰할 수 없다. 전환율을 보는 목적이므로 검증 자체에는 지장이 없다.

   대응: 절대 수치가 필요하면 `experiment_event` 테이블을 본다.

2. **세션 리플레이 무료 한도(월 5,000건)가 이벤트 한도(월 100만 건)보다 먼저 닿는다**

   사용자 1명이 플로우를 한 번 통과하면 이벤트는 10건 내외지만 리플레이는 1건이다. 트래픽이 늘면 리플레이 쪽이 먼저 막힌다.

   대응: Settings → Project → Replay에서 샘플링 비율을 낮춘다.

3. **Project API Key가 저장소에 커밋된다**

   `phc_` 키는 브라우저 노출을 전제로 만들어진 공개 키라 보안 문제는 없다. 다만 프로젝트를 바꾸려면 템플릿을 고쳐야 하고, 로컬 개발 데이터가 같은 프로젝트로 섞여 들어온다.

   대응: 로컬 데이터는 PostHog 인사이트의 `$host` 필터로 제외한다(코드 0줄). dev/prod 프로젝트를 분리하게 되면 그때 `application.yml` + `@environment.getProperty()`로 뺀다.

4. **같은 행동이 두 곳에 쌓인다**

   `experiment_event`와 PostHog가 같은 이벤트를 각각 보관하므로, 두 저장소의 숫자가 어긋날 수 있다.

   대응: 두 저장소가 이벤트 이름을 공유하게 하고, `sessionId`를 PostHog 속성으로도 실어 한쪽에서 찾은 세션을 다른 쪽에서 바로 조회할 수 있게 한다. 구체적인 이벤트 설계는 [PostHog 세팅 가이드](../POSTHOG_세팅_가이드.md)에 둔다.

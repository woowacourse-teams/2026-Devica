# 상태 모델

화면 상태를 어떤 값으로 두고, 어떻게 동기화하는지 본다. 원본 값과 파생 값이 섞이거나 한 값이 여러 역할을 맡으면, 특정 조작 순서에서만 드러나는 버그가 생긴다.

Hook 호출 규칙이나 effect 의존성 누락처럼 린터(Biome)가 잡는 것은 보지 않는다.

## STATE-1 사용자 입력을 가공한 값으로 되돌려 쓰지 않는다 · 필수

입력값을 trim 같은 방식으로 가공해 조건에 넣은 뒤, effect가 그 조건값으로 입력칸을 다시 채우면 입력 도중 글자가 사라진다. 예를 들어 끝 공백이 지워져 `apple macbook`이 `applemacbook`이 된다.

- 입력 상태를 다른 상태로 덮어쓰는 effect가 있는지 본다. 되돌려 써야 하는 경우는 "조건 지우기"처럼 입력을 비울 때뿐인지 확인한다.

## STATE-2 여러 경로로 들어오는 화면의 돌아갈 위치를 덮어쓰지 않는다 · 권장

같은 화면에 여러 곳에서 들어올 수 있으면, 돌아갈 위치를 한 값으로 고정해 저장하는 순간 일부 경로가 깨진다. 예를 들어 A 화면에 들어갈 때마다 "뒤로 가면 B"로 덮어쓰면, C에서 들어온 사용자도 뒤로 가기에서 B로 가고, B가 보여줄 데이터가 없으면 빈 화면을 보게 된다.

- 화면 이동 상태를 쓰는 곳마다, 현재 화면이 어디인지에 따라 기존 값을 유지해야 하는 경우가 있는지 본다.
- 진입 경로를 모두 나열해 보고, 각 경로에서 "뒤로"를 눌렀을 때 갈 곳을 따라가 본다.

## STATE-3 다시 시작하거나 되돌아올 때 이전 흐름이 남긴 상태를 지운다 · 필수

한 흐름이 실패 플래그, 캐시, 진행 중인 요청, localStorage, 스크롤 위치 같은 상태를 남긴 채 끝나면, 같은 흐름을 다시 시작하거나 다른 화면에서 돌아왔을 때 그 상태가 새 흐름에 섞인다. 예를 들어 요청이 실패한 뒤 조건을 다시 고르면 이전 실패 안내가 그대로 보이고, 서버 데이터가 바뀌어 다시 시작해도 캐시된 옛 데이터로 같은 오류를 반복한다.

코드 한 곳만 봐서는 드러나지 않는다. 조작 순서를 따라가야 한다.

- 이번 변경이 만드는 상태를 나열한다. 컴포넌트 밖(모듈 변수, 캐시, 저장소)에 두는 것은 특히 꼼꼼히 본다.
- 그 상태를 만든 흐름을 "다시 시작"하거나 "다른 화면에 갔다가 돌아오는" 경로를 나열하고, 각 경로에서 상태가 지워지거나 다시 받아지는지 따라가 본다.
- 진행 중인 요청이 있는 채로 화면을 떠났다 돌아오면, 돌아온 화면이 그 요청의 완료를 받는지 본다. 요청 상태만 공유하고 완료 알림은 처음 요청한 쪽만 받으면 로딩이 끝나지 않는다.

## STATE-4 화면에 보여 주는 조건은 요청에 쓴 값과 같은 원본에서 만든다 · 필수

사용자가 고친 값으로 요청을 보내면서 화면에는 고치기 전 값을 요약해 보여 주거나, 같은 주소를 한 화면은 열고 다른 화면은 거부하면, 사용자는 자기 조작이 반영되지 않았다고 믿거나 두 화면 중 하나가 틀렸다고 느낀다.

- 조건을 요약해 보여 주는 곳(로딩 화면, 칩, 제목)마다 그 값이 실제 요청 파라미터를 만든 값과 같은 변수에서 나오는지 본다. 원본 응답과 사용자가 고친 값이 따로 있으면 어느 쪽을 쓰는지 확인한다.
- 같은 주소나 같은 조건을 받는 화면이 둘 이상이면, 필수값 검증과 기본값 처리가 같은 함수를 거치는지 본다.

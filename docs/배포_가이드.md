# 배포 가이드

**서버를 직접 다룰 때 보는 문서다.** 파이프라인이 어떻게 구성됐고 왜 그렇게 정했는지는 [CI/CD와 배포 자동화](CI_CD_구축.md)에, 기술 선택의 근거는 [`docs/adr`](adr/README.md)에 있다. 로컬 개발 환경은 [개발 환경 가이드](개발_환경_가이드.md)에서 다룬다.

---

## 1. 배포는 어떻게 이뤄지나

**손으로 할 일은 없다.** 브랜치에 push하면 해당 환경의 CodePipeline이 돌아 배포까지 끝난다.

| push한 브랜치 | 배포되는 곳 |
|---|---|
| `develop` | 개발 서버 `ec2-devica-dev` |
| `prototype` | 운영 서버 `ec2-devica-prod` |

파이프라인은 소스를 받아 테스트하고, 이미지를 만들어 배포 번들에 실어 보내고, 서버의 CodeDeploy 에이전트가 컨테이너를 교체한 뒤 헬스체크로 확인한다. 실패하면 이전 리비전으로 자동 롤백된다. 각 단계의 상세는 [CI/CD 문서 6절](CI_CD_구축.md#6-cd)에 있다.

배포 결과를 확인하는 곳은 [CI/CD 문서 7절](CI_CD_구축.md#7-배포-결과-확인)에 정리되어 있다.

---

## 2. 서버 구성

| | 개발 (dev) | 운영 (prod) |
|---|---|---|
| 인스턴스 | `ec2-devica-dev` (public subnet) | `ec2-devica-prod` (private subnet) |
| 접속 | SSH | **AWS 콘솔의 SSM 세션 매니저만** — EC2 > 인스턴스 선택 > Connect > Session Manager |
| 접근 경로 | `http://<EC2 주소>` (HTTPS 없음) | `https://` → ALB → EC2 |
| 아키텍처 | 둘 다 ARM64 (Graviton). 서버에서 `uname -m`이 `aarch64` | 〃 |
| 실행 | `docker compose -f docker-compose.server.yml` — 호스트 80 → 컨테이너 8080 | 〃 |
| DB | EC2 안의 MySQL 컨테이너. 볼륨 `mysql-data`로 데이터를 유지 | 〃 |

**두 서버가 같은 compose 파일을 쓴다.** 구성이 같고 값만 다르기 때문이다. 환경 차이는 각 서버의 `.env`가 흡수한다 — `SPRING_PROFILES_ACTIVE`가 `dev`냐 `prod`냐에 따라 스키마 반영 정책과 쿼리 로그가 갈린다.

---

## 3. 설정과 비밀값

**비밀값은 각 서버의 `/opt/app/.env`에만 있다.** 규격은 저장소의 `.env.prod.example`에 있고, 실제 값이 담긴 `.env`는 커밋하지 않는다.

`application-prod.yml`은 `${MYSQL_USER}`처럼 참조만 하므로 커밋한다. 운영 설정이 서버에만 존재하면 **인스턴스를 다시 만들 때 무엇이 적용돼 있었는지 알 방법이 없기** 때문이다.

`.env`의 `IMAGE_TAG`는 배포 스크립트가 갱신한다. 값은 커밋 SHA 앞 7자리이므로, **지금 서버에 떠 있는 코드가 어느 커밋인지 이 파일로 확인한다.**

```bash
grep IMAGE_TAG /opt/app/.env
```

### 설정파일의 구성

새 설정을 추가할 때 어디에 적을지의 기준이다. **기준이 없으면 사람마다 다른 곳에 넣는다.**

| 위치 | 담는 것 | 환경별로 다른가 | 저장소에 커밋 |
|---|---|---|---|
| `application.yml` | 환경과 무관한 공통 설정 | 아니오 | 예 |
| `application-{dev,prod}.yml` | 환경별로 값이 갈리는 설정 (`ddl-auto`, 쿼리 로그 등) | 예 | 예 |
| 각 서버의 `/opt/app/.env` | 비밀값과 환경 식별자 (DB 계정·비밀번호, 활성 프로파일, 이미지 태그) | 예 | **아니오** — 규격 예시 파일만 커밋 |

기준은 하나다. **값이 드러나도 되면 yml에, 드러나면 안 되면 `.env`에 둔다.**

`.env`의 `SPRING_PROFILES_ACTIVE`가 그 서버가 어느 환경인지를 정한다. **값이 없으면 컨테이너를 만들기 전에 배포가 멈춘다.** 지정하지 않으면 기본 프로파일(`local`)로 떠서 엉뚱한 DB를 찾다 실패하는데, 그때는 원인이 한참 뒤에 드러나기 때문이다.

운영의 `ddl-auto`는 `validate`로 **고정**되어 있다. 환경 변수로 열어두면 운영에서 `update`로 뜰 수 있고, 그러면 배포가 곧 스키마 변경이 되어 애플리케이션만 되돌아가고 스키마는 남는다. 즉 롤백이 성립하지 않는다.

## 4. 주의사항

**사고로 이어지는 것들이다. 서버에서 명령을 실행하기 전에 확인한다.**

- **운영에서 `docker compose down -v`를 실행하지 않는다.** `-v`는 볼륨을 지워 DB 데이터를 삭제한다. 앱만 교체할 때는 `docker compose -f docker-compose.server.yml up -d app`을 쓴다.
- **compose 프로젝트 이름을 바꾸지 않는다.** 볼륨 이름에 접두사로 붙어 있어(`app_mysql-data`), 이름이 어긋나면 빈 볼륨이 새로 생겨 **DB가 통째로 사라진 것처럼 보인다.** `scripts/deploy.sh`가 `COMPOSE_PROJECT_NAME=app`을 명시하는 이유다.
- **서버를 새로 만들면 `.env`에 `SPRING_PROFILES_ACTIVE`를 먼저 넣는다.** 없으면 배포가 컨테이너를 만들기 전에 멈춘다. 배포 스크립트는 `IMAGE_TAG` 줄만 갱신하므로 이 값은 사람이 한 번 넣어야 한다.
- **로컬에서 만든 이미지를 서버에 올리지 않는다.** 서버가 ARM64라 x86에서 빌드한 이미지는 `exec format error`로 실행되지 않는다. 이미지는 CodeBuild의 ARM 환경에서만 만든다.
- **인스턴스를 재생성하면 데이터가 사라진다.** DB가 EC2 안의 컨테이너이고 백업 방안이 없다.

---

## 5. 알려진 한계

서버 운영에 관한 것만 적는다. 파이프라인 쪽 한계는 [CI/CD 문서 8절](CI_CD_구축.md#8-한계와-개선-방향)에 있다.

| # | 한계 | 언제 다룰 것인가 |
|---|---|---|
| 1 | DB에 백업이 없다 | 인스턴스 장애 시 데이터가 사라진다. `mysqldump` 주기 실행이나 RDS 이전을 별도 이슈로 |
| 2 | 스키마 변경 이력이 남지 않는다 | 운영은 `ddl-auto: validate`로 고정되어 있다. **엔티티가 바뀐 배포는 스키마를 먼저 반영하지 않으면 기동에 실패한다.** Flyway 도입 전까지는 수동으로 반영한다 |
| 3 | 개발 서버에 HTTPS가 없다 | TLS가 필요한 동작은 개발 서버에서 검증할 수 없다 ([ADR 0017](adr/0017-서버-환경-분리.md)) |
| 4 | 로컬(IDE 실행)과 서버(컨테이너 실행)의 실행 방식이 다르다 | 컨테이너 환경에서만 드러나는 문제는 배포 단계에서 처음 확인된다 ([ADR 0007](adr/0007-컨테이너-적용-범위.md)) |

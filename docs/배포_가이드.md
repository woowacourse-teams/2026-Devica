## 2. 서버 구성

현재 확인된 사항이다. 서버를 다루기 전에 먼저 읽는다.

| 항목 | 내용 |
|---|---|
| 인스턴스 아키텍처 | **ARM64 (Graviton)**. 서버에서 `uname -m` 이 `aarch64` 로 확인되었다 |
| 서버 접근 | SSH가 열려 있지 않다. **SSM 세션 매니저**로 접속한다 (AWS 콘솔 > EC2 > 인스턴스 선택 > Connect > Session Manager) |
| 트래픽 경로 | ELB → EC2 **80** → 컨테이너 **8080**. `docker-compose.prod.yml` 이 호스트 80을 컨테이너 8080에 매핑한다 |
| 운영 DB | EC2 내 MySQL 컨테이너. 볼륨 `mysql-data` 로 데이터를 유지한다 |

## 3. 설정 파일

**로컬 개발에는 쓰이지 않는다.** 배포 동작을 확인할 때만 읽으면 된다.

| 파일 | 역할 |
|---|---|
| `Dockerfile` | 빌드된 jar 를 이미지로 감싼다 |
| `docker-compose.prod.yml` | 운영에서 앱 + DB 를 띄운다 |
| `application-prod.yml` | 운영 프로파일 설정. 비밀값은 참조만 한다 |
| `.env.prod.example` | 서버 `/opt/app/.env` 의 규격. 실제 값이 담긴 `.env` 는 커밋하지 않는다 |

**`Dockerfile` 은 jar 를 빌드하지 않는다.** 이미 만들어진 `build/libs/*.jar` 를 COPY 할 뿐이라, 이미지를 만들려면 jar 빌드가 먼저다.

```bash
./gradlew bootJar && docker build -t devica .
```

> 이미지 안에서 Gradle 을 돌리면 컨테이너가 매번 새로 시작해 **의존성 캐시가 남지 않는다.** CI/CD 러너에서 빌드하면 캐시가 재사용되므로 배포마다 의존성을 다시 받지 않아도 된다. 대신 `docker build` 단독으로는 이미지가 만들어지지 않는다는 점을 감수한다.

**비밀값은 서버의 `/opt/app/.env` 에만 있다.** `application-prod.yml` 은 `${MYSQL_USER}` 처럼 참조만 하므로 커밋한다. 운영 설정이 서버에만 존재하면 **인스턴스를 다시 만들 때 무엇이 적용돼 있었는지 알 방법이 없기** 때문이다.

## 5. 주의사항

**사고로 이어지는 것들이다. 서버에서 명령을 실행하기 전에 확인한다.**

- **운영에서 `docker compose down -v` 를 실행하지 않는다.** `-v` 는 볼륨을 지워 DB 데이터를 삭제한다. 앱만 교체할 때는 `docker compose -f docker-compose.prod.yml up -d app` 을 쓴다.
- **Windows나 Intel Mac에서 빌드한 이미지는 그대로 실행되지 않는다.** 서버가 ARM64이기 때문이다. GitHub Actions 의 arm64 러너(`ubuntu-24.04-arm`)를 쓰면 에뮬레이션 없이 빌드할 수 있고, public 저장소라 비용도 들지 않는다.
- **인스턴스를 재생성하면 데이터가 사라진다.** 운영 DB가 EC2 내 컨테이너이고, 백업 방안이 아직 없다.

## 6. 알려진 한계와 다음 액션

| # | 한계 | 언제 다룰 것인가 |
|---|---|---|
| 1 | 운영 DB에 백업이 없다 | 인스턴스 장애 시 데이터가 사라진다. `mysqldump` 주기 실행이나 RDS 이전을 별도 이슈로 |
| 2 | 배포가 자동화되어 있지 않다 | CD 파이프라인 구축을 후속 이슈로 진행 |
| 3 | 스키마 변경 이력이 남지 않는다 | 초기에는 `DDL_AUTO=update` 로 자동 반영한다. 실사용자 데이터가 쌓이면 `validate` 로 되돌리고 Flyway 도입 |
| 4 | 로컬(IDE 실행)과 운영(컨테이너 실행)의 실행 방식이 다르다 | 컨테이너 환경에서만 드러나는 문제는 배포 단계에서 처음 확인된다 ([ADR 0007](docs/adr/0007-컨테이너-적용-범위.md)) |

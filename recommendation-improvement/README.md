# 제품 추천 개선

**사용자 피드백과 행동 지표를 바탕으로 제품 추천을 개선하는 시스템이다.** 피드백 분석부터 제품 추천 정의서(이하 정의서)를 고친 PR 작성까지 자동으로 하고, 팀원은 그 PR 을 검토해 승인한다.

정의서는 제품 추천의 질문과 규칙을 담은 YAML 파일로, 사용 목적마다 하나씩 `src/main/resources/recommendation/purposes/` 에 있다. 이 시스템은 정의서의 규칙과 설문(질문·선택지)을 고친다. 매핑과 점수 구간은 여러 규칙의 효과를 함께 바꾸므로 팀원이 고친다.

### Metric Collector

> 사용자 지표로 개선 가설을 세워 피드백을 만든다

- 사용자 행동 지표에서 제품 추천 결과가 맞지 않았다는 신호를 찾는다.
- 사용자가 바꾼 답과, 그 때문에 어느 항목이 과하거나 부족했다고 추정되는지를 담아 피드백을 만든다.
- 같은 권장안의 같은 항목을 같은 방향으로 지적한 세션은 답 조합이 달라도 한 피드백으로 묶고, 답 조합마다 주소와 건수를 적는다.
- 규칙을 고치면, 그 규칙이 적용되는 사용자의 지표는 고친 규칙이 배포된 뒤부터 다시 수집한다.
- 배포된 개선도 다시 지표에 쌓이므로, 개선이 지나쳤다면 반대 방향의 가설로 이어진다.
- 설문 쪽은 질문 화면의 체류 시간과 이탈, 어디에도 쓰이지 않는 질문에서 설문 지표 피드백을 만든다.

하지 않는 것:

- 근거가 기준에 못 미치거나, 같은 신호의 피드백이 열려 있거나 조회 기간 안에 팀원이 닫았으면 만들지 않는다. 열린 피드백의 신호가 기준 아래로 줄면 닫는다.
- 개인을 식별할 수 있는 정보는 남기지 않는다.

### Feedback Analyzer

> 피드백을 분석해 개선 지시를 내린다

- 피드백을 재현해 원인을 찾고, 판단을 정한다: 
  - 개선 지시 / 보류 / 팀원이 직접 처리 / 이미 바뀜 / 재현할 수 없음
- 근거에 지표 추정이 들어간 개선 지시는 별도로 표시한다.
- 머지되지 않은 개선은 반려 사유와 함께 다시 판단한다. 반려되면 같은 근거로 다른 규칙을 찾지 않는다. 규칙을 새로 더하는 것도 다른 규칙을 찾는 것으로 본다.
- 결과 의견 중 원인이 질문인 것은 원래 이슈의 라벨을 바꿔 설문 쪽으로 넘긴다.
- 설문 피드백은 변경의 위험에 따라 다른 조건으로 설문 개선 지시를 낸다. 모든 사용자가 보는 화면이라, 결과에 쓰이는 코드를 지우거나 바꾸려면 서로 다른 사용자 의견 2건이 있어야 한다.

하지 않는 것:

- 정의서를 고치지 않는다.
- 같은 항목에 처리 중인 개선 지시가 있으면 새로 내지 않는다.

### Recommendation Improver

> 개선 지시대로 정의서를 개선하고 PR 을 올린다

- 개선 지시대로 정의서를 개선하고, 결과가 지시의 기대와 같은지 검증한 뒤 PR 을 올린다.
- 설문 개선 지시로 질문을 지우거나 코드를 바꾸면 옛 코드를 지운 코드 목록에 남긴다. 서버가 옛 결과 링크의 답을 지금 설문에 맞게 바꿔 읽어, 옛 링크와 피드백 주소가 계속 열린다([ADR 0052](../docs/adr/0052-옛-답-변환-위치.md)).
- PR 을 올리지 못하면 그 결과를 남겨 Feedback Analyzer 가 다시 판단하게 한다.

하지 않는 것:

- 피드백 원문을 읽지 않는다.
- 지시 밖은 고치지 않는다.
- 기대와 다르면 PR 을 올리지 않는다.

### 팀원

> PR 을 승인하고, 정의서로 고칠 수 없는 피드백을 처리한다

- 개선 PR 을 검토해 승인한다.
- Feedback Analyzer 가 정의서로 고칠 수 없다고 표시한 피드백(매핑·점수 구간·코드 변경, 루프가 하지 않는 설문 변경, 제품 추천과 무관한 제보)과 개선 PR 이 반려된 피드백을 직접 처리하거나 닫는다.
- 쓰이지 않는 질문의 설문 지표 피드백을 보고, 지워도 되면 `product-recommendation-approved` 라벨을 단다.
- 판단이 "이미 바뀜"이나 "재현할 수 없음"인 피드백을 확인해 닫는다.

## 원칙

- 구성 요소는 서로를 직접 부르지 않고 피드백, 분석 결과·개선 지시, 개선 PR, 개선 결과로만 이어진다. 그래서 각 구성 요소의 구현을 따로 바꿀 수 있다.
- 사용자가 직접 쓴 피드백은 Feedback Analyzer 만 읽는다. Recommendation Improver 는 팀원이 쓴 지시만 따른다.
- 개선 지시는 피드백이 짚은 원인이 정의서의 전제와 어긋나거나, 사용자가 기댄 답을 보는 규칙이 없거나(이때는 규칙을 더한다), 같은 규칙을 같은 방향으로 가리키는 피드백이 여럿이거나, 지표 피드백의 바꾼 답이 특정 규칙을 가리키거나, 추천 결과를 직접 고친 세션이 2건 이상이고 고친 값이 특정 규칙을 가리킬 때만 낸다. 주소가 여럿이면 같은 규칙을 가리키는 주소끼리 묶어 가장 큰 묶음으로 센다.
- 개선은 결과 변화를 추적할 수 있는 최소 단위(규칙 하나를 고치거나 더하기, 질문 하나를 고치기)로 하고, 열린 개선 PR 은 규칙 쪽과 설문 쪽을 합쳐 한 번에 하나만 둔다. 같은 정의서와 스냅숏을 두 쪽이 함께 고치지 않게 하기 위해서다. 그래서 개선 PR 검토를 미루면 두 쪽이 함께 멈춘다.
- 개선 PR 이 승인·머지되면 근거가 된 피드백을 닫는다. 머지되지 않으면 그 사유와 함께 Feedback Analyzer 가 다시 판단한다.
- 지표 추정에 기댄 개선은 개선 지시와 개선 PR 에 표시한다. 검토할 때 사용자가 직접 말한 것과 구분하기 위해서다.

```
recommendation-improvement/

    artifacts/               산출물의 형식
    components/              구성 요소의 명세
    binding.md               산출물과 저장 위치의 바인딩
  metric-collector/          구현. 지금은 에이전트가 예약 실행으로 따르는 지시문(prompt.md)과 스크립트
  feedback-analyzer/
  recommendation-improver/
  common.py                  세 구현이 함께 쓰는 스크립트
```

구현은 `interface/` 에 의존하고 `interface/` 는 구현을 모른다.
## 사용 방법

### 피드백 현황 보기

피드백은 결과에 대한 `product-recommendation-feedback` 라벨 이슈와, 설문에 대한 `product-recommendation-survey-feedback` 라벨 이슈다. 사용자는 결과 화면과 질문 화면의 버튼으로 각각 남긴다. 종류는 제목 머리말로 구분한다.

| 라벨 | 머리말 | 종류 |
|---|---|---|
| 결과 | `[제품 추천 의견]` | 사용자가 남긴 피드백 |
| 결과 | `[제품 추천 지표]` | Metric Collector 가 지표에서 찾은 피드백 |
| 설문 | `[제품 추천 설문 의견]` | 사용자가 남긴 피드백 |
| 설문 | `[제품 추천 설문 지표]` | Metric Collector 가 지표에서 찾은 피드백 |
| 설문 | `[제품 추천 의견]` | 원인이 질문이라 설문 쪽으로 넘긴 결과 피드백 |

각 피드백의 상태는 Feedback Analyzer 가 남긴 분석 결과의 판단에 드러난다.

| 판단        | 뜻                        | 팀원이 할 일     |
|-----------|--------------------------|-------------|
| 개선 지시     | 개선 PR 이 올라온다             | PR 을 검토한다   |
| 보류        | 근거가 더 모이기를 기다린다          | 없다          |
| 팀원이 직접 처리 | 정의서로 고칠 수 없거나, 개선이 반려됐다  | 직접 고치거나 닫는다 |
| 이미 바뀜     | 사용자가 본 뒤 다른 개선으로 이미 고쳐졌다 | 확인하고 닫는다    |
| 재현할 수 없음  | 질문이 바뀌어 같은 결과를 볼 수 없다    | 확인하고 닫는다    |
| 설문이 바뀌어 재현할 수 없음 | 질문이 바뀌어 같은 결과를 볼 수 없지만, 가리키는 규칙은 계속 센다 | 확인하고 닫는다 |
| 설문 쪽으로 넘김 | 원인이 질문이라 설문 쪽에서 판단한다 | 없다 |

처리를 멈추고 싶은 피드백은 이슈를 닫는다. 닫힌 이슈의 개선 지시는 Recommendation Improver 가 처리하지 않고, Feedback Analyzer 도 다시 보지 않는다. 지표 피드백은 세션 기록이 조회 기간 안에 남아 있어도 Metric Collector 가 같은 신호로 다시 만들지 않는다.

### 개선 PR 검토하기

개선 PR 마다 아래를 확인한다.

- 바꾸거나 더한 규칙이 하나뿐인가.
- 더한 규칙이면, 조건이 피드백 사용자가 고른 답으로만 되어 있고 같은 답을 고른 다른 사용자에게 걸려도 맞는가. OS 전용이면 그 OS 에만 해당하는 이유인가.
- 지적한 항목 밖의 값도 바뀌었으면(예: Mac 은 메모리가 오르면 CPU 도 오른다) 그 변화까지 받아들일 만한가.
- 재현 사례의 결과 변화가 피드백이 지적한 방향과 맞는가.
- 영향 범위(바뀐 사례 수, 대표 사용자 중 바뀐 것)가 근거 피드백으로 바꿔도 될 만큼인가. 답별로 나눈 수에 피드백과 상관없는 사용자가 섞여 있지 않은가.
- 같은 규칙을 최근에 반대로 바꾼 적이 있으면, 고쳤다 되돌리는 것이 아닌가.
- 지표 추정 표시가 있으면, 추정한 항목과 방향이 그럴듯한가.
- 근거 피드백의 분석 결과 "팀원이 정할 것"에 작업 이슈로 넘길 지적이 적혀 있으면 넘겼는가. 머지되면 근거 피드백이 닫혀 남은 지적이 묻힌다.

설문 개선 PR 은 아래도 확인한다.

- 바뀐 질문 화면의 문구가 피드백 한 건의 표현을 옮긴 것이 아니고, 연락처·상호 같은 것이 섞이지 않았는가.
- 문구만 고쳤다면 뜻이 그대로인가. 뜻이 바뀌면 코드도 바꿔야 한다.
- 새 선택지가 기존 선택지의 범위를 바꾸지 않는가.
- 변환 표대로 옛 답을 읽어도 되는가. 영향받는 열린 의견 이슈와, 스냅숏의 이름 있는 사례 중 답이 지워진 것의 결과 변화가 받아들일 만한가.

승인해 머지하면 근거 피드백이 닫힌다. 반려할 때는 **사유를 PR 에 남기고 닫는다.** Feedback Analyzer 가 그 사유를 근거에 더해 다시 판단한다. 사유 없이 닫으면 같은 판단을 다시 할 수 있다. 다른 규칙이 원인이라고 보면 사유에 그 규칙을 적는다. 적지 않으면 그 근거 피드백은 "팀원이 직접 처리"로 넘어온다.

### 팀원이 직접 처리할 피드백

판단이 "팀원이 직접 처리"인 이슈는 분석 결과에 무엇을 왜 사람이 고쳐야 하는지 적혀 있다. 매핑·점수 구간·코드 변경, 루프가 하지 않는 설문 변경, 제품 추천과 무관한 제보, 개선 PR 이 반려된 피드백이 여기에 해당한다. 개선 지시가 난 피드백에 남은 지적은 여기가 아니라 위의 개선 PR 검토에서 작업 이슈로 넘긴다. 머지되면 그 피드백이 닫히기 때문이다.

지적을 두 종류로 나눠 처리하고, 모두 끝났을 때 이슈를 닫는다. 어느 쪽이든 무엇을 어디로 넘겼는지 댓글로 남긴다.

- **제품 추천 항목**(질문·선택지·근거 문장·규칙): 반영되고 나서 닫는다. 작업은 이 이슈에서 추적한다.
- **프로젝트 개선 항목**(제품 목록, 가격, 사용 목적 추가 등): 팀원이 판단해 작업 이슈로 올리거나, 반영하지 않는 이유를 댓글로 남기면 끝이다. 작업 이슈의 진행은 그쪽에서 추적한다.

### 설문을 손으로 고칠 때

- 결과 피드백을 손으로 설문 쪽에 넘길 때는 라벨만 바꾸지 말고 [넘김](interface/artifacts/handover.schema.yml) 댓글을 직접 단다. 넘김이 없으면 설문 쪽이 판단하지 않는다.
- 질문·선택지를 지우거나 코드를 바꾸면 지운 코드 목록(`<사용 목적>.retired.yml`)에 줄을 남긴다. 지운 코드는 줄이 기한으로 지워진 뒤에도 다른 뜻으로 다시 쓰지 않는다. 그 코드가 든 옛 링크와 반려 이력이 다른 뜻으로 읽히기 때문이다. Recommendation Improver 는 이 목록의 이력으로 재사용을 막는다.
- 기한이 지난 줄은 지우지 않아도 된다. 다음에 그 목록을 고치는 개선 PR 이 함께 지운다.
- 지운 질문·선택지를 되살릴 때는 목록에서 그 줄을 지우고 문구를 그 줄의 `was` 그대로 되돌린다. 같은 코드를 다른 뜻으로 다시 쓰지 않기 위해서다.

### 기준값 고치기

지표 피드백이 너무 자주 나오거나 안 나오면 [기준값](interface/components/metric-collector.md#기준값)의 신호 최소 건수를 조정한다. 처음 값 2 는 5주간 결과 조회 128건, 답을 바꿔 다시 본 세션 7건이던 때 정한 것이다. 신호를 답 조합과 무관하게 묶기로 한 때(2026-11)는 5주간 추천 결과를 직접 고친 세션이 2건이었다.

## 실행

- 세 구성 요소는 서로 독립적으로 실행된다. 실행 순서와 주기는 맞추지 않아도 된다. 각 구성 요소는 실행될 때 그때까지 쌓인 산출물을 처리한다.
- 각 구성 요소는 한 번에 하나만 실행된다. 겹쳐 실행되면 같은 산출물을 두 번 남긴다.
- Recommendation Improver 는 사용자의 작업과 분리된 작업 공간에서 실행된다.
- 구성 요소마다 필요한 권한과 환경은 [`interface/components/`](interface/components/)의 "의존하는 외부 시스템"에 있다.

지금은 에이전트가 정해진 주기마다 지시문을 따라 실행된다. 구성 요소마다 지시문(`<구성 요소>/prompt.md`)과 스크립트(`signals.py`·`snapshot.py`, 공통 `common.py`)가 있고, 실행될 때마다 `origin/develop` 에서 새로 읽어 온다. 매번 같은 준비는 실행 스크립트(`schedule/run.sh`)가 하고, 에이전트는 지시문의 판단만 맡는다. 리뷰를 거쳐 머지된 내용만 실행되고, 지시문이 바뀌어도 작업을 다시 등록하지 않아도 된다. 구현을 바꾸면 이 절과 구성 요소 디렉터리를 새 구현의 것으로 바꾸고, 이전 작업은 끈다.

### 1. 준비하기

실행 방식과 상관없이 필요하다. 하나라도 빠지면 작업이 중간에 멈춘다.

1. **GitHub CLI**: 레포 멤버 계정으로 로그인하고, 아래 두 번째 줄이 `true` 를 출력하는지 본다.
   ```bash
   gh auth status
   gh api repos/woowacourse-teams/2026-Devica --jq .permissions.push
   ```
2. **`python3`, `ruby`**: `python3 --version` 과 `ruby --version` 이 버전을 출력하는지 본다. macOS 에서 실패하면 `xcode-select --install` 을 실행한다.
3. **레포 clone**: 이 레포의 clone 하나를 작업 폴더로 정한다. 평소 쓰는 clone 이어도 된다.
4. **Feedback Analyzer**: 아래 두 줄이 모두 `200` 을 출력하는지 본다.
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' http://dev.devica.co.kr/api/usage-purposes/BACKEND_DEVELOPMENT/recommendation
   curl -s -o /dev/null -w '%{http_code}\n' https://api.devica.co.kr/api/usage-purposes/BACKEND_DEVELOPMENT/recommendation
   ```
5. **Recommendation Improver**: JDK 와 Docker Desktop 을 설치하고([백엔드 개발 환경 가이드](../docs/백엔드_개발_환경_가이드.md)), 작업이 실행되는 동안 Docker Desktop 을 켜 둔다.

### 2. 예약 작업 등록하기

팀원 한 명만 등록한다. 여러 명이 등록하면 같은 작업이 겹쳐 실행된다. macOS 에서 Claude Code 를 쓰면 [macOS 와 Claude Code 로 등록하기](#macos-와-claude-code-로-등록하기), 아니면 [다른 방법으로 등록하기](#다른-방법으로-등록하기)를 따른다.

#### macOS 와 Claude Code 로 등록하기

1. **Claude Code 확인**: 아래가 버전을 출력하는지 본다. 실패하면 Claude Code 를 설치하고 개인 구독 계정으로 로그인한다.
   ```bash
   claude --version
   ```
2. **PostHog 연결**: claude.ai 의 설정 → 커넥터에서 PostHog 를 팀 PostHog 계정으로 연결한다. 그 뒤 `claude` 를 열고 아래 두 줄을 차례로 보낸다. 두 번째 답에 `638813` 이 나오면 된다.
   ```
   PostHog 활성 프로젝트를 638813 으로 바꿔줘
   PostHog 활성 프로젝트 확인해줘
   ```
3. **등록**: 작업 폴더에서 아래를 실행한다. `등록: <구성 요소>` 가 세 줄 나오면 된다.
   ```bash
   recommendation-improvement/schedule/install.sh
   ```
4. **켜 두기**: 작업이 실행되는 동안 Mac 을 켜 두고 로그인해 둔다. `metric-collector` 는 매일 09:00, `feedback-analyzer` 는 매일 10:00, `recommendation-improver` 는 4시간마다 실행된다.

#### 다른 방법으로 등록하기

1. **PostHog 연결**: 에이전트에 PostHog MCP 서버를 팀 PostHog 계정으로 연결하고, 활성 프로젝트를 `638813` 으로 맞춘다. 에이전트에게 활성 프로젝트를 물어 `638813` 이 나오면 된다.
2. **작업 만들기**: 아래 표의 구성 요소마다 예약 작업을 하나씩 만든다. 작업 폴더는 1-3 의 clone, 주기는 표대로 정한다.
3. **준비와 프롬프트**: 지시문은 `schedule/run.sh` 가 준비(환경 변수, 잠금, 실행 기록 파일, 스크립트·스키마 복사, worktree)를 마쳤다고 전제한다. 그 에이전트 방식으로 같은 준비를 하는 실행 스크립트를 만들고, `run.sh` 처럼 `git show origin/develop:recommendation-improvement/<구성 요소>/prompt.md` 의 출력을 지시문으로 넘긴다. 무엇을 준비하는지는 `run.sh` 의 주석에 있다.
4. **권한**: 표의 권한을 실행 중에 묻지 않도록 미리 허용한다.

| `<구성 요소>` | 주기 | 허용할 권한 |
|---|---|---|
| `metric-collector` | 하루 한 번 | 셸 명령 `git` `gh` `python3` `ruby`. `~/.devica-product-recommendation/metric-collector` 쓰기. PostHog `project-get`, `execute-sql` |
| `feedback-analyzer` | 하루 한 번, `metric-collector` 보다 늦은 시각 | 셸 명령 `git` `gh` `python3` `ruby`. `~/.devica-product-recommendation/feedback-analyzer` 쓰기 |
| `recommendation-improver` | 몇 시간마다 | 셸 명령 `git` `gh` `python3` `ruby` `docker` `./gradlew`. `~/.devica-product-recommendation/recommendation-improver` 쓰기와 그 안의 작업 공간 파일 편집 |

### 3. 첫 실행 확인하기

구성 요소마다 한 번 바로 실행하고, 끝나면 가장 최근 실행 기록을 연다. macOS 와 Claude Code 로 등록했다면 작업 폴더에서 아래 첫 줄로 실행한다. 다른 방법으로 등록했다면 등록한 작업을 바로 실행한다.

```bash
recommendation-improvement/schedule/run.sh <구성 요소>
ls -t ~/.devica-product-recommendation/<구성 요소>/runs | head -1
```

기록에 오류가 있으면 아래 문제 해결을 본다. 이슈·댓글·PR 없이 기록만 남아도 정상이다.
피드백 이슈에 분석 결과 댓글이 달리면 [피드백 현황 보기](#피드백-현황-보기)대로 처리한다.

### 문제 해결

| 이럴 때 | 이렇게 한다 |
|---|---|
| 기록에 "PostHog 커넥터가 프로젝트 … 를 가리켜 멈춘다"가 있다 | 커넥터의 활성 프로젝트를 `638813` 으로 바꾼다 |
| 기록에 `fetch` 실패가 있다 | `gh auth status` 로 로그인 상태를 다시 본다 |
| 기록에 API 호출 실패가 있다 | 개발·운영 서버가 떠 있는지, 지금 네트워크에서 접속되는지 본다 |
| 기록에 테스트 DB 연결 실패가 있다 | Docker Desktop 을 켠다 |
| 기록에 push 실패가 있다 | 로그인한 계정으로 `git push` 가 되는지 본다 |
| "다른 실행이 진행 중이라 끝낸다"고 하고 끝난다(실행 기록은 남지 않고 터미널이나 `launchd.log` 에 찍힌다) | 앞 실행이 아직 돌고 있거나, PC 가 꺼져 잠금 디렉터리가 남은 것이다. 6시간이 지나면 다음 실행이 스스로 지운다. 바로 돌리려면 `rm -rf ~/.devica-product-recommendation/<구성 요소>/lock` 으로 지운다 |

### 설정값

GitHub 레포, API 주소, PostHog 프로젝트, 상태 디렉터리, 개선 브랜치 이름은 각 `prompt.md` 의 설정 표에 있다. 조회 기간과 신호 최소 건수는 [기준값](interface/components/metric-collector.md#기준값)에 있다. 고쳐서 머지하면 다음 실행부터 바뀐 값으로 실행된다.

### 머지 전에 시험하기

브랜치를 push 한 뒤 `SELF_REF=origin/<브랜치> recommendation-improvement/schedule/run.sh <구성 요소>` 로 한 번 실행한다. 지시문과 스크립트를 그 브랜치에서 읽어 온다. 정의서는 `origin/develop`·`origin/main` 에서 읽으므로 브랜치의 정의서 변경은 시험에 반영되지 않는다. 시험 중에도 실제 이슈에 댓글이 달리고 PR 이 올라가므로, 시험용 피드백·개선 지시만 있을 때 돌린다.

### 멈추기

등록한 방식에서 작업을 끄거나 지운다. macOS 와 Claude Code 로 등록했다면 `recommendation-improvement/schedule/install.sh uninstall` 을 실행한다. Recommendation Improver 를 더 쓰지 않을 거면 작업 공간도 지운다. 다른 방법으로 등록했다면 `-C` 뒤를 작업 폴더로 바꾼다.

```bash
git -C ~/.devica-product-recommendation/recommendation-improver/repo worktree remove --force ~/.devica-product-recommendation/recommendation-improver/worktree
```

실행 기록은 `~/.devica-product-recommendation/<구성 요소>/runs/` 에 그대로 남는다.

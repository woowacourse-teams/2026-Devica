# 상품 목록 조회 테스트

`GET /api/product-categories/{categoryCode}/products` (`categoryCode`는 `LAPTOP`)

이 문서는 시나리오와 가정, 측정 전 데이터 확인을 다룬다. 돌리고 기록하는 방법은 [성능 테스트 안내](../../README.md)에, 예상 트래픽(260명)의 근거는 [기준과 근거](../../기준과_근거.md)에 있다.

## 시나리오

### 재현할 흐름

사용자는 두 화면에서 상품 목록을 본다.

| 화면 | 들어오는 경로 | 요청 조건 |
| --- | --- | --- |
| 맞춤 목록 | 추천 결과에서 들어온다. 맥·윈도우 탭 중 하나를 본다 | 그 탭의 권장 사양(OS, CPU 등급, 메모리, 스토리지) |
| 전체 목록 | 상단 메뉴나 맞춤 목록의 "전체 보기"로 들어온다 | 필터 없음 |

두 화면 모두 필요하면 정렬을 바꾸고, 무한 스크롤로 한 페이지씩 내려본다.

테스트는 이 흐름을 **세션**(사용자 한 명이 목록 하나를 스크롤하는 과정) 단위로 재현한다. 정렬이나 탭을 바꾸면 목록을 첫 페이지부터 다시 받으므로 새 세션으로 본다.

### 필터 조합

맞춤 목록의 필터는 추천 결과에서 만들어지고, 추천이 낼 수 있는 조합은 유한하다. 그래서 대표 조건을 고르지 않고 **조합 전체**를 쓴다.

| OS | CPU 등급 | 메모리 (GB) | 스토리지 (GB) | 조합 수 |
| --- | --- | --- | --- | --- |
| Mac | `BASIC` | 16 / 24 / 32 | 256 / 512 / 1024 | 9 |
| Mac | `PRO` | 24 / 48 | 256 / 512 / 1024 | 6 |
| Windows | `P_HS` / `H` / `HX` | 16 / 24 / 32 / 48 | 256 / 512 / 1024 | 36 |

- 조합은 `LaptopBackendAlgorithm`의 결과 범위를 옮겨 적은 것이다. 알고리즘이 낼 수 있는 값이 바뀌면 `sessions.js`와 아래 데이터 확인 쿼리를 함께 고친다.
- 맞춤 목록의 키워드·브랜드·가격 필터는 추천에서 만들어지지 않으므로 제외한다.

전체 목록은 **필터 없이** 요청한다. 사용자가 직접 거는 조건은 조합이 사실상 무한하고 실측 데이터도 없어(아래 가정 표), 진입 직후 상태만 재현한다. 필터가 없으면 노트북 전체의 최저가를 구해 정렬해야 하므로 이 API에서 가장 무거운 조건이다.

### 세션 구성

데이터가 없는 사용자 행동은 균등으로 가정한다.

| 항목 | 내용 |
| --- | --- |
| 화면 | 맞춤 목록 : 전체 목록 = 1 : 1 |
| 맞춤 목록의 탭 | 맥 : 윈도우 = 1 : 1. 필터 조합은 그 OS의 조합 중 균등 |
| 정렬 | 그 화면에서 고를 수 있는 정렬 중 균등 |
| 페이지 | `size=10`, `page=0 → 1 → 2`를 앞 응답을 받은 뒤 차례로. 페이지마다 요청 1건 |
| 다음 페이지 | `hasNext: false`이거나 응답이 200이 아니면 다음 페이지를 요청하지 않는다 |
| 스크롤 간격 | 1~5초 무작위 |
| 재현성 | 시드를 고정해 세션 조건 목록을 만들고, 모든 회차에서 같은 순서로 쓴다 |

화면에 따라 정렬 선택지와 기본값이 다르다.

| 화면 | 정렬 선택지 | 기본값 |
| --- | --- | --- |
| 맞춤 목록 | 추천순, 가격 낮은순, 가격 높은순 | 추천순 |
| 전체 목록 | 가격 낮은순, 가격 높은순 | 가격 낮은순 |

### 부하

예상 트래픽(홍보 직후 10분간 약 260명 유입)을 세션 단위로 바꾸면 다음과 같다.

| 항목 | 값 | 계산 |
| --- | --- | --- |
| 방문당 목록 진입 | 5번 | 정렬이나 탭을 바꾸면 첫 페이지부터 다시 받으므로 진입 한 번으로 센다 |
| 10분간 세션 | 1,300개 | 260명 × 5번 |
| 세션당 요청 | 3건 | 3페이지 × 1건 |
| 평균 RPS | 약 6.5 | 1,300 × 3 ÷ 600초 |

카페 글은 게시 직후에 조회가 몰리므로, 10분 동안 일정하게 걸지 않고 앞에 몰리게 건다. 총 세션 수는 1,300개로 같다.

| 구간 | 세션 시작 | RPS | 세션 수 |
| --- | --- | --- | --- |
| 워밍업 1분 | 분당 130 (평균) | 약 6.5 | 130 |
| 측정 0~2분 | 분당 390 (평균의 3배) | **약 19.5** | 780 |
| 측정 2~10분 | 분당 65 (평균의 절반) | 약 3.3 | 520 |

워밍업은 평균 속도로 건다. 피크를 워밍업에 쓰지 않고 측정 구간에 넣기 위해서다. 판정은 측정 구간 10분 전체로 하므로, 요청의 60%가 몰린 피크 2분이 p95를 좌우한다.

부하를 거는 방식은 실제 사용자를 따른다.

- **세션 시작은 정한 속도로**: 사용자 유입은 서버가 느려도 줄지 않는다.
- **세션 안은 차례로**: 사용자는 앞 페이지를 받아야 다음으로 넘어간다.
- 세션은 몇 초씩 걸리므로, 서버가 느려져도 세션을 버리지 않도록 VU 수를 넉넉히 둔다.

### 형식 검사와 태그

| 항목 | 내용 |
| --- | --- |
| 형식 검사 | 3xx·4xx가 아니다. 200 응답은 `content` 배열, 요청한 `page`·`size`와 일치. `page=0, 1`은 `hasNext: true` |
| 태그 | `screen`(`MATCHED`/`ALL`), `page`, `sort`. 맞춤 목록은 `os`, `cpu_tier`, `memory_gb`, `storage_gb`도 붙인다 |

조건마다 걸리는 상품 수가 269건에서 노트북 전체까지 차이 나서, 결과가 기준을 넘으면 태그로 조건별 응답 시간을 나눠 본다.

### 가정

아래 값은 사용자 데이터가 없어 정한 가정이다. 실측 데이터가 생기면 바꾸고, 바꾸면 RPS도 다시 계산한다.

| 가정 | 값 | 근거 | 실제와 다르면 |
| --- | --- | --- | --- |
| 방문당 목록 진입 | 5번 (정렬·탭 변경 포함) | 없음 | 세션 수가 비례해 바뀐다 |
| 피크 모양 | 첫 2분 평균의 3배, 나머지 8분 평균의 절반 | 없음. 카페 글은 게시 직후에 조회가 몰린다는 관찰에서 모양만 가져왔다 | 피크가 더 높고 짧으면 무거워진다. 실측 유입 추이가 생기면 바꾼다 |
| 맞춤 목록 : 전체 목록 | 1 : 1 | **실측 근거 없음.** PostHog는 화면 전환을 페이지뷰로 남기지 않고 목록 이벤트에도 화면 구분이 없어, 두 화면의 비율을 알 수 없다(2026-10-14 확인) | 전체 목록이 더 무거우므로, 실제 비중이 이보다 작으면 결과는 보수적이다 |
| 전체 목록의 필터 | 필터 없음 | **실측 근거 없음.** 전체 목록에서 검색 조건을 쓴 데이터가 거의 없어 임의로 정했다 | 필터를 걸면 처리할 행이 줄어 가벼워진다. 결과는 보수적이다 |
| 맞춤 목록의 탭 | 맥 : 윈도우 = 1 : 1 | 없음 | 윈도우 조합이 걸리는 상품이 더 많아, 윈도우가 많으면 무거워진다 |
| 정렬 | 화면의 선택지 중 균등 | 없음 | 실제로는 기본값이 대부분일 수 있다. 정렬별 비용은 `sort` 태그로 확인한다 |
| 스크롤 깊이 | 3페이지 | 없음 | 첫 페이지에서 멈추는 사용자가 많으면 RPS가 작아진다. 보수적인 가정이다 |
| 스크롤 간격 | 1~5초 | 없음 | 평균 RPS는 그대로이고, 요청이 몰리는 정도만 달라진다 |
| `size=10` | 프론트엔드의 `PAGE_SIZE`(`frontend/src/products.ts`) | 코드 | 페이지 크기가 바뀌면 `sessions.js`와 데이터 확인 기준(20건)도 바꾼다 |

## 측정 전 데이터 확인

조건에 걸리는 상품 수가 바뀌면 같은 요청이라도 DB가 하는 일이 달라져, 개선 전후를 비교할 수 없다. 그래서 측정 전에 대상 DB에서 아래 쿼리를 실행하고 기준 결과와 비교한다.

조건은 목록 API와 같다. CPU 등급은 그 등급의 최소 점수 이상, 메모리와 스토리지는 이상으로 찾는다. 최소 점수는 `CpuTier.java`에서 옮겨 적었으므로, 점수가 바뀌면 쿼리도 함께 고친다.

```sql
WITH cpu_memory (os, cpu_tier, min_score, memory_gb) AS (
  VALUES
    ROW('MAC', 'BASIC', 20000, 16), ROW('MAC', 'BASIC', 20000, 24), ROW('MAC', 'BASIC', 20000, 32),
    ROW('MAC', 'PRO', 30000, 24), ROW('MAC', 'PRO', 30000, 48)
  UNION ALL
  SELECT 'WINDOWS', t.cpu_tier, t.min_score, m.memory_gb
  FROM (VALUES ROW('P_HS', 20000), ROW('H', 24000), ROW('HX', 35000)) AS t (cpu_tier, min_score)
  CROSS JOIN (VALUES ROW(16), ROW(24), ROW(32), ROW(48)) AS m (memory_gb)
),
combo AS (
  SELECT c.os, c.cpu_tier, c.min_score, c.memory_gb, s.storage_gb
  FROM cpu_memory c
  CROSS JOIN (VALUES ROW(256), ROW(512), ROW(1024)) AS s (storage_gb)
),
matched AS (
  SELECT combo.os, combo.cpu_tier, combo.memory_gb, combo.storage_gb, COUNT(l.id) AS products
  FROM combo
  LEFT JOIN (laptop l JOIN cpu ON cpu.id = l.cpu_id)
    ON l.os = combo.os
    AND cpu.score >= combo.min_score
    AND l.memory_gb >= combo.memory_gb
    AND l.storage_gb >= combo.storage_gb
  GROUP BY combo.os, combo.cpu_tier, combo.memory_gb, combo.storage_gb
)
SELECT COUNT(*) AS combos,
       MIN(products) AS min_products,
       SUM(products) AS total_products,
       SUM(products <= 20) AS combos_without_page_2
FROM matched;
```

### 기준 결과

Flyway 기본 데이터에 [제품 적재 SQL](../../data/seed-products.sql)을 기본값으로 한 번 실행한 상태의 결과다.

| combos | min_products | total_products | combos_without_page_2 |
| --- | --- | --- | --- |
| 51 | 269 | 134,602 | 0 |

| 결과 | 판단 |
| --- | --- |
| 네 값이 모두 기준과 같다 | 측정을 진행한다 |
| `combos_without_page_2`가 0이 아니다 | 그 조합에서 `page=1`의 `hasNext`가 `false`가 되어 형식 검사가 실패하고, 회차가 무효가 된다. 데이터를 확인한다 |
| `min_products`나 `total_products`가 다르다 | 데이터가 바뀐 것이다. 개선 전후 비교에 쓰지 않는다 |

## 로컬에서 스크립트 확인

스크립트를 고친 뒤 로컬 서버에서 돌려 볼 때 쓴다. 로컬 DB에도 [제품 데이터](../../data/README.md)를 적재해야 형식 검사를 통과한다. 개발 서버에서 재고 기록하는 순서는 [성능 테스트 안내](../../README.md)를 따른다.

```bash
# 스모크: 초당 약 0.25세션(약 0.75 RPS), 1분
k6 run performance/k6/product-list/smoke.js

# 부하: 워밍업 1분(평균) → 측정 10분(첫 2분 피크), 약 12분
k6 run performance/k6/product-list/load.js
```

`BASE_URL`을 주지 않으면 `http://localhost:8080`으로 요청한다.

# 성능 테스트 기준과 근거

[성능 테스트 안내](README.md)의 기준과 측정 방법을 왜 그렇게 정했는지 적는다. 테스트를 돌리고 기록하는 데는 이 문서가 필요 없다. 기준을 바꾸거나 결과를 해석할 때 본다.

## 예상 트래픽

| 항목 | 기준 |
| --- | --- |
| 예상 트래픽 | 홍보 직후 10분간 약 `260명` 유입 |
| API별 RPS | `260 × 방문당 해당 API 호출 수 ÷ 600` |

방문당 호출 수와 10분 안에서 유입이 몰리는 모양은 API마다 화면 흐름이 달라 각 테스트의 README에 둔다.

### 평상시가 아니라 홍보 피크를 기준으로 삼은 이유

사용자 데이터가 없어서, 먼저 시장 규모로 평상시 트래픽의 상한을 추정했다. 서비스 점유율은 임의로 정하지 않고 100%로 두었다. 대상 시장의 모든 사람이 devica를 쓴다고 가정한 값이므로, 실제 평상시 트래픽은 이보다 클 수 없다.

| 단계 | 값 | 구분 | 근거 |
| --- | --- | --- | --- |
| ① 국내 개발자 | 약 40만 명 | 근거 | SW 산업 종사자 38.75만 명 (2018 소프트웨어 산업 실태조사) |
| ② 개발자 지망생 | 약 10만 명 | 가정 | 공개 통계를 찾지 못함 |
| ③ 백엔드 비율 | 약 23.5% | 근거 | 2025 상반기 개발자 입사 지원 중 서버/백엔드 비중 |
| ④ 대상 인구 | 약 12만 명 | 계산 | (① + ②) × ③ |
| ⑤ 연간 노트북 구매자 | 약 2.7만 명 | 근거 | 컴퓨터 평균 교체 주기 4.5년 → 연 22% |
| ⑥ 월간 구매자 | 약 2,200명 | 계산 | ⑤ ÷ 12 |
| ⑦ 구매자당 방문 수 | 3회 | 가정 | 고민 기간 중 여러 번 방문 |
| ⑧ 하루 방문 | 약 220회 | 계산 | ⑥ × ⑦ ÷ 30 |
| ⑨ 피크 1시간 집중도 | 하루의 10% | 가정 | |
| ⑩ 방문당 목록 요청 | 15건 | 가정 | 상품 목록 테스트의 세션 구성 (진입 5번 × 3페이지) |
| 목록 API 피크 RPS | 약 0.09 RPS | 계산 | ⑧ × ⑨ × ⑩ ÷ 3,600 |

시장 전체를 가져와도 목록 API는 초당 0.1건이 안 된다. 실제로 이전 홍보 때도 유입은 하루 수십 명 수준이었다. 평상시 트래픽은 성능 위험이 되기 어렵고, 위험한 순간은 홍보글이 노출된 직후 사람이 짧은 시간에 몰릴 때다. 그래서 예상 트래픽을 "홍보가 잘 됐을 때의 피크"로 정의한다.

### 피크 추정

| 항목 | 값 | 구분 | 근거 |
| --- | --- | --- | --- |
| 기준 채널 | 네이버 카페 맥쓰사 (회원 약 81만 명) | 근거 | 이전에 홍보한 채널. 같은 채널을 기준으로 하면 이전 홍보의 실측 클릭률을 그대로 쓸 수 있다 |
| 클릭률 | 17.5% | 실측 | 이전 홍보글 조회 320명 중 56명이 서비스에 들어왔다 |
| 잘 됐을 때의 조회 수 | 1,500회 | 근거 | 2026-10-11 기준 최근 7일 인기글 20개 중 최댓값. 앱 소개 글은 191·212회, 노트북 구매 고민 글은 349~481회, 중간값은 약 190회였다. 이전 홍보글(320회)이 이미 잘 된 편이라, 1,500회를 화제가 된 글이 받는 상한으로 본다 |
| 피크 유입 | 약 260명 | 계산 | 1,500 × 17.5% |
| 몰리는 시간 | 10분 | 가정 | 카페 글은 게시 직후에 조회가 몰리는 편이라 보수적으로 잡았다. 1시간으로 잡으면 RPS는 1/6이 된다 |

## SLO와 유효성

- **p95는 k6 응답 시간이 아니라 서버 처리 시간으로 판정한다.** 200ms는 화면 전체 1초 중 네트워크 왕복과 렌더링 시간을 남기고 API에 배정한 예산이라, 처음부터 네트워크를 뺀 시간이다. k6 p95에는 측정 장소의 네트워크 시간이 들어가므로 측정 장소에서 체감한 응답 시간으로만 기록한다.
- **4xx는 SLO 오류가 아니라 유효성으로 거른다.** 요청 조건은 모두 유효한 조합으로 만들기 때문에, 4xx가 나왔다면 테스트가 의도와 다른 요청을 보낸 것(스크립트 버그나 API 계약 변경)이다. 또 4xx는 검증 단계에서 바로 끝나 응답이 빨라서 p95를 실제보다 좋게 만든다.
- **5xx와 타임아웃은 유효성에 넣지 않는다.** SLO 오류율로 판정하므로, 유효성에 넣으면 SLO가 허용한 오류 한 건으로도 회차가 무효가 된다. 형식 검사도 200 응답에만 한다.
- **판정은 요청 로그로 하고 히스토그램은 참고만 한다.** 히스토그램 p95는 구간 안에서 값을 추정해 실제보다 크게 나올 수 있다.

## 측정 방법

| 항목 | 근거 |
| --- | --- |
| 워밍업 1분 | 2026-10-14 첫 측정(상품 목록)에서 워밍업 첫 10초의 k6 p95(전체 목록 414ms, 맞춤 목록 206ms)가 이후보다 높지 않아, 콜드 스타트의 영향이 보이지 않았다. 서버가 상시 떠 있고 스모크를 먼저 돌려 JIT와 커넥션 풀이 데워진 상태이기 때문이다 |
| 3회 반복, p95는 중앙값 | 한 회차의 p95는 네트워크나 서버 상태에 따라 흔들린다. 중앙값으로 판정하고 최소~최대 범위로 편차를 남긴다 |
| 오류율은 회차마다 | 한 번이라도 1%를 넘는 실패가 났다면 그 부하를 감당하지 못한 것으로 본다 |

## 판정의 범위

부하 테스트의 통과는 "**개발 서버에서, 다른 API 요청 없이, 이 API만 예상 트래픽을 받을 때** SLO를 만족한다"는 뜻이다.

| 범위 | 내용 |
| --- | --- |
| 다른 API | 실제로는 같은 서버·DB·커넥션 풀을 다른 API와 나눠 쓰지만, 테스트는 API 하나만 부하를 건다. 여러 API를 함께 거는 혼합 부하는 API별 테스트가 갖춰진 뒤 따로 다룬다 |
| 서버 | 개발 서버와 운영 서버는 EC2·RDS 사양이 같다(RDS `db.t4g.micro`). 운영은 ALB를 거치지만, p95를 서버 처리 시간으로 판정하므로 판정에는 영향이 없다. 로그 설정은 개발 서버만 `com.wrb.devica`를 debug로 두는데, 앱 코드에 debug 로그가 없어 차이가 없다 |
| 데이터 | 운영 데이터가 아니라 [적재 SQL](data/README.md)로 만든 합성 데이터에서 잰다. 데이터 규모와 분포가 다르면 결과도 달라진다 |

## 측정의 한계

- **요청 로그에서 테스트 요청만 골라낼 수 없다.** k6는 `User-Agent: devica-k6/<테스트 이름>`을 붙이지만 요청 로그에 User-Agent가 남지 않는다. 그래서 측정 중에는 개발 서버를 함께 쓰지 않는다.
- **구간 경계가 조금 다르다.** 로그는 측정 구간을 시각으로 자르고, k6는 `<name>_measure` 시나리오로 나눈다. 구간 경계에 걸친 세션 몇 개만큼 두 값이 다른 요청을 포함한다.
- **로그의 처리 시간에는 Tomcat 스레드를 기다린 시간이 빠진다.** 요청 필터에 들어온 뒤부터 재기 때문이다. 동시 요청이 많은 높은 부하에서는 실제보다 작게 나올 수 있다. 커넥션 풀을 기다린 시간은 들어간다.

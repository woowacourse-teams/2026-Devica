# 성능 테스트 데이터 적재

MySQL 8.4의 개발 DB에서 SQL 파일을 직접 실행해 테스트 데이터를 만든다. Python 실행이나 대용량 SQL 파일 생성은 필요 없다. 두 파일은 수동 적재용이며 Flyway 마이그레이션에 포함되지 않는다.

| SQL 파일 | 기본 생성량 |
| --- | --- |
| `seed-products.sql` | 제품 20,000건, 노트북 20,000건, 판매처 60,000건 |
| `seed-board-posts.sql` | 게시글 1,000,000건, 본문 500자 |

## 제품 데이터

SQL 파일 상단의 세 값을 원하는 데이터 규모에 맞춘다.

```sql
SET @perf_run_id = 'baseline-1';
SET @perf_product_count = 20000;
SET @perf_batch_size = 1000;
```

- `perf_run_id`: 데이터를 구분하는 영문·숫자·하이픈 1~24자. 제품 코드는 `PERF-BASELINE-1-000001`처럼 대문자로 저장된다.
- `perf_product_count`: 추가할 제품 수, 1~999,999개.
- `perf_batch_size`: 한 번에 저장할 제품 수, 1~1,000개.

대상 DB에 연결한 전용 세션에서 **파일 전체**를 실행한다. `DELIMITER`와 저장 프로시저를 지원하는 SQL 클라이언트를 사용한다. `mysql` CLI에서는 다음과 같이 실행한다. 비밀번호는 프롬프트에서 입력한다.

```bash
mysql -h DB_HOST -P DB_PORT -u DB_USER -p devica < performance/data/seed-products.sql
```

개발 서버의 MySQL은 외부 포트를 열지 않으므로 위 명령은 DB 연결 경로가 확보된 환경에서 사용한다. 서버 컨테이너에서 실행할 때도 동일한 SQL 파일을 표준 입력으로 전달하면 된다.

실행 계정에는 대상 테이블의 `SELECT`, `INSERT`와 `CREATE TEMPORARY TABLES`, `CREATE ROUTINE`, `ALTER ROUTINE`, `EXECUTE` 권한이 필요하다. 프로시저 생성·삭제는 진행 중인 트랜잭션을 커밋할 수 있으므로 다른 DB 작업과 세션을 섞지 않는다. 같은 DB에서 이 파일을 동시에 실행하지 않는다.

### 제품이 만들어지는 방식

1. `LAPTOP` 카테고리와 Apple·Intel CPU 기준 데이터, 입력값, 같은 실행 ID의 기존 제품을 확인한다. 조건이 맞지 않으면 제품 삽입 전에 중단한다.
2. 재귀 CTE로 배치에 사용할 0~999 범위의 번호를 임시 테이블에 만든다. 제품 수가 늘어도 재귀 깊이는 기본 제한 1,000 이내다.
3. 프로시저의 반복문이 번호로 브랜드·사양·가격을 계산해 `INSERT … SELECT`로 저장한다. 제품마다 `laptop` 1건과 `ON_SALE` 판매처 3건이 생긴다.
4. 제품 1,000개마다 커밋한다. 마지막 배치는 남은 수만큼 저장한다. 제품 ID는 DB가 부여하며, 노트북과 판매처는 고유 제품 코드로 실제 ID를 찾아 연결한다.
5. 이번 실행의 건수를 출력하고 임시 테이블과 보조 프로시저를 정리한다.

기본값의 검증 결과는 제품 20,000건, 노트북 20,000건, 판매 중인 판매처 60,000건, 판매처 수가 3개가 아닌 제품 0건이다. 기존 데이터는 유지되며 검증 결과에는 이번 실행 ID의 데이터만 포함된다.

SQL 오류가 나면 현재 배치를 롤백하고 오류를 전달한다. **이미 커밋한 배치는 남으므로 같은 파일을 바로 재실행하지 말고 해당 실행 ID의 데이터를 확인한다.** `mysql --force`처럼 오류 후에도 계속 실행하는 옵션은 사용하지 않는다. 오류로 보조 프로시저가 남으면 다음 파일 실행 시 교체되지만, 삽입된 제품은 자동 삭제되지 않는다.

제품 사양과 가격은 반복 가능한 합성 값이며 실제 서비스의 상품 분포를 그대로 재현하지는 않는다. SQL 파일이 작아져도 DB에 저장되는 행 수와 데이터 규모는 같다. 적재 후 전체 제품을 대상으로 상세 조회하려면 [k6 ID 준비 방법](../k6/README.md)에 따라 DB에서 조회한 ID 배열을 JSON 파일로 저장한다.

## 게시글 데이터

`seed-board-posts.sql`은 현재 `board-load.js`가 조회하는 `LAPTOP / BACKEND_DEVELOPMENT` 게시판에 데이터를 추가한다. 위의 전용 세션, 실행 권한, 오류 시 중단 규칙은 이 파일에도 적용된다.

파일 상단에서 실행 ID, 게시글 수, 배치 크기, 본문 길이를 지정한다.

```sql
SET @perf_run_id = 'baseline-1';
SET @perf_post_count = 1000000;
SET @perf_batch_size = 1000;
SET @perf_content_chars = 500;
```

- `perf_run_id`: 영문·숫자·하이픈 1~24자. 제품과 게시글은 서로 다른 테이블에 적재하므로 같은 실행 ID를 사용할 수 있다.
- `perf_post_count`: 추가할 게시글 수, 1~9,999,999건. 150만 건이 필요하면 `1500000`으로 변경한다.
- `perf_batch_size`: 한 번에 저장할 게시글 수, 1~1,000건.
- `perf_content_chars`: 본문 길이, 1~10,000자. 기본 영문 본문 500자는 500바이트이므로 100만 건의 본문만 약 500MB다. 실제 DB 용량에는 다른 컬럼과 인덱스, 로그 등이 추가된다.

```bash
mysql -h DB_HOST -P DB_PORT -u DB_USER -p devica < performance/data/seed-board-posts.sql
```

재귀 CTE가 최대 1,000개의 번호를 만들고, SQL 반복문이 번호를 재사용해 배치별로 적재한다. 게시글 제목은 `PERF-POST-BASELINE-1-0000001`처럼 실행 ID와 7자리 순번을 포함한다. 실제 게시글 ID는 DB가 부여한다. 작성·수정 시각은 실행 시작 시각을 마지막 글의 시각으로 두고 1초 간격으로 생성해, 목록 정렬에 쓰이는 작성 시각이 모두 같아지지 않게 한다.

해당 게시판의 기준 데이터가 없거나 같은 실행 ID의 게시글이 있으면 삽입 전에 중단한다. 제목에는 고유 제약이 없으므로 같은 DB에서 이 파일을 동시에 실행하지 않는다. 오류가 발생하면 현재 배치는 롤백하고 이전에 커밋한 배치는 유지한다. 재실행 전에 해당 실행 ID의 게시글을 확인한다.

기본값으로 완료하면 검증 결과의 `posts`는 `1000000`, `min_content_chars`와 `max_content_chars`는 모두 `500`이다. 기존 게시글은 유지되며 검증 결과는 이번 실행의 게시글만 집계한다.

현재 게시글 테스트는 목록 조회이므로 ID JSON 파일은 필요 없다. 댓글은 생성하지 않으며, 이 데이터로는 게시글 수와 페이지 깊이에 따른 조회 동작을 확인한다. 댓글이 많은 경우의 조회 비용과 실제 서비스의 본문·작성 시각 분포는 별도로 다뤄야 한다.

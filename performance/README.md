# 성능 테스트

부하 테스트를 돌리고 결과를 기록하는 방법을 안내한다. 기준을 왜 그렇게 정했는지는 ADR([판정 기준](../docs/adr/0039-성능-테스트-판정-기준.md), [측정 범위](../docs/adr/0040-성능-테스트-측정-범위.md), [예상 트래픽](../docs/adr/0041-성능-테스트-예상-트래픽.md))에, 새 테스트를 작성하는 방법은 [k6/README.md](k6/README.md)에 있다.

| 테스트      | 대상 API                                                | 문서                                                     |
|----------|-------------------------------------------------------|--------------------------------------------------------|
| 상품 목록 조회 | `GET /api/product-categories/{categoryCode}/products` | [k6/product-list/README.md](k6/product-list/README.md) |

## 준비하기

측정 전에 아래 네 가지가 되는지 확인한다.

| 준비물           | 쓰는 곳               | 확인                                                                  | 안 되면                         |
|---------------|--------------------|---------------------------------------------------------------------|------------------------------|
| k6, jq        | 부하 걸기, 결과 값 뽑기     | `k6 version`, `jq --version`이 버전을 출력한다                              | `brew install k6 jq` (macOS) |
| 개발 서버 SSH     | 서버 커밋, 테스트 데이터 확인  | 개발 서버에 접속된다. 방법은 [백엔드 배포 가이드](../docs/백엔드_배포_가이드.md)의 "서버 구성"을 확인한다 | 서버를 관리하는 팀원에게 SSH 키와 권한을 받는다 |
| Grafana Cloud | 서버 처리 시간, 서버 자원 조회 | 팀 스택에서 Explore가 열린다                                                 | —                            |
| AWS 콘솔        | DB CPU 조회          | RDS에서 개발 DB의 모니터링 탭이 보인다                                            | —                            |

## 측정하기

명령과 조회는 네 곳에서 한다.

| 어디서 | 무엇을 |
| --- | --- |
| **내 컴퓨터 터미널** (레포 루트) | k6 실행(3·4단계), 결과 파일에서 값 뽑기(값 수집하기의 `grep`·`jq`) |
| **개발 서버 터미널** (SSH 접속) | 서버 커밋과 테스트 데이터 확인(2단계) |
| **Grafana Explore** (브라우저) | 서버 처리 시간과 서버 자원 조회 |
| **AWS 콘솔** (브라우저) | RDS CPU 조회 |

내 컴퓨터 터미널에서는 시작하기 전에 두 변수를 정해 둔다. 그러면 아래 명령을 그대로 복사해 쓸 수 있다. 값을 뽑는 명령도 `$TEST`를 쓰므로, 측정이 끝날 때까지 같은 터미널을 쓴다. 새 터미널을 열었다면 변수를 다시 정한다.

```bash
export BASE_URL=<개발 서버 주소>
TEST=<테스트 폴더>
```

| 변수         | 값         | 어디서                                                                  |
|------------|-----------|----------------------------------------------------------------------|
| `BASE_URL` | 요청을 보낼 개발 서버 주소 | [백엔드 배포 가이드](../docs/백엔드_배포_가이드.md)의 "서버 구성" |
| `TEST`     | 돌릴 테스트    | 각 테스트 README의 "테스트 정보"                                               |

### 1. 공지

팀 채널에 공지하고, **공지한 시각에 시작한다.**

**걸리는 시간**: 스모크 + 부하 3회

- 부하 1회는 약 12분이다(워밍업 1분 + 측정 10분 + 마무리).
- 스모크 시간은 각 테스트 README의 "테스트 정보"에 있다.

**팀에 부탁할 것**

| 부탁            | 이유                               |
|---------------|----------------------------------|
| develop 머지 보류 | 머지되면 재배포되어 측정이 깨진다               |
| 개발 서버 사용 자제   | 요청 로그로 판정하는데, 다른 요청이 섞이면 값이 달라진다 |
| 다른 부하 테스트 금지  | 두 테스트가 서로의 결과를 망친다               |

공지 예시:

```
[개발 서버 부하 테스트] 오늘 16:15 ~ 17:00, <대상 API>
테스트 중에는 develop 머지, 개발 서버 사용, 다른 부하 테스트를 피해 주세요. 끝나면 다시 알리겠습니다.
```

### 2. 서버 커밋과 데이터 확인

개발 서버에 접속해 두 가지를 확인하고 기록 표에 적는다.

| 확인할 것   | 방법                                         | 기록 표 항목   |
|---------|--------------------------------------------|-----------|
| 서버 커밋   | 서버 `.env`의 `IMAGE_TAG` 값을 확인한다             | 서버 커밋     |
| 테스트 데이터 | 개발 DB에서 테스트 README의 "측정 전 데이터 확인" 쿼리를 실행한다 | 데이터 확인 결과 |

- 서버 접속, `.env`, 개발 DB 접속 방법은 [백엔드 배포 가이드](../docs/백엔드_배포_가이드.md)의 "서버 구성", "설정과 비밀값", "RDS 설정"에 있다.
- 데이터가 기준과 다르면 개선 전후 비교에 쓸 수 없다. 테스트 README의 판단 표를 따르고, 데이터를 다시 만들 때는 [데이터 적재 안내](data/README.md)를 본다.

### 3. 스모크

적은 부하로 스크립트와 서버가 정상인지 확인하고, 서버를 워밍업한다.

```bash
k6 run performance/k6/$TEST/smoke.js
```

출력 끝의 `checks`와 `dropped_iterations`가 ✓면 다음으로 넘어간다. ✗면 부하 테스트로 넘어가지 않는다.

| 실패한 검사 | 뜻 | 할 일 |
| --- | --- | --- |
| `3xx·4xx가 아니다` | 스크립트가 보낸 요청이 API와 맞지 않는다 | 출력의 실패한 요청 주소를 보고 스크립트나 API 변경을 확인한다 |
| 그 밖의 형식 검사 | 응답이 기대와 다르다. 대개 데이터가 기준과 다르다 | 2단계 데이터 확인으로 돌아간다 |

### 4. 부하 (3회)

아래 명령을 세 번 연달아 실행한다. 회차마다 워밍업이 들어 있으므로 사이에 쉬지 않는다.

```bash
T=$(date +%Y%m%d-%H%M)
k6 run \
  --summary-export=performance/results/$TEST-load-$T.json \
  --out json=performance/results/$TEST-load-$T-raw.json \
  performance/k6/$TEST/load.js
```

- 결과는 회차마다 `performance/results/`에 두 파일로 남는다. `<테스트>-load-<시각>.json`(요약)과 `-raw.json`(요청별 결과)이다.
- 출력 끝의 `checks`나 `dropped_iterations`가 ✗면 그 회차는 [무효](#측정-무효-조건)다.
- `performance/results/`는 Git에서 제외된다. 비교에 쓴 결과는 PR에 기록 표로 남긴다.

### 5. 수집과 기록

1. 종료를 공지한다.
2. `IMAGE_TAG`를 한 번 더 확인해 측정 중에 배포가 없었는지 본다.
3. [값 수집하기](#값-수집하기)대로 회차별 값을 모아 [기록 형식](#기록-형식)의 기록 표를 채운다.
4. [성능 기준](#성능-기준)으로 API가 성능 목표를 만족하는지 판정한다.

## 값 수집하기

회차마다 기록 표의 값을 모은다. 모든 조회는 그 회차의 측정 구간으로 하므로, **측정 구간 시각부터** 구한다. 이 절의 `grep`·`jq` 명령은 측정할 때 쓴 내 컴퓨터 터미널(레포 루트)에서 실행한다.

| 기록 표 항목 | 어디서 |
| --- | --- |
| 측정 일시 (측정 구간) | [측정 구간 시각](#측정-구간-시각) |
| 장소·네트워크 | k6를 돌린 곳을 적는다. 예: `캠퍼스 Wi-Fi`. 개선 전후는 같은 곳에서 잰다 |
| 서버 커밋, 데이터 확인 결과 | 측정하기 2단계에서 확인한 값 |
| 오류율, k6 p95 / p99, 실제 RPS, `dropped_iterations` | [k6 결과](#k6-결과) |
| 서버 처리 시간 p50 / p95 / p99 | [Grafana 요청 로그](#grafana-요청-로그) |
| 서버 p95 히스토그램, CPU, 메모리, 힙, GC, DB 커넥션 | [Grafana 지표](#grafana-지표) |
| RDS CPU | [AWS 콘솔](#aws-콘솔) |

### 측정 구간 시각

측정 구간은 **첫 요청 시각 + 1분(워밍업)부터 10분**이다. 첫 요청 시각은 요청별 결과 파일에서 읽는다. `<시각>`은 측정하기 4단계에서 만든 파일 이름의 시각이다.

```bash
grep -m1 '"type":"Point"' performance/results/$TEST-load-<시각>-raw.json | jq -r .data.time
```

예: `2026-10-14T14:33:24.48+09:00`이 나오면 측정 구간은 14:34:24~14:44:24다.

### k6 결과

요약 파일에서 측정 구간 값만 뽑는다. `<시나리오 이름>`은 테스트 README의 "테스트 정보"에 있다.

```bash
jq -r --arg s <시나리오 이름> '.metrics as $m |
  "k6 p95 / p99 (ms): \($m["http_req_duration{scenario:\($s)_measure}"]["p(95)"] | round) / \($m["http_req_duration{scenario:\($s)_measure}"]["p(99)"] | round)",
  "오류율: \($m["http_req_failed{scenario:\($s)_measure}"].value * 10000 | round / 100)%",
  "실제 RPS: \($m["http_reqs{scenario:\($s)_measure}"].count / 600 * 100 | round / 100)",
  "dropped_iterations: \($m.dropped_iterations.count)"' performance/results/$TEST-load-<시각>.json
```

주의할 점:

- **k6 화면의 값은 쓰지 않는다.** 화면의 오류율(`0.00% 0 out of 48`)과 `rate`는 워밍업까지 섞인 값이다. 위 명령은 측정 구간만 계산한다.
- **화면의 ✓가 모두 통과를 뜻하지는 않는다.** `p(95)>=0`, `count>0`은 값을 요약에 남기려고 걸어 둔 기준이다.
- **타임아웃이 5%를 넘으면 k6 p95는 5,000ms에 붙는다.** 이때는 오류율로 비교하고, 요청별 결과(`-raw.json`)로 1분 단위 오류율 추이를 함께 남긴다. 실패한 세션은 다음 페이지를 요청하지 않으므로 실제 RPS도 계획보다 낮게 나온다.

### Grafana 요청 로그

**판정에 쓰는 값**인 서버 처리 시간을 구한다.

1. Grafana → **Explore**를 연다.
2. 데이터 소스로 Loki를 고른다. 이름이 `grafanacloud-`로 시작해 `-logs`로 끝나는 것이다.
3. 오른쪽 위 시간 선택 → **Absolute time range**에서 From·To에 측정 구간의 시작·끝을 넣는다.
4. 쿼리 편집기를 **Code** 모드로 바꾸고 아래 쿼리를 붙여 넣는다. `<API 경로 패턴>`은 테스트 README "테스트 정보"의 로그 조회용 경로 패턴이다.
5. 쿼리 옵션의 Type을 **Instant**로 바꾸고 실행한다. To 시각 기준 직전 10분을 계산한다.

```logql
quantile_over_time(0.95, {env="dev"} |= "요청 처리 완료" | json | http_route="<API 경로 패턴>" | unwrap event_duration [10m]) by (env)
```

- 결과는 나노초다. 1,000,000으로 나눠 ms로 적는다.
- p50, p99는 쿼리의 `0.95`를 `0.5`, `0.99`로 바꿔 다시 실행한다.

### Grafana 지표

판정에는 쓰지 않는다. 기준을 넘었을 때 원인을 찾는 데 쓴다.

요청 로그와 같은 방법(Explore, 측정 구간, **Instant**)으로 조회하되, 데이터 소스만 Prometheus(`grafanacloud-…-prom`)로 고른다. 쿼리를 하나씩 실행한다.

| 기록 표 항목 | 쿼리 | 단위 |
| --- | --- | --- |
| 서버 p95 히스토그램 | `histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{env="dev", uri="<API 경로 패턴>"}[10m])))` | 초 → ms |
| CPU Usage 평균 | `avg_over_time((1 - avg(rate(node_cpu_seconds_total{env="dev", mode="idle"}[2m])))[10m:1m])` | 0~1 → % |
| CPU Usage 최대 | 위 쿼리의 `avg_over_time`을 `max_over_time`으로 | 0~1 → % |
| Available Memory 최소 | `min_over_time(node_memory_MemAvailable_bytes{env="dev"}[10m])` | 바이트 → MiB |
| Heap Usage 최대 | `max_over_time(sum(jvm_memory_used_bytes{env="dev", area="heap"})[10m:1m])` | 바이트 → MiB |
| GC Pause 합계 | `sum(increase(jvm_gc_pause_seconds_sum{env="dev"}[10m]))` | 초 → ms |
| DB Connections 사용 중 최대 | `max_over_time(sum(hikaricp_connections_active{env="dev"})[10m:1m])` | 개 |
| DB Connections 대기 중 최대 | `max_over_time(sum(hikaricp_connections_pending{env="dev"})[10m:1m])` | 개 |

주의할 점:

- **지표는 60초마다 수집된다.** 1분보다 짧게 치솟은 값은 놓칠 수 있다.
- **히스토그램 p95는 실제보다 크게 나올 수 있다.** 구간 안에서 값을 추정하기 때문이다. 그래서 판정은 요청 로그로 한다.
- **시간 흐름은 `Devica Overview` 대시보드로 본다.** `env`를 `dev`로, 시간 범위를 측정 구간으로 둔다. 요청·CPU·GC 패널은 5분 평균이라 짧은 피크가 낮게 보인다.

### AWS 콘솔

DB 지표는 Grafana에 없어 RDS 콘솔에서 본다.

1. AWS 콘솔 → **RDS** → 데이터베이스 → 개발 DB를 연다. 이름은 백엔드 배포 가이드의 "서버 구성"에 있다.
2. **모니터링** 탭에서 시간 범위를 측정 구간으로 맞춘다.
3. **CPUUtilization** 그래프에서 평균과 최대를 읽는다.

### 기록 형식

| 서버 커밋                             |     |     |     |                 |

| **오류율**                           |     |     |     | 가장 높은 회차의 값     |

### 측정 무효 조건

아래에 해당하면 측정이 잘못된 것이다. 그 결과는 성능 판정에 쓰지 않고 다시 잰다. 해당하지 않으면 아래 성능 기준으로 판정한다.

| 조건                                 | 뜻                            | 다시 잴 범위 |
|------------------------------------|------------------------------|---------|
| 3xx·4xx 응답이 있다                     | 스크립트가 의도와 다른 요청을 보냈다         | 그 회차    |
| 200 응답의 형식 검사(`checks`)가 하나라도 실패했다 | 응답이 기대와 다르다. 대개 데이터가 기준과 다르다 | 그 회차    |
| `dropped_iterations`가 0이 아니다       | k6가 계획한 부하를 다 걸지 못했다         | 그 회차    |
| 측정 전후의 `IMAGE_TAG`가 다르다            | 측정 중에 배포됐다                   | 3회 모두   |

### 성능 기준

API가 성능 목표를 만족하는지 기록 표의 굵은 두 줄로 판정한다. 둘 다 만족해야 통과다.

| 기준                        | 통과 조건               |
|---------------------------|---------------------|
| 서버 처리 시간 p95              | 3회의 중앙값이 `200ms` 이하 |
| 오류율 (5xx, 5초 타임아웃, 연결 오류) | 모든 회차가 `1%` 이하      |

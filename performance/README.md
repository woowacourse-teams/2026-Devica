# 성능 테스트

API마다 담당자가 각자 성능 테스트를 작성한다. 결과를 서로 비교할 수 있도록 통과 기준과 측정 방법은 이 문서와 `k6/common/`에 한 번만 두고, 테스트는 API별 폴더로 나눈다.

## 구조

```
performance/
├── README.md           # 이 문서. 구조, 공통 기준, 공통 측정 방법, 실행 규칙
├── data/               # 테스트 데이터 적재 SQL
├── results/            # k6 요약 결과 JSON(Git 제외)
└── k6/
    ├── common/         # 팀 공통 모듈
    └── product-list/   # 상품 목록 조회
```

API별 폴더 이름은 `도메인-동작` 형태로 한다. 각 폴더는 다음으로 구성한다.

| 파일 | 역할 |
| --- | --- |
| `README.md` | 실행 방법, 입력, 측정 전 확인 방법 |
| `requests.js` | 요청과 응답 검사. 다른 테스트도 가져다 쓴다 |
| 조건 모듈(필요할 때) | 요청 조건을 만드는 모듈. 예: `product-list/sessions.js` |
| `smoke.js` | 적은 부하로 스크립트와 서버가 정상인지 확인한다. 유효성 기준만 적용하고 SLO는 판정하지 않는다 |
| `load.js` | 예상 트래픽으로 부하를 건다 |

API별 실행 방법과 입력은 각 폴더의 `README.md`에 둔다. 데이터 적재는 [data/README.md](data/README.md)를 본다.

| 테스트 | 문서 |
| --- | --- |
| 상품 목록 조회 | [k6/product-list/README.md](k6/product-list/README.md) |

## 공통 기준

| 항목 | 기준 |

| 예상 트래픽 | 홍보 직후 10분간 약 `260명` 유입. 근거는 [예상 트래픽 근거](#예상-트래픽-근거) |
| API별 RPS | `260 × 방문당 해당 API 호출 수 ÷ 600` |

### 예상 트래픽 근거

#### 평상시가 아니라 홍보 피크를 기준으로 삼은 이유

사용자 데이터가 없어서, 먼저 시장 규모로 평상시 트래픽의 상한을 추정했다. 서비스 점유율은 임의로 정하지 않고 100%로 두었다. 대상 시장의 모든 사람이 devica를 쓴다고 가정한 값이므로, 실제 평상시 트래픽은 이보다 클 수 없다.

| 단계 | 값 | 구분 | 근거 |
| --- | --- | --- | --- |
| ① 국내 개발자 | 약 40만 명 | 근거 | SW 산업 종사자 38.75만 명 (2018 소프트웨어 산업 실태조사) |
| ② 개발자 지망생 | 약 10만 명 | 가정 | 공개 통계를 찾지 못함 |
| ③ 백엔드 비율 | 약 23.5% | 근거 | 2025 상반기 개발자 입사 지원 중 서버/백엔드 비중 |
| ④ 대상 인구 | 약 12만 명 | 계산 | (① + ②) × ③ |
| ⑤ 연간 노트북 구매자 | 약 2.7만 명 | 근거 | 컴퓨터 평균 교체 주기 4.5년 → 연 22% |
| ⑥ 월간 구매자 | 약 2,200명 | 계산 | ⑤ ÷ 12 |
| ⑦ 구매자당 방문 수 | 3회 | 가정 | 고민 기간 중 여러 번 방문 |
| ⑧ 하루 방문 | 약 220회 | 계산 | ⑥ × ⑦ ÷ 30 |
| ⑨ 피크 1시간 집중도 | 하루의 10% | 가정 | |
| ⑩ 방문당 목록 요청 | 15건 | 가정 | 상품 목록 테스트의 세션 구성 (진입 5번 × 3페이지) |
| 목록 API 피크 RPS | 약 0.09 RPS | 계산 | ⑧ × ⑨ × ⑩ ÷ 3,600 |

시장 전체를 가져와도 목록 API는 초당 0.1건이 안 된다. 실제로 이전 홍보 때도 유입은 하루 수십 명 수준이었다. 평상시 트래픽은 성능 위험이 되기 어렵고, 위험한 순간은 홍보글이 노출된 직후 사람이 짧은 시간에 몰릴 때다. 그래서 예상 트래픽을 "홍보가 잘 됐을 때의 피크"로 정의한다.

#### 피크 추정

| 항목 | 값 | 구분 | 근거 |
| --- | --- | --- | --- |
| 기준 채널 | 네이버 카페 맥쓰사 (회원 약 81만 명) | 근거 | 이전에 홍보한 채널. 같은 채널을 기준으로 하면 이전 홍보의 실측 클릭률을 그대로 쓸 수 있다 |
| 클릭률 | 17.5% | 실측 | 이전 홍보글 조회 320명 중 56명이 서비스에 들어왔다 |
| 잘 됐을 때의 조회 수 | 1,500회 | 근거 | 2026-10-11 기준 최근 7일 인기글 20개 중 최댓값. 앱 소개 글은 191·212회, 노트북 구매 고민 글은 349~481회, 중간값은 약 190회였다. 이전 홍보글(320회)이 이미 잘 된 편이라, 1,500회를 화제가 된 글이 받는 상한으로 본다 |
| 피크 유입 | 약 260명 | 계산 | 1,500 × 17.5% |
| 몰리는 시간 | 10분 | 가정 | 카페 글은 게시 직후에 조회가 몰리는 편이라 보수적으로 잡았다. 1시간으로 잡으면 RPS는 1/6이 된다 |

API별 RPS는 `피크 유입 × 방문당 해당 API 호출 수 ÷ 몰리는 시간(초)`으로 구한다. 방문당 호출 수와 10분 안에서 유입이 몰리는 모양은 API마다 화면 흐름이 달라 각 테스트의 README에 둔다.

### SLO 판정과 결과 유효성

| 구분 | 기준 | 넘으면 |
| --- | --- | --- |
| SLO 판정 | 오류율(5xx + 타임아웃 5초) `1%` 이하, 서버 처리 시간 p95 `200ms` 이하. 오류율은 k6로 회차별로, p95는 요청 로그로 판정한다 | 실패 |
| 결과 유효성 | 3xx·4xx 응답이 없고, 200 응답은 모두 형식 검사(`checks`)를 통과, `dropped_iterations` 0 | 그 회차는 무효. 결과를 쓰지 않고 원인을 고친 뒤 다시 측정한다 |

- 4xx는 SLO 오류로 세지 않는다. 요청 조건은 모두 유효한 조합으로 만들기 때문에, 4xx가 나왔다면 테스트가 의도와 다른 요청을 보낸 것(스크립트 버그나 API 계약 변경)이다. 또 4xx는 검증 단계에서 바로 끝나 응답이 빨라서 p95를 실제보다 좋게 만든다. 그래서 유효성에서 걸러 낸다.
- p95는 k6 응답 시간이 아니라 서버 처리 시간으로 판정한다. 200ms는 화면 전체 1초 중 네트워크 왕복과 렌더링 시간을 남기고 API에 배정한 예산이라, 처음부터 네트워크를 뺀 시간이다. k6 p95에는 측정 장소의 네트워크 시간이 들어가므로 측정 장소에서 체감한 응답 시간으로만 기록한다.
- 5xx와 타임아웃은 유효성에 넣지 않는다. SLO 오류율로 판정하므로, 유효성에 넣으면 SLO가 허용한 오류 한 건으로도 회차가 무효가 된다. 형식 검사도 200 응답에만 한다.

### 판정의 범위

부하 테스트의 통과는 "**개발 서버에서, 다른 API 요청 없이, 이 API만 예상 트래픽을 받을 때** SLO를 만족한다"는 뜻이다.

| 범위 | 내용 |
| --- | --- |
| 다른 API | 실제로는 같은 서버·DB·커넥션 풀을 다른 API와 나눠 쓰지만, 테스트는 API 하나만 부하를 건다. 여러 API를 함께 거는 혼합 부하는 API별 테스트가 갖춰진 뒤 따로 다룬다 |
| 서버 | 개발 서버와 운영 서버는 EC2·RDS 사양이 같다(RDS `db.t4g.micro`). 운영은 ALB를 거치지만, p95를 서버 처리 시간으로 판정하므로 판정에는 영향이 없다. 로그 설정은 개발 서버만 `com.wrb.devica`를 debug로 두는데, 앱 코드에 debug 로그가 없어 차이가 없다 |
| 데이터 | 운영 데이터가 아니라 [적재 SQL](data/README.md)로 만든 합성 데이터에서 잰다. 데이터 규모와 분포가 다르면 결과도 달라진다 |

### 공통 모듈 (`k6/common/`)

새 테스트는 이 모듈을 쓰고 기준을 따로 적지 않는다.

| 항목 | 내용 |
| --- | --- |
| 서버 주소 | `BASE_URL` 환경 변수. 기본값 `http://localhost:8080` |
| 테스트 표시 헤더 | `User-Agent: devica-k6/<테스트 이름>`. 테스트 트래픽을 구분하려고 붙이지만, 지금은 요청 로그와 지표에 User-Agent가 남지 않아 아직 걸러 낼 수 없다 |
| 요청 옵션 | 타임아웃 5초, 리다이렉트 0. 기대 상태는 200~499로 두어, 오류율(`http_req_failed`)에는 5xx와 타임아웃만 들어가게 한다 |
| 측정 구간 | `warmupAndMeasure(name, scenario, measure?)`. 테스트가 정한 부하 설정으로 `<name>_warmup`(1분)과 `<name>_measure`(10분) 시나리오를 만든다. 측정 구간의 부하 모양이 다르면(예: 피크) `measure`를 따로 주고, 이때 `measure`가 10분을 채워야 한다. 모든 부하 테스트가 쓴다 |
| SLO 기준 | `measureThresholds(name)`. `<name>_measure`의 요청에만 걸고, 오류율만 판정한다. k6 p95와 요청 수는 기록만 한다 |
| 유효성 기준 | `validityThresholds`. 형식 검사(`checks`) 100% 통과, `dropped_iterations` 0. 워밍업을 포함한 전체에 적용한다 |
| 응답 검사 | `checkResponse()`. 4xx가 아닌지 확인하고, 200 응답이면 API별 형식 검사를 한다 |
| 결과 통계 항목 | `avg`, `med`, `p(95)`, `p(99)`, `max` |

## 공통 측정 방법

### 측정 진행

| 항목 | 방법 |
| --- | --- |
| 한 회차 | 워밍업 1분 → 측정 10분을 끊지 않고 진행한다. 워밍업은 결과에서 제외한다 |
| 워밍업 길이 | 1분. 2026-10-14 첫 측정(상품 목록)에서 워밍업 첫 10초의 k6 p95(전체 목록 414ms, 맞춤 목록 206ms)가 이후보다 높지 않아, 콜드 스타트의 영향이 보이지 않았다. 서버가 상시 떠 있고 스모크를 먼저 돌려 JIT와 커넥션 풀이 데워진 상태이기 때문이다 |
| 반복 | 같은 조건으로 3회. 회차마다 워밍업을 포함하므로 회차 사이 휴식은 두지 않는다 |
| p95 집계 | 회차별 값을 모두 기록한다. 판정과 비교는 서버 처리 시간 p95의 중앙값으로, 편차는 최소~최대 범위로 남긴다 |
| 오류율 판정 | 회차별로 판정한다. 한 회차라도 1%를 넘으면 실패다 |
| 측정 전 확인 | 테스트 데이터가 기준 결과와 같은지 확인한다. 확인 방법은 API별 README에 둔다. 이어서 같은 서버에 스모크를 돌려 스크립트와 서버가 정상인지 확인하고, 서버를 데운다 |
| 워밍업 확인 | 회차마다 워밍업 첫 10초의 k6 p95가 이후보다 뚜렷이 높은지 본다. 높으면 서버가 덜 데워진 상태라 그 회차는 무효로 하고 다시 잰다. 배포 직후처럼 서버가 막 뜬 상태에서는 측정하지 않는다 |

### 관찰 지표

| 대상 | 지표 | 위치 |
| --- | --- | --- |
| 앱 서버 | 서버 처리 시간 p50·p95·p99 | Grafana Explore(`grafanacloud-logs`). 요청 로그의 처리 시간으로 계산한다 |
| 앱 서버 | p95 (히스토그램) | Grafana Explore. 측정 종료 시점에 p95 패널의 쿼리 기간을 `[10m]`으로 바꿔 조회한다 |
| 앱 서버 | CPU Usage, Available Memory | Grafana `Devica Overview` |
| JVM | Heap Usage, GC Pause | Grafana `Devica Overview` |
| 커넥션 풀 | DB Connections (사용 중·대기 중) | Grafana `Devica Overview` |
| DB | CPU 사용률 | RDS 콘솔 (CloudWatch) |

대시보드의 p95는 직전 5분 기준이라 측정 구간 전체를 담지 못한다. `p95 Latency by URI` 패널의 쿼리에서 기간만 `[10m]`으로 바꾼다.

```promql
histogram_quantile(0.95, sum by (le, uri) (rate(http_server_requests_seconds_bucket{env="dev", uri!="/readyz"}[10m])))
```

SLO의 p95는 요청 로그의 처리 시간으로 판정한다. 히스토그램 p95는 구간 안에서 값을 추정해 실제보다 크게 나올 수 있어 판정에 쓰지 않는다. 로그의 처리 시간은 요청 필터에 들어온 뒤부터 재므로 Tomcat 스레드를 기다린 시간은 들어가지 않는다. 동시 요청이 많아지는 높은 부하에서는 실제보다 작게 나올 수 있다.

로그 쿼리에는 두 가지 한계가 있다.

- 요청 로그에 User-Agent가 없어 테스트 요청만 골라내지 못한다. 측정 중 다른 사람이 같은 API를 호출하면 판정 값에 섞이므로, 실행 규칙대로 측정 중에는 개발 서버를 함께 쓰지 않는다.
- 로그는 측정 구간을 시각(시작 후 1분~11분)으로 자르고, k6는 `<name>_measure` 시나리오로 나눈다. 구간 경계에 걸친 세션 몇 개만큼 두 값이 다른 요청을 포함한다.

측정 종료 시점에 아래 쿼리를 즉시 조회(Instant)로 실행한다. `0.95`를 `0.5`, `0.99`로 바꿔 p50, p99를 얻고, 결과(나노초)를 1,000,000으로 나눠 ms로 적는다.

```logql
quantile_over_time(0.95, {env="dev"} |= "요청 처리 완료" | json | http_route="<API 경로 패턴>" | unwrap event_duration [10m]) by (env)
```

DB가 RDS에 있어 DB 지표는 대시보드에 없다. 대시보드의 CPU와 메모리는 앱 서버만 나타낸다. 병목이 DB로 의심되면 해당 쿼리의 실행 계획(`EXPLAIN ANALYZE`)을 확인한다.

### 기록

k6 요약 결과는 JSON으로 `performance/results/`에 저장한다. 이 폴더는 Git에서 제외하므로, 비교에 쓴 결과는 PR이나 성능 테스트 문서에 첨부한다.

```bash
k6 run --summary-export=performance/results/<테스트 이름>-<YYYYMMDD-HHmm>.json performance/k6/<API>/load.js
```

측정 구간 값은 `{scenario:<name>_measure}`가 붙은 항목에서 읽는다. 실제 RPS는 `http_reqs{scenario:<name>_measure}`의 `count`를 측정 시간(600초)으로 나눈다. 요약의 `rate`는 워밍업까지 포함한 전체 시간으로 나눈 값이라 쓰지 않는다. 요약에 이 값들을 남기려고 판정하지 않는 기준(`p(95)>=0`, `count>0`)을 걸어 두었으므로, 이 항목들의 ✓ 표시는 통과를 뜻하지 않는다.

k6 p95는 타임아웃(5초)에 걸린 요청을 5,000ms로 센다. 측정 구간 요청의 5% 넘게 타임아웃이 나면 k6 p95는 5,000ms에 붙어 개선 전후를 비교할 수 없다. 이때는 오류율과 1분 단위 추이(요청별 결과 `--out json`에서 계산)를 함께 남긴다. 세션은 응답이 200이 아니면 다음 페이지를 요청하지 않으므로, 오류가 많으면 실제 RPS도 계획보다 낮게 나온다.

## 개발 서버 실행 규칙

- 시작과 종료 시각을 팀 채널에 공지하고, 공지한 시각에 시작한다.
- 주소는 `BASE_URL=https://2026-devica.vercel.app`이다. Vercel이 `/api` 요청을 개발 서버(`dev.devica.co.kr`)로 프록시하므로 k6 응답 시간에는 Vercel을 거치는 시간이 들어간다. 판정은 서버 처리 시간으로 하므로 영향이 없다.
- 테스트 중에는 develop 머지를 보류한다. 머지되면 재배포되어 측정이 깨진다.
- **두 사람이 동시에 부하 테스트를 실행하지 않는다.**
- 개선 전후 측정은 같은 장소, 같은 네트워크에서 한다.
